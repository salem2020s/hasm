# HASM — Phase 3.8B-2: Stock adjustments from an approved stocktake (as built)

Second slice of Phase 3.8B (plan: `docs/PHASE-3.8B.md`; first slice `docs/PHASE-3.8B-1.md`). Sources: SRS §9 (stocktake and adjustments), ROADMAP 3.8B, PHASE-3.6 (costing engine), PHASE-3.7A–D (accounting configuration, posting, reversal, UI).
The negative-stock exception (3.8B-3) is untouched; the costing engine and its constraints are unchanged; **no existing constraint was changed** (migration 0019 is purely additive).

## What exists
* **Company migration 0019** (`CompanySchema.StockAdjustment.cs`): `StockAdjustment` (one per stocktake, unique; branch, warehouse, date = count date, number, fiscal year), `StockAdjustmentLine` (item, base unit, direction −1 shortage / +1 surplus, quantity, counted and book quantity at generation, reason), `StockAdjustmentPosting` (issue and receipt costing operations, configuration version, journal entry, total value), `StockAdjustmentPostingLine` (value per line) and `StockAdjustmentReversal` (compensating operations, journal action 0/1/2 as in 3.7C, date, who, reason). All append-only; runtime role SELECT/INSERT only. PostgreSQL enforces: the adjustment belongs to an **approved** stocktake of the same branch, warehouse and date; at least one line (at commit); one line per item; `quantity × direction = counted − book` exactly; no line added after posting; one posting per adjustment with at least one costing operation, each used once; one reversal per posting; **an approved stocktake with an adjustment can never be cancelled** (trigger on the stocktake table). An added nullable column `InventoryAccountingVersion.AdjustmentCounterAccountId` (+ FK).
* **Generate** (`POST /api/v1/company/stocktakes/{id}/adjustment`, If-Match = stocktake revision): under the company stock lock and the stocktake row lock; a repeated or concurrent request returns the same adjustment (`replayed`). Variance = counted base quantity − **current** book quantity (costing ledger, that warehouse, on or before the count date, read now — never the frozen snapshot); zero lines omitted, nothing to adjust → `no_variance`. Items and base units are checked like any stock line; the count date must lie in an open period; number type `stock_adjustment` (default prefix `SA`). Generating moves nothing.
* **Post** (`POST /api/v1/company/stock-adjustments/{id}/posting`, body = amounts of the surplus lines): one transaction re-validates warehouse, items, units, period; shortages = one **issue** operation of the costing engine (actual cost, FIFO/average as configured), surpluses = one **receipt** operation at the amounts entered by the poster (exactly like a receipt; zero allowed; never on a shortage line); one balanced **gross** draft journal entry (surplus: Dr inventory account of the item group / Cr adjustment counter account; shortage: Dr adjustment counter account / Cr inventory account), source key `stock_adjustment:<id>`; total value = gross value moved; no journal when nothing of value moved. Exactly once: identical retry returns the posting, other amounts → `already_posted`, concurrent requests post once. Accounting state derived exactly as for stock documents (pending, not required, posted, failed, reversed).
* **Reverse** (`POST /api/v1/company/stock-adjustments/{id}/reversal`): the 3.7C rules — date in an open period, not before the posting date, within the posting period while the entry is unposted; both operations taken back (an inflow only while untouched); the entry cancelled while unposted or reversed by a draft reversal entry once posted; once only.
* **Close probe**: `inventory_valuation_differences` also treats adjustment postings (module in use; a failed adjustment posting blocks the close until reversed).
* **Accounting configuration**: the dedicated adjustment counter account is saved in a new immutable version, validated like the other counter accounts (exists, postable, active, base currency, never an inventory account). Without it, posting an adjustment with value is refused (`adjustment_counter_account_not_configured`) and nothing is written. The content hash includes it only when set, so earlier configurations keep their hash.
* **Follow-ups of the 3.8B-1 review**: M2 fixed (each stocktake line returns the units of its item — base, active alternates and the saved unit — so a reloaded line can be counted in any unit); L6 fixed (cancel guard above, service code `adjustment_exists` and PostgreSQL).
* **Shared UI (Web and Tauri)**: on the stocktake screen an approved stocktake shows **Generate adjustment** (actions outside the tabs, with a confirmation) and then an **Adjustment** tab (no placeholder tab before): number, date, accounting state, lines with type, quantities, book at generation, reason, an amount input for each surplus line, Post, and Reverse (date and reason). Cancel is hidden once an adjustment exists, with an explanation. Inventory accounts → Main accounts gains the adjustment counter account. Arabic RTL / English LTR.

## Decisions (standing authority, conservative)
* **3.8B-2/D1 — dedicated adjustment document, not a fourth stock document type.** A type 4 in `StockDocument`/`StockPosting` would require changing existing CHECK constraints, which migrations may not do (no `DROP`, enforced by `MigrationScript`) and which the 3.8B plan excludes for slices 1–2. The adjustment therefore has its own append-only tables and reuses the 3.7 machinery in code (costing engine, `EnsureConfiguredAsync`, automatic journal path, `DeriveState`, the 3.7C journal handling, the period gate, the stock lock). It is posted and reversed from the stocktake screen, not from the Stock Documents Posting tab.
* **D2 — two costing operations** (issue for shortages, receipt for surpluses) in one transaction and one journal: the costing engine stays unchanged.
* **D3 — born approved.** The adjustment's content is fully determined by the approved count (whose separation of duties already held), so it is not submitted/approved again; it cannot be edited or cancelled. A wrong adjustment is undone by posting and reversing it, or simply left unposted (it has no stock or ledger effect).
* **D4 — date = count date, book = current book quantity up to the count date at generation.** The engine refuses back-dated entries, so posting is refused (`backdated_not_supported`) if the item has movements dated after the count date; then a new stocktake is needed.
* **D5 — permissions, no new code:** generate = `company.stocktake.view` + `company.stockdocs.create` on the warehouse; read = `stocktake.view` or `stockdocs.view`; post = `stockdocs.post`; reverse = `stockdocs.reverse`; all warehouse-scoped, nothing disclosed to others.
* **D6 — no fallback** to the issue/receipt counter accounts: an adjustment uses only its dedicated counter account.
* **D7 — inactive items/base units** are refused at generation and posting, as for stock documents.
* **D8 — a generated but unposted adjustment does not block a period close** (same as an approved but unposted stock document).
