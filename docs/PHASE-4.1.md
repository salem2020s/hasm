# Phase 4.1 - Identity completion: MFA and identity security (PLAN, no code)

Status: PLAN for independent security review. This document changes no code, migration or schema.
Sources: SRS section 4 (TOTP for supported accounts, protected emergency account, audit of administrative and sensitive operations, second approval); `docs/ROADMAP.md` Phase 4.1 (prerequisite 3.7D, system migrations); owner decision **D-080** (recorded in PR #110, pending merge; binding, quoted below as "D-080 (n)" for its numbered clauses 1-7); the TOTP primitive `Identity/Totp.cs` (#72); the existing session, login-throttle, access and audit code.
Everything below is a PROPOSAL derived from D-080 unless marked "D-080". Items marked **[Q]** are open questions for the lead/owner; nothing marked [Q] is built before it is answered. Decision IDs and system migration numbers are placeholders (**D-?**, **M-A..M-D**) until the lead allocates them.

## 1. What exists today (verified in the tree)
* `Totp` (RFC 6238, SHA-1, 30 s, 6 digits, window <= 2): pure; `Verify` returns the matched step; the caller owns replay protection (atomic compare-and-set of `last_step`) and throttling.
* `AuthService.LoginAsync`: normalised login, three throttle counters (pair, source, global; `ThrottleScope.Login|Source`), identical failure outcome for unknown/wrong/disabled, session created right after the password check. Sessions: opaque token, hash at rest, idle and absolute expiry, `SessionClient.Web` (HttpOnly `__Host-hasm_session` cookie) or `Desktop` (bearer). Revocation reasons: Logout, Administrative, PasswordChanged.
* `Users.IsIdentityAdministrator`; company roles via `AccessService`; `AdministratorContinuity` (per-company lock so the last usable Company Administrator cannot be removed); per-company approver grants through the admin tool (`grant-*-approver`); audit streams (system and per-company business) with keyed chain and external anchors; `Hasm.Admin` offline commands (`bootstrap-admin`, `audit-*`, `encryption-keygen`, backup commands).
* `KekRing` / `FileKekRing` (`Security/FileEncryption.cs`): versioned master keys by id, owner-only key directory, HKDF-derived wrapping key, fail closed on a missing key, never an implicit replacement. This is "the existing protected key ring" of D-080 (2).
* Not present: enrolment, second-factor login, MFA state on sessions, privileged-role classification, company MFA policy, recovery, emergency account, DR procedure, a generic independent-approval framework for system-level operations, any notification channel.

## 2. Principles (D-080 restated as design rules)
1. **No half-authenticated sessions.** A session is created only after every required factor succeeded. The password step alone yields a short-lived single-purpose challenge, never a session.
2. **MFA is never silently disabled.** States are `NotEnrolled`, `EnrolmentRequired`, `Active` (and `Revoked` for a replaced secret). There is no "off" transition for a user who is required to have it; recovery moves the user to `EnrolmentRequired` (a new authenticator must be enrolled before any session exists).
3. **No general bypass.** No master code, no backdoor flag, no configuration switch, no password-only path for a user whose requirement is on. The emergency account and the DR procedure are narrow, time-limited, audited procedures that still carry a second factor held by separate custodians (sections 8, 9).
4. **Server-side only.** Requirements, challenges, step-up freshness and approvals are decided and enforced by the ASP.NET Core API and the admin tool. The frontend renders state; it never decides it.
5. **One implementation for Web and Tauri** (CLAUDE.md shared-frontend rule): same screens, same API; the only platform difference stays the existing cookie vs bearer session transport. The challenge token travels in the JSON body on both.
6. **Independent approval = a different, currently MFA-verified person, bound to the exact parameters, single use, expiring, audited** (section 7).
7. Everything security-relevant is audited in the existing keyed system audit stream; alerts for privileged recovery events are immediate (section 10).
8. AD/Kerberos is out of Release 1 (D-080 (7)): no code, schema or hook that could block native authentication.

## 3. Requirement model (who must have MFA)
* **Central privileges always enforce MFA, whatever company is selected (D-080 (1)).** A fixed, code-defined set `MfaMandatory`: system administrator (`IsIdentityAdministrator`), Company Administrator in ANY company, holders of sensitive grants (section 7), and the emergency account. It is evaluated from the user's union of privileges across ALL companies at login and at every privilege change, not from the currently selected company. A user cannot avoid MFA by having no company selected or by entering a company without a policy.
* **Company policy for other roles (D-080 (1)):** a per-company setting `MfaPolicy` = `Off | RequiredForRoles(list) | RequiredForAll`, changed only by a Company Administrator (an MFA-fresh, audited action). Effective requirement for a session in company C = central OR policy(C). At company selection, if the session is not MFA-verified and C requires it, the API answers `mfa_step_up_required` and the client runs step-up; no company data is served before.
* Requirements are recomputed on every grant or revoke; a user who becomes subject to one while logged in gets `mfa_step_up_required` on the next privileged request (session kept, nothing privileged served until step-up).
* **[Q1]** the exact list of "privileged administrative roles" beyond Company Administrator and identity administrator (for example fiscal/journal/import approvers, commercial approver, backup/restore operators). The plan implements a catalog flag `RequiresMfa` per permission/role so the list is data reviewed in one place; the owner confirms it.

## 4. Secret protection and enrolment (slices S1, S2)
**Storage (D-080 (2)).** New system table `user_totp` (name from the generated `SystemSchema` scheme): `user_id` (unique), `secret_cipher`, `nonce`, `tag`, `kek_id`, `state` (`Pending|Active|Revoked`), `created_at`, `confirmed_at`, `last_step` (bigint, replay CAS), `failed_confirmations`. The secret is encrypted with AES-256-GCM under a key derived by HKDF-SHA-256 from the `KekRing` master with a DISTINCT label `hasm-totp/v1/<kekId>` (separate from the file-wrapping label, so a file key never decrypts a TOTP secret and vice versa); AAD = `user_id | kek_id | row version`, so a ciphertext copied to another user or key fails authentication. The plaintext secret exists only in memory during enrolment display and verification, is zeroed after use, and never reaches logs, exceptions, responses (after enrolment) or audit detail.
* **Rotation:** admin tool `totp-rewrap --to <kekId>` re-encrypts every secret under the active key in batches inside transactions, idempotent and resumable; `totp-rewrap --check` reports which key ids are still referenced. Retiring a key is an independent-approval operation (section 7) refused while any secret references it. A missing key fails closed: MFA users cannot sign in (and are not downgraded), the operator sees `totp_key_unavailable`.
* **Access restrictions:** the runtime database role gets only the privileges it needs on the table (no DELETE); `secret_cipher` is never selectable by reporting roles; no API returns it.
* **Backup exclusions (mandatory, pinned by the #104 test):** the new table is added to `SystemSchema.SecretStoreTables` and to the backup exclusions in the SAME slice. A TOTP secret never enters a company backup set or trial restore. KEK key-material custody is outside the database and follows decision K of Phase 4.3.
* **Enrolment (API + shared UI):** `POST /auth/mfa/enrol/begin` (session or `enrol` challenge, section 5) generates a secret, stores it `Pending` (replaced if repeated, expires after 15 minutes), returns the `otpauth://` URI and Base32 once for the shared QR component; `POST /auth/mfa/enrol/confirm {code}` verifies with `Totp.Verify`, atomically sets `Active` and `last_step`, audits `mfa.enrolled`, and revokes the user's OTHER sessions. Confirmation attempts are throttled. Re-enrolment of an `Active` user (new device) requires step-up with a current code; the old secret stays valid until the new one is confirmed, so there is never a gap or an off state.
* **Parameters:** fixed at SHA-1/6 digits/30 s for authenticator-app compatibility, window 1 at login; throttling and replay protection compensate and are documented as part of the design.
* **No static recovery codes in Release 1 [Q2]:** static codes are an extra bypass surface that D-080 (3) and (5) avoid by design. Recommendation: none. If wanted for non-privileged users, a later policy-gated slice (hashed, single use, alerting, never for `MfaMandatory` users).

## 5. Login and session changes; enforcement points
**Two-step login (S2).** `POST /auth/login` returns, when a second factor or enrolment is required, `{ status: "mfa_required" | "mfa_enrolment_required", challenge }` and creates NO session. The challenge is an opaque 256-bit random token (only its hash stored), bound to user id, client (`Web|Desktop`), source address and purpose (`login` or `enrol`), valid 5 minutes, single use, small attempt budget. `POST /auth/mfa/verify {challenge, code}` verifies the TOTP (constant time; the `last_step` CAS and the challenge consumption in one atomic statement) and then creates the session with `mfa_verified_at = now`, `auth_methods = password+totp`. An `enrol` challenge accepts only enrol begin/confirm; confirming enrolment completes the login. Every failure (wrong code, expired, used, unknown challenge) has the same body, so there is no oracle.
**Throttling:** new `ThrottleScope.Mfa` (per user and per user+source) on the existing counters and block policy; a failed second factor never resets password counters; a success clears only the pair counter; lockouts are time-based so other sources cannot lock a user out indefinitely.
**Session state:** sessions gain `mfa_verified_at`, `auth_methods`, `emergency` (bool). `AuthenticatedSession` exposes them; `GET /auth/status` reports `mfaVerified`, `mfaRequired`, `stepUpRequired` for the shared UI.
**Step-up (S3):** `POST /auth/mfa/step-up {code}` for a session that is not MFA-verified or whose proof is older than the freshness window (default 15 minutes, bounded 5..60) when an operation declares `RequireFreshMfa`: role grants, recovery approval, key retirement, restore, emergency/DR administration, company MFA policy change, state changes of administrators.
**Enforcement points (all server-side):**
1. Login (password step -> challenge) and the verify/enrol endpoints.
2. The session authentication handler (`HasmAuthentication`): populates MFA claims; authorization policies `MfaVerified` / `MfaFresh` are attached to every privileged endpoint group (access administration, user administration, company administration, approvals, backup/restore endpoints when they exist). A unit test enumerates the endpoint table and fails for any privileged endpoint without the policy, so a new endpoint cannot silently skip MFA.
3. Company selection and company-scoped endpoints: company policy check, `mfa_step_up_required` (HTTP 401, stable code) until step-up.
4. Privilege changes (grant of a mandatory/sensitive role): fresh MFA of the grantor plus independent approval (section 7); the grantee becomes `EnrolmentRequired` immediately and gets no session until enrolled.
5. Admin tool (`Hasm.Admin`): runs on the host with database administration credentials and has no user identity, so it enforces by PROCEDURE: commands that change privileged state or key material (key retirement, restore, emergency activation, DR reset, recovery execution from the tool) refuse to run without an approved, unexpired, unconsumed, MAC-verified approval request whose payload hash matches the command (section 7), and write the execution to the audit stream. `bootstrap-admin` creates the first administrator in `EnrolmentRequired`; the first login completes enrolment before any session exists.
6. Web and Tauri are identical. The Tauri client keeps the bearer token in the existing secure desktop storage adapter; the challenge token lives in memory only; nothing in the MFA flow needs a platform-specific business path. Shared screens: login second step, enrolment (shared QR component, Base32 fallback), security settings (status, re-enrol), step-up dialog, recovery request and approval inbox, company MFA policy. Arabic RTL / English LTR, keyboard accessible, UI-1 design system; tabs only where a screen has several meaningful groups (Security settings: Authenticator / Recovery requests).

## 6. Lost-authenticator recovery (slice S5; D-080 (3))
Recovery is a request through the independent-approval framework (section 7), never a switch:
1. **Request:** an administrator (acting for a locked-out user after **verified identity**) files `mfa.recovery` for target user T. Verified identity is an out-of-band check recorded as mandatory structured evidence in the request (method, who verified, when, reference). Software cannot verify a person; the evidence is audited, not trusted blindly **[Q3: acceptable verification methods]**.
2. **Independent approval:** approver != requester, approver != T, a different MFA-fresh administrator holding the approval permission. A cooling-off delay (default 4 hours, bounded 1..72) applies between approval and execution; T and all administrators are alerted and ANY administrator can cancel. The request expires after 72 hours.
3. **Execution:** T's TOTP becomes `Revoked`, ALL T's sessions are revoked (new reason `MfaRecovery`), T becomes `EnrolmentRequired`. T passes the password step and then enrols a NEW authenticator before any session exists. A `MfaMandatory` user is never usable without a factor.
4. **Audit:** request, evidence, approval, cancel, execution and the later re-enrolment each write a system-stream event with actor, target, approver, request id and payload hash.
5. **No second administrator available:** the emergency account (section 8) or the DR procedure (section 9); never self-approval and never a unilateral admin-tool reset.

## 7. Independent-approval framework (slice S4; D-080 (6))
One generic mechanism for sensitive system-level operations, used by recovery, sensitive role grants, encryption-key retirement and restore (Phase 4.3 live restore, D-081).
* **Table** `admin_approval_request` (system database): `id`, `operation` (closed enumeration in code), `target_ref`, `payload` (parameters, no secrets), `payload_hash` (SHA-256 of canonical JSON), `requested_by`, `requested_at`, `expires_at`, `not_before` (cooling-off), `status` (`Pending|Approved|Rejected|Cancelled|Executed|Expired`), `approved_by`, `decided_at`, `executed_at`, `executed_by`, `evidence`, and `mac` (HMAC with the active AUDIT key over the immutable fields and each recorded status transition, so a row forged or altered by someone with raw database access fails verification in the service and the admin tool, which hold the key ring).
* **Rules in ONE service** (a test pins that no endpoint or command changes a covered operation without it): approver != requester; approver != target where the operation has a target user; approver holds the per-operation approval permission (a new permission family that is itself a sensitive grant); approver's session is MFA-fresh at decision time; approval bound to `payload_hash` (a changed parameter needs a new request); single use (execution consumes the request in the same transaction as the operation and its audit event, under a row lock so concurrent executions cannot both win); expiry; a decided request cannot be re-decided; a failed execution leaves the request `Approved` and retryable until expiry, never half-applied.
* **Covered operations:** `mfa.recovery`; `role.grant.sensitive` (Company Administrator, approver permissions, any `RequiresMfa` role; list per [Q1]); `encryption.key.retire` (admin tool `encryption-retire-key` refuses without an approved request AND a pre-check proving no stored object or TOTP secret references the key); `restore.execute` (the 4.3 live company restore: this framework is the "independent administrative approval" of D-081, the 4.3 slice integrates it); `emergency.rotate`; `dr.keys.change`.
* **Sensitive role grants** run through the access service only via a request; the direct grant path for those roles is removed from the API (a regression test calls the old path and expects refusal).
* Approver identity is the authenticated MFA-fresh session; the framework never accepts a password or code as proof of approval. The admin-tool consumer identifies the request by id and re-verifies MAC and payload hash.
* **[Q4]** admin-tool operations by a host operator have no user identity at execution time. The plan attributes them to the requesting and approving users on the request plus the operator's OS account captured by the tool; the owner confirms that is sufficient.

## 8. The one emergency account (slice S6; D-080 (4))
* **Exactly one**, enforced by a partial unique index on an `is_emergency` flag and by the creation command refusing a second one. Created ONLY by the admin tool (`emergency-create`), never by API; it has a distinct login, state `Disabled` by default.
* **Offline credential custody:** `emergency-create` generates a high-entropy password (>= 24 random characters) and a TOTP secret and prints each ONCE to separate output the operator seals offline (password to custodian A, TOTP secret to custodian B). Only the password hash and the KEK-protected TOTP secret are stored; nothing is kept in plaintext, logs or backups. There is NO MFA exemption: the second factor is held by a different custodian (split custody).
* **Time-limited access:** `emergency-activate --minutes N --reason "..."` (host command) sets the account `Active` for N minutes (default 30, hard maximum 120, no extension; another activation is another audited action) and records the reason. The session lifetime is capped to the window. At expiry or `emergency-deactivate` the account returns to `Disabled` and **its password and TOTP secret are rotated** (a used credential is never reusable); new custody material must be sealed.
* **Immediate alerting and audit:** activation, every login attempt (success or failure), every request of the emergency session (flagged `emergency`, so every audit event of that session carries the flag), deactivation and rotation raise an alert (section 10) AND write system-stream events. A failed alert delivery never blocks the audit write and is surfaced and retried.
* **Scope:** it cannot approve its own operations, grant itself roles, or approve requests it filed. It may act as the independent approver of an MFA recovery ONLY while its activation window is open and only when the operator records that no other administrator is available; every such use is audited with the `emergency` flag. **[Q5]** confirm "approver of last resort", or rely on DR (section 9) alone.

## 9. Disaster-recovery procedure (slice S7; D-080 (5))
For when no second administrator is available and the emergency account is unavailable or its custody lost. Independently controlled, never a general bypass:
* **Offline DR signing keys:** at installation (or by a later `dr.keys.change` approval) N public Ed25519 keys are registered; the private keys are generated offline and held by N separate custodians (recommended N >= 3, threshold 2). The system never holds a private key.
* **DR authorization token:** produced offline: canonical JSON `{operation: "mfa.dr.reset", targetUser, notBefore, expiresAt (<= 24 h), nonce, reason}` with at least TWO signatures from distinct registered keys; valid for ONE target and ONE operation.
* **Execution:** `Hasm.Admin mfa-dr-reset --token <file>` on the host verifies signatures against the registered keys, the threshold of DISTINCT keys, the window, and that the nonce was never used (stored), then performs the same safe transition as normal recovery (target `Revoked` -> `EnrolmentRequired`, sessions revoked). The tool grants no login. Audit event with signer key ids, nonce and operator OS account; immediate alert; every failed attempt audited and counted.
* A DR reset never yields a session and never disables MFA: the target still passes the password and enrols a new authenticator.
* Key rotation or replacement is a `dr.keys.change` request (independent approval; the new set must be signed by the old threshold).
* **[Q6]** custodian count/threshold and the organisational statement of who the custodians are (a process control software cannot verify; documented in the slice S8 runbook).
* The runbook includes a rehearsal on a disposable database; tests exercise the full verification logic with generated keys (never real custody keys).

## 10. Audit and notifications
* Audit events (new range in the system stream, codes allocated with each slice): enrolment begun/confirmed/replaced/revoked, challenge issued/failed/succeeded (counts, never codes), step-up result, MFA policy changes, approval requested/approved/rejected/cancelled/expired/executed, recovery evidence, emergency created/activated/login/deactivated/rotated, DR token verified/rejected, `totp-rewrap`, key retirement. Details never contain secrets, codes, tokens or key material (a test scans audit rows and log output for them).
* **Notifications:** the repository has no notification channel. The plan adds a small `ISecurityNotifier` with (a) a durable in-app security-notice table written in the same transaction as the audit event (visible to administrators and to the affected user at next sign-in) and (b) an optional configured outbound channel **[Q7]** (SMTP and/or webhook, the owner chooses). Alerts for recovery requests, approvals, executions, emergency activation and DR use go to the target user and all administrators. Delivery failure never blocks the protected operation or hides the audit record.

## 14. Risks recorded
* An operator holding raw database administration plus the audit key ring can forge approval rows; the control is the separation of custody of the key ring and the external audit anchors, the same assumption the audit design already makes. Documented, not solvable in software.
* TOTP is phishable; no phishing-resistant factor (WebAuthn) in Release 1.
* Loss of ALL KEK custody makes TOTP secrets unreadable; every user must then re-enrol through the DR procedure. Key backups follow decision K.
* The cooling-off delay slows legitimate recovery; the emergency account and DR exist for urgent cases.
* The audit-trail first-touch scoping fix (PR #112) is a prerequisite for relying on audit appends inside long-lived pooled connections.
