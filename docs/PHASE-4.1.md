## 1. What exists today (verified in the tree)
* `Totp` (RFC 6238, SHA-1, 30 s, 6 digits, window <= 2): pure; `Verify` returns the matched step; the caller owns replay protection (atomic compare-and-set of `last_step`) and throttling.
* `AuthService.LoginAsync`: normalised login, three throttle counters (pair, source, global; `ThrottleScope.Login|Source`), identical failure outcome for unknown/wrong/disabled, session created right after the password check. Sessions: opaque token, hash at rest, idle and absolute expiry, `SessionClient.Web` (HttpOnly `__Host-hasm_session` cookie) or `Desktop` (bearer). Revocation reasons: Logout, Administrative, PasswordChanged.
* `Users.IsIdentityAdministrator`; company roles via `AccessService`; `AdministratorContinuity` (per-company lock so the last usable Company Administrator cannot be removed); per-company approver grants through the admin tool (`grant-*-approver`); audit streams (system and per-company business) with keyed chain and external anchors; `Hasm.Admin` offline commands (`bootstrap-admin`, `audit-*`, `encryption-keygen`, backup commands).
* `KekRing` / `FileKekRing` (`Security/FileEncryption.cs`): versioned master keys by id, owner-only key directory, HKDF-derived wrapping key, fail closed on a missing key, never an implicit replacement. This is "the existing protected key ring" of D-080 (2).
* Not present: enrolment, second-factor login, MFA state on sessions, privileged-role classification, company MFA policy, recovery, emergency account, DR procedure, a generic independent-approval framework for system-level operations, any notification channel.

## 2. Principles (D-080 restated as design rules)
1. **No half-authenticated sessions.** A session is created only after every required factor succeeded. The password step alone yields a short-lived single-purpose challenge, never a session.
2. **MFA is never silently disabled.** The user row carries `mfa_state` = `None | EnrolmentRequired | Enrolled | RecoveryRequired` (section 4). There is no "off" transition for a user who is required to have it; recovery and DR move the user to `EnrolmentRequired` (a new authenticator must be enrolled, with a one-time enrolment code, before any session exists), and a system restore turns every `Enrolled` user without a stored secret into `RecoveryRequired`, never into a password-only enrolment.
3. **No general bypass.** No master code, no backdoor flag, no configuration switch, no password-only path for a user whose requirement is on. The emergency account and the DR procedure are narrow, time-limited, audited procedures that still carry a second factor held by separate custodians (sections 8, 9).
4. **Server-side only.** Requirements, challenges, step-up freshness and approvals are decided and enforced by the ASP.NET Core API and the admin tool. The frontend renders state; it never decides it.
5. **One implementation for Web and Tauri** (CLAUDE.md shared-frontend rule): same screens, same API; the only platform difference stays the existing cookie vs bearer session transport. The challenge token travels in the JSON body on both.
6. **Independent approval = a different, currently MFA-verified person, bound to the exact parameters, single use, expiring, audited** (section 7).
7. Everything security-relevant is audited in the existing keyed system audit stream; alerts for privileged recovery events are immediate (section 10).
8. AD/Kerberos is out of Release 1 (D-080 (7)): no code, schema or hook that could block native authentication.

## 3. Requirement model (who must have MFA)
* **Central privileges always enforce MFA, whatever company is selected (D-080 (1)).** A fixed, code-defined set `MfaMandatory`: system administrator (`IsIdentityAdministrator`), Company Administrator in ANY company, holders of sensitive grants (section 7), and the emergency account. It is evaluated from the user's union of privileges across ALL companies at login and at every privilege change, not from the currently selected company. A user cannot avoid MFA by having no company selected or by entering a company without a policy.
* **Company policy for other roles (D-080 (1)):** a per-company setting `MfaPolicy` = `Off | RequiredForRoles(list) | RequiredForAll`, changed only by a Company Administrator (an MFA-fresh, audited action). Effective requirement for a session in company C = central OR policy(C). At company selection, if the session is not MFA-verified and C requires it, the API answers `mfa_step_up_required` and the client runs step-up; no company data is served before.
* Requirements are recomputed on every grant or revoke; a user who becomes subject to one while logged in gets `mfa_step_up_required` on the next privileged request (session kept, nothing privileged served until step-up).
* **LEAD D-096 (Q1), fail-closed:** a role is privileged when it holds ANY central/system administrative permission, is the Company Administrator preset, or holds ANY permission to manage roles or grants, keys and encryption, backup or restore, audit administration, or security settings; when in doubt it counts as privileged. The classification is ONE central definition (catalog flag `RequiresMfa` per permission, derived role predicate `IsPrivileged(role)`), covered by a test that enumerates the whole `PermissionCatalog` and fails for any permission not explicitly classified, so a new permission cannot silently be unprivileged.

## 4. Secret protection, MFA state and enrolment (slices S1, S2)
**State lives in the user row, the secret does not (H1).** The MFA requirement and enrolment state are a column of the existing `Users` row (`mfa_state`: `None | EnrolmentRequired | Enrolled | RecoveryRequired`, plus `mfa_state_changed_at`), added by M-A. The user row IS in the system dump, so a restore never loses the fact that a user is enrolled. Only the secret goes to the new system table `user_totp`, which is INCLUDED ONLY IN ENCRYPTED backup runs (a secret store with a per-table backup rule, see below; Phase 4.3 slice 5, D-091). Consequence after any system restore: a user whose row says `Enrolled` but who has no `user_totp` secret is treated as `RecoveryRequired` (the restore procedure also marks them explicitly and audits it). A `RecoveryRequired` user can NOT self-enrol with a password: the only ways back are recovery (section 6) and DR (section 9). The emergency account stays `Disabled` after a restore until `emergency.rotate` has been approved (section 8). A restored system therefore never has an MFA-mandatory user that can enrol with only a password.

**Secret storage (D-080 (2)).** `user_totp` (name from the generated `SystemSchema` scheme): `secret_id` (uuid, primary key), `user_id`, `secret_cipher`, `nonce`, `tag`, `kek_id`, `state` (`Pending|Active|Revoked`), `created_at`, `confirmed_at`, `last_step` (bigint, replay CAS), `failed_confirmations`. **Schema constraints (M2):** a unique index on `user_id` WHERE `state = 'Active'` and a unique index on `user_id` WHERE `state = 'Pending'` (at most one active and one pending secret per user, enforced by the database, not by code alone). The secret is encrypted with AES-256-GCM under a key derived by HKDF-SHA-256 from the `KekRing` master with a DISTINCT label `hasm-totp/v1/<kekId>` (separate from the file-wrapping label, so a file key never decrypts a TOTP secret and vice versa). **AAD = `user_id | kek_id | secret_id` (M3)**: a ciphertext copied to another user, key or row fails authentication, and nothing mutable (no row version) is in the AAD, so a state change never invalidates a stored secret. The plaintext secret exists only in memory during enrolment display and verification, is zeroed after use, and never reaches logs, exceptions, responses (after enrolment) or audit detail.
* **One verifier (M1):** every TOTP check in the product goes through ONE `MfaVerifier` (window 1, the atomic `last_step` compare-and-set, `ThrottleScope.Mfa`). A unit test scans the solution and fails if any other caller of `Totp.Verify` exists (the primitive stays public only for the verifier and tests of the primitive itself).
* **Rotation:** admin tool `totp-rewrap --to <kekId>` re-encrypts every secret under the active key in batches inside transactions, idempotent and resumable; `totp-rewrap --check` reports which key ids are still referenced. A missing key fails closed: MFA users cannot sign in (and are not downgraded), the operator sees `totp_key_unavailable`. Retiring a key is governed by section 7 (`encryption.key.retire`).
* **Access restrictions:** the runtime database role gets only the privileges it needs on the table (no DELETE); `secret_cipher` is never selectable by reporting roles; no API returns it.
* **Backup rule (per table, pinned by the #104/4.3 slice 4 test; S1 depends on #104 merging):** `user_totp` is added to `SystemSchema.SecretStoreTables` with the rule **"included only in encrypted runs"** (lead decision, consistent with D-080 (2) and D-085): the secret is already wrapped by the key ring (`hasm-totp/v1`, section 4), and an ENCRYPTED backup set protects the dump again; an unencrypted DEV/TEST run EXCLUDES it. Session and login-throttle tables stay ALWAYS excluded. The pin is a per-table rule ("always excluded" or "included only in encrypted runs"), not a single exclusion list; a TOTP table is never in a company backup set or trial restore (those are company databases). **Restoring TOTP data requires the key export (D-087)**: the secrets are unreadable without the KEK that wrapped them. **The H1 safeguard holds in full whatever the backup contained:** any restore that brings back NO usable secret for a user whose row says `Enrolled` (a DEV/TEST restore from an unencrypted run, a lost key export, a partial restore, a missing `kek_id`) leaves that user `RecoveryRequired`, never password-only enrolment; the restore procedure marks them and audits it. KEK key-material custody is outside the database and follows decision K of Phase 4.3. **S1:** restore without `user_totp` rows (state kept, users `RecoveryRequired`, no password-only enrolment). The encrypted-run restore tests (with and without the key export) move to the 4.3 slice 5 implementation PR. **Sequencing (LEAD D-120):** S1 ships with `user_totp` in `SystemDumpExclusions`, i.e. ALWAYS excluded, and does not wait for #116. Whichever of S1 and the 4.3 slice 5 implementation merges SECOND sets `user_totp` to "included only in encrypted runs". Until both are on main, it is always excluded. Until then every system restore leaves `Enrolled` users `RecoveryRequired`, which the H1 safeguard already handles.
* **Restore effects (N2; LEAD D-106, D-107; fail-closed):** after a system restore, logins stay BLOCKED until the restore procedure has re-applied every credential revocation recorded AFTER the backup point (TOTP revoke or recovery, password change, disable), taken from the preserved audit chain and the external anchors; if it cannot complete that, every restored `Enrolled` user becomes `RecoveryRequired`. A restore into a DIFFERENT installation id makes every user `RecoveryRequired`. The restore procedure also INVALIDATES every unconsumed `mfa_enrolment_code_hash` on user rows (L-a), so a code issued before the backup point cannot be used after it. Logins are unblocked ONLY by the restore procedure's audited completion step: a named administrator with MFA, or the DR custodian quorum if no administrator is available; if the post-backup audit chain is unavailable, that counts as "cannot re-apply" and the fail-closed rule above applies (L-b). The restore tests never need to decrypt TOTP rows (they assert state, counts and the `RecoveryRequired` transitions only).
* **Enrolment (API + shared UI):** allowed only from `EnrolmentRequired` (a new user, a grantee, or a user after a completed recovery/DR reset), never from `RecoveryRequired`/`Enrolled` without step-up. **One-time enrolment code (M8):** after a recovery (section 6) or a privileged grant (section 7) the enrolment additionally needs a one-time enrolment code that the approver gives the VERIFIED subject out of band. The code is generated at approval time and shown once to the approver, stored only as a hash inside the approval request (under its MAC), bound to that request and subject, valid from execution for at most 24 hours, single use, and its use raises an alert (section 10). `POST /auth/mfa/enrol/begin {enrolmentCode}` (an `enrol` challenge, section 5) generates a secret, stores it `Pending` (replaced if repeated, expires after 15 minutes), returns the `otpauth://` URI and Base32 once for the shared QR component; `POST /auth/mfa/enrol/confirm {code}` verifies through `MfaVerifier`, atomically sets `Active` and `last_step`, sets the user row to `Enrolled`, audits `mfa.enrolled`, and revokes the user's OTHER sessions. The first administrator created by `bootstrap-admin` receives the enrolment code printed once to the host operator; there is no approval request in that case, so the hash of THAT code is stored on the user row itself (`mfa_enrolment_code_hash` with its expiry and consumed flag, added with `mfa_state` in M-A, single use, valid 24 hours) and nowhere else. For every other case the hash lives inside the approval request under its MAC. Confirmation attempts are throttled. Re-enrolment of an `Enrolled` user (new device) requires step-up with a current code; the old secret stays valid until the new one is confirmed, so there is never a gap or an off state.
* **Parameters:** fixed at SHA-1/6 digits/30 s for authenticator-app compatibility, window 1 at login; throttling and replay protection compensate and are documented as part of the design.
* **LEAD D-097 (Q2): no static recovery codes in Release 1.** They are an extra bypass surface that D-080 (3) and (5) avoid by design; recovery is only by the approved procedures of sections 6 and 9.

## 5. Login and session changes; enforcement points
**Two-step login (S2).** `POST /auth/login` returns, when a second factor, enrolment or recovery is needed, `{ status: "mfa_required" | "mfa_enrolment_required" | "mfa_recovery_required", challenge }` and creates NO session. The challenge is an opaque 256-bit random token (only its hash stored), bound to user id, client (`Web|Desktop`), source address and purpose (`login`, `enrol` or `recovery_request`), valid 5 minutes, single use, small attempt budget. `POST /auth/mfa/verify {challenge, code}` verifies through `MfaVerifier` (the `last_step` CAS and the challenge consumption in one atomic statement) and then creates the session with `mfa_verified_at = now`, `auth_methods = password+totp`. An `enrol` challenge accepts only enrol begin/confirm (with the enrolment code); a `recovery_request` challenge accepts only the self-filed recovery request of section 6. Every failure (wrong code, expired, used, unknown challenge) has the same body, so there is no oracle.
**Throttling (L4, LEAD D-121):** the second-factor counters live in the existing login throttle table, scope `Login` (0), under their OWN key domains `mfa-pair:` (user and source) and `mfa-user:` (user); migrations may not DROP, so the scope check is NOT widened (relaxing the no-DROP rule is a database-safeguard change that belongs to the owner). Every throttle key is `SHA-256(domain + content)` and the domains (`login:`, `pair:`, `source:`, `chpw:`, `mfa-pair:`, `mfa-user:`; `ThrottleKeyDomains`) are PREFIX-FREE (none is a prefix of another; a unit test pins it), so two keys of different domains can never be the same hash input whatever the content, attacker-chosen login text included. MFA failures never count toward, and an MFA success never resets, any password-login, source or change-password counter, and the other way round (unit tests drive both directions through a shared store). The MFA bounds are their own constants, `MfaThrottleOptions`, independent of `AuthOptions`: 5 failed second-factor attempts per (user, source) and 100 per user across sources inside the 15-minute window, then a 15-minute block (a test pins 5, 100, 15 and that the limiter cannot see `AuthOptions`). A failed second factor never resets password counters; a success clears only the (user, source) MFA counter; lockouts are time-based so other sources cannot lock a user out indefinitely. A per-user lockout (the per-user bound reached) raises an alert to the user and the administrators (section 10).
**Session state:** sessions gain `mfa_verified_at`, `auth_methods`, `emergency` (bool). `AuthenticatedSession` exposes them; `GET /auth/status` reports `mfaVerified`, `mfaRequired`, `stepUpRequired` for the shared UI.
**Step-up (S3):** `POST /auth/mfa/step-up {code}` for a session that is not MFA-verified or whose proof is older than the freshness window (default 15 minutes, bounded 5..60) when an operation declares `RequireFreshMfa`: role grants, recovery approval, key retirement, restore, emergency/DR administration, company MFA policy change, state changes of administrators.
**Enforcement points (all server-side):**
1. Login (password step -> challenge) and the verify/enrol endpoints.
2. The session authentication handler (`HasmAuthentication`): populates MFA claims; authorization policies `MfaVerified` / `MfaFresh` are attached to every privileged endpoint group (access administration, user administration, company administration, approvals, backup/restore endpoints when they exist). A unit test enumerates the endpoint table and fails for any privileged endpoint without the policy, so a new endpoint cannot silently skip MFA.
3. Company selection and company-scoped endpoints: company policy check, `mfa_step_up_required` (HTTP 401, stable code) until step-up.
4. Privilege changes (grant of a mandatory/sensitive role): fresh MFA of the grantor plus independent approval (section 7); the grantee becomes `EnrolmentRequired` immediately, needs the enrolment code (M8) and gets no session until enrolled.
5. **Admin tool (`Hasm.Admin`): ONE authorization model per command (M4).** The tool runs on the host with database administration credentials; the table below is the single list, and sections 6 to 9 only refer to it. `N` = a named HASM administrator authenticated with password and TOTP through `MfaVerifier` and the same throttling (no session issued; LEAD D-099); `A` = an approved, unexpired, unconsumed, MAC-verified approval request whose payload hash matches the command (section 7); `Q` = a DR custodian quorum token, 2 of 3 distinct custodian signatures (section 9). Every execution writes the audit stream and an alert.

## 6. Lost-authenticator recovery (slice S5; D-080 (3))
Recovery is a request through the independent-approval framework (section 7), never a switch:
1. **Request (L3, N1):** by an administrator on behalf of the subject T, or SELF-FILED by T. A subject who lost the authenticator cannot pass the second factor, so a self-filed request is made through a `recovery_request` challenge that is issued ONLY by an explicit "I lost my authenticator" call after the password step (the normal login response does not change and never offers it). A self-filed request carries NO contact details and NO free text supplied by the requester. The callback uses only contact details registered BEFORE the request; any note an administrator adds is length-bounded and shown as untrusted text. There is at most ONE `Pending` request per subject, and a repeated call returns the identical response (no oracle, no flooding). Requests are rate-limited per user and per source, and the subject is alerted on EVERY channel (audit, in-app and outbound) for each one. A self-filed request has NO effect by itself: it only creates a `Pending` request and alerts all administrators. **LEAD D-098 (Q3):** there is NO self-service recovery; an independent administrator must verify and approve. Requester, approver and subject are each distinct, except that the requester may be the subject.
2. **Independent approval and evidence (L3):** the APPROVER verifies the subject's identity out of band, in person or by a callback to contact details registered BEFORE the request, and ENTERS the evidence (method, who verified, when, reference) at decision time; the evidence is part of the decision and is covered by the request MAC, so the requester cannot supply or alter it. Approver != requester and approver != T, a different MFA-fresh administrator holding the approval permission. A cooling-off delay (default 4 hours, bounded 1..24 h) applies between approval and execution; T and all administrators are alerted and ANY administrator can cancel. **(L1)** The request expires 72 hours after it was filed; configuration is validated at start-up so that cooling-off plus a 24-hour execution window is always shorter than the expiry, and execution is possible only between `not_before` and `expires_at`. At approval the approver also receives the one-time enrolment code (section 4, M8) to hand to the verified subject.
3. **Execution:** T's TOTP becomes `Revoked`, ALL T's sessions are revoked (new reason `MfaRecovery`), T's user row becomes `EnrolmentRequired`. T passes the password step and then enrols a NEW authenticator with the enrolment code before any session exists. A `MfaMandatory` user is never usable without a factor.
4. **Audit:** request, evidence, approval, cancel, execution, the enrolment-code use and the later re-enrolment each write a system-stream event with actor, target, approver, request id and payload hash.
5. **No second administrator available:** the DR procedure (section 9); never the emergency account as approver (LEAD D-100), never self-approval, never a unilateral admin-tool reset. The same path (recovery or DR) is the only way back for a `RecoveryRequired` user after a system restore.

## 7. Independent-approval framework (slice S4; D-080 (6))
One generic mechanism for sensitive system-level operations, used by recovery, sensitive role grants, encryption-key retirement and restore (Phase 4.3 live restore, D-081).
* **Table** `admin_approval_request` (system database): `id`, `operation` (closed enumeration in code), `target_ref`, `payload` (parameters, no secrets), `payload_hash` (SHA-256 of canonical JSON), `requested_by`, `requested_at`, `expires_at`, `not_before` (cooling-off), `status` (`Pending|Approved|Rejected|Cancelled|Executed|Expired`), `approved_by`, `decided_at`, `evidence` (entered by the approver at decision time), `enrolment_code_hash` (where the operation has one), `executed_at`, `executed_by`, `restore_epoch`, **`mac_key_id` and `mac` (L2)**: HMAC with the audit key identified by `mac_key_id` over the immutable fields and each recorded status transition, so a row forged or altered by someone with raw database access fails verification in the service and the admin tool (which hold the key ring), and verification keeps working across audit-key rotation.
* **Rules in ONE service** (a test pins that no endpoint or command changes a covered operation without it): approver != requester; approver != target where the operation has a target user; approver holds the per-operation approval permission (a new permission family that is itself a sensitive grant); approver's session is MFA-fresh at decision time; approval bound to `payload_hash` (a changed parameter needs a new request); single use (execution consumes the request in the same transaction as the operation and its audit event, under a row lock so concurrent executions cannot both win); expiry; a decided request cannot be re-decided; a failed execution leaves the request `Approved` and retryable until expiry, never half-applied. **The emergency account is never a requester or approver in this framework (M5).**
* **Restore epoch (M6):** a system restore EXPIRES every `Pending` and `Approved` request (audited) and records a new restore epoch (installation id, epoch counter and the restore time, written by the restore procedure after the data is restored). Requests created or approved before the latest epoch can never execute.
* **Covered operations:** `mfa.recovery`; `role.grant.sensitive` (Company Administrator, approver permissions, any privileged role per LEAD D-096); `encryption.key.retire`; `restore.execute` (the 4.3 live restore: this framework is the "independent administrative approval" of D-081, the 4.3 slice integrates it); `emergency.create`; `emergency.rotate`; `dr.keys.change`.
* **Key-retirement pre-check (M7), fail closed:** `encryption-retire-key` refuses unless an approved request exists AND an inventory proves that nothing still needs the key: no TOTP secret, no active attachment, no REMOVED but retained attachment (decision R), no import-file original (refused until imported files have a retirability signal), and no retained backup set whose manifest lists the key. If any part of the inventory cannot be completed, the retirement is refused (a missing inventory is never read as "unused").
* **Every path that makes a user privileged is routed or removed (H2).** S4 enumerates all of them and moves each onto `role.grant.sensitive` or removes it: `POST /api/v1/admin/users` with `IsIdentityAdministrator = true` (removed: administrators are created through a request, and the flag is never accepted on user creation), `Hasm.Admin grant-company-admin`, `grant-fiscal-approver`, `grant-journal-approver`, `grant-import-approver` (and the commercial-approver and any later approver grant), re-activating a disabled identity administrator (`POST /api/v1/admin/users/{id}/state`, classified as privilege-granting: it restores central privilege, so it goes through `role.grant.sensitive`), role/assignment changes in the access service that give a role classified privileged by LEAD D-096. **A test enumerates the admin-tool commands and the API routes** and fails for any privilege-granting path that is not classified (routed through the framework, or `bootstrap-admin`). `bootstrap-admin` stays limited to the case where no administrator exists.
* **First second administrator and first approver (LEAD D-105):** when the independent approval is impossible because no eligible approver exists ("no eligible approver" is computed SERVER-SIDE under the approval lock at execution time; eligible excludes the emergency account and anyone `RecoveryRequired`, disabled or not MFA-enrolled; the check is never a flag supplied by the caller), the grant is made fail-closed through the admin tool with a DR custodian quorum token (`Q`, 2 of 3), audited and attributed to `admin-tool:<os-user>@<host>` plus the custodian ids; it is never unilateral. S4 ships a test that the quorum path REFUSES (with no configuration switch to enable it) until the S7 verifier exists; Phase 4.1 is not complete until S7.
* Approver identity is the authenticated MFA-fresh session; the framework never accepts a password or code as proof of approval. The admin-tool consumer identifies the request by id and re-verifies MAC and payload hash.
* **LEAD D-099 (Q4):** privileged admin-tool operations require the operator to authenticate as a NAMED HASM administrator with MFA (the table in section 5) and are attributed to that account in the audit event and on the request; operations where no such login is possible are attributed to `admin-tool:<os-user>@<host>` plus the ids of the custodians whose signatures were verified. The tool never accepts an identity from a command-line flag alone.

## 8. The one emergency account (slice S6; D-080 (4))
* **Exactly one**, enforced by a partial unique index on an `is_emergency` flag and by the creation command refusing a second one. Created ONLY by the admin tool (`emergency-create`, section 5 table), never by API; it has a distinct login, state `Disabled` by default.
* **Offline credential custody:** `emergency-create` generates a high-entropy password (>= 24 random characters) and a TOTP secret and prints each ONCE to separate output the operator seals offline (password to custodian A, TOTP secret to custodian B). Only the password hash and the KEK-protected TOTP secret are stored; nothing is kept in plaintext, logs or backups. There is NO MFA exemption: the second factor is held by a different custodian (split custody). Its `user_totp` secret follows the same per-table backup rule as every other (included only in encrypted runs), but **after ANY system restore the emergency account stays `Disabled` and cannot be activated until `emergency.rotate` has been approved** and new custody material has been sealed (H1).
* **Time-limited access:** `emergency-activate --minutes N --reason "..."` (authorization `Q`, section 5 table) sets the account `Active` for N minutes (default 30, hard maximum 120, no extension; another activation is another audited action) and records the reason. The session lifetime is capped to the window. At expiry or `emergency-deactivate` the account returns to `Disabled`, **ALL its sessions are revoked immediately (revocation reason `EmergencyEnded`, M5)**, and **its password and TOTP secret are rotated** (a used credential is never reusable); new custody material must be sealed.
* **Fixed permission allow-list (M5):** the emergency account holds a code-defined, fixed allow-list of permissions (Release 1 candidates: system status, audit verification and anchoring, running and verifying a backup, reading user state) that no role assignment can widen. It can NOT request or approve anything in the approval framework, cannot grant roles or change its own state, cannot execute a restore, and cannot enrol or recover users. A test pins the list and fails when a permission is added to it.
* **Immediate alerting and audit:** activation, every login attempt (success or failure), every request of the emergency session (flagged `emergency`, so every audit event of that session carries the flag), deactivation and rotation raise an alert (section 10) AND write system-stream events. A failed alert delivery never blocks the audit write and is surfaced and retried.
* **LEAD D-100 (Q5): scope.** The emergency account is for disaster-recovery ACCESS only. It is NEVER an approver (of anything, and never of last resort) and never approves its own use. The DR procedure (section 9) is the last resort for the no-second-administrator case.

## 9. Disaster-recovery procedure (slice S7; D-080 (5))
For when no second administrator is available. Independently controlled, never a general bypass:
* **Offline DR signing keys (LEAD D-101, Q6):** exactly 3 custodians, threshold 2 of 3. At installation (or by a later `dr.keys.change` approval) 3 public Ed25519 keys are registered together with an **installation id** (random, generated at install, stored in the system database); the private keys are generated offline and held by the 3 separate custodians, each of whom signs a custody statement (recorded in the runbook and the audit log at registration). The system never holds a private key.
* **DR authorization token (`Q`):** produced offline: canonical JSON `{operation, installationId, targetUser (or target of the operation), issuedAt, notBefore, expiresAt (<= 24 h), nonce, reason}` with at least TWO signatures from distinct registered keys; valid for ONE operation and ONE target. **(M6)** The token binds the installation id, and the tool REFUSES a token whose `issuedAt` is earlier than the latest restore epoch (a system restore resets the used-nonce store to the backup's content, so older tokens must never become valid again) or whose installation id differs.
* **Operations a token can authorize:** `mfa.dr.reset`, `emergency.activate`, the first-grant of H2 (`role.grant.first`), and `emergency.rotate`/`emergency.create`/`dr.keys.change` where no administrator is available. Nothing else; there is no generic "run as administrator".
* **Execution:** e.g. `Hasm.Admin mfa-dr-reset --token <file>` on the host verifies signatures against the registered keys, the threshold of DISTINCT keys, the window, the installation id, the restore epoch and that the nonce was never used (stored), then performs the same safe transition as normal recovery (target `Revoked` -> `EnrolmentRequired`, sessions revoked) and prints a one-time enrolment code for the custodians to hand to the verified subject (section 4, M8). The tool grants no login. Audit event with signer key ids, nonce and operator OS account; immediate alert; every failed attempt audited and counted.
* A DR reset never yields a session and never disables MFA: the target still passes the password and enrols a new authenticator with the enrolment code.
* Key rotation or replacement is a `dr.keys.change` request (independent approval; the new set must be signed by the old threshold).
* Who the custodians are is an organisational control software cannot verify; the signed custody statements and the registration are documented in the slice S8 runbook.
* The runbook includes a rehearsal on a disposable database; tests exercise the full verification logic with generated keys (never real custody keys).

## 10. Audit and notifications
* Audit events (new range in the system stream, codes allocated with each slice): enrolment begun/confirmed/replaced/revoked, challenge issued/failed/succeeded (counts, never codes), step-up result, MFA policy changes, approval requested/approved/rejected/cancelled/expired/executed, recovery evidence, emergency created/activated/login/deactivated/rotated, DR token verified/rejected, `totp-rewrap`, key retirement. Details never contain secrets, codes, tokens or key material (a test scans audit rows and log output for them).
* **Notifications:** the repository has no notification channel. The plan adds a small `ISecurityNotifier` with (a) a durable in-app security-notice table written in the same transaction as the audit event (visible to administrators and to the affected user at next sign-in) and (b) an outbound channel, **LEAD D-102 (Q7):** every notification is ALWAYS written to the audit log and to the in-app administrator notification list; the outbound channel is SMTP first, with a webhook as an option. If no outbound channel is configured the status report shows DEGRADED (exit 8 style); production readiness REQUIRES a configured channel and it is an acceptance criterion of Phase 4.1. Alerts for recovery requests (including self-filed ones), approvals, executions, enrolment-code use, per-user MFA lockouts, emergency activation and DR use go to the target user and all administrators. Delivery failure never blocks the protected operation or hides the audit record.

## 14. Risks recorded
* An operator holding raw database administration plus the audit key ring can forge approval rows; the control is the separation of custody of the key ring and the external audit anchors, the same assumption the audit design already makes. Documented, not solvable in software.
* TOTP is phishable; no phishing-resistant factor (WebAuthn) in Release 1.
* Loss of ALL KEK custody makes TOTP secrets unreadable; every user must then re-enrol through the DR procedure. Key backups follow decision K.
* **Recorded limitation (dated):** 2026-11-21 (Phase 4.1 S1, review M2 of PR #133, lead decision D-048): the system database runtime connection is not least-privilege for user_totp; the hasm.totp_rewrap flag is code discipline only, settable by any session. A system-database runtime-role grant model is an architecture change outside slice S1; it is a follow-up of the S4 authorization or the database-role work, is on the owner/DBA register, and is a blocker for production readiness until closed or explicitly accepted.
* **L6 of the review of PR #133 (won't fix: conflicts with restore; fail-closed by the secret check, lead decision D-048):** a BEFORE INSERT trigger restricting `mfa_state` on the user row would break the COPY-based system restore (D-106, D-107), which reloads Enrolled users. A user row inserted as Enrolled without an Active secret is not a bypass: the password step issues only a challenge, no code can verify, and no session is created (pinned by a PostgreSQL test in `MfaLoginTests`).
* **S2 review follow-ups (G, PR S2):** (L1) the VOLUNTARY enrolment has an API (`enrol/begin` with a password in a live session, `enrol/confirm`) but NO screen yet: neither the Web nor the Desktop client offers it, so it is a deferred feature, not a platform parity gap; the security-settings screen of S3 carries it. (L2) the client-kind and source bindings of a login challenge are CONSISTENCY checks only (a challenge issued to the Web client is not accepted by the Desktop client or from another address): the client kind is chosen by the caller and the address can change behind a proxy, so neither is an authentication factor; the factors are the password and then the single-use token plus the TOTP code.
* **S2 limitations (lead decisions D-048, recorded with the S2 slice):** (1) the enrolment screen is TEXT ONLY: the Base32 secret and the `otpauth://` link, which is the plan's own fallback; the shared QR component is a follow-up whose dependency choice is reviewed separately (no new dependency and no hand-written encoder in S2); (2) until S4's admin authorization (D-099) exists there is NO admin-tool command that issues an enrolment code, so until S4 a required enrolment cannot start without a code already stored on the user row (the bootstrap-administrator case); a user without one stays without a session (fail closed); (3) the Tauri compilation is covered by the hosted desktop-build job (the crates are not available offline).
* **S5 follow-ups (review of PR #133):** (L4) revoking all secrets and moving the user's state are two calls today and must become ONE atomic operation in recovery; (L5) `MfaStore.FindActiveSecretAsync` fails closed (a user whose secret cannot be read cannot sign in and is not downgraded), recovery from `Enrolled` exists for that user, and a key-availability pass that marks users whose secret is unreadable `RecoveryRequired` is added with recovery.
* The cooling-off delay slows legitimate recovery; DR exists for urgent cases.
* After a system restore that brings back no usable secret (unencrypted DEV/TEST run, lost key export, partial restore), MFA users must come back through recovery or DR; this is intended (H1) and must be rehearsed in the restore runbook. An encrypted run restores the wrapped secrets, readable only with the key export (D-087).
* If the recovery (backup) private key is suspected compromised, a rewrap alone does not help: every user must re-enrol their authenticator AND reset their password (the backed-up wrapped secrets and password hashes must be treated as exposed).
* The audit-trail first-touch scoping fix (PR #112) is a prerequisite for relying on audit appends inside long-lived pooled connections.
