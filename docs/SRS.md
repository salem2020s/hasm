# حسم HASM — Software Requirements Specification (SRS)

> **الحالة:** مسودة تجميع للمراجعة والاعتماد، وليست تفويضاً ببدء البرمجة.
> **الإصدار:** SRS Draft 0.2 — 2026-11-08 (تدقيق اتساق؛ دون تغيير القرارات المعتمدة)
> **المنتج:** HASM Local — نظام المحاسبة والمستودعات
> **قاعدة العمل:** كل قرار معتمد سابقاً مثبت هنا؛ التفضيلات التنفيذية الصغيرة قابلة للضبط، ولا تُعامل كعائق لاعتماد نطاق الإصدار الأول.

## 1. الهدف والنطاق

حسم نظام محاسبة وإدارة مستودعات أصلي، يعمل محلياً داخل الشركة، بواجهتين عربية (RTL) وإنجليزية (LTR). يتضمن المحاسبة العامة والمبيعات والمشتريات والذمم والبنوك والشيكات والمخزون والتقارير والطباعة والاستيراد والإدارة والأمان والتراخيص والنسخ الاحتياطي. يعمل دون اتصال دائم بالإنترنت.

**ضمن الإصدار الأول:** تطبيق Windows، واجهة Web داخل الشبكة، Backend API، PostgreSQL، دعم شركة واحدة أو عدة شركات، فروع ومخازن متعددة، جميع قدرات المحاسبة والمخزون الواردة أدناه.

**خارج نطاق الإصدار الأول:** SaaS متعدد العملاء عبر الإنترنت؛ الرواتب والموارد البشرية؛ التصنيع؛ ربط مباشر إلزامي بالبنوك؛ تكييف ضريبي/فوترة إلكترونية محددة لبلد واحد؛ PostgreSQL PITR كمتطلب إلزامي. تُترك نقاط امتداد مدروسة لهذه القدرات مستقبلاً.

## 2. التقنيات وطريقة التشغيل

- **Frontend:** React + TypeScript، واجهات مشتركة بين Web وDesktop.
- **Desktop:** Tauri 2 على Windows.
- **Backend:** ASP.NET Core باستخدام C#، ويضم منطق الأعمال والصلاحيات والترحيل والتكلفة.
- **DBMS:** PostgreSQL على Windows Server أو Linux Server حيث يلزم.
- كل العملاء يتصلون حصراً بـ Backend API عبر HTTPS؛ **لا اتصال مباشر من Desktop أو Web بقاعدة PostgreSQL**.
- نماذج نشر مدعومة: جهاز Windows واحد لكل المكونات، سيرفر مركزي للتطبيق وقاعدة البيانات، أو سيرفر تطبيق وسيرفر قاعدة بيانات منفصلان.
- معالج تثبيت وإعداد أولي، يدعم PostgreSQL محلياً أو خارجياً، إعداد الشهادات والأسرار، حساب المدير الأول والشركة الأولى، وفحوص سلامة البيئة.
- السيرفر المحلي لا يحتاج إلى إنترنت للعمل اليومي؛ ترخيص/تحديث أوفلاين مدعوم.

## 3. الفصل بين الشركات والفروع

- قاعدة بيانات نظام مركزية **يُشار إليها منطقياً** باسم `Hasm_System`، تحتوي كتالوج الشركات والتراخيص وهويات المستخدمين والمراجع المشتركة؛ لا يشترط أن يكون هذا اسمها الفيزيائي في PostgreSQL.
- **قاعدة PostgreSQL مستقلة لكل شركة محاسبية**، وتحوي حساباتها وقيودها وفروعها ومخازنها وذممها وسنواتها وإعداداتها ومرفقاتها المرجعية.
- `Party` ككيان أعمال مشترك: `GlobalPartyId` على مستوى النظام، و`LocalPartyId` داخل الشركة. بيانات تعريفية مشتركة مقابل بيانات مالية مستقلة لكل شركة.
- تعديل البيانات التعريفية المشتركة يخضع لاقتراح من مستخدم مخوّل وموافقة مركزية مع تدقيق؛ لا يسمح هذا بمشاهدة أرصدة شركة أخرى.
- صلاحيات محددة بالشركة والفرع والمستودع؛ لكل فرع صناديق ومستودعات وربط بمراكز التكلفة عند اللزوم.
- تسويات بين الفروع داخل الشركة، مع إمكان نقل المواد بين المستودعات.
- التقارير متعددة الشركات تنفّذ في Backend بالتجميع والتحويل اللازم للعملات، وليست بوصل SQL مباشر بين قواعد الشركات.
- التجميع البسيط للشركات منفصل عن التوحيد المالي الرسمي، الذي يتطلب خرائط حسابات ومعالجة عمليات بين الشركات وإلغاءات وتسويات فروق العملة.

## 4. المستخدمون والصلاحيات والموافقات

- مستخدمون محليون، وخيار تكامل Active Directory/Kerberos محلياً حيث تسمح البيئة؛ MFA عبر TOTP للحسابات المدعومة، وحساب طوارئ محمي.
- RBAC متقدم بأدوار وصلاحيات تفصيلية، ونطاقات الشركة/الفرع/المستودع، بما فيها صلاحيات السعر والتكلفة والتواريخ والتعديل والموافقة والنسخ الاحتياطي.
- سياسات موافقات قابلة للضبط حسب نوع المستند والقيمة والفرع والخطر؛ فصل المهام (SoD) يوجب موافقاً مختلفاً حين تكون السياسة مفعّلة.
- تعديل مستند **معتمد لكنه غير مرحّل نهائياً** في حقول مؤثرة يعيد دورة الموافقة وفق السياسة؛ أما المستند/القيد **المرحّل** فلا يُعدّل ولا يُحذف، ويصحح بمستند عكس أو تسوية مستقل. العمليات المجدولة والترحيل الآلي لا تتجاوز الضوابط.
- حسابات المستخدمين لا تحصل على صلاحيات DBA؛ تدقيق العمليات الإدارية والحساسة وأحياناً الموافقة الثانية.

## 5. الحسابات العامة والفترات المالية

- شجرة حسابات مرنة غير محدودة العمق عملياً؛ أنواع حسابات الميزانية والأرباح والخسائر؛ قوالب أولية لشركات متنوعة.
- قيود يومية يدوية وآلية، متوازنة ومدققة، تترحل كوحدة ذرّية؛ توزيع حسب الفرع ومركز التكلفة.
- **لا يُعدّل أو يُحذف القيد المرحّل**: التصحيح بعكس قيد أو بقيد تسوية، مع حفظ سلسلة المراجع وسجل التدقيق.
- دعم سنوات مالية متعددة مفتوحة بالتزامن، وفترات شهرية/ربع سنوية، وحالات `Open` و`Soft Closed` و`Final Closed`.
- إغلاق الفترة يتطلب معالجة الفروقات والتسويات الجوهرية المعلّقة؛ إعادة فتح استثنائية بموافقة وصلاحيات وتدقيق.
- ترحيل أرصدة السنوات والطبقات والمستندات المفتوحة دون مضاعفة أو فقدان بيانات.
- العملات المتعددة، العملة الأساسية للشركة، أسعار صرف فعالة بالتاريخ، وسعر قابل للتجاوز بصلاحية مع السبب والتدقيق؛ إثبات فروقات العملة.

## 6. الضرائب

- محرك ضرائب مرن قابل للتمديد، معدلات مؤرخة، تصنيفات عمليات ومواد وجهات، أكثر من ضريبة، استثناءات وإعفاء وصفر بالمائة، شامل/غير شامل.
- تحديد قواعد أساس الحساب والتقريب وأولوية تطبيق الضرائب حسب نوع المستند والعملية.
- حفظ **لقطة ثابتة** من القاعدة والنسب والنتائج على المستند النهائي؛ عدم تغيير الفواتير القديمة تلقائياً عند تعديل السياسات.
- تكاملات الامتثال الوطني والفوترة الإلكترونية تُضاف كوحدات توطين مستقبلية بعد تحديد الدولة والمتطلبات.

## 7. دورة المبيعات والمشتريات

- عروض أسعار، أوامر بيع/شراء، فواتير، مرتجعات، سندات قبض/صرف، نقدي/آجل/مختلط، خصومات، ضرائب، عملات، حدود ائتمان، مندوبون.
- نمطان بحسب العملية: **فاتورة مباشرة** تنشئ أثر المخزون المطلوب، أو **تسليم/استلام منفصل** مع شحنات جزئية وروابط بين المستندات.
- يجب ضمان عدم تكرار حركة المخزون أو أثر الأستاذ العام بين الفاتورة وسند التسليم/الاستلام.
- **في نمط الفاتورة المباشرة:** يُثبت حدث التسليم/الاستلام المادي عند اعتماد الفاتورة المتضمنة هذا الحدث، وتحدث حركة المخزون مرة واحدة. **في النمط المنفصل:** تنشأ حركة المخزون عند اعتماد وثيقة التسليم/الاستلام المادي، لا بمجرد اعتماد الفاتورة. في الحالتين يُرحّل الأثر المحاسبي الواجب تلقائياً أو يبقى **في حالة ترحيل محاسبي معلّق صريحة** مع السبب، وربط المستندات، وحماية إقفال الفترات؛ ولا تُنشأ حركة أو قيود ثانية لنفس الحدث.
- دعم حسابات وسيطة مثل GRNI عندما تستلم البضاعة قبل فاتورة المورد.
- ترقيم مرن حسب الشركة/الفرع/نوع المستند/السنة المالية، مع بادئات وتسلسل مقاوم للتزامن؛ الرقم الرسمي عند الاعتماد/الإصدار؛ الملغى لا يُعاد استخدام رقمه تلقائياً.

## 8. محرك التسعير والخصومات

- قوائم أسعار متعددة وقواعد أولوية حتمية وقابلة للضبط حسب العميل ومجموعته، الكمية، وحدة القياس، العملة وتاريخ السريان.
- تسلسل واضح لحل التعارض بين الأسعار والخصومات وتسجيل القاعدة التي اختيرت؛ صلاحيات تجاوز السعر أو الخصم يدوياً مع السبب.
- مراقبة هامش الربح وحدود الحد الأدنى أو طلب موافقة استثنائية بحسب السياسة.
- حفظ السعر والخصم والتكلفة/الضرائب ذات الصلة كلقطات تاريخية على الفواتير الصادرة؛ تغيير القائمة لاحقاً لا يعيد تسعير مستند مرحّل.

## 9. المواد والمستودعات والتكلفة

- أصناف وخدمات ووحدات بديلة وتحويلات بين الوحدات، باركود، دفعات Lot، أرقام تسلسلية، انتهاء صلاحية، جرد وتسويات وتحويلات وحجوزات.
- طريقتا التقييم المعتمدتان: **FIFO** و**المتوسط المرجح المتحرك**؛ سياسة الاختيار على مستوى الشركة أو مجموعة المواد مع ضوابط تغيير الطريقة وإعادة التقييم.
- **التكلفة لكل مادة ولكل مستودع بصورة مستقلة** في الطريقتين؛ عند التحويل تنتقل التكلفة الفعلية ويُعالج استقبالها بطريقة المستودع المستقبِل؛ تجميع قيمة المخزون في التقارير.
- منع المخزون السالب افتراضياً؛ استثناء محدود ومخوّل للمواد المؤهلة بنظام المتوسط المتحرك مع تكلفة مؤقتة وتسوية لاحقة. يمنع للمادة FIFO أو المتتبعة بالدفعة/الرقم التسلسلي.
- حركات بأثر رجعي مسموحة ضمن سياسة الفترات والصلاحيات: تحليل الأثر، معاينة التكلفة الجديدة، إعادة حساب طبقات FIFO/المتوسط للحركات اللاحقة والمتسلسلة عبر المستودعات، مستندات تسوية مخزنية ومحاسبية مستقلة تعتمد قبل الترحيل.
- لا يُعدّل تاريخ قيود مالية مرحّلة أو بياناتها الأصلية؛ الفترات المقفلة نهائياً لا تقبل ترحيلاً رجعياً إليها. الفروقات المعلقة الجوهرية تمنع إقفال الفترة.
- تمييز تاريخ العملية وتاريخ التسجيل/الاعتماد لأغراض التدقيق.

## 10. الذمم والقبض والصرف

- ذمم العملاء والموردين وأعمار الديون وكشوف الحساب وحدود الائتمان، صناديق وبنوك وتحويلات وسندات وإشعارات دائن/مدين.
- تخصيص سند قبض/صرف إلى فاتورة أو عدة فواتير؛ سداد جزئي أو أكثر من سند للفاتورة الواحدة.
- تخصيص يدوي أو اقتراح تلقائي حسب الاستحقاق، مع مراجعة قبل الاعتماد؛ دفعات مقدمة، مبالغ زائدة/غير مخصصة، الإشعارات الدائنة وفروقات العملة.
- فك التخصيص وإعادة توزيعه بصلاحيات وتدقيق؛ **الربط أو إعادة الربط لا ينشئ قيد قبض/صرف مكرر**.

## 11. الشيكات والتسوية البنكية

- دورة حياة متقدمة للشيكات الواردة والصادرة: حافظة، مؤجل، إيداع، برسم التحصيل، محصّل، مرتجع، ملغى، ومظهّر حيث يسمح النظام والقواعد المحلية.
- ربط الشيكات بالجهات والفواتير والذمم والقيود، وتواريخ الاستحقاق وإشعارات الحالة والتقارير؛ قيود وسيطة وتسويات مرتجعات بحسب سياسة الشركة والتشريعات المطبقة.
- تسوية بنكية يدوية وذكية عبر استيراد CSV/Excel؛ معاينة وأداة تعيين أعمدة، كشف المكرر، اقتراح مطابقة بالمبلغ/العملة/التاريخ/المرجع، دعم جزئي ومتعدد، ثم اعتماد.
- لا يولّد ربط حركة بنكية بقبض مسجل قيداً مكرراً؛ رسوم البنك أو فروقات الصرف الجديدة تولد مستند تسوية مستقل تحت الموافقات.
- تكامل API مباشر مع البنوك غير إلزامي في v1.

## 12. المستندات والقيود المتكررة

- قوالب وجدولة دورية للقيود والفواتير والمصاريف والاستحقاقات والدفعات المجدولة، بتواريخ وتواتر مخصصين.
- **إنشاء مسودة افتراضياً**؛ خيار ترحيل/اعتماد تلقائي مشروط بنوع العملية والصلاحيات وفصل المهام والفترة المالية.
- تنفيذ Idempotent لمنع إنشاء نفس مستند الدورة مرتين؛ عدم تعديل المستندات السابقة عند تغيير القالب؛ تنبيهات فشل/اعتماد وسجل تنفيذ وتوقف مؤقت.
- لا تنفّذ الجدولة تحويلات مصرفية فعلية بلا تكامل مخوّل خارج نطاق الإصدار الأول.

## 13. التقارير والطباعة وتجربة المستخدم

- تقارير جاهزة للميزانية والأرباح والخسائر والأستاذ والموازين والذمم والمخزون والتكلفة والمبيعات والمشتريات والضرائب والبنوك والشيكات والفروع ومراكز التكلفة.
- فلاتر مرنة ومقارنات وتفصيل/تجميع مع مراعاة حدود الصلاحيات والشركات والعملات.
- **مصمم تقارير مرئي متقدم**: حقول، فلاتر، تجميع، صيغ، مخططات، تصدير PDF/XLSX.
- **مصمم مستندات مستقل**: قوالب فواتير ومستندات، A4/A5/حراري، باركود، لغات وإصدارات قوالب تاريخية.
- الواجهة عربية RTL وإنجليزية LTR، تصميم مؤسسي بسيط، مناسب للوحة المفاتيح والاختصارات.
- **قوائم مكتبية متدرجة تفتح بالمرور Hover** على عنوان القائمة والعنصر الأب؛ الأمر النهائي لا ينفذ إلا بالنقر أو اختيار لوحة المفاتيح؛ تأخير قصير ومرور آمن بين القوائم، فتح بالنقر للأجهزة اللمسية، وإتاحة ARIA/keyboard.
- تطبيق الهوية البصرية والشعار الرسمي الذي اعتمده صاحب المشروع؛ لا تُستبدل ملفات الشعار الرسمية بصورة مولّدة أو معدّلة دون موافقته.

## 14. الترحيل من الأنظمة القديمة والمرفقات

- استيراد Excel/CSV بتعيين الأعمدة وStaging وDry Run والتحقق من التكرار والاتساق وقيود/ذمم/مخزون الافتتاح.
- يدعم أرصدة افتتاحية فقط أو تاريخاً كاملاً عند توفر البيانات؛ **موافقة مخوّلة إلزامية** قبل تنفيذ الاستيراد النهائي، ومنع تضاعف المستندات والأرصدة.
- المرفقات تحفظ **كملفات على السيرفر** (قرص محلي أو SMB/NFS)، وبياناتها الوصفية في قاعدة الشركة؛ فصل الشركات وسلامة Hash والتحكم بالوصول عبر Backend فقط. المرفقات المصنفة حساسة تُحمى بتشفير على مستوى التطبيق وإدارة مفاتيح مناسبة، وليس فقط بتشفير القرص.
- تنسيق النسخ الاحتياطية والاستعادة بين قاعدة البيانات ومجلدات المرفقات، وتشفير الملفات الحساسة عند اللزوم.

## 15. التراخيص والنسخة التجريبية

- تراخيص مدفوعة: **Named User** أو **Concurrent Users**، باشتراك سنوي أو ترخيص دائم.
- الترخيص المتزامن يحتسب **كل جلسة نشطة**؛ مستخدم واحد على Web وDesktop = جلستان؛ تبويبات الجلسة الواحدة لا تتكرر؛ Heartbeat وLease Timeout قابلان للضبط.
- انتهاء الاشتراك السنوي يحوّل العمليات إلى قراءة/تصدير فقط مع حفظ المسودات؛ انتهاء صيانة الترخيص الدائم لا يوقف استخدام النسخة المملوكة.
- دعم أمني وإصلاح عيوب مجاناً لكل إصدار رئيسي مدعوم لمدة **36 شهراً**، حتى بعد انتهاء الصيانة؛ الميزات الجديدة وفق استحقاق الصيانة؛ إشعار نهاية الدعم مسبقاً.
- ترخيص موقّع وتفعيل أونلاين/أوفلاين؛ استخدام أوفلاين مستمر؛ نقل أو استبدال الترخيص بسبب نقل سيرفر أو تعطله **عبر دعم HASM الفني حصراً** وليس ذاتياً.
- Trial بلا مفتاح ولا مدة انتهاء: **شركة واحدة، مستخدمان، فرع واحد، مستودع واحد، 100 معاملة أعمال مرحّلة** (لا تُحسب قيودها الآلية كمعاملات إضافية). وحدات وتقارير أساسية فقط، بلا مصممين ولا عملات متعددة/شيكات/تجميع شركات. بعد الحد يسمح بالقراءة والتصدير، والترقية تحفظ البيانات.
- حد مساحة المرفقات التجريبية قيمة سياسة ترخيص قابلة للضبط، **لم يُعتمد رقم نهائي**؛ لا نعطّل اعتماد المواصفات بانتظار اختيار هذا الرقم.

## 16. النسخ الاحتياطي والاستعادة والتحديثات

- نسخ يدوية ومجدولة (يومي/أسبوعي/شهري)، احتفاظ ووجهات متعددة محلية/شبكية، تشفير، تنبيه ومراقبة نتيجة النسخ، واختبارات استعادة فعلية.
- استعادة تثبيت كامل أو **شركة واحدة مع مرفقاتها دون إرجاع بقية الشركات أو `Hasm_System`** إلى الماضي؛ فحوص توافق وروابط الأطراف المشتركة وإجراء استعادة تجريبية ثم Cutover مدروس.
- PostgreSQL PITR نقطة توسع مستقبلية وليس شرطاً للإصدار الأول.
- RPO/RTO **أهداف تشغيلية تُضبط وتُقاس** حسب جدولة النسخ ومكان التخزين وحجم البيانات؛ لا نَعِد بوقت ثابت دون اختبار.
- التحديثات **يدوية حصراً**: حزم موقّعة عبر تنزيل أو نقل Offline؛ فحص التوقيع والتوافق ونسخة DB والصلاحيات والنسخة الاحتياطية والرجوع الآمن، مع توافق عملاء Web/Desktop.

## 17. الأمان والسجل التقني

- TLS للاتصال بالـ API وقاعدة البيانات، حماية الأسرار وإدارة تدوير المفاتيح والاستعادة دون اشتراط إنترنت.
- كلمات المرور تخزن باستخدام Hash آمن، لا تشفير قابل للاسترجاع؛ تشفير نسخ احتياطية ومرفقات حساسة وحقول محددة بحسب الحاجة.
- سجل تدقيق Append-only على مستوى التطبيق مع سلسلة أو بصمات كشف عبث، وقيود وصول وتصدير/احتفاظ ونسخ خارجية محمية؛ لا يُدّعى أنه غير قابل للتعديل من مدير نظام يسيطر على كافة البنية.
- داخل **قاعدة الشركة الواحدة** يُثبَّت الحدث المالي وقيده وتدقيقه وسجل منع التكرار ذرّياً في معاملة واحدة عند لزوم الترحيل. أما العمليات العابرة إلى `Hasm_System` أو شركة أخرى فلا تُفترض لها ذرّية موزعة؛ تُستخدم آليات موثوقة لتسجيل الطلبات وإعادة المحاولة والتسوية مع إبقاء الحدث المحلي متسقاً. الترحيل التلقائي لا يتجاوز الموافقات.
- **ترميز مادي غير وصفي لأسماء قواعد البيانات والجداول والحقول التجارية عموماً**، وكذلك أسماء العلاقات والفهارس والقيود المسماة عندما تكشف معنى العمل؛ مع قاموس ربط منطقي/فيزيائي خاص بالمنظومة، ومعرفات ثابتة، وعمليات Migrations واختبارات تعمل على هذه الأسماء. لا تضع أسماء شركات أو مصطلحات مالية مكشوفة في مُعرّفات PostgreSQL الفيزيائية. تظل الأسماء المنطقية مفهومة لفريق التطوير في الطبقات الداخلية المصرح بها، ولا تُعرَض خريطة الربط ضمن واجهات العملاء أو تقارير الأخطاء. لا تعتمد حماية النظام على غموض الأسماء؛ إذ يمكن لـ DBA ذي صلاحية كاملة تحليل مخطط PostgreSQL وبياناته، والحماية الأساسية بالوصول الأقل وصلاحيات الشبكة ومنطق الأعمال في Backend والتشفير.
- تسجيل صحة الخدمة والتشخيص الفني والنسخ الاحتياطي برسائل منقّحة لا تحتوي على أسرار، مع حزمة دعم فني محمية.

## 18. الأداء والاختبارات ومعايير القبول

- اختبار مرجعي على **8 vCPU، 32 GB RAM، SSD 500 GB** يجمع Backend وPostgreSQL، وبواقع **5 شركات و50 جلسة نشطة متزامنة**.
- بيانات مرجعية موزعة على الشركات الخمس: 20,000 مادة، 10,000 عميل/مورد، 100,000 فاتورة، 500,000 قيد وحركة مخزنية؛ اختبار حمل مستمر **60 دقيقة**.
- أهداف P95 الأولية: البحث عن مادة/عميل < 1 ثانية؛ شاشة اعتيادية < 2 ثانية؛ حفظ/ترحيل فاتورة اعتيادية < 3 ثوانٍ؛ تقرير اعتيادي < 5 ثوانٍ. نتائج القياس، لا هذه العتاد الافتراضي، تحدد المتطلبات الموصى بها للعملاء.
- Unit/Integration/E2E واختبارات الأستاذ العام والتكلفة وإعادة الحساب والاستيراد والأمن والتزامن والنسخ والاستعادة والتثبيت والترقية إلزامية قبل إصدار تجاري.
- لا إصدار بعيوب Critical/High مفتوحة أو اختبارات إلزامية فاشلة؛ تحقق ذرية القيود، وعزل الشركات، ومنع حركات مخزون مكررة أو مزدوجة عند التزامن.
- بيئتا DEV وTEST داخليتان لفريق HASM، ولا يُفرض على العميل الاحتفاظ ببيئة Staging دائمة؛ يمكن اختبار الاستعادة بصورة معزولة.

## 19. قواعد تنفيذ لا يجوز خرقها

1. مصدر الحقيقة للبيانات المالية داخل قاعدة الشركة؛ لا تعديلات مباشرة من واجهات المستخدم على DB.
2. اعتماد المستند لا ينشئ أكثر من أثر مالي/مخزني واحد لكل حدث أعمال (Idempotency).
3. لا تغيير أو حذف للمستند المحاسبي المرحّل؛ التصحيح عبر عكس وتسوية بوثائق مستقلة.
4. لا رؤية عابرة للشركات بسبب مشاركة هوية طرف أو جلسة مستخدم.
5. لا ترحيل إلى فترة Final Closed، ولا تجاوز للموافقات من المهام التلقائية.
6. عدم فقدان المسودات أو المستندات المرتبطة عند انتهاء الترخيص أو انقطاع الاتصال.
7. فصل حالات مستند البيع/الشراء عن التسليم المادي، وعن الترحيل المحاسبي الفعلي عند استخدام النمط المنفصل.
8. قابلية تتبع كاملة لسعر البيع والضريبة وسعر الصرف وتكلفة البضاعة ومصدر قرار الموافقة.

## 20. تفاصيل تنفيذية مؤجلة دون فتح أسئلة جديدة

هذه عناصر **إعدادات أو معايير قبول تقنية** تختار لها فرق التنفيذ قيماً افتراضية منضبطة، وتوثقها وتختبرها قبل الإصدار، ولا تعطل إقرار نطاق المتطلبات: الحصة الرقمية لمرفقات Trial، القيم الابتدائية للـ RPO/RTO، مهلة تحرير الجلسة المتزامنة، تفاصيل مفاتيح الترخيص وطرق تدويرها، وخيارات عرض القوائم/التأخير الافتراضي، والمواصفات الموصى بها لأجهزة الإنتاج بناء على القياسات الفعلية.

## 21. حالات قبول أساسية للتدقيق قبل التطوير

هذه **سيناريوهات قبول مشتقة من القرارات السابقة** وليست توسعة للنطاق:

1. في عملية بيع مباشرة، تُرحّل حركة المخزون مرة واحدة، بينما يربط نمط التسليم المنفصل الحركة بوثيقة التسليم المعتمدة، مع عدم تكرار القيد عند اعتماد الفاتورة لاحقاً.
2. لا يمكن تعديل قيد مرحّل مباشرة، حتى لمستخدم مرتفع الصلاحيات؛ يتم التصحيح بالعكس/التسوية مع توثيق الموافقة والمراجع.
3. لا يتمكن مستخدم الشركة A من استعلام أرصدة الشركة B، حتى لو اشتركتا في `GlobalPartyId`.
4. في عملية ذات أثر محاسبي معلّق، تظهر الحالة صراحة ولا يمكن إقفال الفترة عندما تبقى فروقات جوهرية غير معالجة.
5. تُعاد تكلفة المخزون المتأثرة بتاريخ سابق ضمن الفترات المسموحة، مع معاينة الفروقات وتسويات منفصلة دون تحريف القيود الأصلية.
6. لا يؤدي تخصيص سند قبض، أو مطابقة كشف بنك، أو إعادة المحاولة بعد انقطاع الاتصال إلى إنشاء عملية قبض أو قيد مكرر.
7. تفشل عملية مجدولة لا تستوفي قواعد الموافقة/فصل المهام أو كانت فترتها مقفلة، ويُحفظ سبب الفشل للتدقيق.
8. تظل إعادة الشركة الواحدة ممكنة دون استرجاع قواعد الشركات الأخرى أو قاعدة النظام إلى نقطة زمنية قديمة، مع التحقق من روابطها المشتركة ومرفقاتها.
9. تُفتح القوائم المكتبية المتدرجة بمرور المؤشر، ولا تنفَّذ أي عملية فعلية إلا بعد الاختيار النهائي بالنقر أو بلوحة المفاتيح.
10. تُختبر أسماء PostgreSQL الفيزيائية غير الوصفية عبر إنشاء قاعدة جديدة وترقية مخطط قائم واستعادة نسخة احتياطية، دون افتراض أن إخفاء الأسماء يمنع تحليل DBA.
