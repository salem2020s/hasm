# Phase 3.2D — Generic import framework and Chart of Accounts Excel/CSV import

Approved scope and the six owner decisions are recorded in `docs/PHASE-3.2D-PROPOSAL.md`. This document records what was BUILT, slice by slice. Slices: S1 secure infrastructure and parsers, S2 mapping/normalization/validation/dry run, S3 independent approval and controlled application, S4 shared Web/Desktop wizard, S5 the real Chart of Accounts adapter. The opening-balance adapter is NOT part of this phase (decision 6 describes it for later).

## Isolation rule
Imports write only to the import tables (staging). Nothing in the generic framework knows any business data, and no import table references a business table. Business data is changed only by an adapter's apply step, after validation, a dry run, an independent approval and a re-validation inside the application transaction.

## S1 — Secure infrastructure and parsers (built)

### Encryption (reusable for future sensitive attachments)
* `EnvelopeEncryptor`: AES-256-GCM per file with a fresh random 256-bit data key and fresh random 96-bit nonces for every encryption (no (key, nonce) reuse); the data key is wrapped under a versioned master key (key-encryption key, KEK) with AES-256-GCM key wrapping (associated data: format, key id, context). The file is authenticated together with a context string (`company` + `batch`), so a ciphertext cannot be moved to another batch or altered; the tag is verified before any plaintext is returned. Stored with the ciphertext: format version, key id, wrapped data key, nonces, tags. Format `HFE1` (documented in `FileEncryption.cs`). Only .NET primitives (`AesGcm`, `HKDF`, `RandomNumberGenerator`).
* `FileKekRing`: master keys are files `<keyId>.ekey` (base64, at least 32 random bytes) in a key directory configured by `Hasm__Encryption__KeyDirectory` / `Hasm__Encryption__ActiveKeyId`, outside the repository, the database and the encrypted-file storage, with the same owner-only permission rules as the audit keys (Linux modes 0700/0600, Windows ACLs without broad read access; `AllowInsecureFilePermissions` exists for disposable test environments only). The wrapping key is derived with HKDF-SHA-256 from the master secret (domain-separated from the audit keys). Several key versions live side by side; the active id wraps new files; older keys stay available until every file was re-wrapped. **Fail closed**: missing configuration, missing/short/malformed key file, unreadable directory — the operation throws (HTTP 503 `encryption_unavailable`), nothing is stored, no replacement key is ever generated implicitly. Key material never appears in logs, exceptions or responses. Keys are not tied to a machine (a central-server migration moves the key directory).
* Administration: `Hasm.Admin encryption-keygen <key-id>` creates a new random key file (owner-only, never overwrites). **Rewrap procedure** (key rotation): create the new key, set it active, call `POST /api/v1/company/imports/maintenance/rewrap` (permission `company.imports.configure`; audited per file; idempotent; atomic file replacement; only the wrapped data keys change, the ciphertext and its tag do not), then retire the old key only after every company reported zero files left on it. **Backup/recovery**: the key directory must be backed up SEPARATELY from the database and the encrypted files and recovered together with them; without the key the originals are unreadable (the parsed staging rows and all hashes remain in the database).
* This is **not** an enterprise KMS: there is no HSM, no automatic rotation, no key escrow service.
* `EncryptedFileStore`: ciphertext only, one owner-only directory per company under `Hasm__Imports__StorageDirectory` (absolute path, required), generated file names `<32 hex>.enc` validated on every call (no traversal), exclusive creation + atomic move, atomic replace for re-wrap, idempotent delete. No download route exists; no plaintext temporary file is ever written (the plaintext lives in memory only for parsing and is zeroed).

### File reading (`ImportFileReader`)
* Formats: `.xlsx` and `.csv` only. The extension must agree with the real content: legacy `.xls`/OLE containers, `.xlsm`, PDFs, executables, a zip renamed `.csv` and text renamed `.xlsx` are refused (`unsupported_format`).
* **Excel library: ExcelDataReader 3.9.0** (pinned exactly, MIT license — no commercial redistribution restriction; maintained, last release 2025; read-only API; no NuGet vulnerability advisory reported for it by `dotnet list package --vulnerable`; no transitive dependencies on the net8+ target) — used only to read cell values of `.xlsx`. **Concrete gap found and handled without a custom parser:** ExcelDataReader returns cached values and exposes neither formulas nor the package structure, so the required refusal of formulas/macros/external links/bombs is done by a **streaming security scan of the zip container before any value is read** (our code reads no cell values itself): entry-count limit, declared AND actually produced expanded-size limits (a lying header cannot defeat it), path traversal / absolute / duplicate entry names, DTD and entity expansion prohibited in every XML part, nesting depth, per-text-node length, rows/columns/worksheets, processing-time budget, refusal of VBA projects, macro sheets, ActiveX, embedded OLE objects, data connections/query tables/pivot caches, external links (workbook references and relationships) and **any formula cell** (`<f>` — `formula_not_allowed` with the cell address; a cached result is never trusted). The scan is repeated when rows are read.
* Values: numbers become canonical invariant text, with identifier number formats such as `0000` keeping their leading zeros (text cells are kept verbatim, so account codes like `0101` survive in both CSV and XLSX); dates become ISO text; booleans `true`/`false`; all text is Unicode NFC; control characters are refused. Row numbers are the true sheet rows (CSV: record numbers). Blank rows are skipped.
* CSV: strict RFC 4180 parsing (quotes, doubled quotes, newlines inside quotes), delimiter detected or given (`,` `;` tab `|`), encoding chosen explicitly (`utf-8` with optional BOM, `utf-16` with BOM, `windows-1256` for Arabic ANSI exports); invalid bytes are refused, never replaced; NUL bytes mean binary content.
* Defaults (all configurable under `Hasm__Imports__*`, enforced on the server, clear error codes): 10 MB file (`file_too_large`), 50,000 data rows (`too_many_rows`), 200 columns, 20 worksheets, 4,000 characters per cell (`cell_too_long`), 100 MB expanded size (`expanded_too_large`), 200 zip entries, 60 s processing (`processing_timeout`). A value that is not a positive number falls back to the default, never to "unlimited".
* `SpreadsheetSafe.Neutralize` defuses formula injection (`= + - @ tab CR`) for any future export or report of imported values; imported values are only ever shown as text.

### Database (company migration `0010`, system migration `0013`)
* Tables: `ImportBatch` (file evidence: name, kind, size, SHA-256, storage name, key id; options, worksheets, mapping, row count, rows hash, plan hash and plan, revision, idempotency key, creator/submitter, expiry, terminal and purge timestamps, result), `ImportRow` (raw cells, row hash, later normalized values, status, errors, resolution), `ImportEvent` (append-only history bound to a business-audit event) and `ImportSettings` (company retention and pending-expiry days). Opaque names (`CompanySchema.Imports.cs`).
* The life cycle is enforced by PostgreSQL for every writer: states 1 uploaded, 2 staged, 3 mapped, 4 validated, 5 submitted, 6 approved, 7 applying, 8 applied, 9 failed (recoverable), 10 rejected, 11 cancelled, 12 expired; only the defined transitions exist (an approval or application cannot be skipped to); identity and file evidence are immutable; the revision advances by exactly one per change; terminal states are frozen except retention bookkeeping (purge timestamps, key id after a re-wrap); a purge record is final; batches are never deleted or truncated; applying and failed batches cannot expire; staged rows can only be inserted while staging, never change their content, are frozen from submission on and can only be deleted while staging or after the batch finished.
* Permissions (system migration `0013`): `company.imports.view|upload|configure|submit|approve|apply|cancel`, company-wide. The Company Administrator preset holds all except `approve` (separate duty). Runtime role privileges: batches SELECT/INSERT/UPDATE (never DELETE), rows SELECT/INSERT/UPDATE/DELETE (guarded by triggers), history SELECT/INSERT, settings SELECT/INSERT/UPDATE.
* Audit: business-audit event types 1070-1086 (one per history kind) and 1100 (settings); policy history entity 6.

### Service, authorization and API
* `ImportService` (no authorization by design) and `ImportManagementService` (the only entry point): every operation needs the generic permission AND the adapter's own business permission (upload/stage/cancel/renew need the adapter's upload permission, viewing needs its view permission), re-read on every call; listings are restricted inside the SQL, before paging, to the adapters the caller may see; a hidden batch looks exactly like a forbidden one (no existence oracle).
* Upload stores nothing unless everything succeeds: format check, security scan, SHA-256, encryption, then one transaction (batch row, history row, audit event); the ciphertext is removed again if the transaction fails. A client idempotency key (`Idempotency-Key` header) makes a repeated upload return the same batch (same user, same content), otherwise `idempotency_key_reused`.
* Staging parses the decrypted original with the chosen worksheet, header row, encoding and delimiter into `ImportRow`, computes the canonical row hashes and the batch rows hash, and voids any mapping, plan and approval built on earlier rows. A tampered, swapped (another batch's ciphertext) or missing original is never staged (`original_corrupted` / `original_unavailable`); an unavailable key store throws (HTTP 503).
* Cancel, renew (extends expiry; a validated/submitted/approved batch returns to Mapped and must be validated and approved again), settings (revisioned, audited, `ImportSettings` + policy history), maintenance and key rewrap.
* **Retention** (company-configurable, default 30 days; `ImportMaintenanceHostedService` runs hourly over Ready companies and `POST .../maintenance/run` runs it on demand): pending batches whose expiry has passed become Expired; finished batches (applied, rejected, cancelled, expired) lose their encrypted original and staged rows after the retention period; an applying or failed batch is never touched; each step is its own audited transaction (the file is deleted first, idempotently, so a crash is repaired by the next pass); file SHA-256, rows hash, plan hash, history, approvals and audit events stay.
* API `/api/v1/company/imports`: adapters, list, upload (raw body, size-capped before reading), get, stage, rows (paged, at most 500), events, cancel, renew, settings, maintenance. No download route for originals exists.

## S2 — Mapping, dry run and plan (built)
- **Mapping** (`ImportMapping`): per adapter field a source column and/or a default; options `decimalSeparator`, `thousandsSeparator`, `dateFormat` (never the machine locale). Validated against the adapter fields and the real column count (unknown field, required unmapped, bad/duplicate column). `suggestion` matches headers to keys, names and aliases in either language, one column per field.
- **Normalization** (`ImportNormalizer`): trim, NFC, Arabic/Persian digits converted, codes upper-cased with **leading zeros preserved**, strict thousands grouping, exact date formats, booleans/enums by declared aliases only. Every issue is a stable code (translated by the UI).
- **Dry run** writes per-row analysis (valid / invalid / conflict / resolved / exact-duplicate) and a **plan** whose `planHash` covers rows hash, mapping hash, a baseline of the existing data the adapter read, the operations and the reconciliation lines. The plan is frozen from submission on.
- **Stale detection**: submit, approval and apply recompute the plan from the stored rows and the current baseline; any difference refuses with `plan_stale` and the batch must be re-validated (which voids a pending approval).
- **Resolutions**: only the adapter-declared actions per conflicting row; they are part of the plan hash.

## S3 — Independent approval and atomic apply (built)
- Approval uses the shared `DocumentApprovals` (`import_batch`). **Creator and submitter can never approve**; PostgreSQL enforces this (decision trigger + lifecycle guard) in addition to the service. The approval is bound to the batch revision and plan hash; the approver's permission is re-checked at apply.
- New permissions `company.imports.view|upload|configure|submit|approve|apply|cancel` (system migration `0013`). Company Administrator gets all except `approve`; the new preset role **Import Approver** (view + approve) is granted offline with `Hasm.Admin grant-import-approver` / `revoke-import-approver`.
- **Apply** runs in ONE audited transaction under the batch lock: re-verifies approval, plan hash and baseline, performs the adapter operations, stores the result and moves to `applied`. Any error rolls everything back; a second transaction records the failure (`failed`, with a stable code) so the batch can be retried. A concurrent or repeated apply is idempotent (`AlreadyApplied` returns the stored result, no second write, no second audit). There is no durable "applying" state for atomic adapters.
- **Withdraw** voids the approval (batch returns to `validated`). Rejection requires a comment.
- Import approval never substitutes for any approval an adapter's records need under their own rules.

## S4 — Shared Web/Desktop import screen (built)
One screen (`apps/web/src/pages/Imports.tsx`, route `/company/imports`, permission `company.imports.view`) serves the Web app and the Tauri Windows app unchanged. It only drives the server: upload (raw file, one idempotency key per attempt), read options (sheet / header row / encoding / delimiter), column mapping with suggestion, dry run, summary and reconciliation, paged rows (≤ 50 per page) with conflict decisions limited to the adapter's allowed resolutions, submit / withdraw, independent approve / reject (rejection requires a comment; approve is hidden for the creator and the submitter and the server enforces it anyway), apply behind a confirmation dialog, cancel, renew, event history and retention settings. Imported values are rendered only as text. All texts exist in Arabic (RTL) and English; the catalog tests enforce parity.

## S5 — Chart of Accounts adapter (built; fulfils roadmap 3.2A-3)
Adapter `chart-of-accounts` (permissions `company.accounts.create` / `company.accounts.view`), implemented in `Imports/ChartOfAccountsImportAdapter.cs`; creation goes through the new in-work entry point `ChartOfAccountsService.CreateInWorkAsync` (same validation, domain rules, history row and audit event as an ordinary account creation, inside the import's single transaction, after the chart advisory lock).
- **Columns**: `code` (required, leading zeros preserved), `name_ar`, `name_en` (at least one), `parent_code`, `type`, `nature`, `is_group`, `currency_policy`, `currency_code`; headers and enum values are recognised in Arabic and English; XLSX and CSV.
- **Conflict rules** (owner decision: preserve existing records): an import can only **create** accounts or **skip** rows; it never overwrites, merges, recodes, moves, deactivates or deletes. Matching is by code only. Identical existing account = exact match (nothing to do). Same code with any difference (names, parent, type, nature, group flag, currency rule) = conflict, resolvable only by skip. A new code whose Arabic or English name equals an existing sibling's under the same parent = ambiguous match = conflict (skip). Duplicate codes inside the file are handled by the framework (identical repeat: skippable; differing repeat: blocking).
- **Hierarchy**: a parent is named by code and may be an existing account or another row, in any order; blocking errors: missing parent, cycle, own parent, parent not a group, inactive existing parent, type different from the parent's, root without a type. A child of a skipped or undecided parent is a conflict of its own (skip it too or fix the file); a child of an invalid parent is invalid. Analysis is iterative and linear (a 5,000-level chain and a 3,000-row cycle are tested).
- **Application**: atomic, parents first; any failure rolls back every account, history row and audit event and leaves the batch `failed` and retryable with the same approval; a changed chart or enabled-currency set makes the plan stale.
- **Out of scope**: opening balances (future adapter creating Draft journals through the normal journal approval).
