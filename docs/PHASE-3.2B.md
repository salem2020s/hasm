# Phase 3.2B — General Ledger and Journal Posting

**Status:** merged into main (PR #17, merge commit `d2d2a11`; slices S1-S7 verified on the disposable test cluster and by GitHub Actions). Nothing is applied to any permanent database.

## Approved basis
SRS section 5 (manual and automatic entries, balanced, atomic, never edited or deleted once posted; correction by reversal or adjusting entry with a preserved reference chain; branch and cost-center distribution; multi-currency with a base currency, effective-dated rates, an overridable rate with permission, reason and audit, recognition of FX differences), section 7 (flexible numbering by company/branch/document type/fiscal year, concurrency-safe, official number at approval/issue, a voided number is never reused automatically), section 4 and 19 (configurable approval policies by document type, value, branch and risk; separation of duties; no posting into a Final Closed period; automatic posting never bypasses approvals; idempotency per business event; full traceability including the rate and the source of the approval decision), D-009, D-010, D-011, D-015, D-024. The completed phases provide the fiscal calendar and its `FiscalPeriodGate`, branches, the chart of accounts (postable = active and not a group), the approval-request pattern (fiscal reopening), the period close probes and the financial-history probes.

## Design decisions (reasonable defaults; consequential ones flagged)
1. **Numbering:** one rule per document type; the number is `prefix + [fiscal-year label + separator] + [branch code + separator] + zero-padded sequence`. The official number is allocated INSIDE the posting transaction from a row-locked counter, so a rolled-back posting leaves no gap and concurrent postings never collide. Every issued number is recorded in an append-only ledger with a unique constraint; a number that was voided stays recorded and is never issued again. The scope flags (per branch / per fiscal year) cannot change after the first number of a type was issued (changing the prefix, separator or width later is fine and only affects new numbers).
2. **Exchange rates:** a rate is "units of base currency for one unit of the foreign currency", numeric(20,10), strictly positive. Rates are append-only: a correction is a new row for the same date (the latest entry wins) and the old row stays. The effective rate for a date is the latest entered row with `valid_from <= date`; no rate means the currency cannot be used on that date unless an authorized user overrides it on the line (rate, reason and permission recorded). The base currency has rate 1 and is never stored. Base amounts are rounded half away from zero to the base currency's minor units.
3. **Balance and rounding (flag):** an entry must balance EXACTLY in base currency. A multi-currency entry whose individually converted lines differ by rounding only is balanced by one explicit, system-marked rounding line posted to the company's configured exchange-difference account; without a configured account, or when the difference exceeds one minor unit per line, posting is refused. Realized and unrealized FX gains and losses on settlement and revaluation belong to the receivables, payables and banking phases and are not invented here.
4. **Cost centers:** a tree (no fixed depth) of group and leaf cost centers, optionally linked to a branch; allocations on journal lines go only to active leaf cost centers; a line's branch must match a cost center's branch when the cost center has one.
5. **Approval policies:** evaluated by ONE SQL function that both the service and the posting trigger use: an active policy matches a document by type, manual or automatic source, branch (or all) and base-currency amount threshold. A matching policy that requires approval needs an approved `DocumentApproval` for exactly the current document revision, decided by someone other than the creator and the submitter (separation of duties, per policy). Editing an approved but unposted draft invalidates the approval (new revision). With NO policy configured nothing requires approval (the company decides); automatic sources are subject to the same policies and, when approval is required but missing, the entry stays an explicit pending draft and is never posted.
6. **Journal entries:** Draft, Pending approval, Approved, Posted, Reversed, Cancelled (drafts are never deleted; cancelling keeps the record). Posted entries and their lines are immutable at the database level; the only later change is the move to Reversed when a reversal is posted. A reversal is a new posted entry with swapped sides and a reference chain; an adjusting entry is a normal entry that references the entry it adjusts. The posting date decides the fiscal period; Final Closed never accepts postings; Soft Closed only with a separate permission, recorded on the entry; a date outside every period is refused.
7. **Duplicate-source protection:** automatic entries carry a source key that is unique among non-cancelled entries, so retrying a business event cannot post twice.
8. **Permissions (company-wide):** separate view, create, update, submit, approve, post, reverse, post-in-soft-closed and exchange-rate override permissions; the approver permission is not in the preset Company Administrator (as with fiscal reopening) and is delegated like the Fiscal Approver.
9. **Posting** was kept disabled until slices S1 to S4 were implemented and verified; it is enabled by slice S5 together with its database-enforced checks (there is no placeholder posting).

## As built — S1 document numbering (company migration 0008, system migration 0011)
Rules per document type (`journal_entry` registered), number = non-empty segments joined by the separator: `[prefix] [fiscal-year label] [branch code] [zero-padded sequence]` (default `JV-2026-000001`). Counters are row-locked and allocated inside the posting transaction (gapless on rollback); the issue ledger is append-only with `UNIQUE(document type, number)`, so a voided number is never issued again. Branch/year scope is locked after the first number. Audit event 1036; permissions `company.numbering.view|configure`.

## As built — S2 exchange rates (same migrations)
Conventions (final for Release 1 unless the owner changes them):
- **Direction:** `rate` = units of the BASE currency for ONE unit of the foreign currency (1 USD = 0.71 JOD). The base currency is implicitly 1 and never stored; only enabled non-base company currencies can have rates (PostgreSQL trigger).
- **Precision:** `numeric(20,10)`, strictly positive; input with more than 10 decimals is refused, never rounded silently; no floating point anywhere (`decimal` in code, `numeric` in the database).
- **Effective rate:** the entry with the latest `valid_from <= date`. **Deterministic tie-break:** among entries with the same `valid_from`, the one with the highest id (the latest entered) wins. The SQL function `f_…resolve(currency, date)` is the single implementation; the service and the future posting trigger both use it. No rate = no result (never an implicit 1); the authorized per-line override with reason is part of S5.
- **Append-only:** rows are never updated or deleted; a correction is a new row and the old one stays in history. Re-entering the value already effective for that exact date is refused (`rate_unchanged`). Entry is guarded by the currency's latest entry id (`If-Match`), so concurrent entries cannot silently override each other. Audit event 1037; history entity 2; permissions `company.exchangerates.view|create`.
- **Rounding:** base amounts = foreign amount x rate rounded half away from zero to the base currency's minor units (`CurrencyMath.ConvertToBase`); overflow throws.
- **Requirement on S5 (posting snapshot):** every foreign-currency journal line MUST store the applied rate id, the rate value, the rate's valid-from date, the foreign amount and the converted base amount as part of the immutable posted line (not a join to the current rate). Posted amounts are therefore independent of later or backdated rate entries; the posting trigger re-resolves the rate with the SQL function and refuses a snapshot that is not the effective rate (or a recorded authorized override).

## As built — S3 cost centers (same migrations)
- Tree of cost centers (no fixed depth) with stable uuid ids, unique case-insensitive codes (upper-case, re-codable through a separate permission), Arabic/English names (one required), an active/inactive lifecycle (never deleted), controlled moves, PostgreSQL-enforced tree rules (parent is a group, no cycles judged at commit, a node with children is a group, active needs an active parent). Audit events 1038–1043; history entity 3 keeps every earlier name, code and parent; permissions `company.costcenters.view|create|update|activate|recode|restructure`.
- **Branches are separate:** the optional `branch` link is informational and must reference an existing active branch when set; nothing forces a cost center's branch to equal a journal line's branch.
- **Allocation compatibility:** only an ACTIVE LEAF (non-group) can receive allocations (`CanReceiveAllocations`); groups only organize, so roll-ups of leaves up the tree never double count. Allocations reference the stable id, so renaming, re-coding, moving or deactivating never rewrites posted history.
- **Decisions deliberately deferred to posting integration (S5), with alternatives — not defined by the approved specification and not enforced yet:**
  1. *Is a cost center mandatory on a line?* (a) never; (b) per account (profit-and-loss accounts require one); (c) company policy flag. Needs an owner decision; S5 will store a nullable allocation and a per-account/company policy hook once decided.
  2. *Split allocation of one line across several cost centers:* percentages vs amounts; recommended: amounts in the line currency summing EXACTLY to the line amount, the last share absorbing the rounding remainder (largest-remainder), no tolerance.
  3. *Branch of the line vs branch of the cost center:* (a) no relation; (b) must match when the cost center has a branch (documented default in design decision 4); (c) warn only.
  4. *Freezing attributes after use:* S5 adds a trigger so a cost center that has allocations can no longer change its group flag or branch (names, code, parent and activity stay changeable).
  5. *Authorization to allocate:* "unauthorized cost centers cannot receive postings" needs a per-user or per-role cost-center restriction model that the SRS does not define; S5 enforces active-leaf in PostgreSQL and the post permission in the service; a restriction model is left to the owner.

## As built — S4 approval policies and document approvals (same migrations)
- **Policies:** document type, source (manual / automatic / either), branch (or all), base-currency threshold (numeric(20,4), inclusive) and 1-5 DISTINCT approvers. One SQL function (`required approvals`) evaluates them — the strictest matching active policy applies, none = nothing required — and the posting trigger calls the same function, so a service, a retry or an automatic job can never disagree with the database. Automatic entries are covered. Policies are revisioned (If-Match), audited (events 1044-1047, history entity 4), never deleted. Permissions `company.approvalpolicies.view|create|update|activate`.
- **Decisions:** append-only table, one decision per approver per document REVISION, rejections need a comment. A decision is recorded inside the journal transaction (`DocumentApprovals.RecordAsync`) with mandatory separation of duties: the approver is never the creator or the submitter (not configurable). Returning an entry to draft, editing it or rejecting it advances its revision, so earlier approvals stop counting; PostgreSQL checks the approvals of the CURRENT revision on the transition to Approved and again on posting (policies are re-evaluated at posting time, so tightening a policy after approval is honoured).
- **Approval requests:** submitting an entry IS the request (Pending approval when a policy matches, otherwise Approved at once); approve and reject are the decisions; withdrawing or cancelling ends the request.
- **Not defined by the specification and therefore not invented:** the "risk condition" of a policy and multi-level (ordered) approval chains. The policy model counts distinct approvers; ordered levels and risk classes need an owner decision.

## As built — S5 journal and posting engine (same migrations)
- **Lifecycle:** Draft → Pending approval / Approved → Posted → Reversed, and Cancelled; drafts are never deleted. Simple and compound entries (2-500 lines), manual and automatic (unique source key among non-cancelled entries, idempotent retry returns the existing entry), reversal entries (mirror of every line with sides swapped, same accounts, currencies, rate snapshots and allocations, `reverses` chain; the original becomes Reversed in the same transaction) and adjusting entries (reference a posted entry).
- **Database-enforced invariants:** allowed state transitions only; posted/reversed/cancelled entries and their lines are immutable (no UPDATE/DELETE/TRUNCATE; lines and allocations change only while the parent is a Draft); at least two lines and base-currency debits equal credits exactly; every account active and not a group, account currency policy (base / any enabled / one specific), enabled currencies, active branches, active leaf cost centers with allocations summing exactly (line currency AND base); the applied rate must be the effective rate for the entry date (re-resolved at posting) or a recorded authorized override; approvals for the current revision; fiscal period open (or Soft Closed with the separate permission, recorded on the entry), never Final Closed, none = refused; official number issued in the same transaction (gapless on rollback). Reversals are exempt only from the active-state and currency-policy checks (they cancel earlier postings), never from period, approval or balance rules.
- **Multi-currency:** line amounts in the transaction currency; base amounts = amount x rate rounded half away from zero to the base minor units; the applied rate (value, id, valid-from through the rate row, or override reason) is stored on the line, so later or backdated rate entries never change posted amounts. Rounding differences (at most one base minor unit per foreign line) are absorbed by ONE explicit system line to the configured rounding account (`company.ledgersettings`); without it, or beyond the tolerance, the entry stays visibly unbalanced and cannot be submitted.
- **Atomicity/concurrency:** the entry row is locked, `FiscalPeriodGate` share-locks the period inside the posting transaction (a concurrent close waits), numbering uses the row-locked counter, and the state change runs the database checks; any failure rolls back number, audit event, event log and state together. Posting an already posted entry returns it unchanged (idempotent). Tests cover parallel posts of one entry and of many entries.
- **RBAC:** `company.journal.view|create|update|submit|approve|post|reverse` are BRANCH-scoped (every branch the entry touches is checked); `company.journalsoftclosed.post`, `company.journalrate.override` and `company.ledgersettings.view|configure` are company-wide. Permissions are re-read on every call, so a revocation applies before the next approval or posting. `company.journal.approve` is NOT in the Company Administrator preset and the administrator cannot grant it (an administrator cannot grant what they do not hold); it belongs to the preset **Journal Approver**, delegated offline like the Fiscal Approver: `Hasm.Admin grant-journal-approver|revoke-journal-approver <login> <company-id>` (company-wide, audited without an actor).
- **Chart integration:** the posting-history placeholder of the Chart of Accounts is replaced by the real probe (a POSTED or REVERSED line freezes nature, group flag and currency policy of the account); the `general_ledger` financial-history probe freezes the base currency; the `pending_accounting_postings` close probe blocks closing a period that still has Draft, Pending or Approved entries dated inside it.
- **Runtime privileges:** DELETE is granted on exactly two tables, journal lines and allocations, whose rows PostgreSQL lets change only while the parent entry is a Draft (a draft edit rewrites its lines); everything else keeps the no-DELETE rule and the privilege test was updated to state this exception explicitly.
- **Events:** audit 1049-1060; the append-only journal event log has its own audit event per row.

- **Journal list authorization:** the list is restricted INSIDE the SQL query, before ORDER BY / LIMIT / OFFSET. A branch-scoped viewer sees only entries whose header branch and every line branch are within their granted branches (the same rule as opening one); company-wide viewers are unrestricted. Paging (limit 1-500, offset, ordered by date, creation time, id) therefore walks only permitted entries, however many entries other branches hold. Regression test: more than 500 newer entries in another branch.

## As built — S6 ledger reports (read-only)
- Trial balance (opening, period debit/credit, closing per account with group roll-up and leaf-only totals, base currency, optional zero rows) and general ledger (opening balance, every line in date/number/line order with a running balance, original currency, applied rate and base amounts, paging; a group account includes its descendants), filtered by dates, branch and cost center (a cost center includes its descendants and uses the ALLOCATED base shares). Only POSTED and REVERSED entries count; a reversal nets its original; drafts, pending and cancelled entries never appear. Each report runs in one REPEATABLE READ snapshot. Permissions `company.ledgerreports.view|export` are branch-scoped: a branch grant sees only its own branches inside the query.
- CSV export (UTF-8 with BOM, exact decimals, spreadsheet-formula neutralisation). Excel/PDF exports, comparative columns and fiscal-year closing entries are not part of this phase.

## As built — S7 shared frontend
One React/TypeScript implementation for Web and Windows Desktop: Document numbering, Exchange rates (with the rounding account setting), Cost centers, Approval policies, Journal entries (draft editor with allocations and manual rate, submit, withdraw, approve/reject, post, reverse, adjusting entry, history and approvals) and Ledger reports (trial balance, general ledger, CSV download). Amounts are exact decimal text end to end (the API accepts decimal strings); permissions only show or hide controls and the server decides; Arabic RTL and English LTR texts; unsaved-change protection; 412 conflicts are announced and the data refreshed.

## Open decisions and limitations (consequential items are NOT invented)
1. Mandatory cost center per line / per account, branch-to-cost-center matching, and per-user cost-center restrictions: deferred (see S3); any of them is added as a posting rule only after the owner decides.
2. Approval "risk" conditions and ordered multi-level chains: not defined.
3. Fiscal-year closing entries (profit and loss transfer to equity) and opening balances: later phases.
4. Journal Approver delegation is company-wide and offline only (no branch-scoped approver delegation yet).
5. Realized/unrealized FX differences on settlement and revaluation belong to the receivables, payables and banking phases; only the rounding difference of one entry is handled here.
6. Business-type chart templates (3.2A-2) and Excel chart import (3.2A-3) remain mandatory Release 1 items.
