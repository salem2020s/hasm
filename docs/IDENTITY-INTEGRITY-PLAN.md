# Identity integrity plan (register item SEC-RT-SESSION): the runtime database credentials must not be able to mint sessions, identities or grants

**Status: slice S-1 BUILT in its own PR (section 13 records exactly what was built and what was left for later slices); every other slice is still a plan. The rest of this text is the plan as approved; where section 13 differs, section 13 is what the code does.** Originally: PLAN ONLY (a proposal; nothing is built; no decision ID, audit code or migration number is allocated). It answers the finding recorded by Agent OSEC during the review of PR 218 (T2), 2026-11-22, severity **High**, and it is **blocking** for T2 and for any control that relies on the application authenticating a person against someone who holds the database credentials. Implementation starts only after an independent review of this plan and the owner decisions of section 12. Everything here that is not a quoted owner decision is a proposal.

## 1. The problem, restated

The API authenticates a person from rows of the SYSTEM database, and every row that decides "who is this, is the second factor done, what may they do" is writable by the system runtime role (`grant-system-runtime`, `SystemRuntimePrivileges`). Nothing in those rows is bound to a secret that lives outside the database. Whoever holds the runtime credentials (leaked configuration or connection string, a database-side leak of the role's password) can, without any password, TOTP secret or key of the API host:

* **A. mint a session.** `INSERT INTO session` with `UserId` = a victim (an MFA-enrolled one included), `TokenHash` = the plain SHA-256 of a token the attacker chose (`SessionToken.Hash`), expiries ahead, and `VerifiedAt` = now: `Authorization: Bearer <token>` is accepted as the victim, the MFA-fresh gate passes;
* **B. mint an identity.** `INSERT INTO user` with a PBKDF2 hash of a chosen password, state active and `IsIdentityAdministrator = true`: a normal login succeeds as an identity administrator;
* **C. grant.** Insert or change `RoleAssignment`, `RolePermission`, `UserCompanyAccess`, `Role`: every permission in every company.

Also available through the same grants (not executed by the finding): overwrite a victim's password hash; move a victim's MFA state Enrolled to EnrolmentRequired (the state-graph trigger allows that edge) and re-enrol; take over an existing session row.

**What already holds and must stay:** the TOTP secret material (AES-GCM under the key ring, outside the database, plus the owner-only trigger of D-235 system migration 0035) and the HMAC chain of the audit streams (the actions are recorded, but attributed to the impersonated user).

**Threat model of this plan.** The adversary holds the runtime database credentials (SELECT, INSERT, UPDATE, DELETE on the rows below, as the catalog gives them today) and nothing else: not the key ring, not the API host, not the owner or migration account. A compromised API host (it holds the key ring and the runtime credentials) is OUT of scope: no database privilege helps there (the residual already recorded for D-235). A superuser or database-wide-read role bypasses grants and is reported by the check of D-235, not by this plan.

## 2. The principle

Every fact the API takes from a row to decide identity, second factor or authority is **authenticated with a key the database does not hold** (a MAC verified by the API), is **versioned** (a key id and a per-row revision) and **fails closed** (a missing key, a missing tag, a wrong tag or a stale revision is a refusal, never an acceptance, never a silent re-tag). The database stays the store; the API becomes the verifier. No legacy path: a row without a valid tag is not honoured.

## 3. Key custody

**Proposal:** four purpose-bound subkeys of the EXISTING protected key ring, derived exactly as the TOTP precedent derives its key (`KekHandle.DeriveSubkey(purpose)`, HKDF-SHA-256 over the key's wrapping key with the info label `hasm-purpose/v1/<purpose>/<keyId>`, which is also what `TotpSecretProtector` uses with the purpose `totp`):

| Purpose label | Used for | Mitigation |
|---|---|---|
| `identity-token` | the keyed hash of a session token (HMAC-SHA-256) | 1 |
| `identity-session` | the MAC over a session row's security fields | 2 |
| `identity-user` | the MAC over a user row and the anchors (section 5) | 3 |
| `identity-access` | the MACs over role, assignment, company-access and cost-centre rows | 4 |

(Four labels, so that a leak or a bug in one use never gives the others; the key id is the key ring's own key id.) One key ring, one directory, one backup procedure; no new secret store, no new operator duty beyond what the ring already has.

**Does this fit an existing owner decision?** Partly, and the gap must be closed by the owner:
* D-080 (owner, 2026-11-21), item (2): "TOTP secrets are protected by the existing protected key ring, with secure rotation and access restrictions." It names TOTP secrets. Using the same ring for MACs of sessions, users and access rows is the same custody and the same protection, but it is a NEW USE of the ring that the text does not name.
* D-087 (owner, 2026-11-21): "A `backup-keys` operation exports the protected key directory encrypted to the offline recovery public key, to an independently protected destination separate from the normal data backup root. Key-directory recovery is part of the disaster-recovery tests." This covers the recoverability of every key of the ring, so subkeys derived from it are recoverable with the ring.
* D-093 (lead): key ids, rotation and versioning for the backup keys; "no key is retired or deleted here (retirement needs independent approval, D-080(6))". D-080(6) (owner): "Independent approval is required for sensitive role grants, encryption-key retirement and restore operations."
* **Therefore this plan needs ONE owner decision (OD-1)**: extend the protected key ring to authenticate identity, session and access rows (purpose-bound subkeys), with retirement of such a key under D-080(6). The alternative, a separate owner-only key directory, is listed in section 12 (OD-1b) and is worse: a second custody procedure to back up, rotate and recover.

**Fail closed on a missing key.** If the ring has no key for a row's key id (or no active key), every operation that needs a verification answers 503 `service_unavailable` (the same answer as the other encryption-unavailable conditions), never 401 (which would invite a retry loop) and never acceptance. No key is ever generated implicitly (the existing `FileKekRing` rule).

## 4. Mitigation 1 and 2: the session

### 4.1 Keyed token hash (mitigation 1)
`TokenHash = HMAC-SHA256(K_identity-token(keyId), token)` instead of the plain SHA-256. The token format (43 base64url characters) is unchanged. A session row gains `KeyId`. Lookup computes the HMAC under each key the ring accepts for new-and-grace use (the active key and, during a rotation, the previous one: at most two values, `WHERE token_hash IN (@a, @b)`), so rotation needs no second table. The unique index on `TokenHash` stays. **No legacy plain hash is ever accepted**: a plain SHA-256 value cannot match an HMAC value, so every existing session simply stops matching at rollout (forced re-login, section 9). This alone stops an attacker from minting a session with a token he chose (vector A step 1); it does not stop the takeover of an existing row, which mitigation 2 closes.

### 4.2 MAC over the session's security fields (mitigation 2)
`SessionTag = HMAC-SHA256(K_identity-session(keyId), "hasm.session.v1" | length-prefixed fields)` over exactly:

| Covered | Column (logical) |
|---|---|
| row identity | `Id` |
| who | `UserId` |
| the credential | `TokenHash` (the keyed value) |
| client | `ClientKind` |
| second factor | MFA `VerifiedAtUtc` (null encoded explicitly), `AuthMethods`, `Emergency` |
| company context | `SelectedCompanyId` (null encoded explicitly) |
| lifetime | `AbsoluteExpiresAtUtc` |
| revocation | `RevokedAtUtc` (null encoded explicitly) and `RevokedReason` |
| the user row it was issued under | the user's security revision at issue (section 5) |
| key | `KeyId` |

**Not covered, deliberately:** `LastSeenAtUtc` and `IdleExpiresAtUtc` (they change on every request; the API recomputes the idle expiry itself and never extends beyond the covered absolute expiry, so changing them only stretches an existing, otherwise valid session within its absolute limit: an accepted residual, OD-5), `CreatedAtUtc` (informational). A session row also has `Tag` and `UserRevisionAtIssue` (new columns; review R2 of revision 2: the verifier needs the stored revision to recompute the tag).

**Session validity is bound to the user's current revision (review Q1 of PR 220, revision 2).** A session is valid only when its `UserRevisionAtIssue` EQUALS the user's current, anchor-protected `SecurityRevision` (section 5). Password change, revoke-all (`RevokeUserSessionsAsync`) and every administrative revocation BUMP that revision, so every session issued earlier stops being valid at once, and an attacker who writes back a pre-revocation session row (its old tag is valid) cannot undo a revocation: the row's revision is below the anchored one and a row carrying the new revision cannot be tagged without the key. The session that must survive (the one that changed the password, the `exceptSessionId` of revoke-all) is re-tagged under the new revision in the same transaction. A single logout (one row `RevokedAt`) is not a revision bump and stays a recorded residual: a thief holding both the database credentials and a stolen token can write the pre-logout row back; the owner may widen the bump to logout (OD-5 lists it).

The tag is **verified on every lookup** (`FindActiveSessionAsync`) and **recomputed by the API on every legitimate change**. The change sites in the current code, each of which must recompute (the list was checked against the code and is complete): every session is created by ONE primitive, `IdentityStore.InsertSessionAsync` (called by `CreateSessionAsync` for the password-only login and for the login that completed the second factor, and, inside the activation transaction, by `MfaStore.ActivatePendingAsync` through its `reissue` parameter; `AuthService.ActivateAndIssueAsync`, the issue at the end of both enrolment confirmations, builds the `SessionIssue` and reaches `InsertSessionAsync` that way). The tag is computed INSIDE that primitive, and the token hash moves into it too (`AuthService.CreateSessionAsync` and `ActivateAndIssueAsync` stop calling `SessionToken.Hash` themselves), so there is no creation path that can skip the tag. The other change sites: the second-factor proof (`MfaStore.RecordStepUpAsync`: VerifiedAt, AuthMethods), the three company-selection writes (`AccessService` x2, `MfaPolicyService.SelectCompanyAsync`: SelectedCompanyId), and revocation (`RevokeSessionAsync`, `RevokeUserSessionsAsync`: RevokedAt, RevokedReason). **Bulk statements become per-row compare-and-swap that RETRIES until applied (review R3):** revoke-all and the membership-revocation clear of the selected company (`AccessService`, 'ses' update of `SelectedCompanyId`) update many rows in one statement today; each row needs a new tag computed by the API, so each becomes a read followed by a per-row `UPDATE ... WHERE id = @id AND tag = @old`, and on a conflict (for example a concurrent step-up that changed the row first) the row is read again and the statement retried until it is applied, so a concurrent change can never let a session escape a revocation; a row whose tag is already INVALID is not honoured anyway and is revoked unconditionally. With the revision binding above, revoke-all additionally needs no per-row race at all for correctness (the revision bump is one statement), the per-row writes only keep the rows tidy. Each such statement becomes a compare-and-swap on the old tag (`UPDATE ... SET ..., tag = @new WHERE id = @id AND tag = @old`), so a concurrent change or a tampered row cannot be silently re-blessed. Sliding the idle window (`TouchSessionAsync`) does not touch the tag.

Residual that remains by design: a thief can still REVOKE or DELETE a session (denial of service on one session), and can read the table (token hashes are keyed, so reading gives no usable token).

## 5. Mitigation 3: the user row

`UserTag = HMAC-SHA256(K_identity-user(keyId), "hasm.user.v1" | fields)` over exactly: `Id`, `Login`, `PasswordHash`, `State`, `IsIdentityAdministrator`, MFA `State`, and a new per-user `SecurityRevision` (bigint, +1 on every change of a covered field), plus `KeyId`. **Also covered (review H1 of PR 220, demonstrated):** the three enrolment-code columns `EnrolmentCodeHash`, `EnrolmentCodeExpiresAtUtc`, `EnrolmentCodeConsumedAtUtc` (null encoded explicitly). The first draft excluded them on the ground that the enrolment path needs the user's password; that is true only of the VOLUNTARY path (`BeginEnrolmentWithSessionAsync`, state None, password re-confirmed). `BeginEnrolmentWithChallengeAsync`, the path of a user in state EnrolmentRequired (bootstrap administrators before their first enrolment, new users, every user after a recovery or disaster-recovery reset), needs ONLY the one-time enrolment code and an `enrol` challenge, and both are runtime-writable: with the code columns outside the MAC an attacker with the runtime credentials sets his own code for such a user, forges the challenge, enrols HIS authenticator and receives a fully trusted second-factor-passed session. With the columns inside the MAC the runtime role cannot write a code that the challenge path accepts (the user row then fails verification), and the challenge rows are bound too (section 5.1). **Not covered:** `DisplayName` (no authority), `CreatedAtUtc`, `StateChangedAtUtc`, `PasswordChangedAtUtc`, `LastLoginAtUtc`. The TOTP rows are already authenticated (AES-GCM; its AAD binds user id, key id and secret id: to be re-verified at implementation, step S-2).

Checked **at login** (before the password is even compared: a user row without a valid tag cannot log in, and the failure is the same neutral answer as a wrong password, with an audit event for the operator) and **on every request** (the session lookup joins the user; the session tag carries the user's revision at issue, and the lookup refuses when the current user row has a LOWER revision than the session was issued under, or an invalid tag). **Verification sites (every place that makes a decision from the user row):** login (password step), the per-request session lookup, `BeginEnrolmentWithChallengeAsync` (before the enrolment code is compared) and `ConfirmEnrolmentWithChallengeAsync` (before activation), `BeginEnrolmentWithSessionAsync`, `ConfirmEnrolmentWithSessionAsync`, step-up and the second-factor login completion (they load the user), password change. **Recompute sites (every writer of a covered column):** user creation, password change, state change (disable, lock), the MFA state edges (`MfaStore`: begin enrolment, activation, revoke, restore handling), the issue of a new enrolment code and its expiry (the offline commands and the recovery handling), the spending of the code at confirmation (`consumeEnrolmentCode`), the clearing of codes at restore, and `IsIdentityAdministrator` changes (offline commands). The exact list is re-derived from a search of every `UPDATE`/`INSERT` of the user table at S-2, and a unit test pins it (a new writer of a covered column without a recompute fails the test).

**The replay problem and the anchor (OD-4).** A per-user revision alone does not stop REPLAY: an attacker who captured an old valid row (he can SELECT) can write it back with its old valid tag and revision, e.g. the old MFA state `EnrolmentRequired`, or `IsIdentityAdministrator = true` of a person who was an administrator once. The revision only means something against a record the attacker cannot rewind. **Proposal:** a small append-only table `IdentityAnchor` (new; runtime INSERT and SELECT only, never UPDATE, DELETE or TRUNCATE, enforced by a guard trigger like every append-only table) holding `(Kind, SubjectId, Revision, KeyId, Tag)`, one row per security change, tagged with the same subkey. **The rule (review M1 of PR 220):** the verifier takes the maximum ONLY over anchors that carry a VALID tag over `(Kind, SubjectId, Revision, KeyId)` under a key it knows; an anchor with an invalid tag, an unknown key id or a malformed row is IGNORED for the bound and raises an alert (an audit event with the subject, rate-limited per subject; never a 503 and never a lockout), and the row must satisfy `row.Revision >= max(valid anchor revisions)`. Without that rule the runtime role, which may INSERT anchors, could insert one junk anchor with a huge revision that can never be removed (no DELETE) and would lock a real user or administrator out for ever; with it the attacker can neither raise the bar (no key) nor lower it (no DELETE), and the junk rows are only noise that the alert reports. Cost: one extra INSERT per security change and one indexed `max` per login (per request it uses the revision carried by the session tag). **If the owner does not want the anchor table, the replay of a previously valid tagged user row stays an accepted, documented residual** (OD-4); every other attack of this plan is closed without it.

### 5.1 The second-factor challenge table (review M2 of PR 220)

The runtime role holds SELECT, INSERT and DELETE on `MfaChallenge` (and UPDATE of the attempt counter and the consumption time). A challenge row stores a plain SHA-256 of its token, so an attacker can insert a challenge whose token he chose. Each purpose against that attacker (UPDATE of the user, purpose or expiry columns is not granted, but a forged INSERT chooses all of them):

| Purpose | What a challenge opens | Gate that is key-backed after the changes of this plan |
|---|---|---|
| Login (0) | `CompleteMfaLoginAsync`: it skips the PASSWORD step only; it still needs the TOTP code of the user, verified against the secret in `UserTotp` | the TOTP secret (AES-GCM under the key ring, AAD binds user, key id and secret id; the owner-only trigger of D-235): a forged login challenge gives nothing without a valid code |
| Enrol (1) | `BeginEnrolmentWithChallengeAsync` and `ConfirmEnrolmentWithChallengeAsync` of a user in state EnrolmentRequired | the one-time enrolment code, which is covered by the user MAC from this revision (H1) together with the MFA state; a forged enrol challenge without the code is refused; after the code, the new authenticator is the user's own, issued by the API |
| RecoveryRequest (2) | defined in the enum; NO caller exists in the code (checked: only `Login` and `Enrol` reach `TryBeginAttemptAsync`) | none needed today; a future caller must name a key-backed gate in its own plan, and a unit test fails when any code path other than the two above begins an attempt on a challenge (a source scan of the call sites), so a new purpose cannot be added silently |

**Defence in depth, adopted:** challenge rows are bound like sessions: the token hash is the keyed HMAC of the `identity-token` purpose (so an attacker cannot compute the hash of a token he chose, whatever the purpose), and the row carries a `KeyId` and a `Tag` of the `identity-session` purpose (domain label `hasm.challenge.v1`) over `Id`, `UserId`, `Purpose`, `ClientKind`, the source hash, `CreatedAtUtc`, `ExpiresAtUtc`, `TokenHash` and `KeyId`; the attempt counter and the consumption time are NOT covered, and are advisory only: the per-challenge budget and the per-user limit are derived from the append-only attempt log of section 5.2, so resetting or re-arming them gives an attacker nothing (review Q1 of revision 2 withdrew the first draft's argument that only a token holder could profit: that holder is exactly the attacker who knows the victim's password). A challenge without a valid tag is refused as an unknown token. This adds the columns `KeyId` and `Tag` to `MfaChallenge` in the migration (section 10) and no new subkey. Challenges live five minutes, so rotation needs no grace beyond that.

### 5.2 The second-factor attempt log (review Q1 of PR 220, revision 2)

**The gap.** `MfaAttemptLimiter` keeps its counters in `LoginThrottle` (through `IThrottleStore`) and the challenge keeps an `Attempts` counter, and the runtime role may UPDATE and DELETE both. An attacker who holds the runtime credentials AND a user's ordinary password (each password step yields a genuine challenge) could delete the throttle rows and reset the counters and guess TOTP codes without limit (3 valid codes in 10^6 with the window of one step: days). The plan therefore stops trusting any mutable counter.

**The design: an append-only log, the same pattern as the replay signers of PR 218 (N1).** A new table `MfaAttemptLog` (INSERT and SELECT for the runtime role, no UPDATE, DELETE or TRUNCATE, enforced by a guard trigger like every append-only table), one row per second-factor verification attempt: `Id`, `UserId`, `SourceHash` (the existing hashed source), `ChallengeId` (nullable: step-up and enrolment confirmation have none), `Kind` (attempt, success), `AtUtc`, `KeyId`, `Tag`. EVERY record carries a MAC under the `identity-session` subkey (domain `hasm.mfa-attempt.v1`) over all its columns; a record with an invalid or unknown-key tag is IGNORED for every count and alerted (the rule of the anchors: a forged success cannot reset a limit, and a forged failure cannot lock a user out).

**What is derived from it.** For a user: the number of valid attempt records since the latest valid success record within the throttle window (the existing options: window and block minutes, per-user and per-user-and-source maxima) decides whether the user, or the (user, source) pair, is blocked, and until when (the last attempt plus the block time). The per-challenge budget (five) is the number of valid attempt records that name the challenge. `LoginThrottle` is no longer read or written for the second factor (it keeps serving the PASSWORD throttle, where an attacker with the database credentials can read the PBKDF2 hash and crack it offline anyway, so a reset there adds nothing). A deleted or rewritten throttle row, a reset `Attempts`, a re-armed challenge change no limit.

**Lock and ordering: write the attempt before verifying, under a per-user lock.** One verification is: begin a transaction; take `pg_advisory_xact_lock` keyed by the user (so concurrent attempts for one user are serialised, and nothing else contends); read the valid records; if the user, pair or challenge is over its limit, refuse (no verification, no new record); otherwise INSERT the attempt record; COMMIT; only then verify the code against the TOTP secret; on success INSERT the tagged success record (it resets the count; the attempt record stays). Because the record exists before the verification, a failure is the default outcome (a crash, a timeout or an abandoned request between the insert and the verification still counts), and a burst of N concurrent attempts is bounded by the limit: each takes the lock in turn, counts the earlier ones, and at most `max` of them reach the verifier.

**Housekeeping.** The runtime role cannot delete, so old records are removed only by an owner-account command (`identity-log-prune`, beyond a retention far above the window, default 7 days); the records are relevant only inside the window, so a rotated-out key must stay accepted for the window (15 minutes by default) and for no longer.

## 6. Mitigation 4: the authorization rows

Per-row MACs with a revision on the rows that decide what a person may do. The same anchor table protects against deletion-and-resurrection and rollback; without it the residual is the same as in section 5.

| Table | Covered columns | Excluded | Notes |
|---|---|---|---|
| Role | `Id`, `CompanyId`, `PresetKey`, `Name`, `IsActive`, `Revision`, and a **digest of its permission set** (SHA-256 over the sorted permission codes) | `CreatedAtUtc`, `CreatedBy`, `UpdatedAtUtc` | the digest covers RolePermission, so an inserted, changed or resurrected permission row makes the role fail (a permission added to a role by SQL is not honoured) |
| RolePermission | none per row | | protected through the role digest; no per-row tag, no new column |
| RoleAssignment | `Id`, `UserId`, `CompanyId`, `RoleId`, `ScopeKind`, `ScopeId`, `ScopeEpoch`, `WarehouseScopeEpoch`, `RevokedAtUtc`, `Revision`, `KeyId` | `GrantedAtUtc`, `GrantedBy`, `RevokedBy` (history, attribution) | a revocation is a covered change (an attacker cannot un-revoke) |
| UserCompanyAccess | `UserId`, `CompanyId`, `RevokedAtUtc`, `Revision`, `KeyId` | `GrantedAtUtc`, `GrantedBy`, `RevokedBy` | the membership |
| CostCenterAssignment | its scope columns and `RevokedAtUtc` (exact list at S-3) with `Revision` | history columns | not in the brief; it narrows access, and the same attack applies |

The preset roles and permissions are seeded by migrations (which cannot hold a key): they are tagged by the owner command of section 7, and a preset change in a later migration needs the owner re-tag of that role (documented in the migration guard notes). `PermissionCatalog` evaluation keeps reading the rows on every call; the added work is one HMAC per row read (microseconds) and, with the anchor, one aggregated join. A row that fails verification is **skipped as if absent** for the permission computation AND counted: the request that depended on it answers 403, and an audit event with the table and row id is written once per minute per row (so an operator sees the attack without a flood). A missing KEY is the 503 of section 3, not a skip.

## 7. Existing data: the one-time owner tagging

A migration cannot tag rows (no key, no safe judgement). The system migration only adds NULLable columns and the anchor table; every row without a valid tag is **not honoured** from the moment the code that verifies it is deployed. Tagging is an explicit, owner-account, two-step operator procedure, because blind tagging would bless a row an attacker planted earlier:

1. `Hasm.Admin identity-audit-report` (read-only): lists every user, every administrator, every company membership, every role, assignment and cost-centre assignment, and checks each against the authenticated audit streams (the HMAC-chained system audit stream and the access audit projection: the events `UserCreated`, the access events `RoleAssigned`, `RoleAssignmentRevoked`, role changes, membership grants). It prints: matched rows; **orphans** and administrators. **The reconciliation is against the NET state (review M3 of PR 220), not against the existence of a grant event:** per subject the report replays the ordered grant and revocation events of the chain (user created, role assigned, role assignment revoked, membership granted and revoked, role changes) and computes the net state; a live row that the net state does not support is flagged as an orphan: a row with no event, a row whose grant event was later ended by a revocation event in the chain (a REVOKED-THEN-REINSERTED or resurrected row, which matches an old grant event and would otherwise be blessed), or a row whose columns differ from what the net events produced. Only rows supported by the net state are eligible for tagging. Codes and counts only, plus the ids an operator needs (no secrets). It verifies the audit chain first (`audit-verify`); a broken chain refuses the report.
2. The operator (a named person, recorded) resolves every orphan: revoke or remove it, or accept it with a recorded reason (an audit event of the owner account). Then `Hasm.Admin identity-tag --reviewed <report-hash>` tags the rows with the active keys, refuses to run when the report hash is not the hash of a report produced from the current table state minus resolved orphans, and writes one audit event per table with counts.

A fresh installation has no existing rows: `bootstrap-admin` and the services create tagged rows from the start.

## 8. Rotation, retirement, restore

* **Rotation with a grace period.** New writes use the active key id. Verification accepts the active key and, for a configured grace period (proposal: the absolute session lifetime for sessions, 12 hours by default, and "until the re-tag command has finished" for user and access rows), the previous key. `Hasm.Admin identity-retag` (owner account) re-tags rows under the active key; it is idempotent and prints counts per key id. A key is retired only when `identity-verify` shows ZERO protected rows under it, with the independent approval of D-080(6) (OD-1).
* **Missing key:** section 3 (503, fail closed).
* **Restored system database.** Sessions: a restore revokes every session (the restore handling already revokes second-factor state; this adds the sessions) and a restored database accepts no old session. Users, access rows and anchors verify with the restored key ring: if the ring is the installation's own, everything verifies and nothing is lost; if it is a DIFFERENT installation's ring, every row fails verification and the owner must run section 7 again. The secret-store dump rules of D-091 are unchanged (the TOTP rows are handled there).
* **Backups of the key ring** are D-087's `backup-keys`; recovery of the ring is part of the disaster-recovery tests the owner already requires, and gets one added case: after a ring recovery a user can sign in.

## 9. Forced re-login (impact)

At the rollout of mitigation 1 every existing session is invalid (no keyed hash matches): **every signed-in user, Web and Desktop, is signed out once** and signs in again (with the second factor where required). The refusal is the ordinary 401 of an unknown session; the screens already handle it (and D-236 keeps unsaved input in memory across an expiry only while the shell is mounted, which a forced sign-out after a deployment is not). There is no dark mode (a mode that accepts untagged rows would be the vulnerability itself). The deployment order is therefore one maintenance window: the migration, the verifying code and the section 7 commands together; then the operator report and the tagging; then reopening. Until a row is tagged it is not honoured. OD-2 asks the owner to accept the maintenance window and the one-time sign-out.

## 10. The migration (number unallocated)

One additive SYSTEM migration (generated like the other system migrations, `tools/schema` generator and dictionary), in the first implementation PR: NULLable columns `KeyId`/`Tag`/`UserRevisionAtIssue` on `Session` and `KeyId`/`Tag` on `MfaChallenge`; the append-only table `MfaAttemptLog` with its guard trigger and indexes (user and time, challenge); `SecurityRevision`, `KeyId`, `Tag` on `User`; `Revision`, `KeyId`, `Tag` and the permission digest on `Role`; `Revision`, `KeyId`, `Tag` on `RoleAssignment`, `UserCompanyAccess`, `CostCenterAssignment`; the append-only table `IdentityAnchor` with its guard trigger and index. No CREATE OR REPLACE, no DISABLE TRIGGER (the constructs the guard of PR 188 refuses), nothing seeded. `SystemRuntimePrivileges` gains the anchor table and the attempt log (SELECT, INSERT each) and no other privilege changes (the tag columns are written through the existing UPDATE grants; this plan does NOT narrow them, because the point is that a write without the key is not honoured, not that it is impossible). Database-side the migration cannot verify a MAC; it can enforce what needs no key: the anchor append-only rule and that a revision never decreases (a guard trigger on the user and access tables: `NEW.Revision >= OLD.Revision`), which already stops the crudest rollback.

## 12. Tests (isolated PostgreSQL, the REAL restricted runtime role created by the real grant command, the REAL API through the web application factory with the gate on)

1. A session inserted with a chosen token (a plain SHA-256 value, a value under a wrong key): 401; the same row with the keyed value computed WITHOUT the key is impossible, so the test uses an attacker's own key: 401.
2. Changing an existing session's `UserId`, MFA `VerifiedAt`, `AuthMethods`, `Emergency`, `SelectedCompanyId`, absolute expiry or revocation: 401 or the selected company ignored; one case per column.
3. A user inserted with a known hash and the administrator flag: login refused (neutral answer); a victim's `PasswordHash` overwritten, or `State`, or `IsIdentityAdministrator`, or MFA state moved Enrolled to EnrolmentRequired: login refused and the second factor still required; the replay of an old tagged row refused WITH the anchor (or recorded as the residual without it). **The enrolment attack of review H1:** for a user in state EnrolmentRequired the runtime role writes its own `EnrolmentCodeHash` and expiry and a forged `enrol` challenge (its own token hash): `BeginEnrolmentWithChallengeAsync` and the confirmation are refused, no session is issued; the same attempt on the code columns only (valid challenge, forged code), and on the consumed-time column (un-spending a used code), are refused.
3b. **Forged challenges (review M2):** one case per purpose. A forged `login` challenge (a token the attacker chose, plain and wrong-key hashes) is refused as an unknown token; the same with a valid-looking row copied from another user's challenge; a forged `enrol` challenge; a source scan test that no code path begins an attempt on a purpose other than `Login` and `Enrol` (RecoveryRequest).
3d. **Second-factor limits cannot be erased (review Q1):** with a known password, repeated password steps and wrong codes reach the limit; deleting the throttle rows, deleting or rewriting the `LoginThrottle` entry and resetting the challenge `Attempts` do not restore a single guess; a burst of concurrent attempts (more than the limit, one user) lets at most the limit reach the verifier; a forged failure record (invalid tag) does not lock a user out and a forged success record does not reset the count; a crash between the insert and the verification still counts.
3e. **Session replay and revocation (review Q1, R3):** a session row captured before a password change and written back (its old tag is valid) is refused (its issue revision is below the user's current one); after revoke-all and after an administrative revocation the same holds; revoke-all after a password change cannot be undone by writing the old rows back; the session that changed the password stays valid; a concurrent step-up and a concurrent company selection during revoke-all and during the membership-revocation clear never let a session escape (the per-row compare-and-swap retries until applied).
3c. **Anchor lockout (review M1):** the runtime role inserts an anchor with a huge revision and a garbage tag, one with an unknown key id and one malformed for a real user and for an administrator: both can still sign in, the alert is raised, the junk rows are ignored; a VALID anchor higher than the row (a real rollback, produced with the test key) is refused.
4. A role assignment, role permission, company access or role inserted, changed, revoked-then-restored or resurrected by SQL: not honoured (403) and reported; a permission added to a role by SQL does not appear in the effective set. **Net-state tagging (review M3):** a grant event followed by a revocation event in the audit chain, then the same row re-inserted by SQL before the tagging run: `identity-audit-report` flags it and `identity-tag` does not tag it (a live row whose grant event was ended by a later revocation); a row inserted with no event at all, and a row whose columns differ from the net state, are flagged too.
5. Every legitimate flow still works under the restricted role: login, MFA verify, step-up, company selection, password change (other sessions revoked), assignment and revocation through the API, role and permission administration, membership grant, logout, housekeeping purge, emergency access, enrolment and recovery.
6. Key rotation: rows under the old key accepted during the grace period, refused after retirement; `identity-retag` converges and is idempotent; a missing key answers 503 and accepts nothing; a restored system database accepts no old session and verifies users and access rows with the restored ring (and refuses with a different ring).
7. Mutation proofs: removing each tag check (token key, session tag, user tag, **the enrolment-code columns from the user MAC**, challenge token key and challenge tag, role digest, assignment tag, company-access tag, anchor comparison, **the rule that only valid-tagged anchors count**, **the net-state reconciliation of the audit report**, **the attempt-log count and its tag check**, **the session issue-revision equality**, **the retry of the per-row revocation**, fail-closed on a missing key) fails a named test of 1 to 6; one proof per check, run through the CPU gate, recorded in the PR.

Also unit: golden values per MAC (so a silent change of the covered field set fails), field-order and length-prefix ambiguity tests, a key-id test, a constant-time comparison test.

## 13. Owner decisions (final wording, as put to the owner; none is implied by this plan)

**OD-1 - Key custody.** "The existing protected key ring, which already protects authenticator secrets (D-080(2)), will also be used, through four separate derived keys, to authenticate login sessions, short-lived login challenges, user records and permission records. It is backed up and recovered as today (D-087), and a key is retired only with independent approval (D-080(6)). Do you approve? (Alternative, not recommended: a separate owner-only key folder, with its own backup and recovery procedure.)" [Technical reference: section 3; the four subkeys are `identity-token`, `identity-session`, `identity-user`, `identity-access`.]

**OD-2 - Rollout.** "At rollout there is one maintenance window, and every user, Web and Desktop, is signed out once and signs in again with their second factor. There is no transitional mode that would accept unprotected records. Do you approve?" [Section 9.]

**OD-3 - One-time review and tagging of existing records.** "Before existing users and permissions are protected, a named operator reviews a report that checks every user, administrator, membership and permission against the tamper-proof audit trail, using the net effect of every grant and revocation, so that a permission that was properly removed and later re-inserted is flagged, never approved. Each flagged record is revoked, or accepted with a recorded reason. Only then does the owner-account command protect the records. Who is the named operator?" [Section 7.]

**OD-4 - Protection against rolling records back.** "Adopt the append-only history table that stops an attacker from restoring an older, once-valid version of a user or permission record. Only history entries carrying a valid key-backed tag count; junk entries are ignored and reported, so they can never lock anyone out. Do you approve? (Alternative: accept that an older, once-valid record can be written back.)" [Sections 5 and 6; the table is `IdentityAnchor`.]

**OD-5 - Accepted residual risks.** "You accept that: (1) a thief can extend an existing valid session up to its absolute expiry, but not beyond; (2) a thief can sign users out or delete sessions (a nuisance); (3) a fully compromised application server, which holds the key ring, is outside what this plan protects; (4) a database superuser bypasses everything. Do you accept these?" [Items 5 and 6 of the earlier draft (unlimited authenticator-code guessing with the database password and a user's password; undoing a logout or revocation with a stolen cookie) are NOT residuals any more: section 5.2 and the revision binding of section 4.2 remove them. One narrow remainder is listed in section 4.2: a SINGLE logout is not a revision bump, so a thief holding both the database credentials and a stolen token can write the pre-logout row back; the owner may widen the bump to logout, at the cost of signing the user out of every device on each logout.]

**OD-6 - Key rotation grace period.** "When a key is rotated, records protected with the previous key stay valid for: login sessions, their maximum lifetime (12 hours by default); user and permission records, until the re-protection command has finished. Do you approve?" [Section 8; attempt-log records and challenges need only the throttle window and five minutes.]

**OD-7 - Scope.** "Cost-centre assignments are protected together with users, sessions, roles, role assignments and company memberships. The database permissions of the application account are not narrowed in this plan; that is a separate later hardening. Do you approve?" [Section 6.]

**OD-8 - What a refused request is told.** "A missing key answers 'service unavailable'. A record that fails its check is answered as a plain 'not signed in' or 'not allowed', with an audit event for the operator, and never with a message that tells an attacker which check failed. Do you approve?" [Sections 3 and 6.]

## 13. Slice S-1 as built (vector A: sessions)

**What exists.** `IdentityKeys` (the four purposes `identity-token`, `identity-session`, `identity-user`, `identity-access`, derived from the existing key ring with the TOTP construction; active key plus the key ids listed in `Hasm:Encryption:IdentityPreviousKeyIds`, comma separated, accepted during a rotation and under no other); the keyed token hash (HMAC-SHA-256 under the token key, replacing the plain SHA-256 for SESSION tokens; the challenge, throttle and enrolment-code hashes are unchanged and belong to S-2); the session tag (`SessionRow`: id, user, keyed token hash, client kind, creation, absolute expiry, authentication methods, second-factor proof time, emergency flag, selected company, user revision at issue and the key id, canonical length-prefixed encoding, times to the microsecond); the ONE insert primitive `IdentityStore.InsertSessionAsync` (hashes, reads the user revision under a row lock, tags; the login, the MFA login and the enrolment reissue all use it; no other code inserts a session row); per-row compare-and-swap with `SELECT ... FOR UPDATE` and re-tag under the active key at every change site (step-up, company selection, clearing a selection when a membership ends); `User.SecurityRevision` (non-decreasing, database guard trigger) raised by password change, revoke-all, user deactivation and the enrolment reissue, with session validity equal to `UserRevisionAtIssue == SecurityRevision`; a session that fails its tag or revision is revoked, answered with the neutral "not authenticated", and recorded as audit event **1339** (PROVISIONAL, to be allocated by the lead; detail names the session and the cause `tag` or `revision`, never a key or tag), at most once a minute per session; a missing key is `EncryptionUnavailableException` (503 `encryption_unavailable`, nothing written, nothing revoked). The migration is system migration **0036** (additive: three NULLable columns and a check on the session table, `SecurityRevision` with a check and a guard trigger on the user table; no DISABLE/ENABLE, no OR REPLACE, generated by `tools/schema/system-identity-integrity.cjs`). Existing session rows carry no tag and are never honoured: every user signs in again after the rollout (no compatibility mode, OD-2).

**Not in S-1 (later slices, unchanged).** The migration of the plan's section 10 is split by slice: S-1 adds only the session columns and `User.SecurityRevision`; the `MfaChallenge`, `MfaAttemptLog`, `User` tag, `Role`, assignment and `IdentityAnchor` parts belong to S-2, S-2b and S-3 and need their own migration numbers (allocated in `INTEGRATION-STATUS.md` in merge order). The user tag and the anchor are S-2, so `SecurityRevision` itself is not yet tamper-evident (a runtime role can RAISE it, which only signs sessions out; it can never lower it).

**OD-5, the single-logout residual (documented AND tested, NOT eliminated).** A single logout is stored in the revocation column, which the tag does not cover. A runtime role that clears the revocation of a logged-out session revives it with its original valid tag and revision, until its absolute expiry. Revoke-all, password change and deactivation are NOT affected (the revision changes). The test `KNOWN_RESIDUAL_OD5_a_single_logout_can_be_undone_by_the_runtime_role_until_the_logout_record_slice_exists` pins this behaviour; the narrow logout record (OD-5(b): an append-only, tagged logout row checked at validation) needs a new table with its own catalogue entry, privileges and generator, was not built inside this 1 to 2 day slice, and is proposed as slice S-1b. Until it exists, the residual must not be described as closed.

**Key rotation.** Values are always written under the active key. During a rotation, list the retired key id in `Hasm:Encryption:IdentityPreviousKeyIds` for no longer than the configured maximum session lifetime (initially 12 hours, OD-6), then remove it: sessions still under it stop being honoured (they are simply not found; the user signs in again). A changed row is re-tagged under the active key; the token hash of a session is not re-hashed (the token is unknown), so a session whose token was hashed under the retired key stays valid only while that key is listed.

**Operational requirement of S-1.** The API now needs the protected key ring (`Hasm__Encryption__KeyDirectory` and `Hasm__Encryption__ActiveKeyId`, the settings the attachment and TOTP features already use) to sign anybody in or to authenticate any request that carries a session token; without it those requests are 503 `encryption_unavailable` (anonymous endpoints are unaffected). An installation that had no key ring configured must configure one BEFORE this release is deployed. Every existing session ends at the rollout.
