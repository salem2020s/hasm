## 1. What S8d delivers

1. **`replication_pending` at the primary** (a new keep reason in the slice 6 classification): the primary never selects a REPLICABLE run for deletion while any configured destination has no verified copy of it. This can only make the primary keep MORE; it deletes nothing and enables nothing.
2. **The tombstone exception** (reading only): the exact three-condition rule of D-187 that lets a run count as "not pending" at a destination whose OWN retention deleted it, and the two alert states `replica_tombstone_unexplained` and `retention_deletion_incomplete` per destination, replacing S8a's blanket "every tombstone is unexplained" simplification.
3. **Retention per destination:** `backup-retention-plan --destination <id>` (a read-only preview) and `backup-retention-apply --destination <id>` (the existing deletion path of slice 6, pointed at a destination root; INACTIVE).
4. **The audit destination field:** the 2014 to 2017 events gain `destination=<primary|id>`; the per-destination audit reads parse the tokens exactly.
5. **The D-230 protection check inside the deletion executor** (a fourth, independent layer; sections 4 and 4A: at least one VERIFIED, ENCRYPTED, RECOVERABLE copy stored independently of the primary MACHINE, with its keys evidenced) and **L-FG3** (an orphan 2015 is closed by a 2017 `deletion_not_started` and never serves resume, recovery or the pair).
6. **The completion-before-status order** of D-187, made explicit for the primary and every destination.
7. **Destination retirement, the physical-independence confirmation and the off-machine attestation** as explicit, audited, RBAC-protected, approval-gated workflows (owner answers Q2 and Q3; section 5.7 and 5.8). They never delete a backup file. They depend on the Phase 4.1 named-administrator login and independent-approval framework, which are not built, so until then they refuse and the check of section 4A counts only what the software can verify by itself.
8. **Administrator notification when deletion is blocked** (section 5.9).

## 2. How S8d stays separate from automatic deletion

Slice 6 already contains the only deletion path (`RetentionExecutor`, reached through `RetentionService.ApplyAsync`; the rename and delete live in `DeleteRunFolder`, which re-checks the gate). D-137 keeps it inactive through three independent layers: (1) the compile-time constant `AutomaticDeletionActivated = false` (pinned by test; changed only by a separately authorised activation PR, never self-merged); (2) runtime prerequisites on every execution (encryption without the DEV/TEST acknowledgement, valid configuration, readable hold sources, restore-safeguard schema, `RestoreSafeguards.CutoverAvailable`, current and recovery-tested backups); (3) an exact per-installation opt-in absent from every repository configuration. D-227 keeps all of this closed.

S8d is built so that this separation is structural, not a promise:

* **No new deletion routine and no new switch.** S8d adds no code that renames, moves or deletes a run folder, a tombstone or any other file of a backup root. Everything S8d adds is one of: a read (audit stream, destination folders), a keep reason (it makes the primary delete less), a status finding (read-only), an audit field, or a new INPUT to the existing executor (a destination root and its minimums). The only code in the whole backup stack that may delete a run folder stays `RetentionExecutor.DeleteRunFolder`, and it keeps its own gate check as its first statement. A unit test (section 8, T1) scans the backup sources and fails if any other method calls `Directory.Delete`, `File.Delete`, `Directory.Move` or `File.Move` on a path that can be a run folder or a tombstone (the allow-list is the staging cleanup of `ReplicaCopier`, which only touches `<run>.incoming-*` folders it created).
* **D-137 applies to every destination with no separate switch** (D-187): the same three layers, plus the new fourth layer, decide for the primary and for every destination together. There is no per-destination opt-in and no way to enable deletion at a destination only.
* **`backup-retention-plan` stays read-only** at a destination exactly as at the primary: it computes and prints, writes audit 2014 only, and touches no file.
* **`backup-retention-apply --destination` is the existing apply.** With the gate closed (today, always) it writes audit 2017 `retention_deletion_inactive` (with the destination id) and throws before reading any input, as the primary does today.

## 3. What S8d may remove at a destination, and under which gate

**Today: nothing, anywhere.** After S8d the code path that could remove something at a destination exists but cannot run, because layer 1 is a compile-time constant that only an authorised activation PR changes.

If a later activation PR opens the gate, S8d's code may remove **only a complete run folder at a destination**, by the slice 6 mechanism (audit 2015 first, a tombstone, a rename to `<run>.deleting-<hex>`, the delete, audit 2016, the completed marker), and only when ALL of these hold at that moment, each checked inside the executor:

1. D-137 layers 1 and 3 (constant true AND the exact opt-in) and layer 2 (every runtime prerequisite, including `CutoverAvailable`).
2. **The D-230 protection check** (sections 4 and 4A): at least one qualifying, independently stored, verified, encrypted, recoverable copy with its keys evidenced exists NOW, and the copies that remain after this deletion still satisfy retention and recovery; no deletion of a run under an active legal hold, of the last verified recoverable backup, or that breaks the recovery chain.
3. **Status:** the OVERALL status of D-186 is exit 0 AND the destination's own ROOT status is exit 0 (any exit 8 or 1 anywhere, `destination_same_volume` and `recovery_untested` included, refuses with `backups_not_current` and audit 2017).
4. **Locks:** the shared restore lock and that destination's exclusive lock are held; deletion at D never runs during a copy to D.
5. **Eligibility:** the run is eligible under D-131 (classification), D-132 (the DESTINATION'S OWN `DailyKeep`/`WeeklyKeep`, which can only raise 7 and 4), D-133 (recoverability), D-134 (legal holds) and D-135 (pins), using the global facts of D-187 (holds and pins are system tables keyed by run id; a passed recovery test on any copy of any run counts for that recovery key id).
6. The slice 6 per-run re-validation immediately before touching the run, the mass-deletion brake and the clock-consistency check (unchanged).

It may never remove: a backup under an active legal hold; the last verified recoverable backup; a run whose removal breaks the recovery chain; the run from the last qualifying protection location while retention keeps it; a run at the primary because of a destination (the other direction); a tombstone; a folder it did not classify; a staging folder (that is the copy engine's 24-hour sweep, not retention); anything while the gate is closed. Completion of an interrupted deletion at a destination (section 5.3) acts only on a deletion whose 2015 for THAT destination and status hash is in the database; it removes only what that audited 2015 committed to.

## 4. The D-230 protection check inside the executor (the owner's answers, implemented exactly)

The owner's text (verbatim, section 9) requires, for automatic deletion, "at least one verified, encrypted and recoverable backup copy stored independently of the primary machine"; says a second disk inside the same physical machine is not sufficient; says a configured destination alone is not proof (the copy must "actually exist, pass integrity verification, remain accessible for recovery, and have its required decryption keys available"); requires verifying, before deleting any backup, that "the remaining protected copies satisfy the applicable retention and recovery requirements"; and requires deletion to be refused (fail closed) whenever the protection cannot be verified, and when no qualifying destination is configured.

* A new pure evaluator `DestinationProtection.Evaluate` computes the set of QUALIFYING protection locations (section 4A) and returns "sufficient" only when that set is non-empty. It reads configuration, the destination folders and the audit stream; it writes nothing. Anything it cannot read or cannot decide is "not qualifying" (fail closed, never "unknown means yes").
* It is called inside `RetentionExecutor` at the same level as the gate: in `ApplyCoreAsync` before any input is read, again in `DeleteRunFolder` as part of its first statement, and once more per run in the re-validation immediately before a run is touched (so a destination that stops qualifying mid-run stops the run). No entry point can skip it. A failure is audit 2017 with a stable reason (`destination_protection_missing`, `protection_unverified`, `keys_unavailable`, `remaining_copies_insufficient`) and no file is touched.
* It is independent of D-137 layer 1 in both directions: opening the compile-time gate alone deletes nothing while this check fails, and passing this check alone deletes nothing while the gate is closed.
* The same check runs for deletion at the primary AND at every destination.

## 4A. What qualifies as protection, and how each part is verified (fail closed on every part)

A location (a configured destination) QUALIFIES only if ALL of the following (parts 1 to 8) hold at the moment of the check. The evidence for each part is read now (never cached across commands); a part that cannot be verified is a failure.

1. **Stored independently of the primary MACHINE (off-machine).** The per-device volume probe of S8a cannot prove this and is NOT used for it. Two rules: Rule A counts; Rule B is disabled (below); and part 8 adds a confirmation on top of Rule A on every host.
   * **Rule A (automatically verifiable; the ONLY rule that counts today; needs no declaration; review M2 of PR 223):** the destination path lies on a KERNEL network filesystem whose server is not this machine. The evidence is what the KERNEL reports, never text the mounter chose and never DNS:
     * **Linux.** The longest mount containing the path in `/proc/self/mountinfo` has a filesystem type in a closed list of kernel clients (`nfs`, `nfs4`, `cifs`, `smb3`, `ceph`; a fixed list in code, never configuration). **FUSE types are NOT on the list** (`fuse.sshfs`, the native GlusterFS client and every other `fuse.*`): for FUSE the mount source and the subtype are free text chosen by whoever mounts (`-o fsname=...,subtype=...` through `fusermount`, available to unprivileged users), so a local passthrough filesystem can present as `fuse.sshfs` from `otherhost:/x`. The server address is taken ONLY from the **`addr=` super option** of the mountinfo line (the address the kernel connected to), not from the source string and not from a DNS lookup. A mount line with no `addr=` fails closed (not qualifying). The address is normalised and compared against EVERY local address: the whole IPv4 loopback block 127.0.0.0/8, `::1`, IPv4-mapped IPv6 forms (`::ffff:a.b.c.d`) compared as their IPv4 address, IPv6 zone ids stripped before comparison, `0.0.0.0` and `::`, and every address of every network interface of this host (read now). Any of these means "this machine" and the location does not qualify; an address that cannot be parsed fails closed.
     * **Windows.** The volume is a remote drive (`GetDriveType` is remote) or a UNC path, and the server part is normalised before it is judged: `\\localhost`, `\\127.x.x.x`, `\\[::1]` and the IPv6-literal `ipv6-literal.net` forms, the machine's own NetBIOS and DNS names, `\\?\UNC\` forms (and the `\\.\` device forms) are resolved to the same normalised server and refused when they resolve to a local address; the target of a DFS path is resolved to its real server and refused when it refers back to this machine (an unresolvable DFS referral fails closed). Wherever the platform does not let the code tell, the answer is "not qualifying".
     * Limits stated plainly: the evidence is that the data is held by another HOST AS SEEN FROM THIS OPERATING-SYSTEM INSTANCE. **In a container or a virtual machine "this machine's own interface addresses" are those of the namespace or the guest.** An export served by the container's host (for example the bridge gateway) or by the hypervisor is the same physical machine and PASSES Rule A: that is the owner's "second disk inside the same physical machine" in another form, and software inside the guest cannot see it. DNS can lie and a NAS in the same chassis or rack is outside what software can see; the plan claims no more than "another host as the kernel reports it". This is why section 4A part 8 (the physical-independence confirmation) exists.
   * **Rule B (declaration; DESIGNED AND BUILT BUT DISABLED, fail closed; lead default Q6):** for off-machine storage the software cannot recognise (a suitable external disk, an off-site rotation) a device-bound attestation (section 5.8) can be designed and implemented, but it **does not count as qualifying protection** unless the owner explicitly approves it later. The owner's text says a configured destination alone is not proof; a declaration therefore cannot substitute for verification without that explicit approval. The switch is a compile-time constant `OffMachineAttestationCounts = false` in the evaluator (pinned by a test, changed only by a PR that records the owner's approval), so with it off an attestation is stored and shown but never changes the qualifying set. If the owner approves it, the rule is: a named administrator attests, with independent approval, that the destination is stored off-machine; the attestation is bound to the device identity (filesystem UUID of the mounted volume, plus the volume label recorded for the operator), to the destination id and to an expiry (at most 12 months); a different device under the same path voids it at once; it only substitutes the off-machine fact and never replaces parts 2 to 6.
   * **Not sufficient, ever:** a second local disk, a partition, an LVM volume, a bind mount or overlay of the same host (owner text), a loopback network mount, or a path on the primary's own volume.
2. **The copy exists.** The published folder `<D>/<run>/` of the run in question is present (read from the folder, never from an audit event alone, D-185 step 5). For the check "the newest verified copy": at least one run exists there that is replicable (D-182).
3. **Integrity verification passes NOW.** `ReplicaCopier.VerifyStoredAsync` (S8c: the copy alone against its own signed inventory, every encrypted file re-hashed, signatures, HBE1 structure, clean folder) returns no failure for each run the decision relies on, and the last word of the audit stream on that copy is not 2042 (corrupt). A re-hash is performed at apply time for the runs involved; the preview uses the light check and says so.
4. **Encrypted and signed.** The run is replicable (encrypted, signed status that verifies against the trust list, verdict `ok` or `partial`); an unencrypted DEV/TEST run is never protection.
5. **Accessible for recovery.** The destination is readable by the service account and mounted now (the re-hash of part 3 is the proof of readability); an unreachable or unreadable destination does not qualify.
6. **Its required decryption keys are available.** The recovery PRIVATE key is offline by design (D-085), so what counts is evidence that the key demonstrably decrypts THIS copy, plus that the keys the data needs are present:
   * a passing recovery test (the canary) ON THAT COPY: `backup-recovery-test` on the destination copy (D-189, S8c) writes `recovery-test.json` there AND audit 2011. The evidence is both: the proof file valid for the copy's signed status (the preimage hashes to the signed canary hash) and a 2011 event with outcome passed for that run and that destination (S8d adds the `destination` token to 2011), no older than the staleness window (lead default Q4: 35 days, configurable downwards only). The proof's `TestedUtc` is unsigned, so the AUDIT time (the database, which the share's writers cannot forge) is the recency evidence, never the file's timestamp;
   * every key id the copy's signed status lists (`KeyIdsRequired`, `AuditKeyIds`) is present in the configured key directories (the same check as the key-retirement report), so attachments and audit streams can be read after a restore. A missing key id is `keys_unavailable`.
   * absent or stale evidence: the location does not qualify.
7. **After this deletion the remaining protected copies still satisfy retention and recovery.** For a candidate run R at location X, the evaluator recomputes the retention classification (D-131 to D-135, the existing `RetentionClassifier.Plan` and `KeepersPreserved`, extended to the union of the primary and every qualifying location) on the set that remains after R is removed from X, and requires: every run that retention keeps is still held by at least one qualifying location and (where the retention policy needs a recovery chain, D-133) the chain is unbroken; the newest verified recoverable backup is never the one removed and at least one verified recoverable backup remains at a qualifying location; no run under an active legal hold or a pin is removed. Deleting from the LAST qualifying location a run that retention still keeps is refused (`remaining_copies_insufficient`).

8. **Physical independence is CONFIRMED by a named administrator (lead decision on the container and virtual-machine question; stricter than the owner's text, relaxable only by the owner).** Because container and VM detection is itself unreliable, EVERY destination that a deletion relies on additionally requires a RECORDED, AUDITED, MFA-protected confirmation by a named administrator that it is physically independent of the primary machine (not the same physical host, not served by this host's hypervisor or container host, not the same chassis). **This applies IN ADDITION to Rule A, never instead of it, and on every host (not only where a container or VM is detected).** The confirmation is one privileged operation `backup.destination.confirm_independence` of the same Phase 4.1 framework as the retirement (named administrator with fresh MFA; independent approval where the segregation-of-duties policy requires it; payload-bound; single use), bound to the destination id, its resolved path, its device identity and the server address the kernel reported (so a destination that moves to another server, or another device under the same path, voids it at once), with an expiry of at most 12 months and audit 2049 `BackupDestinationIndependenceConfirmed` (operator, approver, destination, server address tag, device identity tag, expiry, reason, outcome). It never substitutes for Rule A or for parts 2 to 7: it is an additional condition, so a confirmation without a verifiable network mount does not qualify and a verifiable network mount without a confirmation does not qualify either. Until the workflow exists (S8d-3, blocked on S4 and D-099) the evaluator reports `independence_unconfirmed` and refuses, which is consistent with the closed gate. **Dependency (review V2 of PR 223):** the second-person approval of this confirmation, and of the retirement and attestation workflows, is only as strong as the approval-request records of the Phase 4.1 independent-approval framework (S4) and the named identities of D-099. The MAC scope of the identity-integrity work (PR 220: users, sessions, challenges, roles, assignments, memberships, cost centres) does NOT list S4's approval-request rows, so a requester holding the runtime credentials could otherwise fake the approver. S8d-3 therefore REQUIRES S4's approval records to be AUTHENTICATED, either MAC'd like PR 220's rows or recorded and read as an authenticated audit event under section 4B; this is a requirement on S4's plan, recorded here and on the S4 checklist, and S8d-3 does not start before S4's plan states it. Recorded as an OPEN OWNER ITEM, CONTAINER-VM-CONFIRMATION (section 9); the owner may relax it later; it does not block delivery.

Where the evaluator cannot decide (an unreadable audit stream, an unresolvable host, an ambiguous mount, a clock inconsistency) the answer is "not qualifying" and the reason is reported; it never guesses.

## 4B. Every audit fact a deletion decision relies on must be AUTHENTICATED (review M1 of PR 223)

The system runtime role holds INSERT on the system audit stream, and the S8c reader reads raw rows (exact tokens, no MAC or chain check; fine for `backup-status`, which authorises nothing). A holder of the runtime credentials could therefore insert a 2011 that makes a stale recovery test look recent, a 2015/2016 pair that with a tombstone copied from the run's own signed status makes a run "not pending", a 2015 that authorises a resume, or 2040, 2042 and 2045 facts that feed the last word, the unaccounted set and retirement. None of it takes effect while the gate is closed, but the evaluator is built now and every one of these must hold at activation:

* **Rule (the chain-verified prefix; reviews V1 and W1 of PR 223).** An audit fact is used if and only if its sequence is at or below **`VerifiedThroughSeq`** of ONE `AuditVerifier.VerifyAsync` pass, and the facts are read in the SAME read-only snapshot as that pass (the plan adds one internal `VerifyAndReadAsync` that runs the verification and reads the 2011, 2015, 2016, 2040, 2042, 2044 to 2049 rows inside the verifier's own `READ ONLY` snapshot transaction, so no row can appear between the two). `VerifiedThroughSeq` is the contiguous prefix from sequence 1 in which every record's hash, MAC (under a known key) and chain link are verified, and in which the sequence has no gap. This is what closes the splice the per-record rule alone would allow: records of a ROLLED-BACK history that an attacker kept from before a system-database restore pass `CheckRecord` when re-inserted above the restored head, but they do not extend the verified prefix (their `PrevHash` does not link to the real head), so they are never evidence.
  * **A forged or spliced row ENDS the prefix.** Everything below it still counts (genuine facts before it are used); nothing at or above it is used, whatever it looks like. The unanchored tail (records after the last manual checkpoint) is INSIDE the prefix as long as the chain verifies, so a fresh 2011 or 2040 is usable without anchoring. A sequence gap ends the prefix at the gap.
  * **What production does after a forged row (review W2 of PR 223).** The real writer (`AuditTrail`) refuses to extend a stream whose head fails `CheckRecord` (`audit_head_corrupt`), so no genuine record ever follows a forged one: the audit trail simply stops growing and every operation that must write a new audited event fails. Every deletion step that needs a NEW event (the 2015 before a deletion, 2016, 2017, 2048, a retirement or confirmation) therefore fails closed, and facts below the forged row stay usable for reading and alerting. The verified prefix ends at the forged row and the blocked-deletion lines report `audit_unverified` with the sequence. (The recovery of such a stream is a separate, pre-existing availability problem and is planned in `docs/AUDIT-HEAD-INTEGRITY-PLAN.md`; S8d does not change the audit writer.)
  * **An unverified remainder is alerted, never used.** A row at or above the end of the prefix is reported (2048 where the writer can still write, otherwise the output and the exit code of 5.9); an unreadable snapshot, a missing key or a failed verification pass fails closed (`audit_unverified`).
  * **Absence-based facts** (no later 2040 for a copy, no 2016 for a 2015, the unaccounted set, the last word on a copy) are evaluated over the verified prefix only, which is sound because the prefix is contiguous and cannot be extended by an insert that does not link to the head.
  * **The whole-stream verdict and the checkpoints stay ALERTING evidence only; they do not gate a deletion. There is NO "start from the last checkpoint" shortcut (review X1 of PR 223).** A checkpoint is the WRITER's anchor of the head it just wrote; it is not a verification result, and the writer can anchor above a spliced history (it anchors whatever head it extends, and a checkpoint is a fact about a hash, not about the records below it). A verification that began at such a checkpoint would bless the records beneath it unseen. The verified prefix is therefore always computed from sequence 1 by a FULL `VerifyAsync` pass. A shortcut would be allowed ONLY from a checkpoint that was itself written by a full pass that returned verdict `Verified` (a distinct "verified checkpoint", recorded by the verifier, never the writer's head anchor), and only for the range below it; no such checkpoint exists today and S8d does not add one. History from before the insert trigger of `docs/AUDIT-HEAD-INTEGRITY-PLAN.md` always needs one full pass first. The cost of a full pass is accepted: an apply is rare, and a deletion that cannot afford to verify its evidence does not run. T22 gains a case: a checkpoint anchored ABOVE a splice does not make the spliced facts evidence (the full pass still ends the prefix at the splice).
  * **Quarantined ranges are never evidence (review X2 of PR 223).** Once the recovery of `docs/AUDIT-HEAD-INTEGRITY-PLAN.md` exists, `VerifiedThroughSeq` runs ACROSS a recovered range, so every quarantined sequence is numerically at or below the prefix end. The rule therefore states it explicitly: a fact at a sequence that lies in a quarantined range (a valid chain-break record naming exactly that range, with its quarantine rows) is NEVER evidence, whatever it looks like; `VerifyAndReadAsync` returns the quarantined set with the prefix and the evidence reader excludes it. T22 gains a case: a forged 2011 or 2015 inside a quarantined range is not evidence, while the genuine facts after the break are.
* **What it covers:** 2011 (the recency of the recovery test, 4A part 6), 2015 and 2016 (the tombstone exception, `retention_deletion_incomplete`, every resume and recovery, L-FG3), 2017 where relied on, 2040 and 2042 (the last word on a copy), 2044 to 2047 and 2049 (retirement, attestation and confirmation, the unaccounted set).
* **At the PRIMARY, a resume also requires the authenticated 2015** (the same rule as at a destination), not only slice 6's file marker: with the resume now running while the status is not ok (5.5), the marker alone is no longer enough. A `.deleting-*` folder at the primary without an authenticated 2015 is left untouched (`resume_unverified`, 2017) and reported. This replaces the sentence of 5.4 that kept the marker rule at the primary.
* **S8c's `backup-status` reading stays informational.** It authorises no deletion; a forged row there can at worst hide a corrupt report until the next re-verification or mislead a status line, and the docs say so (S8c, review L3). The deletion path never uses that reader's output.
* **Tests (T22, the verified prefix; production behaviour through `AuditTrail`, never bypassing it):** (a) with the system runtime role insert a row with an invalid MAC at the head: the verified prefix ends at it, facts below it still count, the writer REFUSES the next event (`audit_head_corrupt`, asserted through `AuditTrail`), and every deletion step that needs a new event fails closed (`audit_unverified`) with nothing deleted; (b) forged 2011, 2015, 2015/2016 pair, 2045 and 2040-after-2042 rows (each shaped exactly like a genuine event, invalid MAC) are not evidence: a stale recovery test is not made recent, the run stays pending, nothing is resumed on a forged 2015, a destination is not retired or counted on a forged 2045, and at the PRIMARY a `.deleting-*` folder with only the file marker and no genuine 2015 is not resumed (`resume_unverified`); (c) SPLICE: build a rolled-back history (genuine records of a stream restored from an older backup, kept by the attacker), re-insert them above the restored head as the runtime role: each passes `CheckRecord` yet none lies at or below `VerifiedThroughSeq`, so none is evidence, and the verified prefix ends at the first of them; (d) a fact in the UNANCHORED tail (written after the last checkpoint, chain intact) IS usable; (e) a sequence gap ends the prefix and fails closed for anything above it; (f) an unreadable snapshot and a missing key fail closed; (g) the facts are read in the same snapshot as the verification (a row inserted between a separate verification and a separate read cannot be used: the test inserts during the pass and shows it is outside the prefix); (h) a checkpoint anchored ABOVE a splice does not make the spliced facts evidence (the full pass from sequence 1 still ends the prefix at the splice; there is no shortcut from a writer checkpoint); (i) once the recovery of the audit-head plan exists: a forged 2011 or 2015 INSIDE a quarantined range is not evidence while the genuine facts after the break are, and `VerifyAndReadAsync` returns the quarantined set.

## 5. Design

### 5.1 Audit reading and the destination field

* `BackupAuditEvents` 2014 to 2017 details gain a `destination=<primary|id>` token. Events written before S8d carry no token and are read as `primary` (never as a destination).
* `ReplicaAuditReader` (S8c) is extended to read 2015, 2016 and 2017 as well as 2040 and 2042 from the system stream, in stream-sequence order, with the exact-token parser (`nas-1` is never `nas-10`). It returns, per destination and run, the ordered facts needed by the three tombstone conditions: the status hash of the 2015 and 2016, whether a pair exists, and whether a 2040 for that run and destination has a LATER sequence than the pair's 2015.
* Slice 6's existing `LIKE` reads (`DeletedRecordedAsync`) stay for the primary, where no destination token exists. Every destination read uses the exact parser (recorded in the lead rulings; L-FG3 relies on it).
* Unreadable database: every read here that a decision depends on fails closed (`audit_unreadable`; the run stays pending; nothing is resumed or deleted). **Every fact a DELETION decision relies on is read only through the chain-verified prefix of section 4B (a fact counts only at or below `VerifiedThroughSeq`; a forged, spliced or gapped remainder is alerted and never used; an unreadable snapshot is `audit_unverified`).**

### 5.2 `replication_pending` (D-187)

* Definition: a REPLICABLE run (D-182) at the primary is pending while any configured destination has no verified copy of it, read from the destination FOLDER (never from an audit event alone). A destination that cannot be read counts as having no copy. No policy is classified "as if" at the destination.
* **Cost choice (technical, under D-048, not an owner question):** "verified" means the published folder passing D-185 step 4 at the time of the check. Re-hashing every byte of every run at every destination during a PREVIEW would be prohibitive, so the plan (preview) uses the light check (folder present, signed status verifies and equals the primary's hash, signed inventory present and bound to the status, clean folder) and marks the reason `replication_pending` or `replication_unconfirmed_preview`; the APPLY re-verifies with `ReplicaCopier.VerifyStoredAsync` (the full re-hash) for every run that would otherwise be eligible at the primary, immediately before it is deleted, under the destination locks. A run that fails the full check is pending.
* The one exception is the tombstone exception (5.3). Anything else is pending and is copied again by `backup-replicate`.
* Consequences stated in D-187 stay: an offline or newly added destination keeps every replicable run at the primary; the primary's disk can fill and the backup then fails loudly; nothing is deleted to make room.

### 5.3 The tombstone exception and the two alert states (D-187)

Read-only classification of a run at destination D (inputs: D's folder, D's tombstone folder, the primary's status hash for that run id, the audit facts of 5.1):

* **Not pending (the exception)** only if ALL THREE hold: (1) the tombstone at D verifies against the signing trust list AND its status hash equals the primary's; (2) the audit stream holds BOTH the 2015 and the 2016 for that run id, that status hash and `destination=D`, and NO 2040 for that run and destination comes later (by sequence) than the pair's 2015; (3) neither `<D>/<run>/` nor a `<run>.deleting-*` folder exists. A 2016 written by the recovery path (`recovered=audit`) counts only together with its 2015.
* **`retention_deletion_incomplete` (exit 1, per destination):** the tombstone verifies with the primary's hash, the database holds a matching 2015 and no 2016, and the folder is gone or a `.deleting-*` folder exists. A deletion HASM started and did not finish; the next `backup-retention-apply --destination` completes it first (5.5).
* **`replica_tombstone_unexplained` (exit 1):** a tombstone at D with no matching 2015 in the database, or whose status hash is not the primary's. Never resumed, never touched; the alert stays until an operator moves it away.
* With a matching 2015 and the run folder still present and verifying (a crash before the rename) there is nothing to complete and nothing to alert: the copy is an ordinary copy.
* These states replace the S8a shortcut in `ReplicaStatus.Inspect` (any tombstone or `.deleting-*` folder counts as unexplained) and are computed by the same one status function, so `backup-status`, `backup-run` and `backup-replicate` agree.
* `backup-replicate` skips a run at D only while the three conditions hold. An explicit `backup-replicate --run <id> --destination <id>` copies it again through D-185 (the old tombstone and pair stay as history; condition 3 then fails).

### 5.4 Retention at a destination

* `backup-retention-plan` and `backup-retention-apply` accept `--destination <id>` (or a root path). The destination root is scanned like a primary root (`RetentionInventory.Scan`); the classification inputs are the destination's runs, with the destination's own minimums (`RetentionOptions` per destination) and the GLOBAL holds, pins and recovery-test proofs: the per-run `ProofValid` of slice 6 becomes "a passed test exists for this recovery key id on ANY copy of ANY run", computed from the primary and every destination.
* Tombstones are written under `<D>/.retention/tombstones/`; the audit events carry the destination id; the `.retention` folder stays outside the "clean run" rule exactly as at the primary.
* Resume and recovery at a destination act only when the database holds the matching 2015 (destination id and status hash). The `deleted.json` marker on the share is never enough (its writers could plant it): without that 2015 the folder is left untouched and reported (`resume_unverified`, audit 2017). At the primary the same authenticated 2015 is required as well (section 4B, review M1 of PR 223): slice 6's file marker alone no longer suffices, because the resume now runs while the status is not ok.

### 5.5 Order of operations in `backup-retention-apply` (explicit; changes slice 6's order)

1. Gate and prerequisites (D-137 layers 1 to 3), then the D-230 prerequisite. Any failure: audit 2017, nothing read.
2. Locks: the run lock and the restore lock (slice 6) plus, for a destination, that destination's exclusive lock.
3. **Completion of interrupted deletions FIRST** for the root being applied (the `.deleting-*` resume and the 2016 recovery), including L-FG3 below.
4. **Then** the status check (overall AND, at a destination, the destination's root status). Completion deletes nothing an audited 2015 did not already commit to, so it does not need a healthy status; without this order an interrupted deletion would raise the status and the status would refuse the very apply that resumes it. Today's code evaluates the status BEFORE the resume loop (`ExecuteAsync`); S8d moves the resume ahead of the check explicitly, for the primary and every destination, and adds a test that pins the new order.
5. Clock sanity, classification, the mass-deletion brake, the per-run re-validation, and (at the primary) the full `replication_pending` re-verification (5.2).

#### 5.5.1 This changes slice 6 behaviour for the primary too: why it is safe, and what pins the old order

* **What changes.** Today `RetentionExecutor.ExecuteAsync` checks the gate, then `ctx.BackupStatusCode != "ok"` (`backups_not_current`), and only then reads the inputs and resumes interrupted deletions. After S8d the resume and the 2016 recovery run first and the status check follows. It applies to a deletion at the PRIMARY as much as at a destination; the order is one code path.
* **Why it is safe.**
  1. **A resume only finishes what was already committed.** It acts only on a `<run>.deleting-<hex>` folder, that is a run whose 2015 was written and whose folder the engine had already RENAMED out of its run id. A renamed folder is not a run folder any more: `backup-status`, `RetentionInventory.Scan`, restore, the recovery test and replication do not read it (they see a `.deleting-*` entry and report it as `retention_deletion_incomplete`). Finishing it cannot reduce what can be restored. The other completion, the 2016 recovery, only WRITES an audit event for a folder that is already gone. A tombstone whose run folder still exists (a crash before the rename) is left alone, as today.
  2. **Nothing new is selected.** The classification, the eligible set, the mass-deletion brake and the clock check still run AFTER the status check and are refused by it exactly as today. The set of runs that can be removed under a status that is not ok is therefore exactly the set a healthy earlier execution had already audited (2015); a status that is not ok still refuses every NEW deletion.
  3. **The same gate and locks.** The resume runs only after the gate (D-137 layers 1 to 3), the D-230 prerequisite, the run lock, the restore lock and (at a destination) the destination lock, so it is as closed as the rest of apply. With the gate closed (today) neither the old nor the new order reaches it.
  4. **Links and paths.** The existing refusals stay: a link is removed, never followed; a folder outside the root or one that is not a `.deleting-*` folder is refused (`symbolic_link_refused`, `path_escaped_deleting_folder`, `not_a_deleting_folder`). The resume needs the AUTHENTICATED 2015 (section 4B) for that root and run, at a destination AND at the primary (review M1 of PR 223): slice 6's file marker alone no longer suffices, because the resume now runs while the status is not ok.
  5. **Why it is needed.** D-187 makes the OVERALL status (primary root plus every destination) the status of a deletion, and an interrupted deletion raises the status (`retention_deletion_incomplete`, exit 1). With the old order the status would refuse the very apply that completes the deletion, and the state could never clear. Today it does not deadlock only because the status code handed to the executor is the run status WITHOUT `retention_deletion_incomplete`, which `backup-status` adds separately (D-187, "How this relates to the code of slice 6").
* **What pins the old order today: nothing.** The existing tests were checked: `RetentionExecutorTests.An_interrupted_deletion_is_completed_by_the_next_execution_and_links_are_never_followed` and `...a crash after the folder was removed and before 2016...` run with a status of `ok` (`Ctx(runs)`), so they pass in either order; `Stale_backups_a_clock_behind_and_a_suspicious_volume_delete_nothing` (status `recovery_untested`, expects `backups_not_current`, nothing deleted) has no interrupted deletion in its fixture, so it also passes in either order and keeps proving that a status that is not ok refuses new deletions. No existing test fails if the order changes, which is why the order is not "protected" today.
* **What S8d adds to pin the NEW order** (test T5, section 8): a unit test on `RetentionExecutor.ExecuteAsync` with a status that is not ok AND an audited interrupted deletion: the resume completes (the `.deleting-*` folder is removed, 2016 written) while the NEW eligible runs are refused with `backups_not_current` and stay byte-identical; the same fixture with the 2015 absent at a destination is not resumed. A refactor that checks the status first fails the first assertion. The two existing tests above stay unchanged.

### 5.6 L-FG3

A matching 2015 with no 2016 and the run folder present and verifying is an orphan 2015 (a crash before the rename). `backup-retention-apply` closes it with audit 2017 reason `deletion_not_started` (destination id and status hash) and the orphan never serves resume, recovery, or the pair of the tombstone exception. Exact-token tests cover it.

### 5.7 Destination retirement (owner answer Q3): an explicit, audited, approved workflow

The owner (verbatim, section 9): removing a destination "must use an explicit, audited retirement workflow with appropriate RBAC authorization"; it "must not automatically delete existing backup files"; it must not "silently remove the last qualifying protection location"; where privileged approval is required under the existing segregation-of-duties policy it is enforced; and the audit records "the operator, destination, timestamp, reason, and outcome".

* **Design.** `backup-destination-retire-request --destination <id> --reason <text>` and `backup-destination-retire-approve <request id>` are one operation `backup.destination.retire` of the Phase 4.1 independent-approval framework (`admin_approval_request`, S4): the approver is a different named administrator than the requester, with fresh MFA, bound to the payload hash (destination id, reason, a fingerprint of the current configured destination set), single use, with an expiry. This slice adds no second approval mechanism (the same rule as the cutover, D-144). The operation and its authorization are entries in the closed code enumeration and the S4 authorization table, classified PRIVILEGED (when in doubt, privileged, D-096). **No preset role grants it: a grant is the owner's decision.**
* **Effect.** Execution writes audit 2045 and nothing else. The destination is immediately excluded from the qualifying set and from the `replication_pending` requirement (otherwise a retired offline destination would block the primary forever). It remains in the environment configuration until the operator removes it; until then `backup-status` reports `destination_retired_still_configured` (exit 8). **It never touches a file of the destination or of the primary:** the workflow code contains no file operation.
* **A retirement is bound to the destination as it was (review L1 of PR 223).** The retirement records the destination id, its resolved path and its device identity (the filesystem UUID or the volume serial). A retired id is NEVER reusable: a configuration that re-adds a retired id is refused (`destination_id_retired`, 2043, exit 3) with a message to choose a new id, and a destination under a new id is a new destination whatever path or device it has. The qualifying, pending and unaccounted sets are keyed by the id together with that identity, so a retirement can never silently cover a different destination.
* **Last qualifying location.** At request AND at execution the evaluator computes the qualifying set WITHOUT the destination; if that set would become empty while the destination itself qualifies, the request or execution is refused (audit 2046 `last_qualifying_protection`). Retiring a destination that does not qualify is allowed (it removes no protection), and deletion stays refused while no location qualifies (Q1).
* **Unaccounted removal.** The set of destinations ever seen in the VERIFIED audit stream (2040, section 4B) minus the configured set minus the retired set (2045) is the UNACCOUNTED set; while it is non-empty the protection check fails closed (`destination_unaccounted`, an ambiguous protection status) and `backup-status` reports it (exit 1). Removing an entry from the configuration without the workflow therefore blocks deletion and alerts; it cannot silently shrink the protection.
* **Audit (from the reserved block 2044 to 2049; the details are exact `key=value` tokens, never a path):** 2044 `BackupDestinationRetirementRequested` (operator, destination id, reason, request id); 2045 `BackupDestinationRetired` (requester, approver, destination id, reason, outcome `retired`, request id); 2046 `BackupDestinationRetirementRefused` (operator, destination id, reason code: `last_qualifying_protection`, `not_authorized`, `approval_missing`, `self_approval_forbidden`, `retirement_unavailable`, `configuration_mismatch`, `request_expired`); the time of each is the audit event time. Audit 2049 `BackupDestinationIndependenceConfirmed` records the confirmation of section 4A part 8 (this plan uses the whole 2044 to 2049 block; nothing remains reserved in it). Audit 2048 `BackupDeletionBlocked` is the notice of 5.9.
* **Dependency and what happens until it is met.** The retirement's independent approval is as strong as S4's approval records, which must be AUTHENTICATED (part 8's dependency note, review V2 of PR 223). The named-administrator login (D-099) and the independent-approval framework (S4) are NOT built. Until both are on main the two commands refuse with `destination_retirement_unavailable` (audit 2046 `retirement_unavailable`), exactly like the cutover commands; nothing is retired, and the unaccounted-removal rule above already protects the installation. A migration is not expected (the state is the audit stream; the operation is a code enumeration entry); **if S4's authorization table needs a data row or a preset change, work STOPS and the lead is asked for the migration number first. No preset grant is made without the owner.**

### 5.8 Off-machine attestation (Rule B of section 4A): built, DISABLED, not counted

* Lead default Q6: only Rule A counts as off-machine evidence. The attestation workflow may be designed and built, but it stays DISABLED (fail closed): the constant `OffMachineAttestationCounts` is `false`, so an attestation never makes a location qualify. Enabling it is an owner approval recorded in a PR that changes that constant (an open owner item, section 9; it blocks nothing: with only Rule A, deletion simply stays refused wherever no verifiable network destination exists).
* `backup-destination-attest --destination <id> --reason <text>` and `backup-destination-attest-revoke --destination <id>` are one operation `backup.destination.attest` of the same framework as the retirement (privileged, independent approval, MFA, payload-bound, single use). The attestation records the destination id, the filesystem UUID read from the mounted volume at that moment, the reason and an expiry (at most 12 months); audit 2047 `BackupDestinationAttested` (operator, approver, destination id, device identity, expiry, reason, outcome) and 2046-style refusals.
* With the constant off the status shows an attested destination as `attestation_recorded_not_counted` (information) so the operator is not misled into thinking it protects deletion. With the constant on, the check re-reads the device identity every time: a different UUID, an expired, a revoked or an unreadable identity means "not attested", and an attestation never overrides a failed copy verification, a missing key or a stale recovery test.
* Until S4 and the D-099 login exist the commands refuse (`attestation_unavailable`) in any case.

### 5.9 Administrator notification when deletion is blocked

HASM has no push channel (no e-mail, no in-app notification) today, and this plan builds none. A blocked deletion is made unmistakable through what exists, all of it read-only:

* `backup-retention-plan` and `backup-retention-apply` print a `Deletion blocked:` block with every reason code and the location it concerns, and `backup-status` prints a `Deletion readiness:` line (ready / blocked with the reasons) for the primary and for each destination, so an operator or an operating-system monitor sees it on every check.
* `backup-retention-apply` exits non-zero when blocked (the refusal exit codes 3 and 4 are unchanged; a blocked deletion is audit 2017 and exit 1 as a refusal result).
* Audit 2048 `BackupDeletionBlocked` is written when the BLOCKING SET CHANGES (not on every attempt, so the stream is not flooded), with the reason codes, the location and the previous state hash: this is the durable, queryable notice.
* **Lead default Q5:** these means are sufficient WHILE THE GATE IS CLOSED. **Activation condition (binding on the 4.3-ACT PR):** before any activation, the external notification channel required by the owner's T2 D2 (an authorized e-mail endpoint or equivalent) must also be wired for deletion-blocked alerts, with its own tests; the activation PR is refused without it. S8d builds no channel.

## 9. The owner's answers (verbatim) and the questions that remain

**Owner decisions for backup retention S8d (D-230), 2026-11-22, quoted verbatim.**

Q1 - No backup destination configured
> Yes. If no qualifying independent backup destination is configured, automatic deletion must be refused.
> The system must fail closed whenever the required protection cannot be verified.

Q2 - Independent backup protection
> For automatic deletion, require at least one verified, encrypted and recoverable backup copy stored independently of the primary machine.
> Acceptable examples include a properly configured remote NAS, network backup server, or suitable external/off-machine storage.
> A second disk inside the same physical machine is not sufficient by itself to authorize automatic deletion.
> A configured destination alone is not proof of protection. The required backup copy must actually exist, pass integrity verification, remain accessible for recovery, and have its required decryption keys available.
> Before deleting any backup, verify that the remaining protected copies satisfy the applicable retention and recovery requirements.

Q3 - Backup destination retirement
> Removing a destination must use an explicit, audited retirement workflow with appropriate RBAC authorization.
> Retirement must not automatically delete existing backup files.
> Do not permit retirement to silently remove the last qualifying protection location.
> If the operation requires privileged approval under the existing segregation-of-duties policy, enforce that approval.
> Record the operator, destination, timestamp, reason, and outcome in the audit trail.

Additional mandatory safeguards
> * Automatic deletion remains disabled until the complete retention and protection workflow is implemented, reviewed and tested.
> * Never automatically delete a backup protected by an active Legal Hold.
> * Never delete the last verified recoverable backup or break the required recovery chain.
> * Respect configured retention periods and all existing backup security requirements.
> * Fail closed on missing verification, missing keys, destination failures, or ambiguous protection status.
> * Provide clear administrator notifications when deletion is blocked.
> * Preserve encrypted backups and audit evidence.
> * Do not weaken or bypass existing backup, restore, security, or approval controls.

How each part is implemented: Q1 = section 4 and T10; Q2 = sections 4, 4A, 4B and T11 to T13, T21 and T22; Q3 = sections 5.7, 5.8 and T19, T23; the safeguards = T14 (legal hold), T13 (last recoverable backup and recovery chain), T15 (retention periods), T16 (fail closed), T17 (notification, with the limit stated in 5.9), T18 (preserving evidence), T1 to T3 and T20 (nothing is weakened; the gate stays closed).

**Points the answers raised, settled as LEAD DEFAULTS (the owner authorized the lead to pick reasonable configurable defaults; these are not owner decisions and can be changed by configuration or a later PR):**

* **Q4 (recovery-test staleness window).** The passing recovery test on THAT copy (audit 2011 for the run and destination plus the valid proof file) must be no older than **35 days** by default (a monthly drill plus a week of slack); the window is configurable DOWNWARDS only (never longer than 35 days), and absent or stale evidence means "not qualifying".
* **Q5 (administrator notification).** The existing means (the `Deletion blocked:` block, the `Deletion readiness:` status line, the non-zero exit code for the operating-system monitor and audit 2048; section 5.9) are sufficient WHILE THE GATE IS CLOSED.
