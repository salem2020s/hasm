# HASM — Phase 3.4: Inventory master data (as built)

Source: `docs/PHASE-INVENTORY-1-PROPOSAL.md` (defaults used, no objection from the owner), SRS §9, DECISIONS D-017/D-018/D-019. **Master data only: this phase creates no stock movement, quantity, cost layer or accounting entry.** The costing engine (FIFO and moving weighted average per item and warehouse), negative-stock rules, back-dated recalculation, transfers, stocktaking and the stock/valuation reports are later inventory phases.

## What exists
* **Company migration 0012** (`CompanySchema.Inventory.cs`, opaque names): `InventorySettings` (one row at most), `Unit`, `ItemGroup`, `Item`, `ItemUnit`, `ItemBarcode`. PostgreSQL enforces: normalised unique codes, no delete or truncate (even for the owner), revision +1 per update, immutable unit code/decimals, item code/type/base unit, barcode value/item/unit/kind (only the active flag changes), group tree without cycles and at most 8 levels, and — deferred to commit — no alternate unit equal to the base unit and default purchase/sales/barcode units that are the base or an alternate unit of that item. Runtime role: SELECT/INSERT/UPDATE (DELETE only on `ItemUnit`, the alternate-unit set replaced while an item is edited).
* **System migration 0015** and sixteen company-wide permissions: `company.units|itemgroups|items` view/create/update/activate, `company.barcodes` create/activate, `company.inventorysettings` view/configure, all in the Company Administrator preset only.
* **Domain** (`Hasm.Infrastructure/Inventory`): validation (`InventoryValidation`: shapes, GS1 check digits for EAN-13/EAN-8/UPC-A, exact conversion factors up to 10 decimals, valuation resolution), `CompanyInventoryService` (every change in one audited transaction under an inventory structure lock, optimistic concurrency, unchanged updates write nothing), `InventoryManagementService` (authorization re-read on every call).
* **API** `/api/v1/company/inventory/*` (capabilities, settings, units, groups, items with search/group/status/type/paging, barcodes, exact barcode lookup); `If-Match` revisions, `no-store`, anti-CSRF.
* **Valuation policy (decision 3):** company default (settings) → overridable per item group → items inherit; no per-item override. Stockable goods cannot be created while nobody decided (`valuation_method_unresolved`); services are never valued or tracked. Only the policy is stored.
* **Item codes (decision 2):** automatic `ITM-000001...` (counter in the same transaction, skips codes taken manually) or a manual code; unique, immutable. **Barcodes (4):** company-wide unique, inactive ones keep their value; per item and unit. **Tracking flags (5):** lot/serial/expiry stored as attributes only. **No default accounts (6).** Services are items of type service (7). Conversions are per item (8).
* **Shared UI (Web and Tauri):** units, item groups (tree and company default valuation) and items. The item editor follows the tabs standard (`docs/PHASE-UI-1.md`): General information, Units and conversions, Tracking settings (goods only), Barcodes (saved items only, changes applied immediately and audited on their own); the item identity and Save/Cancel stay visible on every tab; tabs mark errors and unsaved edits; switching never saves or resets input.
* Menu: an **Inventory** group replaces the disabled "Warehouses" module placeholder for users who hold inventory permissions.

## Phase 3.4B: inventory master-data import (as built)
Three adapters on the generic 3.2D import framework (`Hasm.Infrastructure/Imports/InventoryImportAdapters.cs`), each with its own permission pair (`company.units|itemgroups|items.create` to upload, `.view` to see and to approve): **`inventory-units`**, **`inventory-groups`**, **`inventory-items`**. Import in this order: every reference (unit, group) must already exist when a file is analysed; a missing or inactive one is a blocking row error (`unit_not_found`, `group_not_found`, ...), never created silently.
* **Files:** CSV and XLSX through the framework (size/row/column limits, encryption at rest, formulas rejected, text never executed). Codes and barcodes are text: trimmed, upper-cased, Arabic-Indic digits converted, **leading zeros kept**. Column mapping is suggested from headers (Arabic and English aliases) and editable.
* **Items file** (one row per item): `code` (required, imports never generate codes: the plan must be deterministic), `name_ar`, `name_en`, `type` (goods/service, default goods), `group_code`, `base_unit_code`, `purchase_unit_code`, `sales_unit_code`, `alternate_units` (`BOX=12;PACK=0.5`), `barcodes` (`4006381333931;CARTON1@BOX`, optional `@UNIT`), `is_lot`, `is_serial`, `has_expiry`, `notes`. Checks: group and units exist and are active; conversion factors exact (positive, at most 10 decimals); alternate units distinct and never the base unit; default and barcode units are the base or an alternate unit; barcodes verified (a numeric code of 8, 12 or 13 digits must have a valid GS1 check digit); barcodes unique inside the file and against all existing barcodes; goods need a decided valuation policy (group chain or company default, services never); services cannot be tracked.
* **Conflicts:** a code that already exists is an *exact* match when every value equals the stored record (nothing to do) and a *conflict* otherwise; the only resolution is **skip**. Existing records are never overwritten, merged, re-coded, moved or deactivated (same owner decision as the chart import). A group row whose parent row is invalid, skipped or undecided cannot be created and needs its own decision. Cycles, self-parents, missing or inactive parents and trees deeper than eight levels are blocking.
* **Workflow:** the existing shared import screen (upload, mapping, dry run with no business-data change, rows with errors/warnings/conflicts, resolutions, submit, **independent approval**, apply, results and reconciliation); the units, groups and items screens link to it. Arabic and English texts for every new issue and reconciliation line.
* **Application:** atomic, in one transaction after the inventory structure lock, through the module's own audited domain operations (`CompanyInventoryService.*InWorkAsync`), so PostgreSQL invariants and one audit event per record still apply; a plan goes stale (and is refused) if the underlying data changed after the dry run. Nothing here imports quantities, values, opening balances, accounting entries or movements.
* **Tests:** PostgreSQL `InventoryImportTests` (13: full flow with audit and exact values, XLSX with text barcodes, every validation code, valuation policy, duplicates in file and against data, exact/conflict/skip without overwrite, group hierarchy rules, rollback after a failure with retry of the same approved batch, stale plan, permissions, company isolation, malformed files and formula-looking text); web `inventoryImport.test.tsx` (6); CI expected PostgreSQL count 811.
* **Limits:** one flat file per adapter (no multi-sheet workbooks); no update-existing mode (by decision); item codes are mandatory in imports; barcodes are created active; stock quantities and opening balances remain out of scope (opening-balance adapter is a separate open item).
