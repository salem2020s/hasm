# HASM — Development Guide

Scope of the current foundation: Backend health endpoint, shared React frontend (Arabic RTL / English LTR), the Tauri 2 Windows shell, (Phase 2.1) the system database foundation with a minimal company registry, (Phase 2.3A) central identity with local authentication, (Phase 2.3B) company access with role-based access control, (Phase 2.3C-1) authentication and access security hardening, and (Phase 2.3C-2) cryptographic audit integrity. No business modules exist yet.

## Prerequisites
- .NET SDK 10 (`dotnet --list-sdks`)
- Node.js 24 + npm 11
- Rust stable (`x86_64-pc-windows-msvc`) + Visual Studio Build Tools with "Desktop development with C++"; WebView2 (included in Windows 11)
- Tauri 2 is a project dependency (`src/desktop/package.json`); nothing is installed globally.
- PostgreSQL 14+ is required only to initialize the system database and to run the PostgreSQL integration tests. Install it yourself; the repository never installs it.

## Structure
```
assets/branding/                Official branding assets, see BRANDING.md (never modify or regenerate)
src/backend/                    Hasm.slnx, Hasm.Api (ASP.NET Core), Hasm.Infrastructure (PostgreSQL, migrations), Hasm.Admin (admin CLI)
src/frontend/                   npm workspace: apps/web, packages/ui, packages/api-client
src/desktop/                    Tauri 2 shell (src-tauri) loading the shared frontend
tests/unit/                     Hasm.Infrastructure.Tests (no database needed)
tests/integration/              Hasm.Api.Tests (WebApplicationFactory), Hasm.Database.IntegrationTests (real PostgreSQL)
```
Clients talk only to the Backend API over HTTPS; neither the web app nor the desktop shell can reach PostgreSQL.

## Run locally
One-time: `dotnet dev-certs https --trust` (the dev certificate must be trusted; certificate validation is never bypassed).

**Backend** (https://localhost:7241):
```
dotnet run --project src/backend/Hasm.Api --launch-profile https
```
Health: `GET https://localhost:7241/api/v1/health`

**Web** (http://localhost:5173):
```
cd src/frontend
npm install
cp apps/web/.env.example apps/web/.env.local   # optional; sets VITE_API_BASE_URL
npm run dev
```

**Desktop** (starts the Vite dev server itself):
```
cd src/desktop
npm install
npm run dev
```

## Configuration
- Frontend: `VITE_API_BASE_URL` (see `apps/web/.env.example`). Public by nature; never put secrets in `VITE_*` variables.
- Backend: `Cors:AllowedOrigins` in configuration. Empty by default (deny all); `appsettings.Development.json` allows the local Vite and Tauri origins. Set production origins through environment variables (`Cors__AllowedOrigins__0=...`) or an untracked config file.

## System database (Phase 2.1)
Logical `Hasm_System` is one central PostgreSQL database; its **physical name is configurable and must be opaque** (lowercase `[a-z][a-z0-9_]*`, max 63 chars, not `pg_`-prefixed, e.g. `d` + random hex). Each company later gets its own database named by a generated opaque name (`d` + 32 hex chars from a CSPRNG), stored in the registry and never regenerated.

**Configuration** (environment variables only; never commit values):
| Variable | Purpose |
|---|---|
| `Hasm__Database__Host`, `Hasm__Database__Port` (5432) | server |
| `Hasm__Database__SystemDatabaseName` | physical system DB name |
| `Hasm__Database__Username` / `Password` | runtime account used by the Backend (least privilege) |
| `Hasm__Database__AdminUsername` / `AdminPassword` | privileged account, used only by `Hasm.Admin` |
| `Hasm__Database__MaintenanceDatabase` (`postgres`) | DB used to create the system DB |
| `Hasm__Database__SslMode` (`VerifyFull`) | Npgsql SslMode; only `VerifyCA`/`VerifyFull` accepted by default |
| `Hasm__Database__SslRootCertificate` | optional CA certificate file (PEM/PFX) when the server uses a private CA |
| `Hasm__Database__AllowInsecureTransport` (`false`) | explicit opt-in to non-validating modes; disposable test environments only |

Missing or invalid settings fail with a message naming the setting, never its value. Connection strings are built in memory only and are never logged or returned by the API.

**Initialize (explicit, administrative; the API never does this at startup):**
```
$env:Hasm__Database__Host="localhost"; $env:Hasm__Database__SystemDatabaseName="d<random>"
$env:Hasm__Database__AdminUsername="..."; $env:Hasm__Database__AdminPassword="..."
dotnet run --project src/backend/Hasm.Admin -- init-system-db
```
Creates the database only if absent (never drops/alters an existing one), then applies pending migrations. Safe to repeat. Exit codes: 0 ok, 1 failure, 2 usage, 3 bad configuration. Company databases are created by `provision-company` (Phase 2.2). The runtime account's privileges on the registry table must be granted by the DBA (not automated yet).

**Migrations:** forward-only versioned SQL scripts `NNNN_name.sql` embedded in `Hasm.Infrastructure/SystemDatabase/Migrations`. Each runs in its own transaction and is recorded in `migration_journal` with a SHA-256 checksum; applied scripts are immutable (edits abort), a database newer than the build is refused, concurrent runners are serialized by an advisory lock, and `DROP`/`TRUNCATE`/`DELETE FROM` are rejected. Chosen over an ORM because the ORM is undecided (ARCHITECTURE.md §15) and explicit SQL keeps opaque physical names visible and reviewable; the only new runtime dependency is Npgsql.

**Physical naming:** C# uses meaningful names; `SystemSchema` is the single logical-to-physical map (fixed, committed, pinned by tests; migrations use the physical names). It is internal and never exposed by API/clients. Obfuscation is hygiene only, not a security control (D-029).

**Central vs. company data:** central (`Hasm_System`): company id, opaque physical database name (immutable, unique), provisioning state, timestamps. Also central since Phase 2.3A: users, sessions, login throttling. Later central phases: licensing, roles/permissions, global parties. Exclusively per-company: chart of accounts, ledger, documents, inventory, local parties, branches, warehouses, settings, attachments metadata. Company display names/tax data are deliberately not in the registry yet (to be decided with company management). The registry has no HTTP endpoints until authentication/authorization exist.

**TLS to PostgreSQL (production requirement):** Npgsql's `SslMode=Require` (and `Prefer`) encrypts the connection but does **not** validate the server certificate, leaving it open to man-in-the-middle attacks. HASM therefore defaults to `VerifyFull` (chain + host name) and rejects `Disable`/`Allow`/`Prefer`/`Require` unless `AllowInsecureTransport=true`, which is logged by `ToString()` as `InsecureTransport=True`. Production needs a PostgreSQL server certificate whose subject/SAN matches `Hasm__Database__Host`, signed by a CA trusted by the Backend host (system store, or `Hasm__Database__SslRootCertificate` for a private CA). `VerifyCA` skips host-name checking; prefer `VerifyFull`. Certificate validation is never bypassed in code.

## Company database provisioning (Phase 2.2)
Each company gets its own PostgreSQL database. Provisioning is an **explicit administrative operation** run with the privileged account through `Hasm.Admin`; the API never provisions, never starts it, and exposes no endpoint for it (and never returns physical names or credentials).
```
dotnet run --project src/backend/Hasm.Admin -- register-company             # registers Pending, prints the company id only
dotnet run --project src/backend/Hasm.Admin -- provision-company <company-id>
```
Exit codes: 0 ok, 1 failure, 2 usage, 3 bad configuration, 4 another process is already provisioning that company.

**Flow** (`CompanyProvisioner`): take a per-company session advisory lock (dedicated connection to the system database, held throughout; requires direct, non-transaction-pooled connections) → Pending/Failed/Provisioning(no lock holder) → `Provisioning` (attempt counted) → create the database named by the registry's opaque name if absent → apply company migrations (`CompanyDatabase/Migrations`, own `migration_journal`, same runner) → bind identity (single immutable row holding the company id) → `REVOKE ALL ON DATABASE … FROM PUBLIC` → verify the mapping both ways → `Ready`.

**Schema:** system migration `0002` adds `ProvisioningAttempts` (int) and `LastErrorCode` (short sanitized code such as `migration`, `consistency`, `pg_<SQLSTATE>`; never a message) to the registry. Company migration `0001` creates the identity table (+ immutability trigger). Physical names are mapped in `CompanySchema` and pinned by tests; no company names appear in any physical name.

**States:** `Pending → Provisioning → Ready | Failed`, `Failed → Provisioning` (retry). `Ready` is terminal; provisioning a Ready company only re-verifies the mapping.

**Recovery:** a process death releases the lock with its connection, so a company in `Provisioning` with no lock holder is interrupted and is resumed by simply running `provision-company` again; cancellation also leaves `Provisioning`. Every step is idempotent. There is no distributed transaction between system and company databases; the two are reconciled by re-running. A failure records `Failed`; the company database is **never dropped automatically**. A pre-existing database with the registered name is accepted only if empty or already HASM-shaped (identity table present); any other database is refused and left untouched (`consistency`). Protected names (system, maintenance, `postgres`, `template0/1`) are never targets.

**Privileges:** provisioning uses `AdminUsername`/`AdminPassword` only (runtime credentials are rejected). Company databases are not connectable by PUBLIC; granting the runtime role `CONNECT`/table rights on a company database is done by `grant-company-runtime` (Phase 3.1A-1, see "Company runtime foundation").

**Tests:** `CompanyProvisioningTests` (real PostgreSQL, same safety gate as above). Company databases created by tests are named `hasm_test_<hex>` through an injected name generator; teardown drops only names the test generated itself and re-checks the prefix.

**PostgreSQL integration tests** (`tests/integration/Hasm.Database.IntegrationTests`) use a real server and create/drop their own databases named `hasm_test_<random hex>`; they never drop anything else. Destructive tests run only when **all** hold: `HASM_TEST_PG_ADMIN_CONNECTION` is set, `HASM_TEST_PG_DISPOSABLE=yes-this-server-is-disposable` is set (you assert the server is disposable), and the host is a loopback address. Otherwise they are reported *skipped*; with `HASM_REQUIRE_PG_TESTS=1` (CI) a closed gate *fails* the tests instead. Use a role without superuser rights, only `CREATEDB`. To run on a disposable local server you manage yourself:
```
$env:HASM_TEST_PG_DISPOSABLE="yes-this-server-is-disposable"
$env:HASM_TEST_PG_ADMIN_CONNECTION="Host=localhost;Username=<CREATEDB role>;Password=<pw>;Database=postgres;SSL Mode=Disable"
dotnet test tests/integration/Hasm.Database.IntegrationTests
```

**Disposable local test cluster and the cluster-identity gate (since Phase 3.1B, Checkpoint A).** The permanent development cluster (`127.0.0.1:5432`) must never be a test target. Local destructive tests use a separate native cluster: `127.0.0.1:5433`, data directory `C:\HasmTest\pgdata`, **not a Windows service**, controlled by `scripts/test-pg/` (`new-test-cluster.ps1` once, then `start-`/`stop-`/`status-test-cluster.ps1`; override locations with `HASM_TEST_ROOT`/`HASM_PG_BIN`). Credentials are random, test-only (`hasm_test_admin` CREATEDB, `hasm_test_roleadmin` CREATEROLE, a cluster superuser used only by the creation script) and live outside the repository in `C:\HasmTest\secrets` under an owner-only ACL; before running tests dot-source `C:\HasmTest\secrets\test-env.ps1`. Besides the existing checks (connection variable, acknowledgement string, loopback host, `hasm_test_` names, role gate) the destructive tests now require the **server itself to prove it is the disposable instance** (`PostgresClusterIdentity`): (1) the connection port is 5433, or 5432 only inside a GitHub-hosted Actions job (`GITHUB_ACTIONS=true`, `GITHUB_RUN_ID`, `RUNNER_ENVIRONMENT=github-hosted`) - and a disallowed port is refused before any connection is made; (2) the server reports that same port; (3) every database on the instance is built-in or `hasm_test_*`; (4) the marker database `hasm_test_cluster_identity` holds a 256-bit fingerprint equal to `HASM_TEST_PG_CLUSTER_FINGERPRINT` (written when the cluster/container was created; a different cluster cannot produce it). Any error, including an unreachable server, refuses. The CI job writes the marker into its job-local container with a per-run secret, so a locally spoofed CI flag alone opens nothing: the development cluster fails checks (3) and (4) regardless.

**Linux/bash twin of the disposable test cluster (dev tooling, D-048).** `scripts/test-pg/*.sh` give the same safety properties as the PowerShell scripts, for Linux agents and developers: a native cluster (`initdb`/`pg_ctl` from `/usr/lib/postgresql/16/bin`, override `HASM_PG_BIN`), `127.0.0.1:5433` ONLY (the port is hard-coded and `HASM_TEST_PORT` with any other value is refused; the listen address and port are also forced on the server command line, and Unix-domain sockets are switched off), data, logs and secrets under `HASM_TEST_ROOT` (default `/tmp/hasm-test`), data directory 700, secrets directory and files 700/600, random 256-bit passwords for `hasm_test_admin` (`CREATEDB`), `hasm_test_roleadmin` (`CREATEROLE`, no superuser, no `CREATEDB`) and a cluster superuser used only by the creation script, the marker database `hasm_test_cluster_identity` with a fresh 256-bit fingerprint, and a sourceable `secrets/test-env.sh` exporting exactly `HASM_TEST_PG_DISPOSABLE=yes-this-server-is-disposable`, `HASM_TEST_PG_CLUSTER_FINGERPRINT`, `HASM_TEST_PG_ADMIN_CONNECTION` and `HASM_TEST_PG_ROLE_ADMIN_CONNECTION`. PostgreSQL refuses to run as root: when the scripts run as root the server commands run as the `postgres` account through `runuser` (override `HASM_PG_RUN_AS`). Nothing is a service and no credential, data or env file lives in the repository. **The root is protected:** `new-test-cluster.sh` creates it (it must be ABSENT, or a root a previous run of the script created, recognised by its marker file) and never chmods or reuses a pre-existing directory; the path is resolved first and a symbolic link anywhere in it is refused; broad directories (`/`, `/tmp`, `/var`, `/var/tmp`, `/home`, `/srv`, `/opt`, `/mnt`, `/run`, `/root`, `$HOME` and its parent, `/usr/local`) are never the root itself (a sub-directory such as `/tmp/hasm-test` is fine), system and PostgreSQL locations are refused at any depth, and the root must be outside EVERY checkout of the repository (the current worktree, the main checkout found through `git rev-parse --git-common-dir` and every `git worktree list` path - agent worktrees live inside the main checkout) and must not contain one. `/tmp` is pruned by `systemd-tmpfiles` on many distributions (default root, age based): a long-lived cluster belongs in a root such as `/var/tmp/hasm-test` or under another dedicated directory, and a pruned root simply means: run `new-test-cluster.sh` again. `destroy-test-cluster.sh` deletes only the known entries of a root that still carries the marker file and therefore refuses a second time.

**Only one agent or developer may use the cluster at a time, and nobody but `run-pg-tests.sh` should source `secrets/test-env.sh`.** The suites create and drop databases and roles cluster-wide, so two runs on one cluster corrupt each other (observed: random `InProgressElsewhere`, missing credential-file and login failures; the port is fixed at 5433 by the gate, so a second cluster cannot run beside it). Every script that changes the cluster or runs the suite (`new-`, `start-`, `stop-`, `destroy-test-cluster.sh`, `run-pg-tests.sh`) therefore takes the same exclusive `flock` on `$HASM_TEST_ROOT.lock` - a file BESIDE the root, so deleting the root never deletes it and no script ever deletes it - and refuses while another holder has it; `run-pg-tests.sh` holds it for the whole run and records the holder (pid, worktree, start time) in `.run.holder`. A script started by a holder inherits the lock descriptor; the lock descriptor is closed for the PostgreSQL daemon and for build servers so they cannot keep it. `run-pg-tests.sh` also refuses to start, and `destroy-test-cluster.sh` refuses to delete, while any test session (`hasm_test_admin`, `hasm_test_roleadmin` or a `hasm_test_*` database) is connected to the cluster, and the run prints a post-run activity check (expected 0 sessions left). There is no override: a run on a shared cluster is never trustworthy. `status-test-cluster.sh` is read-only and takes no lock. The credentials are test-only and random per cluster, but the files are readable by every process of the same OS user: in a shared container (several agents as root) any of them can read the secrets file, which is acceptable only because the cluster is disposable and loopback-only; destroy it after use.
```
scripts/test-pg/new-test-cluster.sh                 # once: creates, starts and prepares the cluster (refuses if the data directory exists)
scripts/test-pg/start-test-cluster.sh | stop-test-cluster.sh | status-test-cluster.sh
# stop-test-cluster.sh exits 1 for a stopped cluster whenever ANYTHING else holds 127.0.0.1:5433 (also another, legitimate test cluster under a different root); no script depends on that exit code. The PowerShell twin is unchanged.
dotnet build src/backend/Hasm.slnx -c Release
scripts/test-pg/run-pg-tests.sh                     # sources test-env.sh, sets HASM_REQUIRE_PG_TESTS=1 and HASM_REQUIRE_PG_ROLE_TESTS=1, runs the suite,
                                                    # then requires 0 failed and 0 skipped from the TRX counters (add --build to build first; extra arguments go to dotnet test)
scripts/test-pg/destroy-test-cluster.sh             # stops the cluster and deletes data, logs and secrets (only a root that carries the marker file written by new-test-cluster.sh)
```

**Isolated parallel workers (Linux, root; dev tooling).** `scripts/test-pg/run-isolated.sh` lets two (at most three) agents run the PostgreSQL integration suite at the same time, each against its OWN throw-away cluster, without changing anything in the safety chain above: the port stays exactly `127.0.0.1:5433`; `PostgresClusterIdentity`, the acknowledgement string, the restricted roles and the marker/fingerprint flow are untouched and simply see a valid disposable cluster. Isolation comes from a **private Linux network namespace per run** (`unshare --net`): the worker's cluster listens on `127.0.0.1:5433` inside its namespace only and `dotnet test` runs in that same namespace, so no other TCP listener of the machine is reachable from it - not the shared `/tmp/hasm-test` cluster, not another worker, nothing on 5432 - and the worker is not reachable from outside. The namespace isolates TCP/IP only: filesystem Unix-domain sockets are not network-namespaced and stay reachable, so the protection against the development cluster is unchanged and still comes from `PostgresClusterIdentity`, the generated `Host=127.0.0.1;Port=5433` connection strings and `unix_socket_directories = ''` of every test cluster. If `unshare --net` is not permitted (no root/`CAP_SYS_ADMIN`, or a container that forbids new namespaces) the script refuses with that message; use `run-oneshot.sh` (below) or a standing shared cluster instead. Per run:
- a **capacity token** (1..`HASM_ISO_WORKERS`, default 2; values above 3 are refused) is taken with an exclusive `flock` on `/tmp/hasm-iso-capacity/slotN.lock` (never deleted); when all are taken the script waits. The build (`--build`; it needs the network for restore) happens first, outside the namespace;
- everything of the run lives in its own `mktemp -d` directory `W=/tmp/hasm-pgw-XXXXXX` (`root:postgres 0710`: the server account may only traverse it to its `0700` data directory): the cluster root `W/cluster` (data, logs, secrets, TRX), its lock `W/cluster.lock`, and the tests' `TMPDIR` `W/tmp`. Override the parent with `HASM_ISO_TMP`;
- the worktree's own unchanged `new-test-cluster.sh` and `run-pg-tests.sh` run inside the namespace with `HASM_TEST_ROOT=W/cluster` (same root checks as always): a fresh cluster with new random passwords and a new 256-bit fingerprint every run, the same `HASM_REQUIRE_PG_TESTS=1`/`HASM_REQUIRE_PG_ROLE_TESTS=1` strictness and 0-failed/0-skipped check;
- results are copied to `HASM_ISO_RESULTS/<W name>/` (or a kept `mktemp -d` directory `/tmp/hasm-pgw-results-XXXXXX`): `run.log`, `pg-integration.trx`, `postgres.log`. A full run (no extra arguments) is also verified against the per-class registry (`node tools/verify/pg-trx-check.js ... .github/workflows/backend.yml`);
- cleanup always runs (success, failure, Ctrl-C, SIGTERM, SIGHUP): every process of the run's namespace is terminated (found through a namespace descriptor the script holds, never by name; the outer namespace is never targeted), `destroy-test-cluster.sh` deletes the cluster, and `W` - only `W`, after a pattern and ownership check - is removed. A run killed with SIGKILL records its `W` in `/tmp/hasm-iso-capacity/slotN.owner`; the next run on that token, or `run-isolated.sh --recover`, stops that run's namespace (found through the live server of that data directory or a process started with `HASM_TEST_ROOT=W/cluster`, held through a descriptor and re-verified before anything is killed) and removes it. Before the unchanged `destroy-test-cluster.sh` runs, a `postmaster.pid` whose PID is not a live process of that data directory is moved aside inside `W`, so `pg_ctl` can never signal a reused PID (for example another worker's server running as the same account). `scripts/test-pg/test-run-isolated-recovery.sh` (root, no server started) checks this with a live decoy process of the server account behind a stale `postmaster.pid`, and checks that an orphan left in a private namespace is stopped.
- Self-tests (manual, root, no PostgreSQL server): `scripts/test-pg/test-run-isolated-recovery.sh`, `test-destroy-stale-pid.sh` and `test-pid-env-root.sh` (the process-matching helpers of `run-isolated.sh` answer correctly for a process with a large environment under `pipefail`; a `grep -q` there once made `--recover` skip a live orphan now and then).
```
scripts/test-pg/run-isolated.sh "$PWD" --build                       # from your own worktree: build, then the full suite + registry check, isolated
scripts/test-pg/run-isolated.sh "$PWD" --filter "FullyQualifiedName~PricingApiTests"   # a subset (no registry check)
HASM_ISO_RESULTS="$D/pg" scripts/test-pg/run-isolated.sh "$PWD"      # keep results under your own mktemp -d directory
scripts/test-pg/run-isolated.sh --recover                            # clean up runs killed with SIGKILL (busy tokens are skipped)
```
Measured on the shared 4-CPU/15 GB container (full suite, 1167 tests incl. 56 SafetyGate, registry 1111; other agents kept the load average at 15-50, so the numbers are indicative): one worker 1003 s wall, 1942 CPU-s, 2.1 GiB peak; two at once 1342 s for both (about 1.5x the throughput of running them one after the other), 4133 CPU-s, 4.0 GiB; three at once 2851 s for all three, 6441 CPU-s, 5.9 GiB, under a load average of 40-53 - not clearly better than two. The default is therefore 2.
Rules for agents: prefer `run-isolated.sh` to the shared cluster; one run per agent at a time; never create, read or delete another run's `/tmp/hasm-pgw-*` directory, and never touch the capacity tokens or `/tmp/hasm-test*`; do not raise `HASM_ISO_WORKERS` above the value the lead sets (2 on a 4-CPU machine; 3 only when nothing else is building or testing). Requirements: root (network namespaces, `runuser`), `unshare`, `flock`, `python3` or `perl` (to bring the private loopback up; no `ip` needed), `node` for the registry check. Limits: the namespaces isolate the network only - every root process on the machine can still read `W/cluster/secrets` (acceptable for random, test-only, loopback-only credentials, exactly as for the shared cluster); CPU, memory and disk are shared, so each run gets slower as more run; build outputs are per worktree (`bin/obj`), so two workers must use two worktrees (a second isolated run on the same worktree is refused through an `flock` on the worktree directory).

**One-shot shared mode (Linux; the FALLBACK when isolated mode is unavailable; dev tooling).** Which runner to use:

| Situation | Runner |
|---|---|
| Root and `unshare --net` work (this cloud container) | `run-isolated.sh` - PREFERRED: private namespace, several runs side by side |
| No root, or the container forbids new network namespaces (`run-isolated.sh` refuses with that message) | `run-oneshot.sh` - one command, one run at a time on the machine |
| A cluster you want to keep between runs (debugging with `psql`, repeated subsets) | `new-test-cluster.sh` once, `run-pg-tests.sh` as often as needed, `destroy-test-cluster.sh` at the end |

`scripts/test-pg/run-oneshot.sh` creates a fresh disposable cluster, runs the suite of its own checkout, verifies a full run against the per-class registry (`tools/verify/pg-trx-check.js`, the same check as CI and `run-isolated.sh`) and ALWAYS destroys the cluster, its secrets and its directory again: after success, failure, Ctrl-C, SIGTERM and SIGHUP. It adds no provisioning code: the cluster is created, used and destroyed by the unchanged `new-test-cluster.sh`, `run-pg-tests.sh` and `destroy-test-cluster.sh` with `HASM_TEST_ROOT=W/cluster`, `W` being the run's own `mktemp -d` directory `/tmp/hasm-pg1-XXXXXX`, so every safety property above holds as it is (`127.0.0.1:5433` only, no Unix-domain sockets, fresh passwords and fingerprint, the acknowledgement, the restricted roles, the root checks, `PostgresClusterIdentity` untouched). Without a private namespace the cluster listens on the machine's own loopback, so only one can exist at a time; the script refuses instead of sharing:
- where isolated mode IS available (root and a working `unshare --net`) it refuses and names `run-isolated.sh`; `--force-shared` as the first argument overrides that (for testing the fallback itself);
- an inherited `HASM_TEST_ROOT` is refused: a one-shot run never uses, starts, stops or deletes a standing cluster;
- it takes the lock of the default shared cluster (`/tmp/hasm-test.lock`) for the whole run and refuses while a holder has it, and it refuses when anything listens on port 5433 (read from `/proc`; nothing is connected to, and nothing on 5432 is ever touched; when the IPv4 listening table in `/proc` cannot be read it refuses as well). A standing cluster under another root is recognised by its listener on 5433;
- it takes one of the capacity tokens of `run-isolated.sh` (`/tmp/hasm-iso-capacity/slotN.lock`, `HASM_ISO_WORKERS`), so its cluster counts toward the machine-wide limit (it waits for a token, as `run-isolated.sh` does), and it takes the same `flock` on the checkout directory, so the two runners never share `bin/obj`. The capacity directory must belong to the current user (mode 700); a user who cannot use the directory another account created sets `HASM_ISO_CAPACITY_DIR` to an own one;
- cleanup stops every process started for the run (the worker shell as the script's own background job, read from the shell's job table, and read again before the KILL because bash reaps a finished background job without a wait; everything it started by `HASM_TEST_ROOT=W/cluster` in the environment it was started with; never by name; the server is stopped by `destroy-test-cluster.sh`), copies the results out, destroys the cluster and removes `W` after a pattern and ownership check. A run killed with SIGKILL cannot clean up: it leaves `W` recorded in `/tmp/hasm-iso-capacity/oneshot.owner`, and the next one-shot run, or `run-oneshot.sh --recover`, removes it the same way.
- **Results directory (`HASM_ONESHOT_RESULTS`, `HASM_ISO_RESULTS`).** Use a directory only you can write to. A shared results directory that other accounts can write to must have the sticky bit (`chmod +t`) or be trusted: without it another account can rename the new 700 per-run sub-directory away after it was created and put its own there, and the copies at the end follow what is there. The scripts close only planting before creation (`mkdir` without `-p`). When the per-run sub-directory cannot be created the run stops without naming or copying into it.
```
scripts/test-pg/run-oneshot.sh --build                                         # build, then the full suite + registry check; exit 0 and "one-shot: VERIFIED" are the only success signal
scripts/test-pg/run-oneshot.sh --filter "FullyQualifiedName~PricingApiTests"   # a subset: exit 4 and "SUBSET PASSED", never a verification
HASM_ONESHOT_RESULTS="$D/pg" scripts/test-pg/run-oneshot.sh                    # keep pg-integration.trx and postgres.log under your own directory (an existing one keeps its mode, the per-run sub-directory is new and 700; default: a kept /tmp/hasm-pg1-results-XXXXXX)
```

## Identity and local authentication (Phase 2.3A)
Central identities live in `Hasm_System` (system migration `0003_users_and_sessions.sql`, opaque physical names mapped in `SystemSchema.User/Session/LoginThrottle/UserCompanyAccess`). Scope: login/logout, sessions, throttling, administrative user creation and the initial administrator. **Not** in scope: MFA, AD, licensing seats, a login UI.

**Data model:** `User` (stable `uuid`, normalized unique login, display name, password hash, state `Active|Disabled|Locked`, `IsIdentityAdministrator`, timestamps; rows are never deleted and id/login are immutable via trigger), `Session` (server-side; SHA-256 of a 256-bit random token, client kind, last-seen, idle and absolute expiry, revocation time/reason), `LoginThrottle` (SHA-256 key digests, failure counters, block-until), `UserCompanyAccess` (explicit user-to-company link with FK to the company registry; created and revoked only through the Phase 2.3B access service, see below). Authentication never reads or grants company access; the status response contains no company information.

**Login identifiers:** trim, Unicode NFKC, invariant lower-casing; must match `[a-z0-9][a-z0-9._@-]{2,63}` (ASCII only, which rules out homoglyph look-alikes; fullwidth forms fold to ASCII). Uniqueness is on the normalized value, enforced by the application and by a database UNIQUE + CHECK constraint.

**Passwords:** `Microsoft.Extensions.Identity.Core` `PasswordHasher` (Identity v3: PBKDF2-HMAC-SHA512, random 128-bit salt per hash, iteration count stored in the hash, constant-time compare), default 210,000 iterations (`Hasm__Auth__Pbkdf2Iterations`, floor 100,000). Hashes with a lower count are upgraded at the next successful login. No custom cryptography; no plaintext or reversible storage. Policy: 12-128 characters, not trivially repetitive, not equal to the login (length based, no composition rules; there is no breached-password list yet).

**Session transport and storage (rationale):** one opaque, random, server-side session; two transports chosen by the client at login (`"client":"web"|"desktop"`):
- **Web (React):** `__Host-hasm_session` cookie, `HttpOnly; Secure; SameSite=Strict; Path=/` (no Domain). JavaScript never sees the token, so XSS cannot steal it, and it is never placed in `localStorage`/`sessionStorage`. The token is not in the response body. Requires the web UI and API to be same-site (e.g. `app.example.com` + `api.example.com`, or `localhost` ports in development).
- **Desktop (Tauri):** the WebView origin is cross-site to the API, so SameSite cookies are unsuitable. The token is returned once in the login response body and sent as `Authorization: Bearer`. The client must keep it in the OS credential store (Windows Credential Manager, from the Rust side), never in WebView storage; **this client side is not implemented in this phase**.
- Opaque server-side sessions (rather than JWTs) give instant revocation, server-side idle/absolute expiry and the per-session accounting the licensing phase will need. Only the token's SHA-256 is stored, so a database leak yields no usable tokens.
- **CSRF:** SameSite=Strict plus a required `X-Hasm-Request` header on every state-changing `/api` request (cross-site pages cannot send it without a CORS preflight, which only configured origins pass). CORS allows credentials only for the explicit `Cors:AllowedOrigins`.

**Sessions:** idle timeout 30 min (sliding, written at most once a minute), absolute limit 12 h (`Hasm__Auth__SessionIdleMinutes`, `SessionAbsoluteHours`). Each login issues a new token (no fixation). Logout revokes server-side. Disabling/locking a user, and changing a password (all other sessions), revoke sessions in the same transaction. The user's state and administrator flag are re-read on every request. An hourly housekeeping service removes long-expired/revoked sessions and stale throttle rows.

**Brute force / credential stuffing / enumeration:** layered per-(login, client), per-client and per-login-ceiling counters (HTTP 429 + `Retry-After`; blocks are temporary and never change user state or end sessions). Every credential failure returns the same `401 {"error":"invalid_credentials"}` and unknown logins spend the same hashing time. Details, defaults and the trusted-proxy handling of the client address: see "Authentication and access security hardening (Phase 2.3C-1)" below. This replaces the Phase 2.3A single per-login counter, which allowed temporary lockout of a known user, and the earlier advice to set `ASPNETCORE_FORWARDEDHEADERS_ENABLED`, which is now refused at startup.

**Endpoints** (`/api/v1`): `POST auth/login`, `POST auth/logout`, `GET auth/status` (anonymous allowed; returns `authenticated` and, when signed in, user id/login/display name/administrator flag and expiry times), `POST auth/change-password` (current password required; shares the throttle), `POST admin/users`, `POST admin/users/{id}/state` (`Active|Disabled|Locked`; an administrator cannot change their own state). Admin endpoints require an authenticated identity administrator (401/403 otherwise). There is **no public registration**. Auth responses are `no-store`; errors are generic JSON (no exception text; database failures return 503).

**Logging:** auth events log outcome codes, user ids and session ids only. Passwords, tokens, hashes, connection strings and attacker-supplied login strings are never logged (pinned by tests that capture all log output).

**Initial administrator (explicit, offline):**
```
$env:Hasm__Database__AdminUsername="..."; $env:Hasm__Database__AdminPassword="..."   # plus Host / SystemDatabaseName
$env:HASM_BOOTSTRAP_ADMIN_PASSWORD="..."      # optional; otherwise prompted without echo. Never a command-line argument.
dotnet run --project src/backend/Hasm.Admin -- bootstrap-admin <login> ["Display name"]
```
Creates the first identity administrator and refuses (exit 5) when one already exists (serialized by an advisory lock, so concurrent runs cannot create two). Exit codes otherwise as for the other commands.

**Runtime identity and privileges:** the API connects with `Hasm__Database__Username/Password` (never the provisioning admin account; if the runtime account is unusable the API returns 503 rather than falling back). The DBA must grant it, on the system database: `SELECT, INSERT, UPDATE` on the `User` table; `SELECT, INSERT, UPDATE, DELETE` on the `Session` and `LoginThrottle` tables; `SELECT` on `UserCompanyAccess` (extended by Phase 2.3B, see below; physical names are in `SystemSchema`; grants are not automated). The runtime role needs no DDL rights. API connections to PostgreSQL are pooled; all other TLS rules above still apply.

**Tests:** unit tests (login normalization, password policy/hashing, tokens, options) run everywhere. PostgreSQL tests (`IdentityMigrationTests`, `UserCreationTests`, `LoginTests`, `SessionTests`, `BruteForceProtectionTests`, `AuthApiTests`, same safety gate as above) use an injectable clock instead of sleeping and drive the real API in-process via `WebApplicationFactory`. `AuthWithoutDatabaseTests` (no database) covers anonymous access, CSRF header and generic errors.

## Company access and RBAC (Phase 2.3B)
Authorization metadata is central and lives in `Hasm_System` (system migration `0004_company_access_rbac.sql`; opaque physical names mapped in `SystemSchema.Role/RolePermission/RoleAssignment/AccessAudit` plus new columns on `UserCompanyAccess` and `Session`). Company databases are untouched: they hold no authorization data, and access to one company can never expose another company's data.

**Model.** Deny by default. A user may do `resource.action` in a company only if **all** hold, evaluated from the database on every request: the user is `Active`; the company is `Ready`; an *active membership* (`UserCompanyAccess`; revoked rows never count) exists; an *active role assignment* of that user in that company exists; the role is active and contains the permission; the assignment's scope covers the target. Authentication alone, and the `IsIdentityAdministrator` flag, grant nothing in any company.
- **Permission catalog** (`PermissionCatalog`, in code): resources with a granularity (`Company|Branch|Warehouse`) x actions (`View, Create, Update, Delete, Approve, Post, Export, Print`); code `resource.action`, e.g. `access.roles.update`. Unknown codes never grant. This phase registers only the access-administration resources (`access.members|roles|assignments|audit`); later phases add their resources together with a migration that extends the preset roles (a test pins the database presets to the code definitions). No business permissions were invented.
- **Roles:** *preset* (shipped with the software, company id NULL, immutable by database trigger: `Company Administrator`, `Access Manager`, `Access Auditor`) and *custom* (belong to one company; created, edited and deactivated by authorized users; never deleted). Role names are unique per company. A user may hold several roles; permissions are the union of the user's grants, each grant keeping its own scope.
- **Scopes:** an assignment is Company-wide, or limited to one Branch or one Warehouse id. Company-wide covers everything; Branch/Warehouse cover only their own id; narrower assignments never exercise coarser (e.g. company-level administrative) resources. Branch and warehouse ids are opaque uuids because those entities will live in the per-company databases (no business module exists yet); **scoped assignments fail closed**: `AssignRoleAsync` accepts a Branch/Warehouse scope only if an `IScopeTargetValidator` confirms the id exists in that company (a validator error counts as "no"). The default validator refuses everything, so until the branch/warehouse phase registers a real one, only company-wide assignments can be made (`400 scope_not_verifiable`). At evaluation time a scoped grant matches only its exact kind and id, never a company-wide target, another kind, or a coarser resource.
- **Last administrator guard:** revoking a membership or a company-wide Company Administrator assignment is refused (`409 last_administrator`) when it would leave the company with no active administrator. An administrator is an `Active` user with an active membership of a `Ready` company holding the active preset Company Administrator role company-wide, so disabled users, revoked memberships and narrower assignments do not count. The check runs inside the per-company lock, so concurrent removals serialize. A company that already has none is not blocked from cleanup, and the offline `grant-company-admin` recovery is unaffected. Since Phase 2.3C-1 disabling or locking a user takes the same lock and is refused when it would remove the last usable administrator (see "Company administrator continuity").
- **Account enumeration:** every `access.*` operation authorizes the caller before it looks anything up, so a caller without the permission (or without a selected company) gets one fixed answer regardless of whether a login or user id exists. Only a caller holding `access.members.create` sees `201` versus `user_not_found` (unknown, disabled, locked and malformed logins are indistinguishable); that is the legitimate add-by-login workflow.
- **Company selection:** `POST /api/v1/session/company` binds the server-side session to a company after a membership check; a non-member, an unknown company and an unavailable company all return the same `403 forbidden`. Company-scoped endpoints take **no company id from the client** (route, query, header and body claims are ignored); the company comes from the session row and every call re-validates it. Revoking a membership clears the selection of that user's sessions.
- **Escalation rules (enforced in `AccessService`, inside the transaction):** the actor needs the corresponding `access.*` permission company-wide **and** must possess every permission they hand out, for the scope they hand it out at (assigning a role; creating a role; editing a role - the editor must hold both its old and its new permissions). Revoking an assignment or membership requires holding what the target holds. Nobody may assign or revoke their own assignments or revoke their own membership. Preset roles cannot be changed. Mutations run in one transaction under a per-company advisory lock and re-read the actor's privileges inside it, so concurrent changes serialize (two administrators revoking each other cannot both succeed). Every change writes an append-only audit row (`AccessAudit`, trigger-protected) in the same transaction; denied or failed attempts write nothing.
- **Immediate effect:** nothing is cached or copied into the session. Revoked assignments and memberships, deactivated roles, disabled or locked users and non-Ready companies stop authorizing on the very next request, without a new login.

**Endpoints** (`/api/v1`; all require authentication, responses are `no-store`, state changes need `X-Hasm-Request`): `GET companies` (the caller's own selectable company ids only: no names, no physical identifiers), `POST|DELETE session/company`, `GET access/me`, `GET access/permissions`, `GET|POST access/roles`, `PUT access/roles/{id}/permissions`, `POST access/roles/{id}/deactivate`, `GET|POST access/members` (a member is added by login), `DELETE access/members/{userId}`, `GET|POST access/assignments`, `DELETE access/assignments/{id}`, `GET access/audit`. Another company's object ids yield `404` (indistinguishable from nonexistent ones), a missing permission `403`, no selected company `409 company_not_selected`.

**Initial administration (no public endpoint).** The first company administrator is created offline with the privileged account:
```
dotnet run --project src/backend/Hasm.Admin -- grant-company-admin <login> <company-id>
```
It grants membership and the preset Company Administrator role company-wide (audited with no actor user), is idempotent, and doubles as the recovery path. The user must already exist (`bootstrap-admin` or the admin API) and the company must be `Ready`. No HTTP route can grant a first administrator, and identity administrators get no company access from their flag.

**Fiscal approver delegation (Phase 3.1D, offline only).** Approving the exceptional reopening of a Final Closed fiscal period or a closed year needs `company.fiscalreopen.approve`, which the Company Administrator deliberately lacks and no company user can grant. The supported, audited way (and the recovery for a company with no approver) is:
```
dotnet run --project src/backend/Hasm.Admin -- grant-fiscal-approver <login> <company-id>
dotnet run --project src/backend/Hasm.Admin -- revoke-fiscal-approver <login> <company-id>
```
The user must already be an active member of a `Ready` company (membership is never created); the preset Fiscal Approver role is assigned company-wide and both commands are audited with no actor user. See `docs/PHASE-3.1D.md`.

**Runtime privileges** added for the API account (grants are not automated; Phase 2.3C-2 adds `SELECT, INSERT` on the audit-event table, see "Upgrade and compatibility" under Cryptographic audit integrity): `SELECT` on the company registry table; `SELECT, INSERT, UPDATE` on `UserCompanyAccess` (replaces the 2.3A `SELECT`-only grant), `Role` and `RoleAssignment`; `SELECT, INSERT, DELETE` on `RolePermission`; `SELECT, INSERT` on `AccessAudit`. `Session` needs the `UPDATE` it already has (selection column).

**Tests:** unit tests (`AccessModelTests`: catalog, presets versus migration seed, scope evaluation, escalation primitives) and real-PostgreSQL integration tests (`AccessMigrationTests`, `MembershipTests`, `RoleTests`, `AssignmentAndScopeTests`, `AccessRevocationTests`, `AccessAuditTests`, `OfflineAdministrationTests`, `ConcurrentAccessChangeTests`, `AccessApiTests`) under the same safety gate as above.

## Authentication and access security hardening (Phase 2.3C-1)
Resolves Phase 2.3A limitations 1 and 2 and Phase 2.3B requirement 3. No schema change: throttle rows stay in the existing `LoginThrottle` table (key digests only; the new counters use distinct key namespaces), so there is no new migration and no new database privilege.

### Login abuse protection
**Root cause.** Failures were counted per login string alone, so anyone could submit five wrong passwords for a known login and block the real user for 15 minutes (a lockout denial of service). The source counter used the raw peer address, so behind a proxy all clients shared one counter.

**Design and trade-offs.** A per-login counter must stay small to stop guessing, but then lets a third party lock the user out. A per-address counter alone cannot stop a botnet. HASM therefore layers three independent counters, each counted within `Hasm__Auth__FailureWindowMinutes` (15) and answering HTTP 429 + `Retry-After` for `BlockMinutes` (15). Blocks never change the account state and never end existing sessions.

| Counter | Key | Default | Effect |
|---|---|---|---|
| Pair | login + client | `MaxFailuresPerLoginSource` = 5 | blocks only that client for that login, so an attacker cannot lock the real user out from any other address |
| Client | client | `MaxFailuresPerSource` = 20 | stops credential stuffing / spraying by one client |
| Login ceiling | login, all clients | `MaxFailuresPerLoginGlobal` = 100 (at least 4x the pair limit) | last resort against distributed guessing; blocks the login for everyone and logs `auth.login_distributed_attack_suspected` (user id only) |

A success clears only the caller's pair counter (the client and ceiling counters are kept, so failures cannot be laundered). Every counter exists for every attempted login string, real or not. Every credential failure (unknown, malformed, wrong password, Disabled, Locked) answers the same `401 invalid_credentials`, blocked answers are identical for existing and non-existing logins, and unknown logins spend the same hashing time. `change-password` failures use their own per-user counter, so other people's failed sign-ins can never block a password change. The "client" is the validated client address (next section); IPv4-mapped IPv6 folds to IPv4 and an IPv6 client is identified by its /64 (one subscriber cannot rotate addresses). No CAPTCHA or external service is used (none was strictly necessary and none was approved).

### Trusted reverse proxy
**Root cause.** No forwarded-header handling existed, and the earlier documentation suggested `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true`, which makes ASP.NET Core trust forwarded headers from **any** sender. HASM now refuses to start when that switch is set.

Settings (section `Hasm:ReverseProxy`, environment `Hasm__ReverseProxy__*`; all optional; the feature is **off** by default, meaning direct connections):

| Setting | Meaning |
|---|---|
| `Enabled` | `true` to honour forwarded headers from the listed proxies. Requires at least one proxy or network. |
| `KnownProxies` | Exact proxy addresses (IPv4/IPv6). `0.0.0.0` and `::` are refused. |
| `KnownNetworks` | CIDR ranges of proxies (internal ranges only: at least /8 for IPv4, /7 for IPv6; `0.0.0.0/0` and `::/0` are refused). |
| `ForwardLimit` | Number of trusted proxies in the chain (default 1, max 10). Only that many right-most entries are read; entries a client prepends are never used. |
| `TrustProtocol` | Also honour `X-Forwarded-Proto` from trusted proxies (default `true`). |

`X-Forwarded-For` and `X-Forwarded-Proto` are applied **only** when the immediate peer is a configured proxy or inside a configured network. From anyone else they are ignored and the connection address is used; a client cannot impersonate a proxy by naming its address in a header. The framework's implicit loopback trust is removed: list `127.0.0.1` and `::1` yourself if the proxy runs on the same host. Invalid configuration stops the process at startup with a message that names the setting but never its value. The middleware runs first in the pipeline, so HTTPS redirection, HSTS and throttling see the validated client.

The proxy must overwrite (or append to) the client-supplied `X-Forwarded-For`, and must be the only way to reach the API (bind Kestrel to loopback or a private interface, and firewall the port).

*Linux (nginx on the same host, Kestrel on loopback, systemd):*
```
# /etc/systemd/system/hasm-api.service.d/proxy.conf
[Service]
Environment=ASPNETCORE_URLS=http://127.0.0.1:5000
Environment=Hasm__ReverseProxy__Enabled=true
Environment=Hasm__ReverseProxy__KnownProxies__0=127.0.0.1
Environment=Hasm__ReverseProxy__KnownProxies__1=::1

# nginx location (edge proxy: set, do not append, the client address)
proxy_pass http://127.0.0.1:5000;
proxy_set_header X-Forwarded-For $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_set_header Host $host;
```
With a further trusted hop in front of nginx (load balancer, CDN), use `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`, list both hops in `KnownProxies`/`KnownNetworks` and set `Hasm__ReverseProxy__ForwardLimit=2`.

*Windows Server (API as a Windows service behind a reverse proxy on another host, e.g. IIS ARR, HAProxy or nginx at 10.20.0.5):* use an untracked production configuration file next to the API, for example `appsettings.Production.json`:
```json
{ "Hasm": { "ReverseProxy": { "Enabled": true, "KnownProxies": [ "10.20.0.5" ], "KnownNetworks": [ "10.20.1.0/24" ], "ForwardLimit": 1 } } }
```
or machine environment variables (elevated shell, then restart the service): `setx /M Hasm__ReverseProxy__Enabled true` and `setx /M Hasm__ReverseProxy__KnownProxies__0 10.20.0.5`. For IIS ARR enable "Preserve client IP in the following header" = `X-Forwarded-For`, and restrict the API's firewall rule to the proxy host. Never set `ASPNETCORE_FORWARDEDHEADERS_ENABLED`. These Windows/IIS steps follow the ASP.NET Core documentation and have **not** been exercised on a Windows server in this phase.

### Company administrator continuity
**Root cause.** The last-administrator guard covered only membership and assignment revocation. Disabling or locking a user through the identity API bypassed it, and two identity administrators could disable each other concurrently.

`IdentityStore.SetStateAsync` now runs these steps in one transaction (`AdministratorContinuity` is the single definition of a usable administrator, shared with `AccessService`):
1. Take an identity-administrator advisory lock and require the acting user to still be `Active`.
2. Refuse (`409 last_identity_administrator`) to take the last Active identity administrator out of Active.
3. Find the Ready companies where the target is a usable administrator, take each company's advisory lock (the same lock `AccessService` uses; sorted order, restarting with a larger set if a membership appears meanwhile), and refuse (`409 last_company_administrator`) if any would be left with none.

The check, the update and the session revocation commit together, so disabling, locking and revoking serialize against each other and the loser sees the winner. The response carries no company information. Re-activation and moves between non-Active states are never blocked. A company that already has no usable administrator blocks nothing (cleanup stays possible) and the offline `grant-company-admin` recovery is unchanged. Identity administrators still get no company access from their flag.

Trade-off: a compromised sole Company Administrator cannot be disabled through the API. First appoint a second administrator (offline `grant-company-admin`, or another administrator through the access API), then disable the account. A direct database change, or an administrator's own password loss, still needs offline recovery.

### Company MFA policy: operator notes (Phase 4.1 S3b-1b, D-167..D-169)
* **What it is.** Each company has an MFA policy `off` (the default; a company with no stored policy is Off), `roles` (the holders of the listed roles) or `all`. A Company Administrator (`access.mfapolicy.update`, with a FRESH second factor) changes it with `PUT /api/v1/access/mfa-policy`; every change is audit event 1338 in the system stream.
* **Optimistic concurrency.** `GET /api/v1/access/mfa-policy` returns the policy with its `revision` (0 while nothing is stored, 1 after the first write, +1 per change) in the body and as the `ETag`. `PUT` must send that revision in `If-Match` (for example `If-Match: "0"` for the first write): 428 `precondition_required` without it, 400 `invalid_if_match` when it is not a number, 412 `revision_conflict` with `currentRevision` when another change came first (read again and repeat).
* **Users without an authenticator in a company whose policy is not Off.** They are refused in that company (403 `mfa_enrolment_required` at company selection and on every company route) but can always list and leave companies, change the password and sign out. **Until the S3b-2b screens ship** (the policy screen and the company-selection prompt) they enrol on their own through the Security screen, `/account/security` (header button "Security"; Web and Desktop, shipped with PR 178), or through the API (`POST /api/v1/auth/mfa/enrol/begin` with the password in the live session, then `POST /api/v1/auth/mfa/enrol/confirm`); after enrolling they sign in with the second factor and select the company again.
* **Company selection and concurrent requests.** Selecting a company is one decision (membership, then the policy; the selection is stored only when both allow it), so a refused selection leaves the previously selected company in place. A client that sends requests in parallel with a company switch can receive 409 `company_selection_changed` (the request was authorized for the company selected before): it repeats the request. A password-only session of a user who enrolled afterwards is no longer a session (401; the user signs in again with the second factor).
* **Identity administration is not affected.** `/api/v1/admin/users/*` and `/api/v1/admin/parties/*` are not company-scoped and are never refused because of the SELECTED company's policy; they keep the administrator claim and `MfaVerified`/`MfaFresh`.
* **Resetting a company's policy to Off.** The supported, audited way is the API: a Company Administrator of that company who signs in with a second factor selects the company, reads the policy and sends `PUT /api/v1/access/mfa-policy` with `{"policy":"off"}` and the current revision in `If-Match`. EVERY change of the policy, switching it Off included, requires that the administrator making it has an authenticator and a fresh second factor (otherwise 409 `mfa_policy_requires_own_enrolment`, whether or not the policy covers them); an administrator of that company who has no authenticator first enrols as described above. **There is no `Hasm.Admin` command for this today.** If no administrator of the company can present a second factor and none can enrol, there is no supported reset yet; editing the policy tables directly is NOT a supported procedure (it would bypass the audit event). **Follow-up (recorded, not built in this slice): an audited admin-tool reset command** (`Hasm.Admin`, review L1 of PR 181).

## Cryptographic audit integrity (Phase 2.3C-2)
Resolves Phase 2.3B production requirement 1 (audit-log tamper evidence). System migration `0005_cryptographic_audit_integrity.sql` adds one append-only table (`SystemSchema.AuditEvent`, opaque physical names). Existing history (`AccessAudit`, migration 0004) is **not** rewritten, backfilled or deleted.

### Architecture
- **Independent streams.** One `system` stream (identity events) and one stream per company (`company:<id>`). Each has its own gap-free sequence (1, 2, 3, …), its own hash chain and its own checkpoints; they share no lock and no key-derived state, and verification of one stream reads only that stream (company isolation). A database CHECK ties a row's stream to its company.
- **Event record.** `stream, seq, event id (uuid), occurred-at (UTC, microseconds), event type, company, actor, target, subject, legacy ref, detail (≤1000 chars, short structured text, never secrets), format version, key id, prev hash, hash, mac`. Event types are numeric and never renumbered: 1-7 company access (existing), 100-103 identity (`UserCreated`, `InitialAdministratorCreated`, `UserStateChanged`, `PasswordChanged`), **1000+ reserved** for future accounting, inventory, approval and privileged-administration events: a future module appends `new AuditEventData(type, …)` in its own transaction through `AuditTrail.AppendAsync`; no change to the mechanism is needed. Successful logins/failures are deliberately not chained (volume; they remain in the throttle table and log).
- **Deterministic, versioned serialization** (`AuditCanonical`, format version 1; documented in the class): fixed magic, big-endian integers, length-prefixed UTF-8 strings, explicit presence flags (so `null`, empty and absent differ), the key id and the previous hash inside the authenticated bytes. A golden test pins version 1 forever; a change needs a new version number and a retained old reader. Unknown versions are reported as *unverifiable*, never as valid.
- **Chain and authentication.** `hash = SHA-256(canonical)`; the next record's `prev hash` is this hash (the first record uses a per-stream genesis value). `mac = HMAC-SHA-256(eventKey, canonical)`. The hash alone proves nothing against someone who can write the database (they can recompute it); the keyed MAC means a database-only attacker cannot produce a valid record.
- **Atomicity.** `AccessService` and `IdentityStore` append the chained event **inside the same PostgreSQL transaction** as the mutation (`AuditTrail.AppendAsync(conn, tx, …)`), then commit through `AuditTrail.CommitAsync`. If the event cannot be written (key missing, damaged chain, checkpoint store failing) an exception is thrown, the transaction is abandoned and the mutation does not happen (HTTP `503 audit_unavailable`; the client sees one generic code, the log carries only the short reason code). Denied or failed attempts write nothing. Audited today: all seven company-access events (including the offline `grant-company-admin`), user creation, initial administrator, user state change (with its session revocation) and real password changes (a transparent rehash is not an event). The `AccessAudit` table is still written in the same transaction as a readable projection (the access API still serves it); each chained event carries the projection row id, and verification cross-checks both directions.
- **Concurrency.** Appends to one stream are serialized by a transaction-scoped advisory lock taken **last** in every transaction (after the company/identity locks), so there is one order and no gap even under contention; a rolled-back append consumes no sequence number. A transaction that appends twice to one stream (e.g. `grant-company-admin`) validates and anchors only committed state.
- **Append-only.** A trigger rejects UPDATE and row DELETE, even for the table owner; `PUBLIC` has no privileges; the runtime role gets `SELECT, INSERT` only. `TRUNCATE` cannot be intercepted by a trigger under the migration-safety rules (and the table owner can disable triggers), so these are **detected** (below), not prevented.

### Cryptographic mechanism, trade-offs and key management
Only established .NET primitives are used (`SHA256`, `HMACSHA256`, `HKDF`, `RandomNumberGenerator`, `CryptographicOperations.FixedTimeEquals`); nothing custom.
- **Why HMAC-SHA-256 (not per-event digital signatures).** An HMAC is fast on the write path, needs no key-pair management and is secure against anyone without the key, which is the threat here (a DBA or database-level attacker). The cost: verification needs the same secret, so the verifier host must be trusted with the key, and a third party cannot verify without it. ECDSA P-256 (built into .NET) would let auditors verify with a public key only, at the price of private-key handling, signature size and speed; it can be added later as a new format version (checkpoint signing is the natural first use) without touching existing records.
- **Key derivation.** One 256-bit master secret per *key id*; `HKDF-SHA-256` derives two independent sub-keys (`event`, `checkpoint`) bound to the key id, so an event code can never be replayed as a checkpoint code and vice versa. Keys are random (≥ 32 bytes), never derived from a password.
- **Key files.** `Hasm__Audit__KeyDirectory` holds `<keyId>.hkey` (one base64 line). No key is in Git (`*.hkey`/`*.hcp` are git-ignored), in the database, in a record, a log, an exception or a command line. `Hasm.Admin audit-keygen <key-id>` creates one with a CSPRNG, **never overwrites**, restricts it to the owner (Linux 0600 in a 0700 directory; Windows: protected ACL, current user only) and prints only the id. At load the permissions are checked: Linux refuses any group/other access; Windows refuses read access for Everyone, Users or Authenticated Users. A missing, malformed, short or exposed key makes audited mutations fail closed. Key identifiers are `[a-z0-9][a-z0-9-]{0,31}`.
- **Rotation.** Create the new key (`audit-keygen 2027-a`), set `Hasm__Audit__ActiveKeyId=2027-a` and restart. New records and checkpoints use it; **every old key file must stay in the directory** so older records keep verifying (a record carries its key id; the id is authenticated). Removing a retired key does not break integrity: its records become *incomplete* (unverifiable), never *verified*. If the head record's key is unavailable the system refuses to append. Keys are cached per process; a restart picks up changes.
- **Backup and recovery of keys.** The key directory is the one thing that cannot be rebuilt. Back it up when created and after every rotation (offline: encrypted removable media or a sealed printout in a safe, stored apart from the database backups and from the checkpoint copies). Restore it with the same ownership/permissions (Linux `chown <service-user> && chmod 700 dir && chmod 600 *.hkey`; Windows: remove inherited ACEs, grant only the service account, `icacls <dir> /inheritance:r /grant:r "<service-account>:(OI)(CI)F"`). If *all* copies of a key are lost, records written under it can never be verified again (the data is intact but unauthenticated); rotate to a new key immediately, keep the checkpoints and document the break. A compromised key: rotate, then treat records authenticated by that key (and anything after the suspected time) as untrusted; checkpoints made by other keys, kept elsewhere, bound what could have changed.
- **Windows/Linux.** Same configuration on both. Windows paths such as `D:\HasmAudit\keys`; run the service under a dedicated account. The Windows ACL checks run in the unit tests on Windows (this phase was developed on Windows); the Linux mode checks run in CI, and the Linux behaviour was **not** exercised locally.

### Protected checkpoints (outside the database, offline)
- A **checkpoint** states "record *N* of stream *S* has hash *H*", authenticated with the checkpoint sub-key, and chained to the previous checkpoint of that stream (so a checkpoint removed from the middle is detected). One append-only JSON-lines file per stream in `Hasm__Audit__CheckpointDirectory`; file names are hashes of the stream key (no company ids); each append is flushed to disk. The directory must **not** be inside the audited database host's data directory and should be on separate media or a separate machine's mount, with write access only for the service account (Linux: refuses a group/other-writable directory; Windows: refuses broad write ACLs). No network, cloud service or internet is used; copying the directory to removable or write-once media is the offline anchoring step, and `audit-verify --checkpoint-dir <copy>` verifies against any copy.
- A checkpoint is written **after every commit** (`MaxUnanchoredEvents` = 0). Checkpoints only move forward; the same sequence with another hash is refused as a fork.
- **Fail-safe.** If anchoring fails after a commit, the mutation stays committed (it cannot be undone) and the failure is logged (reason code only); the *next* audited mutation first tries to catch the checkpoint up and is refused (`503`) if it cannot, so the unanchored window never exceeds `MaxUnanchoredEvents` (0..1000; raise it only if you accept a larger window and want to tolerate brief storage outages). Before every first write of a transaction the head is also re-verified against its MAC and the newest checkpoint: a damaged head, a stream shorter than its checkpoint (deleted tail, restored older database), an emptied stream with checkpoints or a head that contradicts its checkpoint refuses all new events. The chain is **never reset or silently extended**; an operator investigates, restores or consciously re-baselines.
- **Configuration** (environment variables; none have defaults and none are committed): `Hasm__Audit__KeyDirectory`, `Hasm__Audit__ActiveKeyId`, `Hasm__Audit__CheckpointDirectory`, optional `Hasm__Audit__MaxUnanchoredEvents`. `Hasm__Audit__AllowInsecureFilePermissions=true` exists only for disposable test environments. Invalid or missing settings are reported by setting name, never by value. The API still starts without them (anonymous endpoints work) but every audited mutation returns `503 audit_unavailable`.

### Upgrade and compatibility
The migration only adds a table (repeatable: checksummed, run once, a no-op afterwards). An upgraded installation keeps all `AccessAudit` rows untouched; the chain of each stream starts at the first event written after the upgrade (genesis prev hash). Rows from before that point cannot be authenticated retroactively; verification reports them as *legacy, unauthenticated* (a note, not an error). Runtime database grants to add: `SELECT, INSERT` on the audit-event table (physical name in `SystemSchema.AuditEvent`) and `SELECT` on it for the account that runs `audit-verify`; no `UPDATE`, `DELETE` or `TRUNCATE` for any application account.

### Verification tool (read-only)
```
export Hasm__Database__Host=… Hasm__Database__SystemDatabaseName=… Hasm__Database__Username=… Hasm__Database__Password=…   # runtime (least-privilege) account; no admin account is needed
export Hasm__Audit__KeyDirectory=/secure/keys Hasm__Audit__CheckpointDirectory=/mnt/audit-anchor
dotnet run --project src/backend/Hasm.Admin -- audit-verify system
dotnet run --project src/backend/Hasm.Admin -- audit-verify <company-id>                       # or company:<id>
dotnet run --project src/backend/Hasm.Admin -- audit-verify <company-id> --checkpoint-dir /media/offline-copy
```
It runs in a READ ONLY, snapshot-consistent transaction and never repairs, rewrites or deletes anything. It prints the stream, the verdict, the record count and range, the **verified range** (contiguous prefix whose records are fully authenticated), checkpoint counts, unanchored records and findings (code, sequence number, fixed message). It never prints keys, credentials, connection details, physical names or event payloads.

| Exit code | Meaning |
|---|---|
| 0 | **Verified**: chain, authentication codes and checkpoints all check out and the head is anchored |
| 6 | **Failed**: tampering or corruption detected (see findings) |
| 7 | **Incomplete**: nothing contradicts the evidence but integrity cannot be proven (missing key or checkpoint, unanchored tail, unreadable checkpoint line, unknown format) |
| 1 / 2 / 3 | operational failure / usage / bad configuration (as for the other commands) |

Findings: failures `seq_gap`, `seq_order`, `link_broken`, `hash_mismatch`, `mac_invalid`, `stream_mismatch`, `checkpoint_mismatch`, `checkpoint_unmatched`, `tail_truncated`, `checkpoint_mac_invalid`, `checkpoint_chain_broken`, `checkpoint_order`, `projection_mismatch`/`projection_missing`/`projection_unchained`; incomplete `key_missing`, `checkpoint_key_missing`, `no_checkpoints`, `unanchored_tail`, `checkpoint_unreadable`, `unsupported_format`; note `legacy_unprotected_rows`.

`audit-anchor <stream> [--establish-baseline]` writes the current head of an otherwise **sound** stream to the checkpoint store; it refuses (exit 6) if the stream shows any failure or unverifiable record, and never writes to the database. Catching up an unanchored tail needs no flag. When **no** checkpoint exists at all it refuses unless `--establish-baseline` is given, because anchoring then defines what is trusted from now on (a stream whose tail was deleted together with the checkpoints looks perfect): review the stream and compare with any offline copy first. The same rule applies at runtime: if events exist but no checkpoint does (store wiped, replaced, or the very first anchor never succeeded) audited mutations are refused with `audit_baseline_missing` until an administrator establishes the baseline. `audit-keygen <key-id>` creates a key (above).

*Scheduling later (not implemented):* run `audit-verify system` and each company from cron / a systemd timer or Windows Task Scheduler (e.g. nightly), alert on any non-zero exit (6 = incident, 7 = investigate evidence), and copy the checkpoint directory to offline media after each run. A scheduled in-process verifier or an alert channel is future work.

### Crash consistency and recovery
| Situation | Behaviour |
|---|---|
| PostgreSQL commits, checkpoint write fails (storage down, full, permissions) | The mutation and its event stay committed. The failure is logged (reason code). The stream is **Incomplete** (unanchored tail) until anchored; the next audited mutation first tries to catch up and is refused with `503` if it cannot. |
| Process dies after commit, before or during the checkpoint write | Same as above on restart: committed data is preserved, the next verification reports `unanchored_tail` (never Verified), the first audited write after restart anchors the head if the store works. A torn checkpoint line is ignored by readers (reported `checkpoint_unreadable`, Incomplete) and the next append starts on a fresh line. |
| Process dies before commit | Nothing is persisted: no event, no mutation, no sequence gap, no checkpoint (checkpoints are written only after a successful commit). |
| Ambiguous commit (connection lost during COMMIT) | If it committed, it is treated as the first case; if not, as the previous one. |
| Checkpoint store wiped, replaced or empty while events exist | No silent re-baselining (`audit_baseline_missing`; see `audit-anchor`). |
| Checkpoint ahead of the database, head differing from its checkpoint, damaged head | New events refused; nothing is repaired automatically. |
Verification never reports **Verified** unless every record's hash and MAC check out, the sequence is contiguous from 1, the head is covered by a valid checkpoint, and no key, checkpoint or format is missing. An empty stream beside unauthenticated history (projection rows, users) is **Incomplete** (`no_authenticated_history`), not Verified. Events written in the window between commit and anchoring (at most `MaxUnanchoredEvents`, default 0 before the next write is refused) are the only ones whose silent loss could go unnoticed if an attacker also removes the matching checkpoints.

### Checkpoint trust boundaries
Storing checkpoints outside PostgreSQL does **not** make them immutable: they are ordinary files. What they add is a second place an attacker must also reach.
- **Who can touch the files.** The API/Admin service account creates the directory and appends; it necessarily has write access to the files, so a compromised API process **can** alter or delete previous checkpoints (the code only appends, but the account could do more). Other unprivileged OS accounts have no access (Linux: refused if group/other-writable; Windows: refused if Everyone/Users/Authenticated Users can write). Root / local Administrators can read, alter or delete anything, including keys.
- **Database administrator** (database access, no OS access to the application host): can alter or delete records but cannot produce valid codes without the key and cannot rewrite checkpoints, so tampering, deletion and tail truncation are detected. **Not** protected if the checkpoint directory or key directory is on the database host or readable/writable by the DBA's account. Keep keys and checkpoints off the database server.
- **Compromised OS administrator of the application host:** not protected (keys, checkpoints and the running process are all in reach). Only checkpoint copies already taken to independent offline media bound what they can rewrite (everything up to the last offline copy remains checkable).
- **Optional OS hardening (not implemented, recommended):** on Linux make each checkpoint file append-only for the service account (`chattr +a`, set by root after the first append of a stream) or keep the directory on a mount the service can only append to; on Windows grant the service account "append data" but not "delete"/"write attributes" on the files via NTFS ACLs. Verify that the service still works before relying on it.
- **Offline backup to an independent protected destination (no cloud, no new service).** Checkpoint files are append-only, so each copy must be a *prefix-compatible superset* of the previous one: (1) after each `audit-verify` run, copy the checkpoint directory to removable media (or a write-once / read-only-mounted disk) kept in a different place from the database backups and the key backup; (2) before overwriting an older copy confirm the new file begins with the old one (`cmp -n <old size> old new` on Linux, `fc /b` or a hash of the old byte range on Windows) and keep both generations; (3) record the file size and SHA-256 of each copy in a signed or physically secured log; (4) periodically run `audit-verify <stream> --checkpoint-dir <copy>` (read-only) from a trusted machine that holds a key backup; (5) store the key backup apart from the checkpoint copies, because the key alone lets someone forge checkpoints and the copies alone are useless to them. A copy older than the attacker's actions is the only evidence that survives a full compromise of the host.
- **HMAC, not signatures.** Checkpoints and events are authenticated with a shared secret (HMAC-SHA-256). Anyone who holds the key can create valid records and checkpoints; verifying them needs the same secret. This is *not* a public-key digital signature: it gives no third-party verifiability or non-repudiation. A public-key scheme (ECDSA) would let auditors verify without holding a forging capability and is future work.

### Database roles
The migration/administrative account (`AdminUsername`) owns the audit table; the API runtime account (`Username`) must **not** own it and must hold only `SELECT, INSERT` on it (no `UPDATE`, `DELETE`, `TRUNCATE`, no DDL). `audit-verify` runs under the runtime account and adds the informational finding `verifier_account_can_modify_audit` when the connected account owns the table or holds one of those privileges, so a mis-granted runtime role is visible. Do not give the runtime account membership in the owning role.

### What is and is not detected
| Scenario | Result |
|---|---|
| Modified payload, timestamp, actor/target, event type, id, key id, legacy ref, stream/company, sequence | Detected (hash mismatch; a recomputed hash still fails the MAC) |
| Inserted event (end or middle) without the key | Detected (`mac_invalid`, gap, checkpoint disagreement) |
| Reordered events | Detected |
| Deleted middle event | Detected (gap, broken link, unmatched checkpoint) |
| Deleted **tail** events / whole table truncated / database restored from an older backup | Detected **only through the external checkpoints** (`tail_truncated`) and refused at the next write; a database-only chain cannot show it and reports `Incomplete` without checkpoints |
| Broken chain link; swapped key id; unknown format version | Detected / reported unverifiable |
| Altered, removed, reordered or forged checkpoints | Detected (MAC, chain) |
| Newest checkpoints removed from the file | Reported as an *unanchored tail* (Incomplete), indistinguishable from an anchoring lag; the chain itself still verifies. Compare with an offline copy |
| Tampering with the readable `AccessAudit` projection | Detected through the authenticated events (mismatch, missing row, unchained row) |
| Pre-upgrade `AccessAudit` history | **Not authenticated**; reported as legacy |
| An attacker who holds the audit key **and** database access **and** the checkpoint directory (and its offline copies) | **Not protected**: they can rebuild a consistent chain and checkpoints. This includes a compromised server administrator controlling all keys, checkpoints and backups |
| An attacker with the key and database access but without the checkpoint store | Can forge records, but cannot make the new head match old checkpoints without rewriting those too; anything newer than the last offline copy is exposed to rewriting |
| Loss of every copy of a key; deletion of both database and checkpoints and backups | Evidence is lost (not forgeable, but unrecoverable) |
| Events never written because the application skipped auditing (a bug) or a mutation done directly in SQL | Not detected (only mutations through the audited code paths are covered) |
| Reading audit data, denial of service, host compromise of the running API | Out of scope |
| Timestamps | Come from the Backend clock; the chain proves they were not changed, not that the clock was right |

### Operational limits of this phase
- **Several API instances** may share one checkpoint directory only on a filesystem with reliable exclusive file locking (a local disk, or a correctly configured share); each append holds an exclusive handle across "read newest checkpoint" and "append". Multi-host locking over network filesystems was not tested.
- The checkpoint files grow by about 330 bytes per audited commit and are never rotated or pruned yet (rotation must keep the chain: archive whole files only).
- No export for auditors, no scheduled/in-process verification and no alerting yet; the offline copy of the checkpoint directory is a manual step.
- HMAC verification requires the secret on the verifier's host (see trade-offs); there is no public-key verification yet.
- Audit-table ownership stays with the account that ran the migration; the runtime role privilege rules are under "Database roles" (reported, not enforced).
- A first anchor that never succeeded (bad checkpoint directory at the very first write) leaves events without any checkpoint: an administrator must run `audit-anchor --establish-baseline` after fixing the storage.
- Only mutations that go through `AccessService`/`IdentityStore` are audited; future modules must append their own events in their transactions (extension point above).

## System runtime account: least privilege for the TOTP secret store (owner decision D-235, register item M2-TOTP)
Scope: the privileges of the API runtime account (`Hasm__Database__Username`) on the SYSTEM database, as reviewed code, with a fail-closed check for the TOTP secret store. It closes review M2 of PR 133 for the runtime account. **Second layer (system migration 0035, provisional number):** a BEFORE UPDATE trigger on the TOTP table refuses any change of the secret material (cipher, nonce, tag, key id) unless the role that runs the statement is the table owner or a member of it; so even a runtime account wrongly granted `UPDATE` on those columns, with the session flag `hasm.totp_rewrap` on, cannot replace a secret. The migration is additive (one function, one trigger; the function of 0031 is not replaced and its flag check stays as a further layer), reads no catalog table (the owner is recognised through the `information_schema` table-privileges view, which lists a row granted by a role to itself only for the owner and shows it only to that role and its members, plus the allowed `pg_has_role`), and has none of the constructs the migration guard of PR 188 refuses. The owner-account rewrap (`MfaStore.RewrapAsync`) is unchanged and works.

* **The catalog (`SystemRuntimePrivileges.Tables`).** One entry per system table (a unit test fails when a table has none). It turns the DBA grants documented in the sections above (Phase 2.3A, 2.3B, 2.3C-2, 3.1A-2, 3.9A) into code and grants nothing beyond them. Tables that had no documented grant: `CostCenterAssignment` and `MfaChallenge` (what the API services do with them), the TOTP secret store (below), and the two backup-retention tables and the system `migration_journal` (NOTHING: only the administrative tool uses them). The registry is `SELECT` plus `UPDATE` on the three projected display-name columns only. Two UPDATEs are narrowed to columns (review round 1, L3): `CostCenterAssignment` to its two revocation columns (what `AccessService` updates when it ends an assignment) and `MfaChallenge` to the attempt counter and the consumption time, with `DELETE` kept for the expired-challenge purge that the identity housekeeping runs every hour (`IdentityHousekeepingService`; it was dead code before).
* **The TOTP secret store.** `SELECT`, `INSERT`, and `UPDATE` ONLY on the state, confirmation time, last accepted step and failure counter. No `UPDATE` on the cipher, nonce, tag, key id or identity columns, no `DELETE`, `TRUNCATE`, `REFERENCES`, `TRIGGER`. The runtime account must read the ciphertext (it verifies codes); it can never replace it. Rewrap is an owner-account operation (`MfaStore.RewrapAsync` has no caller in the API and no admin command yet).
* **Why not a migration.** The runtime account's name is deployment configuration; a migration may not build SQL dynamically (migration guard), and the migration account cannot create a fixed group role (roles are cluster-wide; the account is `NOCREATEROLE`). The grants are therefore code, applied by a command.
* **`Hasm.Admin grant-system-runtime`** (owner account; no arguments). In one transaction: revokes everything the runtime account and `PUBLIC` hold on the schema, the tables and the sequences of the system database (the runtime account's revokes with `CASCADE`, so a privilege it passed on `WITH GRANT OPTION` goes with its own and the command converges; `PUBLIC` loses USAGE and CREATE on the schema as in the company twin, so a role that needs USAGE on the schema is granted it explicitly), grants exactly the catalog, verifies it, and prints the remaining findings (codes and logical table names only). It never creates a role or sets a password (the DBA creates the login role: `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`), never names or changes the owner, and refuses, changing nothing, when: the runtime account is the administrative account (`runtime_account_is_admin_account`), does not exist (`runtime_account_unknown`), is a superuser or has BYPASSRLS (`runtime_account_is_superuser`), is a member of ANY role (`runtime_account_has_role_membership`) or owns system objects (`runtime_account_is_owner`); the database is not a migrated system database, in particular a company database (`not_a_system_database`, `system_database_not_migrated`); or the connected account is not the owner (`not_the_owner_account`). Safe to re-run. **Run it after `init-system-db`, after every system migration that adds a table, and after restoring a system database** (what a restored dump does with the grants is NOT verified yet). It does not revoke what an operator granted to OTHER roles: it reports them. Exit 0 = least privilege; 1 = refused or a violation remains. **Not audited** (the same recorded limitation as `grant-company-runtime`; follow-up: audit both grant commands).
* **The check (`SystemRuntimePrivileges.FindAsync`).** Violations (refused): `runtime_superuser`, `runtime_reads_all_data` (member of `pg_read_all_data` or `pg_write_all_data`), `runtime_role_membership` (ANY membership of the runtime account, as the company twin: it can `SET ROLE` to the role or inherit from it, which for a superuser role is every table), `runtime_role_attributes` (CREATEDB, CREATEROLE, REPLICATION), `runtime_owns_objects`, `runtime_owns_database`, `runtime_schema_create`, `totp_owned_by_runtime`, `totp_runtime_overgrant` (anything beyond the catalog on the secret store, table or column level, and any privilege held `WITH GRANT OPTION`), `totp_reader_all_data` and `totp_writer_all_data` (another non-superuser role that reads or writes every table through `pg_read_all_data` or `pg_write_all_data`: the usual way a BI role is set up, now refused like an explicit grant), `totp_other_grantee` (ANY other role or `PUBLIC` holds a table or column privilege on the secret store), `totp_reader_by_membership` (another non-superuser role can act as the owner or the runtime account), `runtime_account_unknown`. Notes (reported, never refused): `overgrant:<Table>` for the other system tables and `uncatalogued_table_access`. Not aligned with the company twin on purpose: database-level CONNECT, CREATE and TEMPORARY (PUBLIC holds them by default, other roles need CONNECT; changing them could lock out a legitimate role). **"Reporting roles"** in the owner's decision is read as: every database role other than the table owner and the configured runtime account (the team's reading; no reporting role exists in the product).
* **The gate (`SystemRuntimeGate`).** It asks the check with the ACTUAL connected role (`current_user`). At start-up (`SystemRuntimeGateService`): a violation stops the API from starting (critical log line `REFUSED` with the codes). If the database is not configured or not reachable at start-up the API starts as before, and the MFA store applies the same gate on its connections (cached for 60 seconds; a violation answers 503 `service_unavailable`), so the secret store is never used unchecked. MFA enforcement is unchanged: nothing is downgraded, a refusal fails closed.
* **Opt-out `Hasm__Database__AllowOverprivilegedSystemRuntime=true`** (default false; the twin of `AllowOverprivilegedCompanyRuntime`): for disposable single-account test environments only. The refusal becomes a critical log line (`UNSAFE`, with the codes) at start-up and on every check; it is never silent. The PostgreSQL test assembly sets it once (`TestAssemblyDefaults`) because its suites run with one account.
* **Upgrade step for an existing installation (start-up behaviour change).** An installation whose runtime account is the administrative account no longer starts. Create a separate login role, set `Hasm__Database__Username/Password` to it, run `grant-system-runtime`, then start the API.
* **Residual risks (recorded).** The API process holds the key ring and `SELECT` on the ciphertext: database privileges do not protect against a compromised API process. A superuser reads every table whatever the grants say (the check refuses a superuser or BYPASSRLS runtime account and any runtime membership, and refuses other non-superuser roles that are members of `pg_read_all_data` or `pg_write_all_data`; it cannot prevent a superuser). The enrolment-code hash is a column of the user table, outside the secret store. **After a restore, rerun `grant-system-runtime`; until then the API fails closed** (backup dumps use `--no-privileges`, so a restored system database carries no runtime grants); a test of a restored system dump is a follow-up. **Not tested at database level:** a real superuser or BYPASSRLS role and a real member of `pg_read_all_data` or `pg_write_all_data` (the role administrator of the test clusters is `CREATEROLE` only: it cannot create a superuser or grant a predefined role). The rules are tested with ordinary roles instead: any membership of the runtime account is refused (so a membership of a superuser role is refused whatever the role is), and the two database-wide roles are parameters of the check, which the test sets to stand-in roles.
* **Tests.** Unit: `SystemRuntimePrivilegesTests`. PostgreSQL with a real restricted login role (role-capable disposable cluster, `PostgresRoleFact`): `SystemRuntimeLeastPrivilegeTests`.

## Company runtime foundation (Phase 3.1A-1)
Scope: how the API reaches a company database with least privilege, the company schema version gate, the administrative commands that provision and upgrade company databases, and the company-business cryptographic audit stream. **Not** in scope: company profile or settings tables, branches, warehouses, fiscal years, accounting, inventory, UI, licensing (later phases). No business endpoint exists yet; the only HTTP change is that `/api/v1/company` joins the `no-store` paths, and unexpected company-database failures return one generic `503 {"error":"company_unavailable"}`.

### Runtime connections (`CompanyDatabaseResolver`)
`OpenAsync(companyId)` resolves the company through the existing `Hasm_System` registry (runtime account), requires state `Ready` (anything else is refused before any connection, and nothing is created), reads **that company's own credential**, and opens a pooled connection with that company's own PostgreSQL role. The connection string is built from the opaque physical database name; names, roles, hosts and secrets never appear in exceptions, API responses or logs (only short codes such as `company_database_unavailable` and the company id are logged). Failures are `CompanyDatabaseException` with a code: `company_not_found`, `company_not_ready`, `company_database_unavailable`, `company_runtime_not_provisioned`, `company_schema_unmigrated`, `company_schema_incompatible`, `company_runtime_overprivileged`.

- **Pooling is bounded**: `Hasm__Database__CompanyMaxPoolSize` (default 10, 1-50) connections per company, `Min Pool Size=0`, idle connections closed after 60 s, 5 s connect timeout, 30 s command timeout. The role's PostgreSQL `CONNECTION LIMIT` is `CompanyMaxPoolSize + 2`, so the bound is also enforced by PostgreSQL. Size `max_connections` for companies x pool size.
- A successful registry/credential lookup is reused for 15 s and a successful schema check for 60 s (an authentication failure drops the cached lookup and retries once). **What the cache does and does not delay:** it holds only the company registry state and the credential/connection string (and the schema-gate result). It is **not** part of authentication, sessions or RBAC: users, sessions, membership, roles and permissions are re-read from `Hasm_System` on every request by `AuthService`/`AccessService` (no authorization cache, as established in Phase 2.3B), so session and permission revocation remain immediate. Residual delays: (1) a company state change away from `Ready` would reach company-database access after up to 15 s (no such transition exists today: `Ready` is terminal; a future suspend/archive feature must either shorten this, call `Forget`, or be enforced in the authorization path); (2) a rotated credential is used after up to 15 s, and an old password fails closed; (3) a `REVOKE CONNECT` or role change applies to new connections at once, while already-pooled connections of that role live until recycled (idle 60 s, otherwise until `DROP`/`pg_terminate_backend` by a superuser); (4) a schema change (for example an over-privilege fix or a newer database) is noticed within 60 s.
- A credential whose user name is not the company's expected role is refused before connecting, so a misplaced credential file cannot open another company.

### Schema version gate (`CompanySchemaGate`)
Run on first use of a company (and every 60 s). It rejects, with a safe code and no SQL or names: a database without the migration journal or with migrations the backend knows but the database lacks (`company_schema_unmigrated`), a database with a migration this backend does not know or an edited migration checksum (`company_schema_incompatible`: a newer database is never written by an older backend), an identity row that is not this company's (`company_schema_incompatible`), a runtime role that cannot read the schema state or read/append the audit table (`company_runtime_not_provisioned`), and, **unless `Hasm__Database__AllowOverprivilegedCompanyRuntime=true`** (disposable test servers only), a runtime principal that is a superuser/owner/has DDL, create, membership or audit-modifying rights (`company_runtime_overprivileged`). Company databases created before this phase upgrade safely: they report `company_schema_unmigrated` until `migrate-companies` has run (it applies migration 0002 only; no existing data is touched).

### Database isolation and privilege model
Each company has its own login role (`hasm_rt_<32 hex>`, derived by a one-way hash from the opaque database name; roles are cluster-wide, the prefix makes them recognisable). **Isolation is enforced by PostgreSQL, not by the application:** `CONNECT` is revoked from `PUBLIC` on the company database and granted to that company's role only, so company A's login is refused (`42501`) on company B's database. Verified with real distinct principals (see Tests).

| The runtime role | Granted |
|---|---|
| Database | `CONNECT` on its own company database only (no `CREATE`, no `TEMPORARY`) |
| Schema `public` | `USAGE` only (no `CREATE`) |
| Identity binding table, migration journal | `SELECT` |
| Business audit table | `SELECT`, `INSERT` only |
| Never | ownership of the database, schema or any object; DDL; `UPDATE`/`DELETE`/`TRUNCATE`/`REFERENCES`/`TRIGGER` on audit; superuser, `CREATEDB`, `CREATEROLE`, `REPLICATION`, `BYPASSRLS`; role memberships; any privilege in another company or the system database |

The privileges are code (`CompanyRuntimePrivileges.Tables`); `grant-company-runtime` strips everything the role and `PUBLIC` hold on the company's tables and re-grants exactly that list, so re-running converges whatever earlier builds granted. Later phases append their business tables there with the least privileges the services need. Defence in depth: even with an accidental `UPDATE`/`DELETE`/`TRUNCATE` grant, the append-only triggers refuse (row triggers act when rows exist) and the API gate refuses an over-privileged role. The role cannot disable the triggers (not the owner). The runtime role also does not own the audit table (the migration account does), and `audit-verify` run under it no longer reports `verifier_account_can_modify_audit`.

**What PostgreSQL cannot do here:** a role that may `CONNECT` to a database through `PUBLIC` (by default the system database and `postgres`) can connect but holds no table privileges there; operators may additionally `REVOKE CONNECT ... FROM PUBLIC` on the system database after granting it explicitly to the system runtime account, and should restrict `pg_hba.conf` by database and role (`hostssl <database> <role> <address> scram-sha-256`). Global PostgreSQL settings are never changed by this software.

### Credential handling and rotation
- The password is generated by `grant-company-runtime` (256-bit CSPRNG, URL-safe), handed to PostgreSQL only as a **SCRAM-SHA-256 verifier** (so the plaintext never reaches the server statement log or `pg_stat_activity`), and written once to `<Hasm__Database__CompanyCredentialDirectory>/<company-id>.hcred` (JSON, created owner-only: `0600` file, restricted ACL on Windows; the API refuses group/world-accessible credential files). The file is staged privately and moved into place atomically, **before** the grants are applied, so a later failure never loses it. It is never printed, never logged and never stored in an application table (`CompanyRegistry` has no credential column).
- The directory may be a mounted secrets-manager volume; back it up like the audit keys (a lost credential is replaced by `--rotate-credential`, not recovered). Restrict it to the API service account.
- **Rotation failure and recovery:** the new password is staged in a private temporary file first, PostgreSQL is changed, then the file is atomically moved into place. If PostgreSQL accepts the new password but the file cannot be installed, the command **restores the previous password** from the still-installed credential (the installed file then remains valid) and exits 1 with `credential_install_failed` saying so. If the previous password is unknown (a newly created role, or an unreadable file) or the restore fails, the command exits 1 with `credential_install_failed` stating that the API cannot log in for this company and that the fix is to repair the credential directory and run `grant-company-runtime <id> --rotate-credential` again (generates a fresh password; idempotent). The staged temporary file is always removed, so no stray plaintext remains. The API fails closed meanwhile (`company_database_unavailable`, authentication failure logged by code only). Covered by two role tests.
- **Rotation:** `grant-company-runtime <company-id> --rotate-credential` sets a new password and replaces the file; the API picks it up within 15 s (or on its next authentication failure), and existing pooled sessions end when their connections are recycled. Plan it with the TLS/secrets process of the deployment; rotate after any suspected disclosure and when staff with access leave.
- A role that already exists (pre-created by a DBA) is **adopted only when safe** (no superuser/createdb/createrole/replication/bypassrls attributes, no memberships); otherwise the command stops (`role_unsafe`). If the DBA set its password, install the credential file by hand or rotate.
- Transport: the TLS rules of the system database apply unchanged (`VerifyFull` by default; non-validating transport only through `AllowInsecureTransport` on disposable servers).

### Administrative commands (`Hasm.Admin`, privileged; never started by the API)
```
dotnet run --project src/backend/Hasm.Admin -- migrate-companies [--company <id>]
dotnet run --project src/backend/Hasm.Admin -- grant-company-runtime <company-id> [--rotate-credential]
dotnet run --project src/backend/Hasm.Admin -- audit-verify business:<company-id> [--checkpoint-dir <dir>]
dotnet run --project src/backend/Hasm.Admin -- audit-anchor business:<company-id> [--establish-baseline]
```
**`migrate-companies`:** applies pending forward-only, checksummed company migrations (each in its own transaction) to every `Ready` company, or one. Per company: the same per-company session advisory lock as provisioning (a busy company is reported `Busy`, not waited for), the database must carry that company's identity (a foreign database is `Failed [consistency]` and untouched), a newer/edited journal is `Failed [migration]`. A failure in one company never stops the others and never undoes them: the output lists one line per company (`Migrated (applied 0002)`, `UpToDate`, `NotReady` (skipped, use `provision-company`), `Busy`, `Failed [code]`) and a summary. Exit codes: 0 all current, 1 total failure, 4 busy, **8 partial failure** (some companies migrated, some failed). Idempotent; it never deletes or drops anything and uses only the admin account.
**`grant-company-runtime`:** requires a `Ready`, fully migrated company; creates the role if missing, writes the credential (new role or `--rotate-credential`), applies the privilege list above, then **proves** it: re-reads the catalog (`role_attributes`, `role_membership`, `owns_*`, `*_modifiable` ... must all be absent) and exercises the API's own login and schema gate with the installed credential. Exit 0 only when that succeeds; 1 for any failure (`role_unsafe`, `schema_unmigrated`, `privilege_verification_failed`, `runtime_login_failed`, `role_privilege_required`); 4 busy. Only the selected company's role and database are touched. Output never contains the password, database or role names; PostgreSQL errors print the SQLSTATE only.
**Privilege separation / prerequisite:** creating a role needs `CREATEROLE`. The intended path is a dedicated, non-superuser account that holds only `CREATEROLE`, configured as `Hasm__Database__RoleAdminUsername` / `RoleAdminPassword` (used only to create/alter the runtime role); the grants themselves are issued by the database owner (the `AdminUsername` account that provisioned the database), and the API holds neither. Without it the command stops with `role_privilege_required` and leaves nothing behind; alternatively the DBA creates the role (`CREATE ROLE "<name>" LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION`) and the command adopts it. `CREATEROLE`/`SUPERUSER` are never granted to the ordinary test account. On PostgreSQL 16+ a `CREATEROLE` account can only hand out attributes it holds itself, which is why the runtime roles carry none.
**Upgrade of an existing installation:** 1) deploy the new backend (company databases report `company_schema_unmigrated` and the API refuses them safely); 2) `init-system-db`; 3) `migrate-companies`; 4) `grant-company-runtime <id>` for each company (and again after any later migration that adds tables); 5) set `Hasm__Database__CompanyCredentialDirectory`. Run step 4 after step 3 for every migrated company: until then the gate reports `company_runtime_not_provisioned`.

### Company-business cryptographic audit (revised Option B)
Company business mutations and their authenticated audit events are committed by **one PostgreSQL transaction in the company database**; the event table lives next to the data it protects, so nothing can commit without its event or the reverse (no cross-database transaction, no outbox).
- **Company migration 0002** adds one append-only table (physical names in `CompanySchema.BusinessAudit`; `UPDATE`/`DELETE`/row triggers and a `BEFORE TRUNCATE` trigger raise `audit events are append-only` even for the owner; a `BEFORE INSERT` trigger refuses an event whose company is not the one bound in the identity table; checks pin the stream to exactly `business:<company-id>`, event types >= 1000, 32-byte hashes; `PUBLIC` has no access). No foreign keys (users live in the system database). It is the only table the runtime appends to; the migration contains no grants.
- **Reuse, not duplication:** the same `AuditCanonical` format (version 1, unchanged), HMAC-SHA-256 event keys, per-stream hash chain, checkpoint files (`FileCheckpointStore`), `AuditVerifier` and anchoring. The only new abstraction is `AuditTableMap`, chosen from the stream (`AuditStream.ForBusiness`), which parameterises table and column names; the system tables and their streams (`system`, `company:<id>`) are unchanged and untouched, and no existing event is rewritten.
- **Stream-domain separation:** the stream key `business:<company-id>` is inside every authenticated record and checkpoint, so genesis hashes, sequence numbers, advisory locks, checkpoint files (named by a hash of the key) and MACs are independent of the access stream `company:<id>`; a business record relabelled to another stream fails verification (`hash_mismatch`). Business events use only the reserved range 1000+ (earlier phases register their types there) and carry no legacy projection.
- **Atomic append for services:** `CompanyAuditedTransactions.ExecuteAsync(companyId, work)` opens the company through the resolver, runs `work` in one transaction (`CompanyAuditedWork.Connection/Transaction`, `AppendAuditAsync`), appends the events inside it, commits once and then anchors the new head in the checkpoint store. An exception rolls back both; a mutation that appends no event is refused and rolled back; if the audit cannot be written (key, checkpoint store, damaged chain) the business change is not committed. Take business locks first: the stream lock is taken last.
- **Fail-closed integrity (unchanged behaviour):** a missing baseline (`audit_baseline_missing`), a stream shorter than its checkpoint (`audit_stream_truncated`), a fork, a damaged head or a checkpoint failure beyond the allowed lag refuse the next audited mutation; `audit-anchor business:<id> --establish-baseline` is the deliberate human decision.
- **Verification and anchoring:** `audit-verify` / `audit-anchor` accept `business:<company-id>` and connect with that company's runtime credential (never an owner/admin account); output and exit codes are those of the other streams.
- **Restore limitations (important):** a company database restored from an older backup rolls its business stream back while the external checkpoints stay ahead, so verification reports `tail_truncated` and the next audited write is refused (`audit_stream_truncated`) - correct and safe, but **there is no controlled restore procedure yet**. A future phase must add an explicit, audited *restore acknowledgement* (who restored what, to which sequence, authorised by a privileged administrator and recorded in the system stream) that starts a new checkpoint epoch instead of an administrator editing checkpoints by hand. Until then restoring a company database requires a manual, supervised procedure outside this software, and the registry (`Hasm_System`) and the company database must be restored to consistent points. The checkpoint directory and its offline copies remain the only protection against deletion of the stream tail (see "Cryptographic audit integrity").

### Production blockers recorded by this phase
1. **No cryptographic audit of runtime provisioning.** `grant-company-runtime`, credential rotation and `migrate-companies` are privileged operations that are not yet written to any audit stream (only operator logs and the exit status exist). Before production they must (a) be authorized: executable only by an identified, authorized privileged administrator (not merely anyone holding the admin database account), with separation between who can rotate credentials and who can read them; (b) append HMAC-chained events (actor, company id, action, outcome code; never secrets or names) to the system stream in the same transactional discipline as other audited changes, including failed and partial attempts; (c) alert on rotations and on `role_unsafe`/`runtime_login_failed`. Event types for this must be reserved in the 1000+ range.
2. **No controlled restore acknowledgement** (see restore limitations above).
3. **Credential storage and rotation policy** are deployment work (secrets manager, schedule, backup, access list); files are protected by OS permissions only.
4. **`pg_hba.conf` per database and role, TLS and `PUBLIC` connect on the system database** are documented recommendations, not enforced by the software.
5. **Company state changes are not enforced instantly in the company-database path** (15 s cache, see above) - acceptable while `Ready` is terminal; must be revisited before any suspend/archive/delete feature.
6. **The CI workflow has never run on GitHub**: the 338-test table, the `CREATEROLE` test account and PostgreSQL 16 behaviour of the role tests (verified locally on PostgreSQL 18 only) are first exercised by the pull request.

### Migrations (forward-only, checksummed)

### Authorization, audit and history
Permissions are re-read from `Hasm_System` on every call (no cache) and checked for the selected company; a cross-company id is never accepted. Every mutation runs in `CompanyAuditedTransactions`: change + `ConfigRevision` + authenticated audit event commit or roll back together (an unwritable audit, as proven by tests, leaves nothing saved). Events (business stream): 1000 profile created, 1001 updated, 1002 settings created, 1003 updated, 1004 currency enabled, 1005 disabled, 1006 base currency set. **Sensitive fields (registration/tax numbers, address lines, postal code, phone, email, website) are recorded as "changed" only - their values are never written to the audit event or the history**; permitted fields (names, legal name, country, city, region, settings, currency flags) keep before/after in `ConfigRevision`. The audit `Detail` carries the field names, the revision and a SHA-256 prefix of the history JSON (a tamper-evident link). Authorization (system database) and the company transaction are different databases: a permission revoked in the instant between the check and the commit is not seen by that one in-flight request.

### Display-name projection
The company database is authoritative. After a successful commit the service writes both names to the registry `WHERE display_name_revision < @rev` (monotonic: a delayed update can never overwrite newer data). A failure is logged by code and company id only, reported as `projection:"pending"` and never undoes the committed change; any later authorized profile read or the sync endpoint re-projects. `/companies` returns only the caller's own active memberships with the two projected names (a null name = not projected yet; the UI shows a neutral label, never an identifier). Residual: a company nobody opens stays un-projected until someone reads its profile. **Authorization of the registry write:** the system runtime account must hold column-level `UPDATE` on exactly the three projection columns (`SystemSchema.Company.DisplayNameAr/En/Revision`) and nothing broader on the registry (`GRANT UPDATE (<three columns>) ON <registry table> TO <runtime account>`, issued by the database owner; this software never grants it and never changes global PostgreSQL settings). A registry trigger (system migration 0006) enforces the monotonic rule inside PostgreSQL: the revision can never decrease and the names change only with a newer revision, so even a compromised runtime account with that grant cannot roll a projection back or alter a name silently (it can still overwrite the display names of any company with a higher revision number - a display-only integrity limitation, because the API holds no per-company authority over the registry).

### Base currency and the financial-history lock contract
`IFinancialHistoryProbe` (per required domain: `general_ledger`, `inventory_valuation`, `opening_balances`) is evaluated inside the configuration transaction. **No real probe exists yet: every domain is a registered placeholder reporting `Implemented=false`**, so today nothing can lock the base currency (an empty fiscal year never does, by design) and the API/UI say so (`checksImplemented:false`). `FinancialHistoryGuard` replaces a placeholder only for its own domain, an unknown domain cannot hide a required one, and `ConfigurationSchemaContractTests` fails when a company migration creates a table outside the approved list - the PR adding a financial table must register its probe. The same contract governs changing an established business time zone.

### Release blockers recorded by this phase
1. **No field-level encryption at rest** for registration/tax identifiers, address and contact data (no approved key-management design); they are stored as plain text protected by company-database isolation, never logged, audited or written to history.
2. **Trial restrictions** listed above are unenforced.
3. **Base-currency / time-zone lock probes are placeholders** until the accounting and inventory modules exist.
4. **Currency dataset v1 must be verified against the current ISO 4217 amendment** before release (names, numeric codes, exponents, withdrawn currencies).
5. **Desktop credential storage** is memory-only; no OS credential store, no refresh.
6. **No per-user language field on the server**; the preference is a local setting.
7. **CI** has not run on GitHub for this phase (see CI below); the CREATEROLE-dependent role suites (`CompanyRuntimeIsolationTests`, `CompanyAdminToolRoleTests`) were executed in Phase 3.1A-1 on an isolated, role-capable PostgreSQL instance; in Phase 3.1A-2 they were skipped locally (no CREATEROLE environment) and have not yet been verified on GitHub CI.

## Company backup and trial restore (Phase 4.3)
These administrative commands back up ONE company and trial-restore it. Decisions D-053 and D-058..D-062 apply; the design is in `docs/PHASE-4.3.md`.
```
dotnet run --project src/backend/Hasm.Admin -- backup-company <company-id> <destination-dir>
dotnet run --project src/backend/Hasm.Admin -- trial-restore-company <set-dir> <company-id> <attachment-target-dir> [--keep]
dotnet run --project src/backend/Hasm.Admin -- drop-trial-restore <kept-file>
```
* **Configuration.** As for every command, configuration comes only from the environment:
  * the admin database account;
  * `Hasm__Attachments__StorageDirectory`, which is **required: without it no backup is possible, and there is no override.** A run with a missing setting must never produce a set without the attachments;
  * `Hasm__Encryption__KeyDirectory`, for key coverage and for decrypting sensitive attachments during the trial restore.

  `pg_dump`/`pg_restore` are taken from `PATH` (the same major version as the server). Every path argument must be absolute.
* **Output.** Stable codes, counts, the company id and the files given by or created for the operator. A physical database name, a password or tool output is never printed.
* **Exit codes:**
  * 0: ok;
  * 1: refused or failed (the code is printed);
  * 2: usage;
  * 3: configuration (for example `attachment_storage_not_configured`);
  * 4: the company is busy (provisioning, migration or runtime grant holding its lock);
  * 8: completed with warnings (missing key ids, an older migration level, a stale row key id, a registry link missing locally).
* **`backup-company`:**
  * The company comes only from the registry, and only in state Ready.
  * Its provisioning lock is held for the whole backup.
  * An ICU/builtin locale is refused before the dump (`locale_unsupported`).
  * The dump goes into a fresh private staging folder `<destination>.staging-<32 hex>/` (owner-only 0700 on Linux, verified; on Windows it inherits the parent's ACL, so choose a destination parent only the service account can read), which is removed afterwards. Staging folders of that exact pattern older than 24 hours, left by an interrupted run, are swept by the next run (never a symbolic link), and nothing else is touched.
  * The trial attachment target must also be outside the key directory (`target_overlaps_keys`). `drop-trial-restore` waits at most 5 seconds for the registry lock and then reports `company_busy`.
  * The set (`database.dump`, `attachments/`, `manifest.json` with the locale and the company migration level) is verified before the command reports success.
  * **Back up the key directories separately** with `backup-keys` (decision K, D-087). From slice 5 the set is encrypted and signed (see "Encrypted, signed backups" below).
* **`trial-restore-company`:**
  * The set is restored into a NEW, unregistered database and into `<attachment-target-dir>`, which must be empty and outside the live attachment storage.
  * Then the read-only pre-cutover checks run:
    * the locale and the company migration journal (level and checksums);
    * every linked local party must resolve in `Hasm_System`;
    * every attachment row must have its file, with a matching hash, and must be decryptable when its key is present.
  * A set from a newer installation is refused before anything is created (`set_newer_than_installation`).
  * The database is dropped afterwards. With `--keep` it stays, and an owner-only file `<set-dir>.trial-<random>.json` records it. Nothing is registered, granted or cut over.
* **`drop-trial-restore <kept-file>`** drops only a database that:
  * the file names;
  * is not a registered company, system, maintenance or built-in database;
  * carries the file's token in its comment.
  The registry is locked against changes until the drop has completed. This is the only supported way to remove a kept trial database.
* **Not available yet:** the cutover (replacing a live company database or folder) and the audited restore acknowledgement with a new checkpoint epoch are decided (D-081) and planned in `docs/PHASE-4.3.md` slice 7 (D-143..D-153); cutovers stay unavailable until that slice, the Phase 4.1 approval framework and an owner-instructed activation exist. Until then the procedure under "Restore limitations" above still applies to any real restore. A trial restore does not meet Scenario 21.8 by itself.

### Backup runs of the whole installation, monitoring and retention preview (Phase 4.3 slice 4)
Decisions D-069..D-073; the design is in `docs/PHASE-4.3.md` slice 4.
```
dotnet run --project src/backend/Hasm.Admin -- backup-run <root>
dotnet run --project src/backend/Hasm.Admin -- backup-status <root> [--max-age-hours N]
dotnet run --project src/backend/Hasm.Admin -- backup-retention-preview <root> --keep-last N [--keep-days D]
```
* **`backup-run <root>`** writes one run into a new owner-only folder `<root>/<yyyyMMddTHHmmssZ-8hex>/`:
  * `system/`: the system database dump and its manifest. The table of contents is checked readable; integrity comes from the SHA-256 in the manifest.
  * `companies/<company id>/`: one verified set per Ready company, with the same checks as `backup-company`.
  * `run.json`, written LAST: outcomes, codes, the start and end of every dump, sizes, missing key ids, the excluded data and `encrypted: false`.
  * A folder without `run.json` is an incomplete run (interrupted). It is reported, never deleted.
  * One company's failure never stops the others, and only one run can be in progress. That rule is enforced by a session lock that a periodic no-op keeps alive.
    * If the lock connection is lost, the run is reported `partial` with the warning `run_lock_lost`.
    * Set `idle_session_timeout` of the admin role to 0 (off), or to more than 60 seconds. The per-company locks of the company dumps are held the same way.
  * The configuration is the same as `backup-company`; the attachment storage setting is required.
  * Exit codes: 0 ok, 8 partial (a company busy or failed, or key ids missing), 1 failed (the system dump failed or no set was written), 4 another run in progress, 3 configuration.
* **The system dump is the most sensitive file of a run.** It holds password hashes, memberships and roles, shared-party personal data and the system audit chain.
  * The DATA of the session and login-throttle tables is left out, and later the TOTP secrets too: listed under "excluded" in `run.json` and the manifest. A restored installation therefore starts with no sessions.
  * Slice 5 encrypts and signs every run (see below); an unencrypted run exists only under the DEV/TEST acknowledgement. Back up the key directories with `backup-keys`, never alongside the sets.
* **A run is not one point in time across databases.** The system database is dumped first, then each company. Registry rows, party links, memberships and migration levels can therefore differ between them. A single-company restore compares with the live system database; a full-installation restore (not built) must reconcile.
* **`backup-status <root>`** is read only and needs no database settings: it is meant for the monitor. It reads the newest complete run.
  * Exit 0: ok and younger than `--max-age-hours` (default 26).
  * Exit 8: partial, a company missed two or more consecutive runs (`company_missed_runs`), or a run's `run.json` is unreadable (`unreadable_reports`: damaged or altered; it is never used, and the status stays fail-closed).
  * Exit 1: failed, no run (`backup_missing`), or too old (`backup_stale`).
  * Incomplete runs older than 24 hours are listed (information).
* **`backup-retention-preview <root> --keep-last N [--keep-days D]`** is read only. It lists the complete runs a policy WOULD remove; a run kept by either rule is kept. The newest complete run and incomplete or unreadable runs are never listed. **Nothing is deleted**: deleting backups is an owner decision (package 4.3-2).
* **Scheduling** uses the operating system, under the service account (HASM has no scheduler, and the API never runs a backup). Examples; replace the paths and run with the same `Hasm__*` environment as the other commands:
  * systemd: `/etc/systemd/system/hasm-backup.service`
    ```
    [Service]
    Type=oneshot
    User=hasm
    EnvironmentFile=/etc/hasm/admin.env
    ExecStart=/usr/bin/dotnet /opt/hasm/admin/Hasm.Admin.dll backup-run /srv/hasm-backups
    ```
    and `/etc/systemd/system/hasm-backup.timer`
    ```
    [Timer]
    OnCalendar=*-*-* 02:17
    Persistent=true
    [Install]
    WantedBy=timers.target
    ```
    then run `systemctl enable --now hasm-backup.timer`. For monitoring, a second timer runs `backup-status /srv/hasm-backups` and alerts on a non-zero exit.
  * cron, for the service account (`set -a` exports the variables to `dotnet`; a plain `.` would not, and the run would exit 3): `17 2 * * * set -a; . /etc/hasm/admin.env; set +a; /usr/bin/dotnet /opt/hasm/admin/Hasm.Admin.dll backup-run /srv/hasm-backups`
  * Windows Task Scheduler:
    ```
    schtasks /Create /TN "HASM backup" /SC DAILY /ST 02:17 /RU "<service account>" /TR "\"C:\Program Files\dotnet\dotnet.exe\" \"C:\HASM\Admin\Hasm.Admin.dll\" backup-run D:\HasmBackups"
    ```
    The `Hasm__*` variables are set as machine or user environment variables of the service account.
  * These examples are NOT exercised by an automated test. Verify them in a manual drill: run once, then check that `backup-status` exits 0.
* **Measured RPO/RTO (no promised values, SRS 16).** Record in the drill log:
  * the run's `durationMs` and each company's dump window from `run.json`;
  * the "Measured trial restore time" printed by `trial-restore-company` for that set.

  RPO is at most the schedule interval plus the run duration. RTO is the measured trial-restore time plus the cutover procedure, once that exists (BLOCKED).

### Encrypted, signed backups, key export and recovery test (Phase 4.3 slice 5)
Decisions D-089..D-095 and D-116..D-118 (plus D-120 for the TOTP table); the design is in `docs/PHASE-4.3.md` slice 5.
```
dotnet run --project src/backend/Hasm.Admin -- backup-recovery-keygen <out-dir> [--separate-passphrases] [--passphrase-stdin]     (OFFLINE workstation)
dotnet run --project src/backend/Hasm.Admin -- backup-signing-keygen                                                              (server)
dotnet run --project src/backend/Hasm.Admin -- backup-keys <destination-dir>                                                      (server)
dotnet run --project src/backend/Hasm.Admin -- trial-restore-company <set-dir> <company-id> <attachment-target-dir> [--keep] --recovery-key <file> --signing-trust <signing-trust.json> [--passphrase-stdin]
dotnet run --project src/backend/Hasm.Admin -- backup-recovery-test <run-dir> --recovery-key <file> --signing-trust <signing-trust.json> [--keys-export <dir>] [--passphrase-stdin]
```
* **Encryption is the default.** `backup-run` and `backup-company` write encrypted, signed sets when these are configured, and refuse otherwise (`backup_encryption_not_configured`, exit 3):
  * `Hasm__Backup__RecoveryPublicKeyFile`: the recovery PUBLIC key (`rk-*.pub.pem`); the private key never reaches the server;
  * `Hasm__Backup__SigningKeyDirectory` and `Hasm__Backup__SigningKeyId`: the server's backup signing key (`sk-*`), in its own owner-only directory.
* **Set-up, once:**
  1. On an OFFLINE workstation without `Hasm__Database__*` settings: `backup-recovery-keygen <out-dir>`. The passphrase (at least 20 characters, entered twice) comes from a prompt or, with `--passphrase-stdin`, from standard input; never from an argument or a variable. Put ONLY `rk-*.pub.pem` on the server. Move `copy-1` and `copy-2` (with `rk-*.sha256`) to two separate offline media; with `--separate-passphrases` each copy has its own passphrase and custodian.
  2. On the server: `backup-signing-keygen`. It writes `sk-<id>.key.pem` (private, never exported) and `sk-<id>.pub.pem`, prints the public key's SHA-256 for the recovery kit and writes system audit event 2013. Set `Hasm__Backup__SigningKeyId` to the printed id.
  3. `backup-keys <destination>`: see below. Then take a first `backup-run` and run `backup-recovery-test` on it: until a test passes, `backup-status` reports `recovery_untested` (exit 8) and the recovery key is NOT production-ready (D-085).
* **What an encrypted run contains.** Only `.hbe` files (HBE1: encrypted to the recovery key, authenticated chunk by chunk), their signed manifests (`manifest.json.hbe` + `.sig`), `canary.hbe` and the readable, signed `run.status.json` (verdict, counts, times, key ids, the canary hash; no names). `pg_dump` is piped straight into the encryptor: no plaintext dump exists at any time. `backup-status` verifies `run.status.json` with the server's signing PUBLIC keys; an unsigned or altered status counts as a FAILED run (`status_unsigned`, exit 1).
* **The system dump of an encrypted run** still leaves out the session and login-throttle data (no recovery value). Once Phase 4.1 adds the TOTP-secret table, its rows are INCLUDED in encrypted runs only (they are ciphertext under the key ring; D-120), so a full restore needs the key export.
* **`backup-keys <destination>`** writes ONE encrypted, signed export of every key directory: the encryption master keys (`Hasm__Encryption__KeyDirectory`), the audit key ring (`Hasm__Audit__KeyDirectory`) and the backup signing PUBLIC keys. Signing PRIVATE keys are never exported; after a disaster a new signing key is generated, and old sets still verify with the public keys in the kit.
  * The destination must be absolute and empty, and must not overlap the attachment storage, any key directory, a backup run folder or a folder holding run folders.
  * It holds `keys.hbe`, `key-export.json` + `.sig` (the key ids) and `signing-trust.json`: the trust list of signing public keys, all `active`. Keep a copy of `signing-trust.json` with every recovery kit and mark a key `retired` (with `retiredUtc`) or `compromised` there when that happens; never trust a key carried inside a set.
  * It writes system audit event 2012 and fails closed (the export is removed) when the event cannot be written. Run it after every key generation or rotation.
* **Trial restore and recovery test bring the private key in.** Bring the private-key file on removable media, give its passphrase at the prompt (or `--passphrase-stdin`), and remove the file from the machine afterwards; never copy it to the server's disks (runbook, review L3). `--signing-trust <signing-trust.json>` is the kit's trust list; `--signing-public-key <sk-*.pub.pem>` trusts one key as active.
  * Every signature and stored digest is verified BEFORE anything is decrypted; the dump is decrypted streaming into `pg_restore` and only authenticated chunks are released (D-116). A forged, unsigned, swapped or altered set is refused before anything is created (`signature_missing`, `signing_key_unknown`, `signing_key_compromised`, `backup_set_not_clean`).
  * An UNENCRYPTED (DEV/TEST) set is restored only when this reader's own environment carries the acknowledgement (`unencrypted_set_refused` otherwise); a field inside the set never decides it.
  * `trial-restore-company` writes system audit event 2010 (the operator, key ids, the company and a TAG of the trial database, never its name); `backup-recovery-test` writes 2011. When the event cannot be written the command reports FAILED (D-118).
* **`backup-recovery-test <run-dir>`** verifies the signed status, the run manifest and the canary, restores the system dump and every company set of the run into NEW disposable databases (dropped afterwards; the live databases are never touched), runs the slice 3 checks, and with `--keys-export` decrypts the export and checks that it holds every attachment and audit key id the run needs (TOTP rows are never decrypted).
  * Passed: it writes `recovery-test.json` into the run folder with the decrypted canary (single-purpose random bytes); `backup-status` accepts it only when it hashes to the signed canary hash. Exit 0, or 8 when it passed with warnings (for example `key_export_not_checked`).
  * Failed: exit 1, no proof is written. An unencrypted run is refused (`unencrypted_run`: there is no recovery key to test).
* **DEV/TEST only: unencrypted sets.** `Hasm__Backup__UnencryptedDevTestOnly=yes-this-is-not-production` (exactly) permits unencrypted sets; any other value is a configuration error, and it is refused while a recovery public key is configured. Every output then shows `DEGRADED: unencrypted backups (DEV/TEST only)`, sets and runs carry the file `UNENCRYPTED-DEV-TEST-ONLY`, and `backup-status` exits 8 (`unencrypted_dev_test`). Never set it in production (D-088).
* **Interim mode (dated limitations in RELEASE1-ACCEPTANCE G).** Until Phase 4.1 delivers the administrative-tool login (D-099) and the approval framework, these commands run under operating-system access to the service account; the audit events record the operating-system account (`os:<account>`). Trial restore and the recovery test are restore operations that will then need independent approval (D-118).

### Retention of backup runs and backup legal holds (Phase 4.3 slice 6)
Owner decision D-086; decisions D-130..D-139; the design is in `docs/PHASE-4.3.md` slice 6.
```
dotnet run --project src/backend/Hasm.Admin -- backup-retention-plan <root> [--json <file>]
dotnet run --project src/backend/Hasm.Admin -- backup-retention-apply <root>          (INACTIVE: refuses, see below)
dotnet run --project src/backend/Hasm.Admin -- backup-hold-place (--run <run-id> | --company <id> [--from <yyyy-mm-dd>] [--to <yyyy-mm-dd>]) --reason <text>
dotnet run --project src/backend/Hasm.Admin -- backup-hold-list
```
* **Configuration (`Hasm__Backup__Retention__*`):**
  * `InstallationTimeZone` (required; an IANA id such as `Asia/Riyadh`). It classifies the system part. The server's local time zone is never used.
  * `DailyKeep` (default 7) and `WeeklyKeep` (default 4). These are the D-086 minimums: they can be raised, never lowered. A lower or unreadable value stops the command with exit 3 (`retention_below_minimum`, `retention_config_invalid`); it is never clamped.
  * `WeekStart` (default `Monday`, ISO 8601).
  * `MaxDeletionsPerRun` (default 7, at most 31).
* **`backup-retention-plan <root>`** classifies every run of the root and prints, per run, either its keep reasons or `ELIGIBLE`. Nothing is deleted.
  * It reads each run's signed `run.status.json` with the server's signing public keys and never decrypts anything.
  * It also reads each company's configured time zone and fiscal calendar, and the backup legal holds and pins.
  * It ends with the plan hash and the key inventory of the retained runs (D-138). While the inventory is incomplete, no key may be retired.
  * It writes system audit event 2014. With `--json` it writes the plan to a new file.
* **Keep reasons:**
  * `minimum_daily`, `minimum_weekly`: the newest recoverable run of each of the latest 7 days and 4 weeks that HAVE a run.
  * `last_recoverable`, `newest`, `recovery_test_proof`: always kept.
  * `period_end`, `year_end`: the last run before and the first run after every fiscal period end, calendar month end and fiscal year end. They are never deleted automatically until the owner decides the legal policy.
  * `classification_unknown`: a company whose time zone is not configured or unknown, a run outside every fiscal year, or a company that is not Ready or cannot be read.
  * `legal_hold`, `attachment_hold`, `d114_hold`, `hold_check_failed`: a hold on the run.
  * `recovery_chain`: a pin, or a kept trial restore inside the run.
  * `incomplete`, `status_unverifiable`, `unencrypted`, `recovery_key_untested`: the run is not recoverable. It never counts toward a minimum and is never deleted automatically.
  * `run_not_clean`: the run holds an unexpected file or a symbolic link.
* **Backup legal holds.** `backup-hold-place` takes effect at once and writes system audit event 2018 (the reason is stored in the hold, not in the event). A hold covers either one run, or one company's runs started within the given local dates.
  * **A hold cannot be released with this tool.** Release needs a named administrator and independent approval (Phase 4.1). The database refuses every change to a hold except a single release.
* **Automatic deletion is INACTIVE (D-137).** `backup-retention-apply` writes audit event 2017 and stops with exit 3 (`retention_deletion_inactive`); nothing is deleted. Three independent layers enforce this:
  1. a code gate that is `false` in this release;
  2. runtime prerequisites checked on every execution;
  3. an exact opt-in, `Hasm__Backup__Retention__AutomaticDeletion=yes-delete-eligible-backups`, that no shipped configuration sets.

  Only an activation PR merged on an explicit owner instruction can change the gate. **Until then backups accumulate:** watch the free space of the backup root. Never delete a run folder by hand while a trial restore, recovery test or backup runs. Never delete a run that the plan shows with a keep reason.
* **Trial restores and recovery tests** hold a shared restore lock for their duration. A deletion, once activated, takes that lock exclusively, so the two never overlap. A restore started during a deletion stops with `retention_in_progress`.
* **What a deletion will do once activated** (D-136):
  * it runs only when `backup-status` is `ok`, the clock is consistent, and no more than `MaxDeletionsPerRun` runs, and never more than half of the complete runs, are eligible;
  * it re-validates every run just before touching it;
  * it writes audit event 2015 first;
  * it keeps a tombstone (the run's signed status and signature, plus `deleted.json`) under `<root>/.retention/tombstones/`;
  * it renames the run to `<run id>.deleting-<hex>`, deletes it without following links, and writes audit event 2016.

  An interrupted deletion is completed by the next execution. `backup-status` reports one that is still incomplete.

### Encryption-key retirement report (D-179..D-181)
```
dotnet run --project src/backend/Hasm.Admin -- encryption-key-retirement-report <backup-root> [<backup-root> ...] [--all-backup-copies-listed] [--json <file>]
```
* Run it before retiring an encryption master key (the attachment and import-file key ring). Give EVERY backup root (and, with multiple destinations, every destination).
* **What it does not see.** It reads only the roots you give. It cannot see another disk, an off-site or offline copy, a second destination, or a standalone `backup-company` set (which can hold attachments under an older key). It also cannot see an upload in flight or an orphan file.
* **`--all-backup-copies-listed`** is your attestation that the roots you gave are every place a backup of this installation is kept, and that no standalone set or copy under an older key is kept elsewhere. Without it the report is INCOMPLETE and no key is retirable, because the tool cannot know. Give it only when it is true.
* Each backup root must exist, be a real directory (not a symbolic link) and hold at least one complete run whose signed status verifies. A mistyped path, a share that is not mounted or an empty folder is a blocker, never "nothing needs the key".
* Inside a root, only run folders (named by a run id), unfinished deletions (`.deleting-*`) and `.retention` are allowed. Anything else there (a run moved or copied under another name such as `archive/<run id>` or `<run id>.bak`, a nested or hidden folder, a file, a link) blocks the report with `backup_root_unrecognised_entry:<names>`, because a run under another name is not read. Move it out of the root (or back to its run-id name), and write `--json` outside the roots.
* The same applies one level down. `.retention` may hold only the retention tombstones (`.retention/tombstones/<run id>/` with the deleted run's status and the deletion markers); anything else there is `backup_root_unrecognised_entry:.retention/<path>`. A run folder that holds anything a run does not hold, such as another run copied into it, is `backup_run_unrecognised_content:<run id>`. Move such content out of the root.
* A key is listed `RETIRABLE WITHIN THE SCANNED SCOPE` only when:
  * it is not the active key;
  * no live sensitive attachment needs it (active, removed or purged);
  * no live import original needs it;
  * no backup run present in any given root lists it. Every run on disk counts, also one that retention would delete: it can still be restored.
* Anything unknown makes the report INCOMPLETE (exit 8) and lists the blockers: a company that is not Ready, cannot be read, or has no configured attachment or import storage; an unreadable file or key, or a missing company storage folder; a backup root that is missing, not a directory, a symbolic link or without a complete, verified run; an entry of a root that is not a run folder; a run whose key needs are unknown (unfinished, unverifiable or unencrypted) or an unfinished deletion (a `.deleting-*` folder); no attestation. Then no key may be retired.
* A company that is `Provisioning` or `Failed` blocks every report for as long as it stays so (`company_unreadable:<id>:company_not_ready`). To resolve it, run `provision-company <company-id>` again until the company is `Ready`; it is safe to repeat. A `Pending` company has no database and does not block. There is no command that removes a registered company, so the report stays incomplete until the company is Ready.
* A file or a key that cannot be read (`attachment_key_unknown`, `import_original_key_unknown`): check that the storage folders are mounted and readable; for attachments, `POST .../attachments/maintenance/verify` lists the unreadable items. Restore the file or the folder, then run the report again.
* `missing_from_key_directory` means data or a present backup run needs a key that is not in the key directory: restore it from the key backup (`backup-keys`) before anything else.
* The command is read-only: it writes no audit event and creates no folder (only the optional `--json` file). The JSON names the roots that were scanned, whether the scope was attested and the generation time (UTC): show that file to the approver, and make a new report if anything changed since. Retiring the key is a separate step that needs independent approval (D-080(6)). Keep every retired key with the older recovery kits.
* After a key rotation, run the attachments' and the imports' rewrap (`POST .../attachments/maintenance/rewrap`, `POST .../imports/maintenance/rewrap`). Each reports `oldKeysMayBeRetired`; the report combines them with the backup runs present in the given roots.
* Import originals are not part of backup sets today (D-179). The owner decided that they are to be included (D-224); that is not built yet. Until it is, a restore brings back the batch rows without their originals; such a batch needs a new upload.

### Backup destinations (Phase 4.3 slice 8; S8a: configuration and status only)
Configure each destination as an administrative-tool setting (D-183). HASM stores no network credentials: a network share must already be mounted, or reachable as a UNC path, under the service account's own identity.
```
Hasm__Backup__Destinations__0__Id=nas-1
Hasm__Backup__Destinations__0__Path=/mnt/hasm-nas/backups
Hasm__Backup__Destinations__0__Kind=network
Hasm__Backup__Destinations__1__Id=usb-a
Hasm__Backup__Destinations__1__Path=/srv/hasm-usb/backups
Hasm__Backup__Destinations__1__Kind=local
Hasm__Backup__Destinations__1__DailyKeep=14
```
* At most 8 entries, numbered 0, 1, 2 and so on without gaps. `Id` is lower-case letters, digits and hyphens (up to 32); `Path` is absolute; `Kind` is `local` or `network`. `DailyKeep`/`WeeklyKeep` may only raise the minimums (7 and 4); `MaxAgeHours` is the freshness limit for that destination's copies (default: `--max-age-hours`, 26).
* Any invalid entry, a destination that is or passes through a symbolic link, one that is the backup root or another destination, or one inside or around the backup root, the attachment root or a key directory: `backup-status` refuses with exit 3 and names the rule. No destination is ever skipped.
* `backup-keys` and `trial-restore-company` refuse a folder inside or around a destination (`destination_in_backup_root`): keep the recovery kit and restore staging away from the copies.
* `backup-status <root>` prints every destination and exits with the OVERALL status: 1 when a destination has no verified copy, a stale, corrupt or conflicting copy, or a tombstone nothing explains; 8 when a destination lags behind the newest run, holds staging older than 24 hours, or is on the same volume as the root. A same-volume destination is not a second copy against disk loss (D-230), so it always warns. `backup-status <destination path>` checks that folder alone.
* **S8a makes no copies.** Until the copy engine ships (S8b), every configured destination reports `replica_missing` (exit 1), so do not configure destinations in production before then.

## Stock-period database guard (STOCK-PERIOD-DB, owner decision D-220, company migration 0034)

* **What:** PostgreSQL itself refuses to INSERT a stock or cost posting record dated in a Soft Closed period, a Final Closed period, or no fiscal period, whoever writes it (service, tool or plain SQL). Forward-only and additive: two trigger functions and eleven BEFORE INSERT row triggers (the dictionary is `CompanySchema.StockPeriodGuard.cs`, generated by `tools/schema/company-0034-stock-period-guard.cjs`); nothing existing is altered, replaced or disabled; no existing row is read or validated; no UPDATE trigger.
* **Guarded tables:** cost operations, cost entries, stock postings, stock posting reversals, stock adjustment postings, stock adjustment reversals, negative-stock obligations, settlements and obligation reversals (each by its own effective-date column, function `f_981674fd`), and cost layers and cost consumptions (by the date of the cost entry they reference, function `f_92619584`; the date is the inserting operation's own entry, never the receipt date of an old layer a consumption draws on).
* **Refusals (exact messages, error code P0001):** `the fiscal period is soft closed`, `the fiscal period is final closed`, `no fiscal period covers the posting date`. They come from the unchanged helper of migration 0006 (`f_a26691bc(date, false)`), which also locks the period row FOR SHARE so a concurrent close waits for the posting. There is NO soft-close override for stock (as in the services). The services keep their own refusal codes (`fiscal_period_soft_closed`, `fiscal_period_final_closed`), which fire first.
* **Consequences:** opening stock dated before the first fiscal period cannot be posted; a reversal is judged on its own date only (a reversal dated in an Open period of an original in a closed period is accepted); rows already in now-closed periods are untouched by the migration.
* **Tests:** `StockPeriodGuardTests` and `StockPeriodGuardRuntimeRoleTests` (PostgreSQL; registered in `.github/workflows/backend.yml`). The runtime role cannot switch the triggers off or replace the functions.
* **Merge order with PR 48 (the Phase 3.8D impact preview and recalculation, X1-A plan-execution layer):** its closed-period tests N10 and N28 must accept either trigger's refusal message in EITHER merge order; its catalog test N17 needs a change only if PR 48 merges first (it must then count the guard objects of company migration 0034, functions `f_981674fd` and `f_92619584` and the eleven triggers, as pre-existing).

## Load-test harness (stage 1: foundation; Release 1 acceptance 18.2/18.3)

`tools/loadtest/` is tooling only: no migration, no change to the PostgreSQL registry. It talks to the REAL HTTP API as ordinary users, so every server rule (validation, RBAC, numbering, audit, period and approval rules, optimistic concurrency) applies. Stage 2 (the 60-minute, 50-session runner) is separate and later.

**Safety.** It refuses to run unless `HASM_LOADTEST_DISPOSABLE=this-installation-is-disposable` is set (the operator's statement that the installation and its database are disposable), refuses a non-loopback API unless it is https and `--environment <file>` is given, refuses port 5432 (`--database-port`, `PGPORT`), and refuses a company that holds anything that is not load-test data: an item or party whose code does not START with `LT-` (case-sensitive), a journal entry not described `LT entry ...` or a stock document not referenced `LT-S-...` (read through the API, so a user with a narrower scope sees less: use a company-wide user). `seed` AND `run` make this check before their first write. It cannot see the PostgreSQL cluster behind the API, so these are best-effort protections, not proof: point it only at an installation on the isolated runner's cluster (`scripts/test-pg/`) or the dedicated reference machine. Credentials come only from the environment (`HASM_LT_LOGIN`, `HASM_LT_PASSWORD`; `HASM_LT_APPROVER_LOGIN`, `HASM_LT_APPROVER_PASSWORD` for stock-document approval, which needs a second user). A development certificate is trusted through `NODE_EXTRA_CA_CERTS`; validation is never disabled.

**Prerequisites in the target company** (the seeder checks and names what is missing): a fiscal year covering `--year`, the base currency selected, at least two active postable base-currency accounts, at least one active warehouse (stock documents). It creates its own unit and group (`LT-PCS`, `LT-G`).

```
node tools/loadtest/loadtest.js plan --items 20000 --parties 10000 --journals N --stock-docs N   # the plan digest, no API
node tools/loadtest/loadtest.js seed --api http://127.0.0.1:PORT --company <id> --items 20000 --parties 10000 --journals N --stock-docs N --year 2026 --concurrency 4 > seed-manifest.json
node tools/loadtest/loadtest.js run  --api ... --company <id> --items ... --parties ... --iterations 100 [--duration-seconds S] [--environment env.json] [--out results.json]
node --test tools/loadtest/tests/smoke.test.js                                                     # no database, no real API
```

**Data.** Deterministic: record i of kind k depends only on (`--seed`, k, i) (default seed `hasm-loadtest-1`), so the same seed and counts give the same data and the same plan digest on any machine. Items and parties (Latin and Arabic names; about 60% of parties get a customer role) are idempotent by code. Journal entries (create, submit, post by the maker; found again by their description) and stock documents (receipts first, then issues and transfers; create, submit, approve by a second user; found again by their reference) are idempotent too. A multi-step flow is driven by the state the API reports, one step at a time: a failed or ambiguous call is answered by re-reading the state, never by repeating the chain or creating a second record. Item k is only ever stocked in warehouse (k-1) mod W, so an issue draws only items its warehouse can have received; quantities are not tracked. Approving a stock document changes no stock figure by itself (posting is a later stage), and invoices are not seeded in stage 1: both are listed as missing in every results file, never omitted.

**Scenarios.** Item search, party search, customer search (P95 target 1 s), ordinary screen-load calls (2 s), save and post a journal entry (3 s), trial balance and general ledger (5 s). Declared but not implemented: invoice save/post and the stock balance report; they appear with `implemented: false`.

**Results and the verdict.** A results file records the tool, seed, data counts, load shape, the load generator's host facts and the operator-declared reference environment (`--environment`: `vcpu`, `ramGb`, `diskGb`, `ssd`, `backendAndPostgresTogether`, `companies`; the tool cannot verify it). Samples are measured, never estimated; a scenario without samples shows `null`. The data counts in the verdict are MEASURED from the API at run start (the declared counts are recorded beside them but never used). Only the six documented keys of `--environment` reach the results file. A scenario is within target when p95 is at most (inclusive) its target. The verdict is **NOT VERIFIED** unless every reference condition (8 vCPU/32 GB/500 GB SSD declared, 5 companies, 20,000 items, 10,000 parties, 100,000 invoices, 500,000 entries and stock movements, 50 sessions, 3,600 s, every scenario implemented) is met; the file lists each unmet reason. Stage 1 cannot meet them, so its output is mechanics validation and never acceptance evidence. `loadtest-results/` is git-ignored.

**Validation.** `tools/loadtest/tests/smoke.test.js` (Node, no database): determinism, the guard, the verdict rule, a contract check of every route, request field, query parameter, enum value and response key against the backend sources, and a seed plus short run against an in-process stub. It runs in the hosted `backend-build-test` job of `.github/workflows/backend.yml` (an added step; the workflow's path filter is mirrored by the protected `required-checks.json`, so it runs when `src/backend/**` or `tests/**` change, which is when the contract can break, and on every push to `main`, not on a change that only touches `tools/loadtest/`; the self-hosted twin is unchanged). Beyond the smoke test, the harness was run once end to end against the real API in-process on the isolated runner (60 items, 30 parties, 15 journal entries posted, 10 stock documents approved by two users, 80 scenario iterations, 0 errors); those numbers are meaningless and not recorded.

## Scratch files and PR-body hygiene (multi-agent)

Several agents work in one environment at the same time, so temporary files must never collide and a pull-request description must never be overwritten with another task's text (owner instruction, 2026-11-21). Documentation only; this adds no protected policy.

**Why (2026-11-21 incident):** a reviewer cleaning its files ran a glob (`*.md`) in the shared scratchpad and deleted 45 files of other agents. Nothing in git was lost, but unpushed drafts were. Hence: never glob-delete, and remove only your own `mktemp` directory by its exact path.

1. **One own directory per task.** At the start of a task create it: `D=$(mktemp -d "${TMPDIR:-/tmp}/hasm-<agentLetter>-<task>-XXXXXX"); chmod 700 "$D"`. Every temporary file of that task (PR bodies, review text, test output, patches, TRX copies) goes inside it. Never use the shared scratchpad root or a fixed file name.
2. **No fixed names.** Never reuse a name such as `pr-body.md`, `review.txt`, `out.log` or `pg.out` in a shared place; inside your own `$D` the names are yours alone.
3. **Stay out of other agents' space.** Keep temporary output out of other agents' worktrees and directories. Never read, write or delete anything you did not create.
4. **Cleanup.** Remove only the `$D` you created (`rm -rf -- "$D"`, after checking that it starts with your own `hasm-<letter>-` prefix). Never glob-delete in a shared location and never touch lock files.
5. **Atomic writes for anything sent to GitHub.** Write to `$D/body.tmp`, then `mv "$D/body.tmp" "$D/body.md"` before using it.
6. **Verify before any PR title or description update.** Re-read the pull request (`gh api repos/salem2020s/hasm/pulls/<n>`); check the number, that `head.ref` and `head.sha` are the pull request you intend, and that the first line of the body file matches that pull request's title or topic. Only then PATCH.
7. **Never commit scratch files, credentials or temporary test artifacts.** Review `git status` and the staged file list before every commit.
8. **No protected policy changes** are made through this convention.
9. **Review records name the model family only, never a model identifier.**
10. **No GitHub closing keywords next to a PR or issue number (permanent rule; owner decision, 2026-11-21, D-197).** Never write a closing keyword (any form of close, fix or resolve: `close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved`, in any letter case, with or without a colon) before a PR or issue reference in any form (`#<number>`, `GH-<number>`, `owner/repo#<number>`, a pull-request or issue URL, or a Markdown link whose text is the number), whatever stands between them (a space, several, a tab, a colon, a line break, or nothing), in a PR title, a PR description or a commit message. This holds for lists of next tasks, quotations and negations too: GitHub does not read the sentence, only the keyword and the number.
    * **Why (2026-11-21 incident):** the description of PR #179 (the checkpoint handoff refresh) listed, among the next tasks, an item that put such a keyword directly before the reference to PR 176. When #179 merged into `main` (`9ffaa6c`), GitHub treated it as "this merge completes 176" and closed the open Draft PR #176 two seconds after the merge (#179 merged at 2026-11-21T20:49:15Z; #176 closed at 20:49:17Z). GitHub applies closing keywords to pull requests as well as issues, and nothing warns before the merge. Nobody had decided that PR 176 should be closed; the owner authorized reopening it, and the branch and the review history were intact.
    * **Safe phrasing:** "addresses the findings on PR 176", "follow-up to PR 176", "the PR 176 corrections", "see #176". A bare `#176` mention with no keyword before it is safe. To state that something really is finished, name the merge: "merged as `<sha>`".
    * **Check, by the author before every push and every PR create or update, and by the lead before every merge** (title, description and every commit message of the PR; any hit is removed first):

      ```bash
      P='\b(close[sd]?|fix(e[sd])?|resolve[sd]?):?[[:space:]]*(\[?#[0-9]|GH-[0-9]|[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+#[0-9]|\[?https://github\.com/)'
      gh api repos/salem2020s/hasm/pulls/<n> --jq '.title, .body' | grep -n -i -E "$P"
      git log --format='%H%n%B' origin/main..HEAD | grep -n -i -E "$P"
      ```

      **The grep is a safety net, not the rule.** The rule is: never write a closing keyword before a PR or issue reference. The pattern (GNU grep, for `\b` and the character class) covers `#N`, `GH-N`, `owner/repo#N`, a PR or issue URL and a Markdown link whose text is the number or the URL, with a colon and any white space, or none, in between. It works line by line, so it cannot see a keyword at the end of one line with the reference on the next; read the text as well.

      Both commands must print nothing. A commit message cannot be changed after it is pushed (history is never rewritten), so the grep on commit messages is run BEFORE the push. If a pushed commit message already contains a hit, do not rewrite history: report it to the lead and the owner before the PR is merged; the options are a merge that is known and accepted to close the referenced item, or a new branch carrying the same tree with clean messages.
