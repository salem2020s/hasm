* **Findings:** one High (H1), two Low (L1, L2) and rulings on the named concerns.
  * H1 (High), 0039, the trigger design: the commit-time binding can be ended early by the inserting session (proven above). Both constraint triggers fire only on INSERT of the execution row and of the use row. They are DEFERRABLE, so any session can run `SET CONSTRAINTS ALL IMMEDIATE` (or name the two triggers), which fires the pending checks at that moment. Every row written or changed AFTER that point in the same transaction is never compared with the signed epoch: the layers, the consumptions, the entries and the positions, as far as 0014 and 0036 allow. Design test 4 requires the refusal of "an R line deviation: a layer's remaining quantity or amount changed after the epoch's last entry within the same transaction", and of the P deviations. D4 requires "exact binding to the plan, participants, closure, epoch contents and financial effects" and that partial execution be prevented. The probe commits exactly that deviation under a valid grant. Activation is closed (the runtime role still holds SELECT only), so nothing is exploitable today, but the slice's central guarantee does not hold against the transaction's own session, which is the very actor A3 must constrain.

    Required: make every change to a row the epoch text or the message reads re-run the check, so that the final state is always the one checked. For example:
    * add DEFERRABLE INITIALLY DEFERRED constraint triggers AFTER INSERT OR UPDATE OR DELETE on the operation, member, entry, layer, consumption, position and lineage tables, and on the plan, approval, closure and line tables of the message;
    * each re-runs `f_217072b6` for every execution written by the current transaction (0036 stores the writing transaction id on the execution row, `c_fbd0bc4b xid8`, so `WHERE c_fbd0bc4b = pg_current_xact_id()` finds them);
    * under IMMEDIATE mode the last changing statement then checks the final state.

    Add the probe as a test (SET CONSTRAINTS ALL IMMEDIATE, then a touched-layer change and a position change), with a mutation proof.
  * L1 (Low), test 4c (EpochTextColumnPinTests, from E1b): the pin covers the four 0014 ledger tables, but the text also reads the position table (P group), the member table and the lineage table. The position table has columns the P line does not render (the valuation method `c_a71bfccf`, the last entry date `c_3c880b93`, and created and updated times), and none is classified. A new or repurposed position column would not fail the pin. Recommended: extend 4c to the position, member and lineage tables, with each column classified as signed or excluded with a reason.
  * L2 (Low, information): a cost layer of a touched position that the epoch neither created nor consumed is not in the R group, and the database has no guard that a layer's remaining equals its original minus its consumptions (my control changed a consumed layer's figures, and only the epoch comparison stopped it). A change to such an unrelated layer inside the execution transaction is therefore not bound by the epoch. This is the general cost-ledger integrity question for any runtime-role transaction, not specific to T2; record it for the ledger-integrity workstream (OD-7's least-privilege track).
  * Ruling, session influence: none found. Every value is rendered by a fixed format (lower-case uuid, decimal integer, `numeric` cast to its declared scale 10 or 6, `to_char` with a fixed pattern, `t` or `f`, hex SHA-256 of UTF-8). The sort keys are integers, uuids and booleans (no collation), and every relation and user function is schema-qualified. The PR's test repeats the digest under TimeZone, DateStyle, IntervalStyle, bytea_output, extra_float_digits and lc_numeric.
  * Ruling, savepoints and a second execution: a check fired inside a subtransaction that is rolled back is re-queued by PostgreSQL, so savepoints add nothing beyond H1. A second execution in the same transaction (another plan, its own grant) changes the shared P lines and fails closed at commit, unless H1 is used.
  * Ruling, the three equivalent mutants: all three arguments hold.
    * The plan and executor equality at commit cannot fail: A2's use trigger refuses a mismatching use, and the execution and grant rows are append-only.
    * The use-table trigger adds no case: the use's primary key is the execution id, and every execution committed under A3 already has its one use. No execution predates A3 in production (inert).
    * The `f`-before-`t` order of one entry and layer never decides in real rows, and SQL and .NET use the same order, so a difference fails closed.
  * Ruling, the automatic grant of the test base: it does not weaken the existing tests. Every refusal test asserts its specific reason (`RefusedWith("<reason>")`, 125 uses), so a refusal by A3 ("needs exactly one grant use") cannot stand in for a removed 0036 rule, and every success test now also exercises A3's positive path. The dry run executes the whole script and is always rolled back. A script that fails its dry run gets no grant and meets its own refusal.
  * Ruling, grant reuse across executions: not possible. The use table's unique grant id and its primary key on the execution, plus the execution's unique plan, allow exactly one use per grant and one grant per execution, and A3 counts exactly one use at commit.
  * Information: the key rule at commit refuses a key whose revoke-from is at or before the grant's acceptance (a retroactive revocation, D5), consistent with design 4.6. A revocation dated after the acceptance does not stop the commit; the design leaves that to the readers.
