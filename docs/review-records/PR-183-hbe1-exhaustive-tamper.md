## The security claim, verified independently

`DecryptAsync` parses the header, then compares SHA-256 of exactly the bytes the parser consumed (unsigned part and tag) with the signed header hash, BEFORE the key id is compared, before the SPKI is imported and before any key agreement. The parser is deterministic on a prefix of the file, so a parse that consumes a different number of bytes (the reframing of a length field) hashes a different byte string: it can be accepted only with a SHA-256 collision. An attacker who controls the file but not the signing key therefore cannot make the parser accept another header, and cannot skip, reorder, truncate or append chunks: each stored chunk is compared with the signed list before it is decrypted, and the last-chunk position is compared with the signed count before the tag is checked. Position 53 (high byte of the SPKI length; layout confirmed: 0-3 magic, 4 version, 5 and 6-24 key id, 25 and 26-37 purpose, 38-39 and 40-52 name, 53-54 SPKI length, 55-145 SPKI, 146-177 salt, 178-184 nonce prefix, 185-188 chunk size, 189-220 tag) gives `hbe_malformed`, or `hbe_not_authenticated` when the four stray bytes read as the chunk size are in range (measured 6 and 8 of 1530 flips in two runs); the second is thrown at the header-hash comparison, with nothing written. The author's conclusion (a test-expectation issue, not a weakness) holds.

After a field the parser can only throw `hbe_malformed`, so the single-code regions (magic, the three lengths) are deterministic: I checked by hand that every other value of the key id, purpose and name lengths leads to a parser refusal (fixed-length key id pattern; a shorter purpose or name leaves a name or SPKI length above 512; a longer one takes in a zero byte that the patterns refuse). Every code a table allows was actually reached in the scratch run, so no table has an unjustified entry. Random-dependent outcomes that remain (keys, ephemeral point, salt and plaintext are still random) all stay inside the allowed sets: key id flips (hex digit or not), the SPKI length reframing, and SPKI offset 25 (L2). No flake path was found.

Stricter than the old test: under the original digest the old test accepted five codes at every position, the new one at most two per region and never `recovery_key_mismatch`, `hbe_wrong_file` or `hbe_authentication_failed`; under the recomputed digest the old test accepted five codes everywhere, the new one one or two per region. The only added acceptance is `hbe_not_authenticated` for the SPKI length (L1).

* **L1 (resolved):** every header flip is now ALSO checked under the parser-framed digest (`Hbe1.ComputeDigestAsync` over the tampered bytes). Three tables state the allowed codes per digest: the original signed digest; `SelfDigest` (split at the original header length; for the SPKI length it still allows `hbe_not_authenticated`, documented as the helper's artefact); and the parser-framed digest, under which `hbe_not_authenticated` is never allowed and the SPKI length region allows `hbe_malformed` only. When the parser refuses the bytes no such digest exists, and that refusal must be `hbe_malformed` or `hbe_unsupported_version` as the table allows. A flip that reframes and still parses outside the SPKI length and chunk size fields is a finding. The deterministic reproduction test asserts both: `hbe_not_authenticated` under `SelfDigest`, and under the parser-framed digest `hbe_malformed` with an empty output.

Measured by local mutation, and different from the finding's wording: the refusal does NOT rest on the SPKI hash in the HKDF info alone. The SPKI bytes are bound three times (their hash in the HKDF info; the header MAC, computed over the header bytes that contain them; each chunk's associated data, which carries the header hash). With the HKDF binding removed alone the test still passes; it also passes with any two of the three removed; it fails (file ACCEPTED) only with all three removed. The comments say this.
