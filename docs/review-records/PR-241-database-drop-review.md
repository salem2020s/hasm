* **Findings:** one Medium (M1, open) and three Low (L1 to L3, open with follow-up); no Critical, no High.
  * **M1 (Medium), `src/backend/Hasm.Infrastructure/Backup/DatabaseDrop.cs`, `RunAsync`, the third statement. Open.** The sequence FORCE, plain, FORCE fails in the very case it was written for (a worker and ordinary sessions of the account) whenever a second autovacuum worker reaches the database during the plain drop. The plain drop holds the lock on the database for five seconds while it waits for the ordinary sessions; a worker the launcher starts in that time waits for that lock and enters the moment the plain drop gives up with 55006, so the third statement meets a worker again and is refused with 42501. Reproduced on PostgreSQL 16.15: with `autovacuum_naptime=1s` every time (the old worker terminated at 21:54:19.0, a new one with backend start 21:54:21.7 present when the plain drop returned at 21:54:24.1); with the default 1min the sequence succeeded in my one run, and the window is then about five seconds per naptime, so it is rare but not excluded (a worker that has been busy in a large restored database for close to a naptime when the drop comes). Consequence: the database is left behind and the caller reports the failure (thrown / `false` / `system_copy_drop_failed`), nothing is masked and nothing else is dropped; this is no regression (before the PR the first refusal already ended it), but the fix is incomplete, the flake it removes can come back at a lower rate, and on a server with a short naptime it does not help at all. The class comment ("no waiting", and the implied outcome) is also inaccurate: the plain drop waits five seconds in the server. Suggested correction, verified on the same cluster in the failing state: on 42501, terminate the sessions the account may terminate itself (`SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = @n AND usesysid = (SELECT oid FROM pg_roles WHERE rolname = current_user) AND pid <> pg_backend_pid()`, allowed for the own role without any additional privilege) and then issue the plain drop, which removes the workers itself and waits for the terminated sessions: worker and session present, naptime 1s, database dropped. Still a fixed, short statement sequence, no loop; a unit test for the new order and the existing integration test cover it.
  * **L1 (Low), `tests/integration/Hasm.Database.IntegrationTests/DatabaseDropAutovacuumTests.cs`. Open, follow-up.** The test still depends on when the launcher visits the database (up to 4 minutes, failing otherwise). Moving it to the serial collection is a sound reason (`DisableParallelization = true`; far fewer new databases at that time), but other classes of that collection create databases too, so the bound is not a guarantee, and the hosted result on this head was not yet available. A deterministic alternative exists only after M1 is corrected: the hosted job owns the superuser of its service container and can set a short `autovacuum_naptime` before the tests (with the present sequence that setting would make this test fail, which is M1). Until then the 4-minute bound is acceptable.
  * **L2 (Low), same file. Open, follow-up.** The test proves the precondition (FORCE refused) and the end state (database gone, kept file deleted) but not that the product took the fallback: if the worker ended in the milliseconds between the two, the product's first statement would succeed and the test would pass all the same. With 6,000,000 rows this is unlikely. Also the registry comment says "about one minute: one autovacuum naptime" while the class comment says about two.
