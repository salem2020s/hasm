* **Checks run (commands and results):**
  * **The authenticated record form (`AuditCanonical.Serialize`).** The hash and the MAC cover the stream key, `Seq`, `EventId`, `OccurredMicros`, the event type, the subject and actor ids, the detail, the key id and `PrevHash`. `EventId` is UNIQUE in the table.
    * A genuine record cannot be moved to another sequence number or stream, re-timed, or edited without failing `CheckRecord`, and it cannot be inserted a second time.
    * **"A valid old 2015 made to look current" is therefore impossible by moving or copying it.**
    * **"A genuine 2016 made to fall outside the range" is impossible:** genuine rows cannot be updated or deleted (the append-only trigger, even for the owner; the runtime role has no UPDATE or DELETE), and nothing can be inserted below the head, because every lower sequence number is taken.
  * **The splice that remains (W1).** The canonical form binds each record to its own `PrevHash`, but the per-record rule no longer checks that `PrevHash` equals the stored hash of the actual predecessor. Records from a DIVERGENT history of the same stream therefore pass `CheckRecord`: records written before a system-database restore and rolled back by it, MAC-valid under a key that is still known, each carrying its own sequence number above the restored head.
    * The runtime role can insert them at exactly those sequence numbers while they are free, above the current head.
    * They then count as genuine facts: an old 2011 recovery-test pass, an old 2015/2016 pair, an old 2040 or 2045.
    * Only the link check catches them: the first spliced record's `PrevHash` is the old predecessor's hash, not the current one's.
    * The precondition is a restored system database and an attacker who kept the rolled-back rows (the runtime role can SELECT the table before a restore).
    * The honest writer does not catch them either. `EnsureHeadIsSoundAndAnchoredAsync` checks the head's own record and its agreement with the last checkpoint, not the head's link, so it would extend a spliced head that lies within the unanchored window. That is a pre-existing property; the full `audit-verify` reports it as `link_broken`.
  * **The writer's behaviour after a forged row (W2).** `AuditTrail.EnsureHeadIsSoundAndAnchoredAsync` REFUSES to extend a stream whose head fails `CheckRecord` (`audit_head_corrupt`). Sequence numbers come from the head (`ORDER BY seq DESC LIMIT 1`), so a forged row inserted at the next or at any higher sequence number becomes the head.
    * From then on NO genuine record is written to that stream: the chain stops.
    * 4B's statement "the next genuine record links to the forged record's hash, so … a genuine record after a forged one still counts" describes something the real writer never does, and T22(a) ("genuine records after it still count and a deletion that is otherwise allowed still proceeds") cannot be produced through `AuditTrail`.
  * **A correction to my previous record (V1(a) at 1327f38):** I wrote that checkpoints are written only by the manual `audit-anchor` command. That is wrong. `AuditTrail.CommitAsync` anchors each stream's new head in the checkpoint store right after the commit, and the writer anchors before appending when the lag exceeds `MaxUnanchoredEvents`, so the unanchored tail is normally short. The conclusion that the whole-stream verdict must not gate deletion still holds, because of the forged-row case.
  * **The primitive that fits:** `AuditVerifier.VerifyAsync` already computes `VerifiedThroughSeq`, the highest sequence number such that records 1..n are contiguous and each has a valid hash, MAC AND link. It is computed from the records alone, independently of the checkpoints. Using facts at or below it gives everything 4B wants without the splice:
    * a forged or spliced row ends the verified prefix;
    * every genuine fact before it still counts;
    * a gap ends it;
    * the unanchored tail is inside it.

* **Findings:** 0 Critical, 0 High, 1 Medium (W1), 1 Low (W2), plus one pre-existing item outside this PR. V2 and V3 are resolved.
  * **Medium W1 (the per-record rule accepts spliced records from a divergent history).** See the check above.
    * Resolution: define the rule on the chain-verified prefix. A fact is evidence if and only if its sequence number is at or below `VerifiedThroughSeq` of one `AuditVerifier.VerifyAsync` pass, read in the same read-only snapshot as the facts. The whole-stream verdict and the checkpoints stay alerting only, as now.
    * This keeps every property 4B wants: a forged row is not evidence and alerts; genuine facts before it still count; the unanchored tail counts; a gap fails closed for anything after it.
    * Absence-based facts are then evaluated over the verified prefix. They can only "miss" an event that was never written, and while a stream is halted by a forged head nothing new is written, so every absence-dependent step fails safe: a missing 2016 leaves `retention_deletion_incomplete`, a missing 2011 leaves the test stale.
    * Add a T22 case: records copied from a pre-restore copy of the stream, inserted above the restored head, are not evidence and are alerted.
    * If a full pass per apply is too slow for a long stream, start from the last checkpoint: its stored hash anchors the link of the next record, and everything up to it is covered by the checkpoint chain.
  * **Low W2 (4B and T22 describe a writer behaviour that does not exist).** The real writer refuses to extend a forged head, so no genuine record ever follows a forged one. Resolution: correct 4B's text. Rewrite T22(a) to what production does: a forged row at the head ends the verified prefix; earlier genuine facts still count; the writer refuses further events with `audit_head_corrupt`; every deletion step that needs a new event fails closed. Do not write "genuine records after a forged one" by bypassing `AuditTrail` in a test: that proves nothing about production.
  * **Pre-existing item, outside PR 223 (for the owner register; my rating: High, availability).** The runtime role's INSERT grant on the audit table lets anyone with the runtime credentials insert ONE row that fails `CheckRecord` at the head of the system stream. The writer then refuses every further audited mutation in that stream (`audit_head_corrupt`): logins, MFA, access administration, backup events and everything else that audits to the system stream. The table refuses deletion even for its owner, and "the chain is never reset or silently repaired", so there is no documented recovery path. The same applies to each company stream whose role can insert. Suggested direction for the register item:
    * a database-side insert guard that needs no key: a BEFORE INSERT trigger requiring `Seq = head + 1` and `PrevHash = head.Hash` for the stream. This blocks jumps, forks and splices, though not a junk row at head + 1;
    * a defined, audited owner procedure to recover from a forged head;
    * or audit inserts through a role the runtime credentials do not hold, which is a design change for the owner.
    
    This is the same class as SEC-RT-SESSION.
