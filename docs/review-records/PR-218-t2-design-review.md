* **Checks run (commands and results):**
  * **Probe A, minting a session (run through the CPU gate; isolated PostgreSQL with real LOGIN roles; a temporary test, removed afterwards).** This probe evaluates the threat row "runtime database credentials only". The attacker holds ONLY the system runtime role that the real `grant-system-runtime` routine creates. With it:
    * it inserted a `Session` row for an MFA-enrolled user, with `token_hash = SHA-256(token)` for a token it chose and the MFA-verified time set to now;
    * the real API (`WebApplicationFactory`, restricted role, gate on) accepted `Authorization: Bearer <token>`: `/api/v1/auth/status` returned `"authenticated":true` as the victim;
    * an `MfaFresh` route (`POST /api/v1/access/assignments`) went past the MFA gate (409 `company_not_selected` instead of 401). The same forged row without the MFA time returned 401, which shows that MFA is enforced but that its state is just a runtime-writable column;
    * the same role holds INSERT on `User`, `RoleAssignment`, `RolePermission` and `UserCompanyAccess`, and UPDATE on `Session` (it can also write `SelectedCompanyId`).
    
    The design's Tier 1 signer decides on exactly these inputs: permission on the root warehouse, a fresh MFA step-up, and the identities used for segregation of duties. See C1.
  * **Probe B, the verifier rebuilt from section 4.2** (`rsa_verify(n, k, signature, message)`: signature to numeric, refuse s >= n, 16 squarings and one multiplication with `mod`, full expected encoding `00 01 FF.. 00 || DigestInfo(SHA-256) || sha256(message)` compared as one number; only `numeric`, `get_byte`, `decode`, `repeat`, built-in `sha256`). Run against .NET `RSA.SignData(SHA256, Pkcs1)` with a fresh 3072-bit key (e = 65537):
    * The valid signature passes. A bit flipped in the message or in the signature fails. A PSS signature fails. s = 0, s = 1 and s = n - 1 fail. Cost: 5.5 ms per verification, round trip included.
    * s + n fails with the range check and passes without it; the design states the range check.
    * A 385-byte signature with a leading zero passes unless the length is checked. The design does not state a length check (L1).
    * The document gives enough detail to rebuild `rsa_verify`. It does not give enough to rebuild `replay_message` (M2).
  * **Probe C, shadowing.** In an invoker-rights PL/pgSQL function that names a table without its schema, a TEMP table of the same name (`CREATE TEMP TABLE "ReplayAuthorizationKey"`) replaced the real table for the caller: the function returned 42 instead of 1. `CREATE DOMAIN pg_temp.bytea` is accepted, and pg_temp is searched before pg_catalog for TYPE names. This works only for a role with the TEMPORARY privilege. Today the company runtime role has none: `REVOKE ALL ON DATABASE ... FROM PUBLIC` and the role, and the violation check `database_create_or_temp` in `CompanyRuntimePrivileges`. The design neither names this dependency nor tests it (M1).
  * Code reading, the remaining focus items:
    * Company identity: the company runtime role R holds SELECT only on the company identity table, so the `company=` field cannot be changed by R.
    * Same-transaction binding: 0036 binds every epoch member and entry to an execution written in the current transaction (`pg_current_xact_id()`), so the execution authorization covers them.
    * Settings R cannot use: `session_replication_role` needs a superuser, disabling a trigger needs the owner, and R holds no TRUNCATE (append-only guards).
    * COPY fires the triggers.
    * `SET CONSTRAINTS ALL IMMEDIATE` only moves the deferred check earlier, which refuses R's own transaction: no bypass.
    * Restore: `pg_restore` loads data before the triggers, so the read-side check of section 7 is required; see M4.

* **Findings:** 1 Critical (C1), 0 High, 4 Medium (M1 to M4), 3 Low (L1 to L3). Each finding is listed below with its resolution.
  * **Critical C1 (Tier 1 does not meet the owner's core requirement):** sections 4.3, 5 and 12 D1. The Tier 1 signer signs after "the permission of the user on the plan's root warehouse, a fresh MFA step-up of that user, segregation of duties". All three are read from system-database state that the application's ordinary runtime database credentials can write: sessions (token hash without a server secret, the MFA-verified time, the selected company), users, role assignments, role permissions and company access.
    * Probe A shows a runtime-credential-only attacker minting an authenticated, MFA-fresh session for an enrolled user, accepted by the real API.
    * With sessions for two or three distinct users (existing ones, or users it inserts itself), with the permissions it assigns itself, the attacker drives the honest API. The in-process signer then produces valid creation, approval and execution signatures. The database checks pass, because the signatures are genuine.
    * The threat table's row "the runtime database credentials only: prevented" holds only for the company role R in isolation. It does not hold for "the ordinary application runtime database credentials" in the owner's sense (the API's runtime credentials, the system runtime account included). D1 therefore asks the owner to accept a boundary that is not true as stated.
    * Option (a), the separate executor principal, fails the same way: the API decides when to use E.
    * Resolution required before approval, choose one:
      * (i) Tier 2b as the activation baseline. An offline signer run by a second person on another machine reads the plan through the owner account and shows the closure, lines and amounts; the database side is as designed. This also covers a compromise of the API process.
      * (ii) A redesigned Tier 1 whose authority does not come from runtime-writable state:
        * an owner-registered signer list (written by the owner account, or pinned outside the database), naming each user and that user's TOTP credential id;
        * at each signing, a fresh TOTP code entered for this operation and verified by the signer against that pinned credential's secret (protected by the key ring outside the database and by the owner-only material trigger of D-235), never the session's MFA time;
        * re-enrolment of a registered signer invalidates the registration until the owner re-registers.
    * In both cases section 10 gains adversarial tests that use the system runtime role as well: minting a session, creating a user, assigning a role, writing the MFA time, re-enrolment. Section 5 and D1 must be rewritten to match.
    * Separately, and beyond T2: a holder of the runtime credentials can bypass MFA for any user application-wide. This belongs in the owner register as its own item (mitigations: a server-held key in the session-token hash, and a MAC over the session's user, MFA and company columns).
  * **Medium M1 (name resolution of invoker-rights code):** sections 4.4 and 8. The verifier and the message builder run in the CALLER's session. The guard forbids pinning `search_path` and writing `pg_catalog.`-qualified names. Correctness therefore depends on:
    * (a) every relation named with its schema (`public."..."`);
    * (b) the invariant that the runtime role has no TEMPORARY privilege and no CREATE anywhere, including on restored and newly provisioned databases (probe C: a TEMP table or a pg_temp domain shadows otherwise);
    * (c) a message that does not depend on session settings: TimeZone, DateStyle and IntervalStyle (the `not-after` timestamp), `bytea_output` (hashes via `encode(..., 'hex')`, never `::text`), `extra_float_digits` (no floats), `lc_numeric` (no `to_char` with D or G), and ORDER BY on uuid or integer columns, never on text.
    
    Resolution: state (a) to (c) as requirements and add tests for each (a session with every one of those settings changed must produce the same message; a TEMP shadow attempt must be refused).
  * **Medium M2 (canonical message underspecified):** section 4.3. `payload=` (the SHA-256 of the payload) (which bytes: json text, jsonb text?), `fingerprints=<the seven, in order>` (separator, encoding), `lines=` (the SHA-256 of the ordered plan lines) (row serialization, ordering, numeric scale) and `not-after=<UTC timestamp, seconds>` (exact format) are not specified byte for byte, as 0036 does for the closure hash. Without that, `replay_message` cannot be rebuilt or reviewed, and the application and the database can diverge. Resolution: a byte-exact specification of every field, at the level of the 0036 closure-hash comment.
  * **Medium M3 (key revocation semantics contradict themselves):** sections 4.4, 7 and 13. `replay_authorized` requires the key "not revoked", and the readers and the close probe call it for every execution. Revoking a key would make every epoch it ever authorized unverifiable, so the readers refuse and history becomes unreadable. Section 13 says such rows "remain verifiable". Resolution: an authorization time assigned by the database (trigger, `clock_timestamp()`), a revocation time from which the key stops being valid, rows before it stay valid, and an explicit owner decision on rows made between a suspected compromise and the revocation.
  * **Medium M4 (pinned fingerprints and read-side verification):** sections 4.1, 5 and 7. The readers, the close probe and the post-restore pass "call `replay_authorized`" inside the database. A database owner, or a restored database whose functions differ, can replace that function, so the pinned fingerprints protect only against a different key ROW. They protect neither against a different verifier nor against a restore that loads rows without triggers if the function is also altered. The row "Database owner ... detected" overstates this. Resolution: the readers, the close probe and the restore check verify the signature in the application (.NET) against the pinned public keys over the message they rebuild themselves, independently of database functions; correct the threat table.
  * **Low L1 (signature length not required):** section 4.2. Require `length(signature) = k` exactly, in addition to s < n. Otherwise the same signature has several encodings (probe B), and "the audit detail can carry the signature digest" is not unique. Also state: e = 65537 fixed, k = 384 fixed at registration, a constant DigestInfo, built-in `sha256`, `mod` only (never `/`), and known-answer and edge vectors (Wycheproof-style) in the test list.
  * **Low L2 (verified at insert, not at commit; transaction time):** section 4.4. A creation authorization verified by the BEFORE INSERT trigger can be followed by more closure or line rows in the same creating transaction (0036 allows them while the plan is proposed). The deferred check must therefore re-verify the signature at commit, not just find a row that was verified. `now()` is the transaction start, so a long-open transaction accepts an expired `not-after`: use `clock_timestamp()` and check again at commit.
  * **Low L3 (the execution signature does not bind content):** section 4.3. The execution message names the plan, the approval, the people and the closure, but not the lines, payload or fingerprints. For its 10 minutes, a leaked execution signature authorizes any epoch that 0036 accepts within the closure. Bind the approval's lines digest and the fingerprints, and state what 0036 binds of the replayed amounts.
* **Answers to the specific questions:**
  * **Hand-written RSA in PL/pgSQL:** acceptable, under L1's conditions and mutation tests. It is the only signature verification the guard allows: `pgcrypto` has none and extensions are refused. HMAC is rightly rejected. Verification handles public data only, so timing is not a concern.
  * **Replay and binding:** sound for plan, company (R cannot change the company identity), closure, revision and the single execution; see L2 and L3.
  * **Enforcement completeness:** no bypass found by R alone (SET CONSTRAINTS, session_replication_role, trigger disabling, TRUNCATE, COPY). The restore path depends on M4.
  * **Availability residual (unsigned cancel, reject, stale):** acceptable as recorded.
  * **Rejected option (a):** its rejection as the primary control is sound, but for a reason the document does not give (C1). Combining (a) and (b) adds defence in depth only against a leaked signature, not against C1.
  * **Migration:** one additive company migration, with no guard exception needed for the verifier as designed. A C1 resolution of type (ii) needs at least one SYSTEM migration (the signer registry) and owner decisions. Type (i) needs only the company migration and the offline tooling.
  * **Owner decisions:** D1 to D4 are not complete. D1 rests on a false premise (C1). Missing are: the signer registry and how signers authenticate (C1), the revocation semantics (M3), and the separate register item on runtime-credential session minting.
