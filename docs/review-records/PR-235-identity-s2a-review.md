* **Findings:** one High (H1), two Medium (M1, M2), three Low (L1 to L3) and information items. The core of the slice is sound: one write primitive; verification at the login lookups, the session lookup and the enrolment checks; security-reducing writers that never bless a row; fail-closed keys; rotation; no deadlock found. The mutations confirm the tests are load-bearing.
  * H1 (High), concern 1, IdentityTagging.cs, Hasm.Admin `identity-tag --confirm-reviewed`, plan section 14 (OD-3, D-242; plan section 7). Ruling: an OD-3 bypass. OD-3 requires that a named, authorized operator reviews the complete reconciliation report against the authenticated audit history, that suspicious records receive a documented disposition, and that "the authorized owner-account operation may tag only verified and approved records". Plan section 7 specifies `identity-tag --reviewed <report-hash>`, refusing unless the hash is that of a report produced from the current table state. The built command:
    * tags every row whose tag is NULL, with no report, no verification against the audit trail and no binding to what was reviewed;
    * records only counts, so the operator never sees which users were blessed;
    * is not limited to the upgrade: the runtime role can create "untagged" rows at any time, by INSERT or by setting KeyId and Tag to NULL.

    Probe A proves it: a runtime-minted identity administrator, and a tampered user made identity administrator whose tag was cleared, both sign in as identity administrators after one run. A `--confirm-reviewed` flag is an operator assertion, not the reviewed report. Required change, in this PR:
    * `identity-tag` must refuse, with a message that names OD-3 and slice S-2c, until the S-2c reconciliation report exists. It is then bound to the reviewed report hash and to the current table state, as plan section 7 says. The tagging function may stay for tests (preferably internal).
    * Plan section 14's rollout text must be corrected to agree with section 7 and OD-3.

    OD-3 says the appointment does not block development or testing: fresh installations work (bootstrap-admin creates a tagged administrator) and the tests can call the function directly; only an upgraded installation stays locked until S-2c, which OD-2 and OD-3 already require for a real rollout.
  * M1 (Medium), no recovery for a row whose tag does not verify; plan section 14 (restore text). A runtime-credential holder can make any or every user unverifiable with one UPDATE that the guard allows (e.g. SecurityRevision + 1), including every identity administrator. Nothing in S-2a recovers such a row:
    * identity-tag never re-tags a tagged row;
    * re-activation, password change, MFA transitions and code issue require an authentic row;
    * bootstrap-admin refuses while any identity administrator row exists, because AnyIdentityAdministratorAsync counts unverified rows.

    OD-5 accepts availability attacks as a threat-model boundary, so the lockout itself is accepted. But the plan says that after a restore under another key ring "users cannot sign in until the owner tags them again", and that is wrong for this command: those rows carry an invalid tag, not a missing one, so identity-tag tags nothing. Required: correct the plan text now and record the recovery as an open limitation. The recovery itself, a reviewed re-tag that also covers rows with an invalid tag after their disposition, belongs to S-2c together with H1.
  * M2 (Medium, not fixed in this slice; follow-up S-2d), concern 5. The forged enrolment challenge: the challenge row stores a plain SHA-256 of its token, so the runtime role can insert an Enrol challenge for any user. With a legitimately issued one-time enrolment code, the enrolment then begins without the user's password; the PR's own control in The_enrolment_code_columns_are_covered... gets 200. So a runtime-credential holder who learns a user's one-time code can bind his own authenticator and obtain that user's session. Writing his OWN code is now refused (the code columns are covered; proven by the PR's test and by the mutation above). Ruling: acceptable as a slice boundary only because plan section 14 states it openly and S-2 "closes vector B only with ... the challenge binding in place" (plan section 11). S-2a must not be described as closing vector B, and S-2d is a prerequisite of any release of the identity-integrity work.
  * L1 (Low), defence in depth: several security decisions re-read covered columns in a separate query without the tag, after the verified lookup:
    * AuthService login and the enrolment begin paths, through MfaStore.GetStateAsync and IdentityStore.GetMfaStateAsync;
    * GetMfaRequirementAsync (the admin flag);
    * PartyRegistryStore.IsCentralApprover;
    * the administrator-continuity reads (ReadStateAsync, CountActiveIdentityAdministratorsAsync);
    * AnyIdentityAdministratorAsync.

    None widens access today: the MFA graph guard of 0031 never lets a state go back to None (probe B); the administrator authorization uses the claim of the verified session (AdministratorPolicy), so IsCentralApprover can only deny; and the challenge-enrolment path also needs a code on a verified row. But they are time-of-check/time-of-use reads of tagged fields, and a later change could make them load-bearing. Recommended: take these values from the verified row, in S-2a or S-2b.
  * L2 (Low), concern 3, IdentityDatabaseTests.cs AfterExecAsync and RetagAllUsersAsync. After any test `Exec` that INSERTs or UPDATEs the user table, EVERY user is re-tagged, including a row an earlier `Attack()` tampered with in the same test. Today no test tampers and then calls Exec (the attack writes go through `Attack()`, which is not re-tagged), so no production gap is hidden. A future test could silently bless its own tamper, though. Recommended: re-tag only the rows the statement touched, or refuse when a row that does not verify exists before the re-tag.
  * L3 (Low): user-rejection audit events (1339, cause `tag`) are limited to once a minute per user and per process; the runtime role can mint any number of untagged users to grow the audit stream. This is bounded by its own INSERTs and is the same shape as the S-1 session limit. Recorded only.

Every writer of a covered field raises the revision through the primitive except the transparent password rehash, and the database guard of S-1 lets the revision only stay or grow by one, with an INSERT starting at 0. So a restored older row with a lower revision is refused (tested). The only same-revision older row is the pre-rehash hash of the SAME password, which the attacker can already read, so replaying it gains nothing.
