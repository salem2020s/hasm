* **Findings:** 0 Critical, 1 High (H1), 3 Medium (M1, M2, M3), 2 Low (L1, L2). Each is listed with its resolution.
  * **High H1 (the enrolment-code exclusion is unsafe; vector B is not closed).** Section 5 excludes the enrolment-code columns from the user MAC, justified as "they only matter while the covered MFA state is EnrolmentRequired, and the enrolment path additionally needs the user's own password or the emergency procedure". That justification conflates two paths. `BeginEnrolmentWithSessionAsync` (voluntary, from state None) needs the password; `BeginEnrolmentWithChallengeAsync` (the path for an EnrolmentRequired user) needs ONLY the enrolment code and an `enrol` challenge, both runtime-writable and neither in the plan's MAC scope. The probe takes over the enrolment of an EnrolmentRequired user and gets an MFA-fresh session with the runtime credentials alone. The affected set is exactly the high-value one: bootstrap administrators before first enrolment, new users, and every user after a recovery or DR reset. Verifying the user tag on the enrolment path is NOT sufficient, because the tag does not cover the code.
    * Resolution: include the enrolment-code columns (`EnrolmentCodeHash`, `EnrolmentCodeExpiresAtUtc`, `EnrolmentCodeConsumedAtUtc`) in the user MAC, so the runtime role cannot write a code that the challenge path will accept; AND add the challenge-based enrolment begin and confirm to the user-tag verification sites of section 5; AND state whether `mfa_challenge` rows need their own binding (M2). Add an adversarial test: a runtime-written enrolment code and forged `enrol` challenge for an EnrolmentRequired user, enrolment refused. S-2 cannot be said to close vector B until this is in the plan.
  * **Medium M1 (the IdentityAnchor can be used to lock a subject out).** The runtime role holds INSERT on `IdentityAnchor` (section 10). The verifier requires `row.Revision >= max(anchor.Revision)` for the subject and a valid anchor tag, but the plan does not say over WHICH anchor rows the max is taken. If it is taken over all rows, a single forged anchor with a huge `Revision` and a garbage tag permanently fails every real row for that subject, and the append-only rule means it can never be removed: a per-subject denial of service (a locked-out administrator, an unverifiable user) writable by the runtime credentials. This is the "higher revision that locks a user out" the brief asks about.
    * Resolution: state that the max is taken over VALID-tagged anchors only, that an invalid-tagged or unknown-key anchor is ignored for the bound and alerted (not a 503 and not a lockout), and that a valid tag over `(Kind, SubjectId, Revision, KeyId)` is required for a row to count. The runtime role then cannot raise the bar (no key) nor lower it (no DELETE). The key-ring monotonic-counter alternative is worse: the ring is a key store with no per-subject mutable counter, and it would add per-subject write state to key custody; the in-database anchor with "ignore invalid, max over valid" is the right shape once specified.
  * **Medium M2 (the MfaChallenge table is entirely outside the plan).** The runtime role holds SELECT, INSERT and DELETE on `mfa_challenge`, and the plan protects none of it. Forged `enrol` challenges are the sibling gate exploited in H1. A forged `login` challenge does not help (login still needs the password), but the `RecoveryRequest` purpose is defined and is not analysed in the plan. A forged challenge token hash is a plain SHA-256, so the attacker also chooses the token.
    * Resolution: analyse each `MfaChallengePurpose` against a runtime attacker who can insert challenge rows, and state for each why it is gated by a key-backed secret (the password, or the keyed enrolment code of H1, or the TOTP secret) or bind the challenge row (keyed token hash and a MAC over user id, purpose and expiry). At minimum, fixing H1 closes the demonstrated enrol path; the table must still be covered by the threat analysis.
  * **Medium M3 (one-time tagging can bless a resurrected row).** Section 7 flags a row as an orphan only when it has "no audit event that explains it". A legitimately revoked grant (an administrator assignment, a membership) HAS a grant event in the audit stream; a copy re-inserted by an attacker before rollout therefore matches that event and is tagged as legitimate, even though a later revocation event ended it. The audit chain is HMAC-chained and cannot be forged, but the report must reconcile the CURRENT row against the NET of grant and revocation events, not against the existence of a grant.
    * Resolution: `identity-audit-report` computes, per subject, the net state from the ordered grant and revocation events and flags any live row that the net state does not support (a resurrected or never-revoked-in-the-chain row), not only rows with no event at all. Add a test: a row matching an old grant event whose later revocation event exists is flagged, not tagged.
  * **Low L1 (count inconsistency).** Section 3's heading says "three purpose-bound subkeys"; the table and the rest of the plan use four (`identity-token`, `identity-session`, `identity-user`, `identity-access`). Fix the heading.
  * **Low L2 (verification-site completeness for the session issue).** Section 4.2 lists the session change sites but not `ActivateAndIssueAsync`, which issues a session at the end of enrolment and step-up-less first login. Confirm it goes through the same tagged issue primitive, and name it, so the list is demonstrably complete.
