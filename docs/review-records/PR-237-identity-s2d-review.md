* **Findings:** one Medium (M1), two Low (L1, L2) and information items. The binding itself is sound:
  * a challenge row the runtime role writes (a chosen token, a plain hash, a random or borrowed tag, any changed covered field) is refused, burned and audited;
  * the token hash is keyed, so the role cannot even address a row with a token it chose;
  * the keyed token hash is UNIQUE (0033), so a duplicate of a genuine row cannot be planted;
  * no key fails closed at issue and at attempt.
  * M1 (Medium), the challenge table: DELETE and re-INSERT reset the attempt counter and undo the single use (proven above). The tag does not cover the counter or the consumption time. 0033's guard protects them only against UPDATE ("never decreases", "consumed at most once"), and the runtime role holds DELETE and INSERT. Re-inserting a deleted genuine row carries its valid tag, so it verifies with a fresh budget and no consumption. The plan section 15 therefore states something false: "the database already refuses to lower the counter".
    * The impact stays within the second factor: a Login challenge still needs the user's TOTP code (the TOTP last step is guarded by 0031, so a used code cannot be replayed), and an Enrol challenge still needs the one-time code of the verified user row. Exploiting the reset also needs the challenge token, which only the client that did the password step holds.
    * But it converts the per-challenge budget into unlimited guessing for a holder of the token, and it makes "single use" false. That is more than the S-2b gap as stated, which concerns the throttle rows.
    * Required in this slice: an additional BEFORE DELETE trigger on the challenge table (a new function in 0039; 0033 is not replaced) that refuses to delete a challenge whose expiry has not passed (`OLD.expires >= clock_timestamp()`). The API's only DELETE purges expired rows (MfaChallengeStore line 127), so it keeps working, and re-inserting an expired row gains nothing because the expiry is covered. Add the reset test (the probe above), correct the plan sentence, and name the remaining throttle-row gap as S-2b.
  * L1 (Low), ChallengePurposeSourceScanTests: the scan is weaker than plan section 15 says (proven above).
    * The call-site count skips any call whose argument list does not literally contain `MfaChallengePurpose`, so a call with a variable purpose is not counted.
    * The purpose check only matches `MfaChallengePurpose.<Name>`, so a cast `(MfaChallengePurpose)2` slips through.
    * The store file is excluded entirely, so a new method inside the store goes unseen.

    The runtime safety does not depend on the scan, because no API input selects a purpose. But it is the pin the plan relies on against a silent new caller. Recommended:
    * count every `.TryBeginAttemptAsync(` (the name is unique to the store) and every `Challenges.IssueAsync(` regardless of arguments, and require a literal `MfaChallengePurpose.Login` or `.Enrol` in each;
    * refuse any `(MfaChallengePurpose)` cast and any `Enum.Parse` or `Enum.TryParse` of the enum outside the store;
    * scan the store too, allowing only its own definitions.
  * L2 (Low), MfaChallengeStore.TryBeginAttemptAsync: the rejection audit is limited to once a minute per challenge id and per process (as for users and sessions); the runtime role can insert any number of junk rows, but they only reach the audit when someone presents their token, and the role cannot address its own rows (keyed hash), so the stream cannot be flooded through this path. Recorded only.

    * a Login challenge still needs the user's TOTP code;
    * an Enrol challenge still needs the one-time code of the verified user row, which the role cannot write;
    * the PR 235 M2 path is refused through the real API.

A forged RecoveryRequest row is inert because nothing begins an attempt for that purpose and no API input chooses one. Nothing else stays unreachable.
