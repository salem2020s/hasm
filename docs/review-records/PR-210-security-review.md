* **Findings:** 0 Critical, 0 High, 1 Medium, 2 Low.
  * **M1 (Medium, owner recognition accepts a self-granted row):** any role that holds TRIGGER WITH GRANT OPTION on the table (for example after a broad `GRANT ALL ... WITH GRANT OPTION`) and UPDATE on the secret columns can grant TRIGGER to itself and then pass the owner test, defeating the guard's stated purpose ("even if it were wrongly granted UPDATE ..."); reproduced above. The 0031 flag is no second barrier (any role can set it), and PR 201's check only detects. Fix (verified): require `p.is_grantable = 'YES'` on the grantor = grantee row; the owner's implicit row has it, and PostgreSQL refuses a non-owner's self-grant with grant option. Add a regression test for the self-grant attack; update the migration comment and the PR's residual 2 accordingly.
  * **L1 (Low):** the `CASE ... pg_has_role(current_user, grantee, 'USAGE')` clause is redundant with the view's own visibility rule (a row is visible only to members of its grantor or grantee). It is harmless and unexploitable through shadowing (P2), but the comment should say the view's filter is what decides.
  * **L2 (Low, not verified):** the non-inherit or SET-only member case (PostgreSQL 16 membership options) could not be set up on the test cluster (the test role-admin may not grant the owner role). By the view's `USAGE` rule such a member sees no row and is refused unless it uses `SET ROLE` to the owner, which is the intended fail-closed behaviour; a test would pin it.
