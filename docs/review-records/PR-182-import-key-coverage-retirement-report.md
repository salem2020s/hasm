* **Findings:** High H1 (`EncryptionKeyRetirementService.ReportAsync` with `RetentionService.Scan`/`Plan`; fail-open): a backup root that does not exist, or exists but is empty, is evaluated as a COMPLETE inventory with no keys needed. `Scan` returns no runs for a missing directory (`if (!Directory.Exists(root)) return`), and `KeyInventoryComplete = retained.All(...)` is true over no runs. So an operator typo in the root path, a not-yet-mounted share, or the wrong folder makes the report say RETIRABLE for keys that the real root's retained runs still need. Proven by the probe above; the PR's own test exercises the empty-directory variant as a success case. The "at least one backup root" blocker is therefore only nominal. The same reasoning covers data the report never sees: roots not passed (other destinations) and standalone `backup-company` sets (not runs), which can contain attachment envelopes under the key. This defeats the purpose of the report (D-082/register item K: never retire a key that retained data needs) even though retirement itself is not built. Fix: a missing or symbolic-link root is a blocker (`backup_root_missing`), and a root with no complete, verified run is a blocker (`backup_root_empty`), or needs an explicit acknowledgement flag. Consider requiring the configured roots. State in the output and the docs that standalone sets and roots not given are NOT covered. Add a test for both.
