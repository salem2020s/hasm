* **Findings:** 0 Critical, 0 High, 5 Medium, 3 Low.
  * **M1 (Medium; prompt point 1): the `EpochWriteScope` mechanism is named, not specified or proven.** An `internal` class is constructible by any code of `Hasm.Infrastructure` (and by every assembly named in `InternalsVisibleTo`). The real gate must be, and the plan should say it is, the database condition the engine re-reads at each entry write: the entry's operation is an `EpochMember` of an execution whose `created_xact` is this transaction (from the runtime role this needs INSERT on the four tables, which it lacks until E5). Required in E2a: (a) the engine checks the database condition per entry even when a scope is present (the scope alone never opens the barrier); (b) the scope is sealed with a private constructor, created only by a factory of the executor that is bound to one `CompanyAuditedWork` and transaction and refused with any other; (c) tests: a scope without a member row still answers `backdated_not_supported`; a scope created for another transaction is refused; an IL or reflection scan (like the 1154 scan of `PlanExecutionDisabledTests`) shows that only `CompensationPlanExecutor` references the factory; mutation proofs for removing the member check and for removing the transaction binding.
  * **M2 (Medium; prompt points 1 and 2): changes to existing production paths are understated.** The plan calls E2a "the one change to existing production code", but the slices also change: the NORMAL posting function `PostInWorkAsync` (the plan-scoped member hook and `GREATEST`, E2b); the normal posting service's answer `document_bound_to_plan` (N13 "service answer", E3; today only the database raises it); the reversal service's answer `operation_rewritten_by_epoch` (N14 and N27 "service part"; not in C# today); and the snapshot readers' refusal of histories with epoch members (design section 6). Each touches a path every ordinary posting or reversal uses. Fix: list them as changes to existing code, give each the E2a treatment (ordinary-path pin, the whole posting/reversal/costing suites unchanged, mutation proofs) and show each is inert while no plan or epoch exists.
  * **M3 (Medium; prompt point 6): the X8/D-215 test names a counting path that does not exist, and the compensation journals are not covered.** `TrialEntitlementPolicy` has `posted_business_transactions` `NotEnforced` ("No posting module exists yet"; Phase 4.2 builds it), so E3's "test through the entitlement counting path" cannot be written, and CI (which creates the automatic compensation journals, which D-215 says "do not count separately") has no X8 test. Fix: in E3 and CI pin the structural facts a counter will rely on (the event's document has exactly one stock posting; epoch operations carry no document or posting of their own; compensation journals carry a system source key that marks them as automatic) and record in the handoff, as a binding input to Phase 4.2, that its counter must count each user-originated posted business transaction once and exclude epochs and compensation journals, with a test then.
  * **M4 (Medium; prompt points 2 and 3): E5 gives the runtime credential the T2 capability while nothing calls the executor.** After E5 there is still no endpoint, UI or preset, yet the INSERT grant on the four tables lets any holder of the per-company runtime database credential write a well-formed back-dated epoch (with a raw plan, approval and audit row). The grant has no product use until a caller exists. Fix: E5 registers the executor and runs the full matrix under production grants in its tests, but the runtime catalog grant ships with the first real caller (the endpoint slice), together with the owner's decision on T2 below. On M-B: as specified in design 3.6 it does NOT close T2 against a holder of the runtime credential (that role holds EXECUTE on the definer, and the database cannot authenticate the application user), so it should not be a precondition of enabling. What a database-only attacker cannot forge is the audit authentication code, whose key lives outside the database. **Owner question (proposed wording):** "Before compensation-plan execution is enabled, do you accept that a holder of the company's runtime database password could write a complete, well-formed back-dated replay directly in the database, provided that (a) every execution must carry its audit event, whose authentication code is made with the audit key held outside the database, and (b) a fiscal period cannot be closed while it contains a replay whose audit event does not verify against that key? Or do you require prevention inside the database (the SECURITY DEFINER writer of design 3.6, which needs a `search_path` exception to the migration guard under the Q5 security process), knowing that it does not stop an attacker who controls the application process itself?" If (a) and (b) are chosen, (b) belongs to slice P and needs its own test.
  * **M5 (Medium; design T8): the lock order conflicts with the audit-stream rule.** `CompanyAuditedWork.AppendAuditAsync` takes the business stream lock immediately and requires it to be the LAST lock of the transaction; the plan appends audit 1154 at step 4 (the execution row must name it), and `PostInWorkAsync` appends the posting's own audit event at step 6; after that, rebook (FIFO layer rows), the event's own posting locks (document row, warehouses, items, units) and CI's compensation journals (numbering counters) take further locks. An ordinary transaction that holds such a lock and waits for the stream lock deadlocks with the executor. The plan's section 8 still says the stream lock "stays the last lock". Fix: either take every lock that steps 5-8 and CI need in step 2 (enumerated in E3, with a concurrency test against an ordinary posting and an ordinary journal creation), or let the 1154 event be appended last (the execution table has no foreign key to the audit event; the deferred check verifies it at commit) with the audit trail able to pre-allocate its id; in both cases the posting's own audit append inside the event savepoint must be accounted for.
  * **L1 (Low; prompt point 5):** every N test is assigned to a slice, but the plan names numbers, not the tests that prove them; and "rollback injected at each step of section 5" omits points that matter: between a member row and its entries, inside the event savepoint (rolled back and continued: N9), mid-storno and mid-rebook, a verification mismatch, a failure of CI's journal writer, a failure at commit (deferred check), cancellation, and a failure of the stale-marking transaction.
