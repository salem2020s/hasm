* **Findings:** **High H1** (src/backend/Hasm.Infrastructure/Backup/FileIdentity.cs, Windows branch, struct ByHandleFileInformation): the struct is declared with three long fields after a uint, so it is not the layout of BY_HANDLE_FILE_INFORMATION (the FILETIME fields must be 4-byte aligned; use FILETIME-like uint pairs or Pack = 4). On Windows the fields are read from the wrong offsets: Volume is read from the high word of the file size (almost always 0), Index becomes the native low index word shifted left by 32, and Links is read from the native high file index word, which is the NTFS sequence number shifted left by 16 plus the high record bits and is above 1 for ordinary files. Effect on Windows: VerifyStoredAsync sees Links > 1 on every file and reports every copy as CORRUPT (link), so backup-replica-verify, the re-verification inside backup-replicate and the status (copies no longer count as verified) fail on a good copy; and ReplicaIndependence compares a bogus volume (0 for both) and a half index, so false replica_not_independent is possible. The direction is fail-closed, so no unprotected copy is passed, but it is a regression on a first-class platform: before this PR the Windows count was null (nothing claimed). The PR text says the Windows path is untested, which is right, and this shows why. Fix: correct the struct (FILETIME as two uints, or [StructLayout(LayoutKind.Sequential, Pack = 4)]), add a unit test that asserts Marshal.SizeOf is 52 and the offsets (runs on Linux), and keep the Windows branch disabled (return null) until it is verified on Windows. **Low L1** (ReplicaCopier replicate path): the new refusal uses only .Shares; an Unavailable result there proceeds to the re-verification, which reports link_check_unavailable through its own result, acceptable. **Low L2:** reflinked clones are not detected (stated in the docs).
