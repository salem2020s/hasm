  * **L1 (Low), `src/frontend/packages/ui/src/Tabs.tsx` line 44 (`focus()` before `setInner` / `onChange`). Open, follow-up.** At the moment of the focus event the target tab still has `aria-selected="false"` and `tabindex="-1"`; both are corrected by the render of the same key event. Assistive technology that reads the state synchronously on focus could announce the tab as not selected; before this PR the order was selection first, focus after. Possible fix: commit the selection first (`flushSync` around `setInner` / `onChange`) and then focus, still inside the key event. Effect with a real screen reader not measured (see NOT VERIFIED).
  * **L2 (Low), `Tabs.tsx` `select` and `onKey`, controlled use. Open, not a regression.** When the owner keeps `value`, focus rests on a tab that is not selected, and the next arrow key is computed from `active`, not from the focused tab, so it targets the same tab again. Identical end state before this PR; no consumer does this today. Possible fix: in controlled mode focus the tab only after `value` has changed (an effect keyed on `active`, set by a "keyboard" flag), or document that a vetoing owner must restore focus.
  * **L3 (Low), `src/frontend/apps/web/src/pages/CompanyDetails.tsx` line 42. Open, outside this diff.** The older hand-written tab strip still focuses inside `requestAnimationFrame` after `go(next)`, the same race this PR removes from the shared component. Fix: focus synchronously there too, or migrate the screen to `Tabs` when next revised, as `docs/PHASE-UI-1.md` already plans.
  * **L4 (Low), `src/frontend/packages/ui/src/Tabs.test.tsx`, third and fourth new test. Open, informational.** On the old component the third test fails at its first focus assertion (focus had not left the old tab, so Tab went to the newly selected tab button), not at the assertion after the frame; the fourth fails only through `expect(raf).not.toHaveBeenCalled()`, its behavioural assertions pass on the old code too (the old callback found no list after unmount).
