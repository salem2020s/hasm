# Phase 3.1B — Branch schema, migration, backfill, RBAC, API and UI — **APPROVED; implemented and tested on the disposable cluster; not applied to any permanent database**

Owner decisions (2026-11-13) are incorporated. Status per part: **[B]** schema, initialization, domain service; **[C]** RBAC, activation epochs, authorized facade and API; **[D]** shared Web/Desktop UI - all implemented and tested on the disposable cluster. Physical names follow the existing convention (opaque names in `CompanySchema.Branches.cs`; logical names are used below). Forward-only, checksummed migrations; no change to global PostgreSQL settings. **No migration has been applied to any permanent development database.**

## Approved decisions
1. **Option A** — the main branch is created by migration/provisioning, not by a user action. Provenance is recorded in the row (`seed_migration = 4`, the version in the migration journal). No business audit event is fabricated.
2. **Names:** at least one non-empty name, Arabic or English; both may be given; display uses the existing bilingual fallback (`CompanyNames.Display`).
3. **Code:** immutable; normalised to upper case (`A-Z 0-9 - _`, 1-20 characters, not starting with `-`/`_`); unique case-insensitively within the company.
4. **Seed:** code `MAIN`, Arabic `الفرع الرئيسي` (stored in logical Unicode order, written as `U&'\0627\0644\0641\0631\0639 \0627\0644\0631\0626\064A\0633\064A'`), English `Main Branch`.
5. **ActivationEpoch** increases on both deactivation and reactivation.

## 1. Company migration 0004 [B]

**`Branch`:** `id` uuid PK (`gen_random_uuid()`, stable, never reused/deleted); `code` varchar(20); `name_ar`, `name_en` varchar(200) NULL with a CHECK that at least one is non-empty; `is_active`; `is_main` with CHECK `NOT is_main OR is_active`; `activation_epoch` bigint >= 1; optional `address_line1/2`, `city`, `region`, `postal_code`, `phone`, `email`, `website` (same lengths/validation as the company profile); `seed_migration` smallint NULL (only `4` allowed); `revision` bigint; `created_at`, `updated_at`.

**`BranchRevision`** (append-only history): `branch_id` (FK to `Branch`), `revision`, actor, time, `changes` jsonb, and the composite foreign key to the business audit event written **in the same transaction** (unique, so one revision <-> one event). Row and truncate triggers refuse change even for the owner.
*Design adjustment (needs owner acknowledgement):* branches get their own revision table instead of extending `ConfigRevision`, because widening `ConfigRevision`'s entity check and key length would require `DROP CONSTRAINT`, which the migration framework forbids by design (and which must not be weakened). `BranchRevision` keeps the same guarantees as `ConfigRevision` (append-only, audit-event link) and adds a real foreign key to the branch. The history API of Checkpoint C reads both tables.

**Integrity enforced by PostgreSQL itself:**
- **At most one main:** partial unique index on `is_main`.
- **At least one (exactly one active main):** deferrable constraint trigger (`INITIALLY DEFERRED`) after every insert/update counts active main branches at commit. Deferral makes a swap (unset old, set new) atomic. The migration's final guard and the API schema gate cover the "zero branches" state, which row triggers cannot see.
- **Code:** `UNIQUE (upper(code))` plus the upper-case CHECK; immutable by trigger.
- **No deletion:** `BEFORE DELETE` and `BEFORE TRUNCATE` triggers raise, owner included.
- **Revision fence:** an update must advance `revision` by exactly 1.
- **Epoch rule:** `activation_epoch` must advance by exactly 1 when `is_active` changes and may not change otherwise; `id`, `code`, `created_at`, `seed_migration` are immutable.

## 2. Automatic main branch and existing-company backfill [B]
The migration inserts the main branch `WHERE NOT EXISTS (SELECT 1 FROM Branch)` and ends with a guard that raises unless exactly one active main branch exists; the migration runs in its own transaction, so any failure rolls everything back and the company stays at 0003.
- **New company:** provisioning applies all company migrations **before** the company is marked Ready, so a company never becomes operational without its main branch.
- **Existing company:** `migrate-companies` applies 0004. It creates two new tables and one row; no existing table is altered and no existing row, audit event or credential is read for modification. Re-running is a no-op (journal + `WHERE NOT EXISTS`); an interrupted/repeated run of the seed statement changes nothing (tested).
- **Seed revision and audit:** revision 1, no `BranchRevision` row and no audit event for it (it is not a user action). The first audited change writes revision 2 with before/after in `BranchRevision` and one audit event; from then on every revision has exactly one event.
- **Fail-closed gate:** the API schema gate refuses (`company_schema_incompatible`) any company that does not have exactly one active main branch; it never repairs data.

**Procedure for the permanent development databases (NOT yet executed; needs separate explicit approval):**
0. Logical backup (`pg_dump`) of the system database and the company database to a folder outside the repo; record the before-snapshot (database list/OIDs and per-table row counts, as taken before this work).
1. Deploy the new backend build (the API reports `company_schema_unmigrated` for the company until step 2, by design).
2. `migrate-companies` -> expect `Migrated (applied 0004)` for the dev company (it is at 0003), exit code 0.
3. `grant-company-runtime <company-id>` (adds the Branch/BranchRevision grants; until then the gate reports `company_runtime_not_provisioned`).
4. Verify: exactly one active main branch (`MAIN`, revision 1, epoch 1, `seed_migration = 4`); every pre-existing table's row count unchanged; `audit-verify business:<id>` clean; the API opens the company.
5. Roll-forward only. A failed step 2 leaves the database exactly as before. Recovery after a bad commit = restore the step-0 backup (existing restore limitations apply). No down-migration, per convention. An older backend refuses the newer database.

## 3. Runtime privileges and schema gate [B]
`CompanyRuntimePrivileges.Tables`: `Branch` SELECT, INSERT, UPDATE; `BranchRevision` SELECT, INSERT. Never DELETE/TRUNCATE/REFERENCES/TRIGGER/DDL, no ownership. `grant-company-runtime` converges; the gate reports `branch_modifiable` / `branch_history_modifiable` for extra rights and refuses the overprivileged role. `ConfigurationSchemaContractTests` registers both tables.

## 4. Domain service [B] and audit
`CompanyBranchService` (no authorization by design; Checkpoint C wraps it): create, update, deactivate (main only with an active successor, atomically), reactivate, make-main (atomic swap). Every change runs in `CompanyAuditedTransactions` after one transaction-level advisory lock that serialises all branch-structure changes (taken before the audit-stream lock): change, `BranchRevision` row and audit event commit together or not at all. Events: 1007 created, 1008 updated, 1009 deactivated, 1010 reactivated, 1011 main designated, 1012 main revoked (a main change writes two events because one revision is linked to exactly one event). Sensitive fields (address lines, postal code, phone, email, website) are recorded as "changed" only, never their values; names, city, region, flags and epoch keep before/after.

## 5. Trial limit [B]
`IEntitlementPolicy.MaxBranches` (Trial = 1, enforced; `/entitlements` reports it). Evaluated in the creation transaction under the lock: refused (`entitlement_denied`) when the count of **all** branch rows, active or not, has reached the limit. Rows cannot be deleted (triggers + no privilege), so deactivation never frees a slot; the seeded main branch is the one Trial branch, so a Trial company cannot create another or escape by deactivating the first. Paid editions override `MaxBranches` later; no other licensing change is made. (A database superuser who disables triggers can still delete rows; that is outside the application's control, as for the audit table.)

## 6. Branch-scoped RBAC and ActivationEpoch [C — implemented]
- **System migration 0007:** permission codes `company.branches.view`/`.update` (Branch granularity), `.create`, `.status`, `.set_main` (company granularity); history reuses `company.config.view`; presets receive them like the matching `company.profile.*` codes. Role assignments gain `scope_epoch` (NULL for company scope, required for branch scope); the "one active assignment" unique index is rebuilt to include it so a stale assignment can never block an explicit new one. The migration aborts if any branch-scoped assignment already exists.
- **Rule:** a branch-scoped grant is effective **iff** the branch exists in this company, `is_active`, and `activation_epoch = scope_epoch`. Evaluated on every request, no cache (revocation is therefore immediate for existing sessions and requires no cache invalidation). Deactivation and reactivation each bump the epoch, so older assignments stay recorded but permanently inert; access returns only through a new, authorized assignment that records the new epoch.
- **Cross-database separation:** branch state lives in the company database and assignments in `Hasm_System`; no cross-database transaction is assumed. The branch validator reads the company database through the existing resolver; if it is unavailable, **branch-scoped grants are dropped (fail closed) and are never reinterpreted as company-wide access**; independently valid company-wide grants keep working under the existing rules. A branch deactivated between validation and insert yields an assignment whose epoch is already stale, hence inert.
- `DenyAllScopeTargetValidator` is replaced by the branch validator (existence + active + epoch); Warehouse scope stays deny-all (3.1C).

## 9. As built (Checkpoints C and D)
- **System migration 0007:** `scope_epoch` on role assignments (required for branch scope, NULL otherwise, immutable by trigger, CHECK-enforced), the five branch permission codes on the preset Company Administrator, refusal to run if branch-scoped assignments exist. No `DROP` (the migration rules forbid it), so the existing one-active-assignment index is kept: assigning a branch role retires (audited as a revocation, "stale activation epoch") any same user/role/branch assignment recorded under an older epoch, in the same transaction, so a dead row never blocks the explicit new assignment and never becomes effective.
- **Permissions:** `company.branches.view` / `.update` (branch granularity), `company.branchstructure.create` / `.activate` / `.designate` (company-wide only). Added `PermissionAction.Activate` and `Designate` (appended; existing values unchanged). Deactivating the main branch with a successor needs both `activate` and `designate`.
- **Effective permissions:** `AccessService` drops a branch-scoped grant unless the validator reports the branch active with the recorded epoch; any error drops it (fail closed, never company-wide). `CompanyBranchScopeValidator` reads the company database through the company's own role; it is resolved lazily so hosts without a company runtime still start. `IScopeTargetValidator.GetStateAsync` has a default (constant epoch 1) for test validators; production uses the real one.
- **API:** `/api/v1/company/branches` (list with `can` capabilities, limit and ever-created count; create 201 + ETag; get; update; `/deactivate` with optional `newMainId`; `/activate`; `/make-main`). 404 `branch_not_found`, 409 `branch_code_taken` / `main_branch_deactivation_denied` / `branch_inactive` / `branch_already_*`, 403 `entitlement_denied`, 412 with `currentRevision`, 428, 400 with field errors.
- **UI (one shared React implementation for Web and Windows Desktop, UI-1 components, no new styles):** Branches screen at `#/company/branches` (menu entry under Company, shown also to branch-scoped users) with list, search, status filter, create/edit/view form, main designation, activation/deactivation with confirmation (successor picker for the main branch), RBAC-aware controls from the server's `can`, Trial limit notices, Arabic RTL / English LTR, validation, server error mapping, optimistic-concurrency conflict handling and unsaved-change protection (navigation, close, Tauri window close). Platform differences stay in the existing adapters (cookie vs bearer token).
- **Known limitations:** (1) the existing `/history` endpoint reads `ConfigRevision` only; `BranchRevision` rows exist and are audited but are not yet shown in the history screen (needs a combined history query); (2) a deactivated branch's stale assignments stay listed until retired by a new assignment or revoked; (3) warehouses and fiscal periods are out of scope; (4) existing permanent development databases are not migrated (separate approval required).
