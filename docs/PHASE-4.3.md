# Phase 4.3 - Backup and restore (in progress)

Sources: SRS 14.4, 16.1, 16.2, 16.4; Scenarios 21.8, 21.10; PHASE-3.12 (backup coordination, decision K).

## Slice 1 (this change): coordinated company backup set
`Hasm.Infrastructure.Backup.BackupSet`: a set directory with `database.dump`, `attachments/<32 hex>.att` (active AND removed attachments) and `manifest.json` (written last). The manifest has the company id, hashes and sizes, the master key ids the sensitive attachment envelopes need (never key material) and a count of skipped stray files.

* `Verify` names missing, altered and unlisted files by generated name only.
* `RestoreAttachments(set, target, expectedCompanyId)` verifies the whole set, refuses a set of another company (`company_mismatch`), writes only to an empty target outside the set (staged, re-hashed, then moved), never merges or touches other company folders.
* `CheckKeys` / `ListKeyIds` compare the needed key ids with a restored key directory (names only). Decision K: a key a retained attachment needs must be in the key backup.
* Symbolic links are refused; overlap checks use resolved paths; a failed create removes the partial set.

## Slice 2: database half and hardening
* `PgBackupTool` (Hasm.Infrastructure.Backup): `DumpAsync` (custom-format pg_dump of one company database, `--no-owner --no-privileges`) and `RestoreIntoNewDatabaseAsync` (creates a NEW database, pg_restore into it, drops it again when the restore fails). Refuses an existing target, the source, the system/maintenance/built-in databases. Admin credential only, passed in the child environment (never the command line); tool output is never copied into errors. The restored copy does not carry the source roles; the runtime role is re-applied by `grant-company-runtime` before any cutover (cutover itself is not built).
* Drill (`BackupRestoreDrillTests`, disposable PostgreSQL only): dump, set, verify, restore database and attachments to new targets; another company database proven unchanged; refusal cases; failed restore leaves no database. Needs the PostgreSQL client tools on PATH.
* Hardening of slice 1: optional-parameter seam instead of a static hook; header-plus-size envelope classification (no whole-file read); `RestoreResult` and `BackupVerification.NonEnvelopeFilesWithMagic` surface the counter; manifest without the counter still reads; `RealPath` repeats until stable.

* Review of PR #78 (fixed): the drill proves isolation by a catalog-and-content digest (tables, exact row counts, row hashes) of the source, another company database and the system database before and after; a restore whose half-created target cannot be dropped reports `restore_failed_cleanup_failed`; the restore path must be absolute; a creation race maps to `target_exists`; the target is created from `template0` with the source encoding; tool output goes to a null stream; the child process gets only `PATH`, `SystemRoot` and `PG*` variables; a cyclic symbolic link is a BackupException; CI asserts that `pg_dump`/`pg_restore` have the server's major version (docs/CI-RUNNER.md notes the client-tool requirement).

* Review of PR #78, round 2 (fixed): the child environment is built by a pure, unit-tested method; in verify-ca/verify-full mode without a configured certificate `PGSSLROOTCERT=system` is set (libpq 16+ only; without HOME the tools could not otherwise validate TLS) and a missing certificate makes the tools fail; `PGCONNECT_TIMEOUT` is set; libc collation/ctype of the source are copied (validated) and the drill compares encoding and locale; a failed cleanup keeps the original cause (`BackupException.Cause`); the SQLSTATE mapping and the cyclic-link refusal are tested.

* Review of PR #78, round 3 (fixed): PostgreSQL 14+ is supported and the tool fails closed. The locale provider is read through `to_jsonb(d)->>'datlocprovider'` (the column exists only from 15; absent means libc); `PGSSLROOTCERT=system` is used only when the tool's client major version (read from `--version` before the tool runs) is at least 16; for an older or unknown client in verify-ca/verify-full mode without a configured certificate the call is refused with `ssl_root_certificate_required` (wording corrected in round 4: the refusal follows the `--version` probe, which does launch the binary, and precedes any connection or CREATE DATABASE); an ICU/builtin locale provider, a missing locale or an unexpected locale name is refused with `locale_unsupported` instead of silently using the template0 default (libc names with spaces, such as Windows locales, are reproduced); `UnauthorizedAccessException` while resolving a path is `path_unresolvable`.
* **Decision (standing authorization of the lead, 2026-11-21): keep PostgreSQL 14+ support, fail closed.** Rationale: HASM documents 14+ as supported, and a backup tool that only worked on 16+ would silently shrink that promise. Alternatives rejected: (a) raise the supported minimum to 16 (a product decision outside this slice, and it would strand deployments on 14/15); (b) always set `PGSSLROOTCERT=system` (breaks libpq < 16); (c) fall back to a weaker `sslmode` when no certificate is configured (a TLS downgrade, never acceptable). Operators on 14/15 with verify-ca/verify-full configure a certificate path (`Hasm:Database:SslRootCertificate`).
* Review of PR #78, round 4 (fixed): on PostgreSQL 15+ the CREATE DATABASE clause pins `LOCALE_PROVIDER libc` (template0 may be ICU/builtin there; PostgreSQL 14 has no keyword and only libc). The keyword is chosen by the TARGET server's major version, not by whether the source provider is known: a source captured on 14 (no provider column, libc by definition) restored onto 15+ must be pinned as well. The drill also compares the provider. The client-version probe and the child environment are prepared BEFORE CREATE DATABASE, so `ssl_root_certificate_required` never costs a create/drop round trip. Every tool process (probe and run) gets a fixed working directory (`/`, or the Windows system directory), never the inherited service directory. The probe cache is a `ConcurrentDictionary`. The locale-name rule uses `\A...\z` (a trailing newline is refused) and allows `(` and `)` (Windows names such as `Chinese (Simplified)_China.936`; safe inside the quoted literal). Process wiring is now tested with fake POSIX tools (`PgBackupToolProcessTests`): the environment and working directory a started tool sees, no credential on its command line, the probe, its cache, the refusal order before any database contact, the exit-code mapping and the timeout kill.
* **Decision D-053 (standing authorization D-048, lead, 2026-11-21): the source database locale is captured at dump time and carried by the backup set.** `PgBackupTool.DumpAsync` reads encoding, LC_COLLATE, LC_CTYPE and locale provider of the source (before the dump; a missing source is `dump_failed`) and returns them; `BackupSet.Create` stores them in the manifest as an optional `databaseLocale` record (manifest version unchanged; an older manifest without it reads with null; a malformed stored record invalidates the manifest, `invalid_database_locale` at creation). `RestoreIntoNewDatabaseAsync` uses the captured values; only when they are absent does it read the live source, and when that does not exist either it refuses with `source_locale_unknown` before anything is created. Rationale: a restore is a disaster-recovery operation and must not depend on the source database still existing; the manifest already is the validated description of the set, so this adds one optional record and no new file. Alternatives rejected: (a) read the locale from the dump's TOC (the custom-format archive does carry the source's CREATE DATABASE entry, but using it means extracting and parsing SQL text produced by the tool, which this class deliberately never reads or keeps, and its correctness would depend on the pg_dump version's statement format); (b) refuse every restore whose source is gone (defeats disaster recovery); (c) fall back silently to template0 defaults (a silent collation change, never acceptable).
* The client major version is read from the tool's `--version`, which reports the tool's own version, not the libpq it is linked against. Distribution packages ship matching versions; a tool linked against an older libpq with `PGSSLROOTCERT=system` fails to connect (fail closed, never a downgrade).
* Vendor PostgreSQL installs that need `LD_LIBRARY_PATH` are not supported by the cleared child environment: use distribution packages or binaries with an embedded library path (rpath), and point the tool at them with its binary directory. No new configuration option was added.

## Recorded for the orchestration slice
* Real-tool TLS is not exercised by any test (the drill runs on a non-TLS disposable server); the environment a started tool sees, the timeout and the kill are exercised with fake POSIX tools only (the tests pass without running on Windows: an early return, not a reported skip). The PostgreSQL 14/15 server paths (no provider column; `LOCALE_PROVIDER` on 15) are unit-tested on the clause only and NOT VERIFIED against a real 14/15 server (CI runs 16). The self-hosted workflow has no client-version assertion (owner's call).
* The orchestrating slice must pass the manifest's `databaseLocale` to `RestoreIntoNewDatabaseAsync`.
* `PgBackupTool` validates NAMES only. The orchestrating slice must tie `sourceDatabase` to a real database of the company registry and the dump to the manifest's company before calling it.
* A blocked drop of a failed restore target (the `restore_failed_cleanup_failed` path) is not exercised by a test (no robust way to block a drop on the shared disposable server).

## Slice 3: orchestration - PLAN (not implemented; awaits independent review before any code)
Goal: one company is backed up and trial-restored END TO END from the company registry, through two administrative commands, using the slice 1 set and the slice 2 tool. Risk: Critical (ROADMAP 4.3). Migrations: **none** (the registry is only read; nothing is added to any schema; if implementation shows a migration is needed, work stops and the lead allocates it). No API endpoint and no UI in this slice (the shared Web/Tauri frontend is unaffected; a backup screen belongs to the monitoring/scheduling slice).

### Design
1. **`CompanyBackupService`** (`Hasm.Infrastructure.Backup`; options: `HasmDatabaseOptions`, `AttachmentOptions`, `EncryptionOptions`, a clock; it wraps `PgBackupTool` and `BackupSet`).
   * `BackupCompanyAsync(companyId, destination)`:
     1. the company is read from the registry (`CompanyRegistry.GetAsync`): unknown is `company_not_found`, any state other than `Ready` is `company_not_ready`. The source database is ALWAYS the registry's `PhysicalDatabaseName`; no caller ever names a database (closes the slice 2 Low "validates names only").
     2. `Hasm:Attachments:StorageDirectory` must be configured (`attachment_storage_not_configured`, fail closed: a backup run with a missing setting must never silently produce a set without the attachments); the company folder is `<root>/<company id N>` exactly as `AttachmentFileStore` builds it (a missing folder means no attachments yet).
     3. the destination is checked before anything runs (absolute, empty or absent, outside the attachment root and the key directory: `destination_not_empty`, `destination_overlaps_source`).
     4. `PgBackupTool.DumpAsync` writes the dump to a private staging file next to the destination (`<destination>.dump-<random>`, owner-only, removed on success and failure) and captures the locale.
     5. **restorability at backup time** (D-059): the captured locale must pass the restore rules (`PgBackupTool.EnsureRestorable`: libc provider, character rule); otherwise `locale_unsupported` and NO set is written (an ICU/builtin company is refused up front instead of producing a set that can never be restored).
     6. `BackupSet.Create(companyId, staging dump, company folder, destination, now, locale)`, then `BackupSet.Verify(destination).IsClean` as a post-condition (`backup_set_not_clean`, the set is removed).
     7. key coverage: `BackupSet.CheckKeys(manifest, ListKeyIds(Encryption:KeyDirectory))`; missing key ids are REPORTED (result and exit code 8), not a refusal: the set of what exists is still valuable and the gap already exists in the live system.
     * Ordering: the dump is taken first, the attachment folder copied after it. Attachment files are written BEFORE their row commits (`AttachmentService`) and removed bytes are retained, so every file referenced by a row in the dump is present when the folder is copied; a file uploaded after the dump is an unreferenced extra in the set (harmless; the orphan sweep removes it after a restore). A rewrap during the backup changes only the envelope's key id, which the manifest takes from the copied file.
   * `TrialRestoreAsync(setDirectory, expectedCompanyId, attachmentTarget, keep)`:
     1. the set is verified (`backup_set_not_clean`); its company must equal `expectedCompanyId` (`company_mismatch`) and must exist in the registry (`company_not_found`; a set of a company this installation does not know is not restored by this command).
     2. the locale (D-059): the manifest locale is ALWAYS validated by the restore rules; when the registry's database still exists, the manifest locale must EQUAL the live one (`locale_mismatch`: a database's locale cannot change after creation, so a difference means a tampered or foreign set); when the database is gone the manifest locale is used alone; an older set without it falls back to the live database, and with neither the restore is refused (`source_locale_unknown`, slice 2).
     3. the target database is a NEW generated physical name (`PhysicalIdentifier.GenerateDatabaseName`), never registered, never the registry's name; `PgBackupTool.RestoreIntoNewDatabaseAsync(set dump, target, registry name, manifest locale)`.
     4. attachments: `BackupSet.RestoreAttachments(set, attachmentTarget, companyId)`; the target must be absolute, empty or absent and OUTSIDE the live attachment root (`target_in_live_storage`): a trial restore never writes into live storage.
     5. verification of the restored copy: the database opens with the admin account, its encoding/collation/ctype/provider equal the manifest, the company migration history table is readable and its latest applied migration is reported (count only); key coverage of the restored attachments against the configured key directory is reported.
     6. the restored database is DROPPED after verification by default (only the database this run generated); `--keep` keeps it and reports its generated name for inspection. The attachment target is left for the operator (it is outside live storage). No registry change, no runtime grant, no cutover.
2. **`Hasm.Admin` commands** (D-058): `backup-company <company-id> <destination-dir>` and `trial-restore-company <set-dir> <company-id> <attachment-target-dir> [--keep]`. Configuration from the environment as every other command (admin database account required, `Hasm__Attachments__StorageDirectory`, `Hasm__Encryption__KeyDirectory`); PostgreSQL client tools from `PATH` (no new configuration option). Output: stable codes, counts, the company id and generated names only; never a password, never tool output. Exit codes: 0 ok, 1 refused/failed (code printed), 2 usage, 3 configuration, 8 completed with missing key ids.
3. **Test infrastructure**: `PosixFactAttribute` (unit tests): `Skip` is set on Windows, so the fake-tool tests are REPORTED as skipped instead of passing by an early return; fake tools are written under the test output directory (exec-capable, unlike a possibly `noexec` temp folder), and a helper retries the first `--version` run a few times on a launch error, so an `ETXTBSY` race with a concurrent fork in another test cannot flake the suite. The `PgBackupToolProcessTests` move to it.

### Exact tests
* Unit (`Hasm.Infrastructure.Tests`):
  * `PosixFactAttribute` sets `Skip` exactly on Windows; the existing four `PgBackupToolProcessTests` use it and the new folder/retry helper.
  * `PgBackupTool.EnsureRestorable`: libc and PostgreSQL 14 (no provider) accepted; ICU, builtin, unsafe names refused with `locale_unsupported`.
  * restore-locale choice (pure): manifest = live -> manifest; manifest != live -> `locale_mismatch`; manifest only -> manifest; live only -> live; neither -> `source_locale_unknown`; an invalid manifest locale is refused even when it equals the live one.
  * path rules: destination inside the attachment root or the key directory refused; trial attachment target inside the live attachment root refused (including through a symbolic link, POSIX).
* PostgreSQL (`Hasm.Database.IntegrationTests`, new class `CompanyBackupServiceTests`, **7** tests; the registry in `.github/workflows/backend.yml` is RAISED by 7 at push time, from whatever main is then):
  1. a registered Ready company is backed up into a clean set bound to its id with the captured locale; the source, another company database and the system database are unchanged (catalog-and-content digests, as in the slice 2 drill).
  2. refusals before any dump: unknown company, a Pending company, unconfigured attachment storage, a non-empty destination, a destination inside the attachment root; no staging file and no set remain.
  3. an ICU company database (created `LOCALE_PROVIDER icu` on the PostgreSQL 16 CI server and registered as Ready) is refused with `locale_unsupported` up front; no set, no staging file.
  4. trial restore into a new unregistered database: verification passes (locale equal, migration history readable, attachments restored outside live storage, key coverage complete); the database is dropped afterwards; with `keep` it exists under the reported generated name and the registry is unchanged in both cases.
  5. trial restore refusals: a set of another company (`company_mismatch`), a set of an unknown company, a manifest whose locale was edited to a different valid libc locale while the source exists (`locale_mismatch`), an attachment target inside live storage (`target_in_live_storage`); nothing is created in any case.
  6. disaster recovery: the company's database is dropped after the backup (registry row kept); the trial restore succeeds from the manifest locale and the restored digest equals the pre-backup digest.
  7. the real `Hasm.Admin` binary: `backup-company` then `trial-restore-company` exit 0; usage errors exit 2; a missing storage setting exits 3; stdout/stderr contain neither the admin password nor any tool output.
* Not tested (recorded): real-tool TLS (the disposable server has no TLS); PostgreSQL 14/15 servers (CI runs 16); the blocked-drop path; Windows process tests (reported skipped).
* Commands before every push: `dotnet build src/backend/Hasm.slnx -c Release`, `dotnet test tests/unit/Hasm.Infrastructure.Tests -c Release --no-build`, the API tests; the PostgreSQL suite in CI (postgres-integration authoritative), or locally only through the single-holder lock of the Linux test harness (PR #89) when it is merged and free, never port 5432.

### Stays BLOCKED or out of this slice
* BLOCKED (owner decision): the audited restore acknowledgement and the new checkpoint epoch, and therefore any cutover that replaces a live company database or touches its checkpoints; retention/purge of removed attachments (decision R). Nothing in this slice decides either; no audit event is added (an audited backup/restore record belongs with the acknowledgement and the monitoring slice).
* Not in this slice: scheduling, retention of sets, destinations, set encryption and signing (until then the manifest, including its locale, is NOT authenticated: see D-059), monitoring/alerts, RPO/RTO measurement, full-installation restore, key backup (kept separately by the operator), encrypted import-file originals (decision K follow-up).

### Decisions under D-048 (recorded in docs/DECISIONS.md)
* **D-058** entry points and binding: two `Hasm.Admin` commands over one infrastructure service; the company and its database come only from the registry and only in state Ready; attachment storage must be configured; client tools from `PATH`. Alternatives rejected: an API endpoint now (needs RBAC, licensing and UI decisions of the monitoring slice); accepting a database name (the slice 2 Low); treating missing storage configuration as "no attachments" (silent incomplete backup).
* **D-059** restorability and manifest trust: a set is written only if its captured locale passes the restore rules; the unsigned manifest locale is always validated, cross-checked against the live database when it exists (`locale_mismatch`) and trusted alone only when the database is gone, until set signing exists. Alternatives rejected: check only at restore time (an unrestorable set discovered during a disaster); ignore the live database when the manifest has a locale (a tampered set would silently change the collation); refuse whenever the live database is gone (defeats D-053).
* **D-060** trial restore: a new generated unregistered database plus an attachment folder outside live storage, verified and then dropped by default (`--keep` to inspect), no registry or grant change. Alternatives rejected: restoring under the registered name or into live storage (that is a cutover, BLOCKED); keeping every trial database (orphan databases accumulate on the customer's server).
* **D-061** key coverage is reported, not refused, at backup and trial restore (exit code 8 and the missing key ids). Alternative rejected: refusing the backup (the gap already exists in the live system; refusing leaves the company with no backup at all).

## Limitations (recorded)
* The manifest detects corruption and loss; it is not a signature and the set is not encrypted (later slice).
* `KeyIdsRequired` covers attachment envelopes only. Encrypted import-file originals are outside the attachment folder and need their own key coverage (the import-file rewrap retirability report, decision K follow-up, is not built yet).
* Restore into a NEW database only; replacing a live company database (cutover), full-installation restore, scheduling, retention, destinations, set encryption, monitoring and RPO/RTO measurement are not built.

## BLOCKED / owner decisions
* Audited restore acknowledgement and a new checkpoint epoch after a company restore (`docs/DEVELOPMENT.md`, restore limitations): policy needs an owner decision.
* Retention/purge of removed attachments (decision R).
* Scheduling, retention, destinations, encryption, monitoring, RPO/RTO: not started.
