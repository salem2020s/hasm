# HASM — Phase 3.8B-1: Stocktake and variance, no posting (as built)

First slice of Phase 3.8B (plan: `docs/PHASE-3.8B.md`). Sources: SRS §9 (stocktake), ROADMAP 3.8B (SRS 9.1, 9.4), PHASE-3.5 (document workflow mirrored here), PHASE-3.6 (costing ledger), PHASE-3.8A (book quantities).
**It creates no stock movement, no cost operation and no accounting entry**, and changes no existing constraint (slices 1 and 2 never relax the costing engine). Negative stock is untouched.

## What exists
* **Company migration 0018** (`CompanySchema.Stocktake.cs`, additive only): `Stocktake` (one warehouse, count date, reference, notes, official number, snapshot time, workflow columns, revision), `StocktakeLine` (item, unit, counted quantity in that unit, exact factor, counted base quantity, **book quantity** in the base unit, **variance**, reason) and the append-only `StocktakeEvent`. PostgreSQL enforces: status domain and the closed graph of 3.5 (1 draft → 2 submitted → 3 approved; 2 → 1 withdrawn; 2 → 4 rejected; 1, 2, 3 → 5 cancelled); branch, warehouse and creation data immutable; header, snapshot and lines change only in a draft; never deleted or truncated; the decider is never the submitter; number exactly while approved, kept on cancellation, unique; one line per item; counted quantity ≥ 0, `counted base = counted × factor` and `variance = counted base − book` exactly (a NULL cannot slip through); a submitted or approved sheet has at least one line, every line counted and a reason on every line with a variance (deferred check at commit); history linked to one authenticated audit event each. Runtime role: SELECT/INSERT/UPDATE (DELETE only on lines, which PostgreSQL lets change only in a draft).
* **System migration 0021**: warehouse-scoped permissions `company.stocktake.view|create|update|submit|approve|cancel`, all held by the Company Administrator preset. A stocktake needs the permission on its warehouse; viewing is checked first (no existence probing); the list is restricted inside the query before counting and paging. Stock-document permissions do not grant stocktakes.
* **Numbering:** document type `stocktake` (default prefix `STK`, e.g. `STK-2026-000001`) in the existing engine, issued at approval inside the approval transaction; cancelling an approved stocktake voids its number, which is never reused.
* **Service** (`Inventory/StocktakeService.cs`, `StocktakeManagementService`): create (warehouse + count date, optional lines), update a draft (never the warehouse), **generate sheet** (adds every countable item with a non-zero book quantity at the count date, or exactly the chosen items, that is not on the sheet yet; existing counts kept), submit, withdraw, approve, reject (note), cancel (reason). Every mutation runs under the warehouse-structure advisory lock, is fenced by the revision (`If-Match`; a duplicate or concurrent request fails with 412 and acts once) and writes one history row plus one audit event (1170–1177).
* **Lines:** counted in any unit of the item, converted exactly into the base unit or refused (never rounded); zero is a valid count; services and lot/serial/expiry-tracked items are refused (`tracked_item_not_supported_yet`, as in 3.5); an inactive item is accepted (it may still hold stock to count); at most 2000 lines per sheet.
* **API** `/api/v1/company/stocktakes`: capabilities, warehouses, items, list (status, warehouse, count-date range, number/reference search, paging), get, create, update, `generate-sheet`, submit, withdraw, approve, reject, cancel; `no-store`, anti-CSRF, `If-Match`, field errors like the other endpoints.
* **Shared UI (Web and Tauri):** `Stocktakes.tsx` at `/inventory/stocktakes` (Inventory → *Stocktake*). List with filters, progress (counted of total) and variance count. Editor with the tabs standard: **Details**, **Lines** (book, counted, counted base, variance with an exact preview while typing, reason; generate list; add an item), **History**; identity and workflow actions outside the tabs; unsaved edits survive tab switches; field errors mark their tab; Approve/Reject disabled with the reason for the submitter; stale snapshot shown as a warning and per line. Arabic RTL / English LTR (`messages.stocktake.ts`).

## Decisions (standing authority, conservative)
* **3.8B-1/D1 — book snapshot.** The book quantity is `Σ direction × quantity` of the costing ledger for the item in the warehouse with an effective date on or before the **count date** (the stated as-of date). It is taken when a line is saved, when the sheet is generated, and one last time at **submit**; from submit on it is frozen.
* **3.8B-1/D2 — stale snapshot.** Reading a stocktake recomputes the current book quantity per line; when it differs from the snapshot (a movement dated on or before the count date was posted or reversed later) the line and the sheet are marked **stale**. This is information only: **approval is allowed** and re-checks nothing about the snapshot. The adjustment of 3.8B-2 will use the **current** book quantity at its own time; the stocktake stores only the count and the snapshot.
* **3.8B-1/D3 — workflow mirrors 3.5:** same statuses, transitions, separation of duties (service and PostgreSQL), number issued at approval, and the count date must lie in an **open** fiscal period at approval (the number is per fiscal year).
* **3.8B-1/D4 — reason** is required (at submit, and by PostgreSQL) on every line whose variance is not zero; optional otherwise.
* **3.8B-1/D5 — one warehouse per sheet, fixed at creation.** Several open stocktakes of the same warehouse are not prevented (the SRS states no such rule); 3.8B-2 must make sure one approved stocktake yields exactly one adjustment.
* **3.8B-1/D6 — warehouse deactivation** is not blocked by an open stocktake (unlike stock documents); an inactive warehouse blocks create, save, generate, submit and approve, and the stocktake can still be cancelled.
