## Data (company migration 0024, generated by `tools/schema/company-0024-attachments.cjs`, names derived from `hasm.company.0024.attachments.v1:<token>`)

`Attachment`: record kind and id (a registered kind, validated by the service because a polymorphic reference has no foreign key), display file name, content type (allow-list), size, **SHA-256 of the plaintext**, sensitivity (1 normal, 2 sensitive), opaque stored name (`<32 hex>.att`, unique), key id (sensitive only), state (1 active, 2 removed with who, when and why), revision. PostgreSQL enforces: never deleted or truncated; identity, record, name, type, size, hash, sensitivity, stored name and creation data immutable; only the key id of an active sensitive row changes (re-wrap); a removed row never changes again; a sensitive row has a key id and a normal row has none; the hash is 64 lowercase hex digits; revision advances by one.

## Storage and encryption

* Bytes live under `Hasm:Attachments:StorageDirectory` (absolute path, outside any web root, a sub-directory per company created owner-only; never served statically). Names are generated identifiers validated against `^[0-9a-f]{32}\.att$` on every call, so a path can never leave its company directory; writes are exclusive-temp-then-atomic-move and never overwrite. `MaxFileBytes` defaults to 25 MB.
* A normal file is stored as is (backend-only access, hash verified on every read). A **sensitive** file is envelope-encrypted with the existing `EnvelopeEncryptor` (AES-256-GCM, a fresh data key and nonce per file, the data key wrapped under the versioned master key); the authenticated context binds the ciphertext to its company and attachment id, so a valid ciphertext of another attachment is refused.
* Every read verifies the plaintext hash. A missing file, a failed authentication or a hash mismatch is an **integrity failure**: audited (event 1604), nothing is returned (409 `integrity_failure`). A missing or invalid key is a server problem (503), never an integrity accusation.
* Uploads validate: registered record kind and existing record, sanitized display name (directory part and control or path characters removed, at most 200 characters), allow-listed content type (PDF, PNG, JPEG, text, CSV, docx, xlsx) **with a matching signature** (text must be UTF-8 without NUL), non-empty and within the size limit. A refusal leaves no file.
* Removal needs a reason and the revision. The metadata and the bytes are **kept** (the retention policy is an owner decision, see the blocker register below); the file is simply no longer reachable.

## Authorization and audit

`company.attachments.view|upload|delete` and `company.attachmentssensitive.view|upload` (company-wide, all in the Company Administrator preset, system migration 0026). A sensitive file additionally needs the sensitive permission: without it the file is **absent from lists and looks missing** on download and removal (no existence probing). Audit events 1600-1604: uploaded, removed, sensitive downloaded, key re-wrapped, integrity failure. Downloads are `Content-Disposition: attachment`, `nosniff`, `Content-Security-Policy: sandbox`, `no-store`; no DELETE route.

## Key provisioning, rotation and recovery (runbook; the import files use the same keys)

* **Provision:** `Hasm.Admin encryption-keygen <key-id>` creates a random 256-bit key file in `Hasm:Encryption:KeyDirectory` (owner-only, never overwritten); set `Hasm:Encryption:ActiveKeyId`. Back the key directory up **separately** from the data and the database (it is not tied to a machine; a server migration moves it).
* **Rotate:** create a new key, make it active, call `POST /api/v1/company/attachments/maintenance/rewrap` (needs `company.attachmentssensitive.upload`; the import files have their own rewrap endpoint). Each sensitive file's data key is re-wrapped, the file replaced atomically and the key id audited; the envelope names its own key, so a crash mid-way leaves every file readable. The old key may be retired ONLY when the response says `oldKeysMayBeRetired: true` (`failed` is 0 AND `retainedUnderOtherKeys` is 0) for EVERY company AND `POST .../maintenance/verify` lists no old key id in `keyIdsInUse`: REMOVED sensitive attachments keep their bytes and their key id (a removed row never changes again), so while one exists the key it names must be kept (owner rule, 2026-11-20: never retire a key that retained attachments still require; fail-closed `KeyUnavailable` otherwise). Import files have their own rewrap and the same rule. The drill is automated in `AttachmentTests`.
* **Recover:** without the key a sensitive file stays unreadable (fail closed, 503); restoring the key directory from its separate backup makes it readable again. Restore the database and the attachment folders from the same backup set; the stored hash proves each restored file.

## Review hardening (docs/review-records/PR-3-12-attachments.md)

Upload is authorized before the body is buffered; the file is written before the transaction (no lock during I/O) and removed only when no row exists; `POST /api/v1/company/attachments/maintenance/sweep` removes orphan files older than one hour; every decryption failure other than a missing key is an audited integrity failure; names lose bidirectional/zero-width/format characters and are truncated on a character boundary; the plaintext digest of a sensitive file is neither returned nor audited; list, upload, download and removal also require the owning module's view permission (parties, items); a charset parameter is accepted and a Windows-labelled .csv is read as text/csv.

## Backup and restore coordination (SRS 14.4, 16)

* **The backup set has three parts that must come from the same moment:** (1) the company database (the attachment rows), (2) the attachment folder of the company (`Hasm:Attachments:StorageDirectory/<company>`; the bytes of REMOVED attachments are included: they are retained), (3) the master key directory (`Hasm:Encryption:KeyDirectory`), stored and protected SEPARATELY from (1) and (2) so that a stolen data backup does not carry its keys. Order: copy the folder after the database snapshot is taken (a file with no row is an orphan and harmless; a row with no file is a missing file and is reported).
* **Restore:** restore the database and the folder, then the key directory; start the application; run `POST /api/v1/company/attachments/maintenance/verify` (permission `company.attachmentssensitive.upload`). The report proves the set: `clean` is true only when every row (active and removed) has its file, decrypts with an available key and matches its stored plaintext SHA-256. Otherwise it lists attachment ids (never names or paths) as `missing`, `hashMismatch`, `keyUnavailable` and `unreadable`, counts `orphanFiles` (never deleted by the verification) and gives `keyIdsInUse`: the master keys the sensitive files need, which the key backup must contain. A `keyUnavailable` file becomes readable when its key is restored; a `missing` or `hashMismatch` file must be restored from an older backup or re-uploaded. The verification writes one audit event (1607).
* **Drill:** `AttachmentTests` restores a copy of the folder into a fresh directory and proves it clean, then restores with a lost file, a corrupted file, a stray file and without the key and checks that each problem is named.
* **Not covered here:** scheduling and encryption of the data backup itself (Phase 4.3), and retention/purge of removed attachments (owner decision R).

## Open owner decisions (blocker register)

* **Retention of removed attachments:** the bytes of a removed attachment are kept. A purge policy (and the backup-retention interplay) needs an owner decision; nothing is deleted until then.
* **Per-company quota and malware scanning:** not built; both are owner/deployment decisions.
* **Per-record authorization:** attachment access is company-wide by permission in this phase; per-branch or per-document scoping follows the commercial document framework (3.13).
