# Phase 3.8D - impact preview and recalculation design proposal

Status: **design proposal with internal arithmetic and an authorized read-only ordinary-history snapshot adapter; the public feature is not implemented**. This is the next dependency-ready inventory phase after merged 3.7C and 3.8A. It does not approve a new accounting rule, remove the existing `backdated_not_supported` barrier, or claim that back-dated posting, revaluation or method changes work today. Independent design review is required before implementing the proposed persistence/execution slices.

## Approved scope and existing behavior

Sources: approved SRS 9.2, 9.5, 9.7 and scenario 21.5; ARCHITECTURE 7-8; decisions D-009, D-017, D-018 and D-020; ROADMAP 3.8D. FIFO and moving average retain item x warehouse x company valuation. Back-dated work requires impact preview, propagation through chained transfers, reproducible recalculation and separately approved stock/accounting adjustments. Posted journals and historical source records remain immutable. Final Closed periods remain barriers. Transaction/effective dates and recording dates remain distinct.

The current engine (`InventoryCostingService`, `CostingMath`) already uses exact fixed-unit integer arithmetic, deterministic position sequences, FIFO allocations, moving-average rounding and explicit transfer pairs. Its posting barrier rejects earlier dates. Stock posting, reversal, accounting-pending states, stocktakes, adjustments and negative-stock obligations already exist and must continue to work. No second implementation of the costing rules or journal workflow is proposed.

## Delivery slices and gates

1. **3.8D-1: read-only impact planning.** Extract/reuse pure costing arithmetic and replay inputs without changing live positions, layers, obligations, approvals or journal state. Load an authorized, consistent company snapshot; identify the complete affected transfer closure; return before/after values, changed consumptions and separately identified adjustment requirements. Unsupported history must be refused explicitly, never silently omitted. The existing posting barrier remains.
2. **3.8D-2: reproducible replay and adjustment proposal.** Cover receipt, issue, transfer and reversal history for both approved methods; integrate stocktake/adjustment and negative-exception history. Store proposed adjustment contents only, with no independently postable journal or normal adjustment draft. Preview is neither approval nor posting. No slice is described as general back-dated support while a required history type is missing.
3. **3.8D-3: approved execution.** Revalidate the plan, permissions, periods, approvals, account mapping and concurrency token under the existing posting/position lock conventions; atomically apply the approved new event and its required valuation/accounting effects within the company transaction. Idempotency, rollback and pending-accounting close protection remain mandatory. Do not enable the posting path before this transaction and its failure/concurrency tests exist.
4. **3.8D-4: valuation-method change and revaluation.** Produce a separate reviewed design for conversion of existing FIFO layers/average positions and the adjustment-account contract. Existing `valuation_method_changed` guards stay active until that design and its tests are complete. A consequential accounting ambiguity is recorded as an owner-held proposal, not resolved by implementation. Unaffected preview work can proceed.
5. **Shared UI and final verification.** One React implementation for Web and Tauri, existing Tabs/unsaved standards, Arabic RTL/English LTR, permission and cost-visibility checks, shared interaction tests, backend/real-PostgreSQL tests and desktop build. Phase completion requires every slice, full exact-head CI and independent review; a design-only PR remains Draft.

## Proposed read-only plan contract

* Inputs identify the existing stock-document revision, proposed effective date and exact quantities/receipt amounts already validated by the normal document path. No floating-point money or client-supplied accounting truth.
* Preserve the established order of existing events on each position and the source/destination relation of transfer legs. The proposed event follows existing events on its effective date, matching the current same-day append behavior, and precedes later dates. A deterministic ordering specification and tied-date transfer/reversal examples must be reviewed before coding the replay scheduler.
* Resolve every affected downstream warehouse for the item, including repeated transfers. Check authorization for the entire impact closure before returning cost data. Hidden warehouses or cost amounts must not leak through partial plans or error details. Do not query another company's data.
* Use a consistent read-only transaction and a server-computed plan fingerprint over source revision, event history/position sequences, valuation policy, relevant account-map versions and period states. The precise snapshot/query design is an implementation proposal, not a promise that an unlocked preview is executable. Approval and execution must reject a stale plan and require a fresh preview.
* Return a comparison with exact currency minor-unit totals and reference links. Original posted amounts remain visible as original; recalculated values are explicitly labelled as proposed. Reversal history must reference the original operation and its recalculated allocations; it must not be treated as an unrelated receipt/issue with an invented amount.
* Negative-stock obligations and settlements must be included in the history model. A quantity/value omitted from the current normal cost ledger is not zero. A preview that cannot account for an obligation, historical settlement or reversal fails closed with a stable code. No provisional-cost source or eligibility rule is changed by this design.
* Final Closed periods are checked across the affected history and proposed adjustments. Existing pending-state/close rules are reused; no silent posting into a closed period or historical journal rewrite is permitted.

## Required evidence before enabling execution

Pure replay fixtures for FIFO and average, exact remainders, free receipts, equal dates and both transfer directions; complete chained-transfer propagation; reversals; stocktake/adjustment origins; negative obligations and settlements; repeatable fingerprints; changed source/policy/period/history stale-plan rejection; company and warehouse isolation and cost visibility; read-only preview with no position/layer creation; approval/SoD and fiscal gates; idempotent concurrent execution; fault-injected full rollback; immutable original journals and separate adjustment references; fresh and upgrade migrations; shared Web/Tauri interaction coverage. SRS scenario 21.5 is not complete until these are demonstrated.

## Independent design review follow-up

The initial review of checkpoint `b22cbe0` identified a High design omission: ordinary journal workflows could independently post adjustment drafts created before their source event. The proposal now forbids such drafts. Until guarded execution is implemented, adjustments are **non-postable proposal data only**. Any eventual materialization must be bound to one execution group whose source event and complete adjustment set commit atomically. Every normal and automatic posting path must respect that binding. A stale plan invalidates the entire group and its approvals; approvals cannot be reused for changed contents. No current executable path was affected by this omission.

Before implementing persistence or execution, the following contracts still need explicit review: reconciliation of original and replayed amounts by account, branch, cost center, currency and period; historical versus current mappings; a transition matrix for negative coverage/settlement changes that never mutates or silently reopens old obligations; deterministic transfer-cycle and reversal examples; and fingerprints covering adjustment contents, original/reversal links, obligation/settlement state, mapping versions and approval binding. Authorization and revocation must always be rechecked live, regardless of fingerprint equality. Consequential accounting questions without an approved answer stay with the owner; the read-only primitive does not decide them.

The initial code slice is an internal, immutable receipt/issue replay primitive reusing `CostingMath`, with exact numeric fixtures. The next internal snapshot adapter now classifies ordinary history and refuses unsupported transfer, reversal, negative-exception or stocktake cases until they are modeled. Neither is a scheduler, public API or posting service. Existing back-dated and method-change guards stay unchanged.

## Initial arithmetic checkpoint

`CostReplay` now implements only the internal, already-ordered ordinary receipt/issue primitive. It reuses existing FIFO/moving-average rounding, returns immutable trajectories/consumptions, refuses unsupported operation kinds before partial calculation, and matches the live engine's per-event numeric bounds. Aggregates beyond the existing arithmetic conversion range fail with a stable code. There is no database access, clock, scheduler, API, dependency-injection registration or production caller; it cannot create a position, obligation, approval or journal.

Nineteen new unit cases cover exact remainders, free receipts, shortages, FIFO allocations, inserted-receipt changes under both methods, immutable/repeatable results, unsupported history, input identity/precision, numeric boundaries, long FIFO histories and cancellation. The full local unit suite passed **887/887**, with zero skips. FIFO replay considers only the consumed layer prefix instead of repeatedly sorting every remaining layer.

## Authorized snapshot checkpoint

`CostHistorySnapshotService` is internal and has no API, dependency-injection registration or production caller. It checks the existing warehouse-scoped stock-balance cost-visibility permission before opening the company database and again before returning. A repeatable-read, read-only transaction loads the resolved method, base currency, position and complete ordinary receipt/issue trajectory. It replays and reconciles every historical amount and balance against the existing engine. Real stock-document sources must match document type, warehouse and the posting's exact cost-operation link. It never creates positions, changes layers, writes audit entries or takes posting locks.

Transfers, reversals, stock adjustments, tracked items and any negative-obligation history (including settled obligations) are explicitly refused. A 100,000-entry bound refuses oversized history rather than truncating it. The immutable snapshot's hash identifies this limited history evidence only; it is **not** an approval, authorization or executable-plan token. Cancellation reaches reads and replay work.

Seventeen new PostgreSQL cases passed on isolated port 5433, zero skips: FIFO/average reconciliation, empty position without creation, unsupported histories, real posted-document provenance and invalid links, scope/company isolation, live revocation, concurrent writer snapshot consistency, read-only isolation, method changes and resource bounds. Registry increases from 962 to 979. Independent full-diff review confirmed the source-provenance and FIFO-work findings fixed, with no remaining Critical/High/Medium in this checkpoint. Final committed-head review and applicable CI are separate gates.

Public preview, transfer/reversal/obligation replay, proposal persistence, approval/execution, method conversion/revaluation and shared UI remain unimplemented. The PR stays Draft; no broader 3.8D capability is claimed complete. The owner approved compensation by original accounts/dimensions and prospective quantity/value-preserving conversion as D-044/D-045; [PHASE-3.8D-ACCOUNTING-PROPOSAL.md](PHASE-3.8D-ACCOUNTING-PROPOSAL.md) distinguishes those bases from the still-proposed transition details.

## Ordinary-history comparison and conversion-design checkpoint

`CostImpactPreview` now computes internal read-only before/after trajectories for inserting one ordinary receipt/issue into the complete supported history. It preserves original same-date sequence and inserts after existing ties; revalidates baseline amounts/balances; retains original entry/operation links; includes balance changes even when an event cost is unchanged; and refuses the whole comparison if any revised event would create a shortage. It has no API, production caller, persistence, fiscal approval or execution authority. Its returned history fingerprint is baseline evidence only and does not bind or approve the proposal.

Thirteen comparison unit cases and five numerical conversion-contract fixtures pass; the full unit suite is **905/905**, zero skips. Real PostgreSQL snapshot-to-comparison assertions pass for both methods (2/2), conserving total250: FIFO issue120/inventory130, average issue150/inventory100. This supplements, rather than weakens, the existing 17 snapshot cases; registry remains979. No live financial behavior changes.

[PHASE-3.8D-CONVERSION-CONTRACT.md](PHASE-3.8D-CONVERSION-CONTRACT.md) proposes deterministic cross-basis restitution order, mandatory complete replay for cross-basis inflow reversals, and compensation-entitlement allocation with exact final remainders. Independent review's three Medium clarity findings were addressed with explicit rules/examples and numerical fixtures. Basis-epoch persistence, complete negative/transfer/reversal integration and the mandatory activation matrix remain incomplete. Numerical fixture success is not conversion-execution acceptance.

## Internal multi-position ordering checkpoint

`ReplaySchedule` now implements an internal, immutable dependency scheduler, without money calculation, database access or production caller. It receives complete classified operation groups and per-position history order; one transfer group contains both warehouse legs. Position order is an explicit input proved by the eventual snapshot adapter, not a timestamp/UUID guess or an assumption that a conversion is an existing cost-entry kind. Conversion/basis anchors will need their own reviewed adapter contract before use.

The initial scheduler is for one item's ordinary receipt/issue/transfer/reversal history. Receipt/issue groups contain one position, transfers two distinct positions, and a reversal's position/leg set must exactly match its referenced original (which cannot itself be a reversal). There is at most one reversal per original. Each group occurs once per affected position at one positive contiguous canonical ordinal; duplicate/interleaved group occurrences are rejected, never silently deduplicated. The future adapter must prove its compression from ledger rows. A proposed ordinary receipt/issue affects one position only. Caps, including a proposal, are100,000groups,10,000positions,200,000legs and400,000unique edges; validate before growing beyond them and check cancellation during validation, graph construction and traversal. These limits refuse oversized histories rather than returning partial schedules.

Preserve every existing per-position order edge. Add an original-before-reversal dependency and require the referenced operation to be present. A proposed ordinary event is inserted after all existing events of its effective date on each affected position and before later events; it never reorders existing ties. Dependencies across transfer legs are grouped, so neither leg is scheduled independently. A stable topological order uses effective date then a canonical ordinal comparison of the event's Guid string for otherwise independent ready groups. That tie-breaker is determinism only, not a claim about recording chronology. A backward-date dependency, missing origin/leg, duplicate position ordinal/event identity, or cycle refuses the entire schedule before any costing output.

Example: A has receipt R-A then transfer T to B, while B has receipt R-B then T then transfer U to C, and C has receipt R-C then U. Existing position constraints are R-A→T, R-B→T→U and R-C→U. An earlier proposed receipt P at A must precede T; recalculation therefore propagates through the atomic T group into B and through U into C. Independent R-A/R-B/R-C events may use the stable tie-breaker without changing their per-position costing. The eventual authorization snapshot must include the complete affected closure before returning data.

Malformed-cycle example: A orders T before U while B orders U before T, with both T/U transferring between A/B. This has no valid replay order and fails closed. Sorting by effective date or UUID must not hide the cycle. Same-date P follows every existing same-date group touching its affected position; disjoint ready groups do not acquire an invented accounting dependency. Scheduler success is neither history completeness proof, cost validation, authorization, approval nor execution authority.

Fourteen scheduler cases cover chains, same-date insertion, transfer reversals, missing/mismatched origins, cycles, chronology, ordinals/duplicates, canonical ordering across cultures, bounds and cancellation. Full unit regression passed919/919, zero skips. Independent full-diff review confirmed the three design-clarity requests implemented and found no new Critical/High/Medium code finding. No transfer costing, multi-warehouse snapshot adapter, conversion anchor, negative history or execution path is implemented merely by scheduling its identifiers.

## Private position-state preparation

The ordinary batch primitive now keeps its incremental quantity, value and FIFO layers in a private PositionState. The same complete-batch validation and exact CostingMath execute unchanged, with no mutable cursor or partial result exposed. This prepares reuse; it does not implement transfer replay or make unsupported history eligible. Focused replay21/21 and full unit921/921 passed locally with zero skips. Two additional cases preserve a derived issue value1.8e18 across two valid9e17 receipts and retain both FIFO components, distinguishing user receipt limits from legitimate aggregate outflow cost. Independent full-diff review found no Critical/High/Medium in this checkpoint; final committed-head CI is separate.

The next transfer adapter must mirror each consumed FIFO layer in order with deterministic identity and provenance, as the existing InventoryCostingService does. A single averaged destination layer would change downstream issue costs. Chained/returning transfers need complete history closure and both source/destination reconciliation; derived transfer amounts must retain exact value even above a single receipt-input cap. No such adapter, negative-history transition or execution path is activated by this refactor.
