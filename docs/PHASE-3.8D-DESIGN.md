# Phase 3.8D - impact preview and recalculation design proposal

Status: **design proposal; implementation has not started**. This is the next dependency-ready inventory phase after merged 3.7C and 3.8A. It does not approve a new accounting rule, remove the existing `backdated_not_supported` barrier, or claim that back-dated posting, revaluation or method changes work today. Independent design review is required before implementing the proposed slices.

## Approved scope and existing behavior

Sources: approved SRS 9.2, 9.5, 9.7 and scenario 21.5; ARCHITECTURE 7-8; decisions D-009, D-017, D-018 and D-020; ROADMAP 3.8D. FIFO and moving average retain item x warehouse x company valuation. Back-dated work requires impact preview, propagation through chained transfers, reproducible recalculation and separately approved stock/accounting adjustments. Posted journals and historical source records remain immutable. Final Closed periods remain barriers. Transaction/effective dates and recording dates remain distinct.

The current engine (`InventoryCostingService`, `CostingMath`) already uses exact fixed-unit integer arithmetic, deterministic position sequences, FIFO allocations, moving-average rounding and explicit transfer pairs. Its posting barrier rejects earlier dates. Stock posting, reversal, accounting-pending states, stocktakes, adjustments and negative-stock obligations already exist and must continue to work. No second implementation of the costing rules or journal workflow is proposed.

## Delivery slices and gates

1. **3.8D-1: read-only impact planning.** Extract/reuse pure costing arithmetic and replay inputs without changing live positions, layers, obligations, approvals or journal state. Load an authorized, consistent company snapshot; identify the complete affected transfer closure; return before/after values, changed consumptions and separately identified adjustment requirements. Unsupported history must be refused explicitly, never silently omitted. The existing posting barrier remains.
2. **3.8D-2: reproducible replay and adjustment proposal.** Cover receipt, issue, transfer and reversal history for both approved methods; integrate stocktake/adjustment and negative-exception history. Build auditable adjustment drafts through existing services. Preview is neither approval nor posting. No slice is described as general back-dated support while a required history type is missing.
3. **3.8D-3: approved execution.** Revalidate the plan, permissions, periods, approvals, account mapping and concurrency token under the existing posting/position lock conventions; atomically apply the approved new event and its required valuation/accounting effects within the company transaction. Idempotency, rollback and pending-accounting close protection remain mandatory. Do not enable the posting path before this transaction and its failure/concurrency tests exist.
4. **3.8D-4: valuation-method change and revaluation.** Produce a separate reviewed design for conversion of existing FIFO layers/average positions and the adjustment-account contract. Existing `valuation_method_changed` guards stay active until that design and its tests are complete. A consequential accounting ambiguity is recorded as an owner-held proposal, not resolved by implementation. Unaffected preview work can proceed.
5. **Shared UI and final verification.** One React implementation for Web and Tauri, existing Tabs/unsaved standards, Arabic RTL/English LTR, permission and cost-visibility checks, shared interaction tests, backend/real-PostgreSQL tests and desktop build. Phase completion requires every slice, full exact-head CI and independent review; a design-only PR remains Draft.

## Proposed read-only plan contract

* Inputs identify the existing stock-document revision, proposed effective date and exact quantities/receipt amounts already validated by the normal document path. No floating-point money or client-supplied accounting truth.
* Preserve the established order of existing events on each position and the source/destination relation of transfer legs. The proposed event follows existing events on its effective date, matching the current same-day append behavior, and precedes later dates. A deterministic ordering specification and tied-date transfer/reversal examples must be reviewed before coding the replay scheduler.
* Resolve every affected downstream warehouse for the item, including repeated transfers. Check authorization for the entire impact closure before returning cost data. Hidden warehouses or cost amounts must not leak through partial plans or error details. Do not query another company's data.
* Use a consistent read-only transaction and a server-computed plan fingerprint over source revision, event history/position sequences, valuation policy, relevant account-map versions and period states. The precise snapshot/query design is an implementation proposal, not a promise that an unlocked preview is executable. Approval and execution must reject a stale plan and require a fresh preview.
* Return a comparison with exact currency minor-unit totals and reference links. Original posted amounts remain visible as original; recalculated values are explicitly labelled as proposed. Reversal history must reference the original operation and its recalculated allocations; it must not be treated as an unrelated receipt/issue with an invented amount.
* Negative-stock obligations and settlements must be included in the history model. A quantity/value omitted from the current normal cost ledger is not zero. A preview that cannot account for an obligation, historical settlement or reversal fails closed with a stable code. No provisional-cost source or eligibility rule is changed by this design.
* Final Closed periods are checked across the affected history and proposed adjustments. Existing pending-state/close rules are reused; no silent posting into a closed period or historical journal rewrite is permitted.

## Required evidence before enabling execution

Pure replay fixtures for FIFO and average, exact remainders, free receipts, equal dates and both transfer directions; complete chained-transfer propagation; reversals; stocktake/adjustment origins; negative obligations and settlements; repeatable fingerprints; changed source/policy/period/history stale-plan rejection; company and warehouse isolation and cost visibility; read-only preview with no position/layer creation; approval/SoD and fiscal gates; idempotent concurrent execution; fault-injected full rollback; immutable original journals and separate adjustment references; fresh and upgrade migrations; shared Web/Tauri interaction coverage. SRS scenario 21.5 is not complete until these are demonstrated.

## Preserved boundaries

OD-11 remains OPEN and blocks 3.8C. This design does not decide lot/serial selection versus costing or add specific-identification costing. It also does not decide purchase-cost composition (OD-2), licensing transaction counts (OD-12/T-2), formal consolidation (OD-1), or unresolved naming (T-1). The four PR #46 Medium follow-ups remain scheduled before 3.9B. Production deployment, migrations against non-test databases, release and billing changes remain outside this work.
