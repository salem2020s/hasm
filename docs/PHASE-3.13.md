## 3. Design principles (invariants, each proven by a test below)

1. **Three independent tracks, none derived by writing the others' flag.** Commercial status (what the business agreed), physical (what moved), accounting (what the ledger shows). Physical and accounting state are DERIVED from append-only event rows and the journal/stock facts; only commercial status is a stored column, changed by a guarded state machine.
2. **One effect per business event.** An event is a (document, event kind, sequence) triple with a deterministic key `commdoc:<document id>:<kind>:<n>`. The key is the unique source key of the stock posting, the costing operation and the journal entry, and the primary identity of the event row. A retry returns the original; concurrent requests produce exactly one effect.
3. **Posted means immutable.** A document that has an executed physical event or a posted/pending accounting effect cannot be edited, cancelled or deleted; correction is a separate linked return/reversal/adjustment document.
4. **Nothing is ever removed.** Documents, lines, links, events and numbers are never deleted (cancel/void only), PostgreSQL refuses UPDATE of identity and DELETE/TRUNCATE, like every module so far.
5. **Snapshots are values, and the SERVER produces them.** A snapshot hash only proves internal consistency (the 3.10/3.11 hash is tamper evidence, not authentication), so a client-submitted sealed snapshot is never accepted as proof of a price, tax or rate. At line save the server, in the SAME transaction as the line write: (a) prices the line through the pricing quote path (`PricingConfigService.QuoteAsync`: the item group from the item, the customer group from the stored assignment, never from the caller); a manual override of price or discount is accepted only from a caller holding `company.pricing.override` AND with a reason (1-500 characters), exactly as the quote endpoint does; (b) resolves tax through `TaxConfigService.ResolveAsync` and the engine for the document type, operation, item class and party class at the document date; (c) takes the exchange rate from the dated rate table, or from an authorized override with permission, reason and audit (3.2B); (d) obtains the unit cost from the server (costing ledger) whenever the margin control needs it: the quote's caller-supplied `UnitCost` is NOT used for a document line (recorded obligation of PR #75, `docs/PHASE-3.11.md`). The three results are stored as values with their hashes and are then immutable; later list/rule/rate changes cannot alter them. Stored values are re-`Verify`d for consistency only; they are never accepted from the client.
6. **Derived, never stored, quantities.** Ordered, fulfilled, invoiced and returned quantities per line are computed from the link rows (append-only), so a counter can never drift; a constraint-backed check refuses over-fulfilment (Q3).
7. **Company-scoped and RBAC-checked server-side**; both clients use the same API; no frontend-only security.
8. **Fail closed.** Missing configuration (accounts, numbering rule, open period, rate) yields a refusal or an explicit pending state with a reason, never a guess.

## 6. State machines and rules

**Commercial status (stored, SQL-guarded):** draft -> submitted -> approved (official number allocated here, Q7) -> (S3/S4 effects happen at approval or later, section 6.2); submitted -> rejected; draft/submitted/approved -> cancelled **only while no physical event and no accounting effect exists**; rejected -> draft (new revision). Cancelling an approved numbered document voids its number (never reused). A cancelled or rejected document is retained forever.

**Re-approval (SRS 4.4):** (the list of material fields below is a PROPOSAL for owner confirmation; the SRS only says "material fields") editing an approved document that has no executed physical event and no accounting effect, in a MATERIAL field (party, branch, currency, date, mode, any line item/unit/quantity/price/discount/tax/warehouse), moves it back to draft with a new revision; the previous approval stays in the history but is bound to the old revision and never counts for the new one; the official number is kept (not reallocated). Non-material fields (internal note, reference text) change in place and are audited. A document with a physical or accounting effect cannot be edited at all: only a linked return/reversal/adjustment document (S3/S4).

**6.2 Effects (S3/S4), exact rules from SRS 7.3:**
* **Direct mode (invoice):** approving the invoice creates ONE physical event (key `commdoc:<id>:physical:1`) that executes ONE stock document through `StockPostingService` in the SAME transaction as the approval (so approval cannot succeed without its stock effect, or fail leaving it half done), then the accounting effect (below).
* **Separate mode:** approving the invoice creates no stock effect. Approving a delivery/receipt document creates its physical event and stock effect; the invoice and the delivery are linked (S2); approving the invoice later creates **no** second stock movement and **no** second ledger effect for the delivered quantities (the invoice's own accounting is defined by Q4/Q5; the framework refuses any path that would post the same quantity twice, test below).
* **REQUIRED CHANGE TO MERGED CRITICAL CODE (3.7B), to be reviewed separately before S3:** `StockPostingService.PostAsync` (`StockPosting.cs`) opens its OWN company transaction (`transactions.ExecuteAsync`, then the private `ExecuteAsync(work, ...)` does the work), so the rule "approving an invoice executes ONE stock document in the SAME transaction as the approval" is impossible today. S3 therefore needs a new internal entry that runs the existing execution inside an AMBIENT transaction (`PostInWorkAsync(work, ...)`), the same refactor pattern as `CancelInWorkAsync/ReverseInWorkAsync` in 3.7C: validation, locks, costing, journal creation and audit unchanged, only the transaction owner differs. This is a change to merged, Critical 3.7B code and must be its own small PR with its own independent full-diff review and the full existing 3.7B/3.7C test suites unchanged and green, BEFORE S3 builds on it. The public `PostAsync` behaviour (including idempotent replay and concurrency) must remain byte-for-byte equivalent (a regression test pins it).
* **Who approves the auto-created stock document:** the stock-document independent-approver rule (3.7A) forbids the creator from approving. In direct mode the stock document is created by the system on behalf of the invoice approver; it is created ALREADY APPROVED as a derived document whose approval source is the invoice approval record (so the approver of the invoice is the approval source, and the invoice creator/last editor remain barred from approving the invoice). This is a new rule on top of 3.7A and is listed as an owner decision with the S3 questions (Q16 area): default fail-closed = the stock document is created only when an authorized, independent invoice approver exists; otherwise the invoice approval is refused (`no_independent_approver`), never auto-approved by the creator.
* **Accounting:** each event automatically creates one draft journal entry through the automatic path with key `commdoc:<id>:accounting:<event>`; if configuration or period state prevents it, an explicit pending state with a stable reason code is recorded (never silently skipped); period close is blocked while a pending effect remains (scenario 21.4); a Final Closed period is never posted into.
* **Foreign currency (ROADMAP):** a document is created and posted at its dated document rate (3.2B rates; manual override only with the existing permission, reason and audit); any settlement or allocation of such documents across currencies or rates is refused with code `fx_settlement_not_supported` until 3.18. S4 delivers the single gate function (the refusal and its test); 3.17 must call it.

## 7. Idempotency and the counting hook

* **Create idempotency:** `IdempotencyKey` unique per (company, document type, creator): a repeated create returns the original document with `replayed = true`; a key reused with a DIFFERENT payload is refused (`idempotency_key_reused`), exactly as the stock posting treats different amounts.
* **Event idempotency:** the deterministic event key of principle 2; the stock posting, costing operation, journal entry and the event row all carry it; replays return the originals.
* **Counting hook:** interface `IPostedBusinessTransactionCounter.RecordAsync(work, kind, sourceId)`, called INSIDE the posting transaction of every business document that reaches a posted/executed state, once per business event; the registered implementation is a no-op until 4.2 defines the Trial unit (OD-12). Tests: it is invoked exactly once per event, never on a replay, never for the automatic journal of a counted document or a reversal (the OD-12 proposal, recorded not decided), its absence of persistence (no-op leaves no row), and a throwing counter aborts the posting transaction (fail closed, nothing committed).

## 10. Risks and how the plan contains them

* **Duplicate effect under concurrency** is the principal risk: contained by deterministic event keys that are unique in three places (event row, stock posting/costing, journal source key), row locks on the document, and concurrency tests with real parallelism per slice.
* **Accounting rules invented by accident:** contained by Q4-Q6 defaults (explicit pending, no seeded mapping, no sales-return valuation) and by listing every such rule as OPEN.
* **Cross-slice drift of totals and snapshots:** snapshots stored as values with hashes and verified on storage.
* **Approval bypass by automatic tasks:** every automatic path goes through the same SQL approval gate and period gate; tested.
* **Scale of the change:** six slices, each independently reviewed against the full diff; no slice starts before its predecessor is merged; migration numbers are allocated by the lead per slice, never claimed in advance beyond 0028.

## 11. What is explicitly NOT assumed

No document type is activated for users, no account mapping is seeded, no revenue/COGS/GRNI posting rule is chosen, no sales-return valuation, no tolerance, no credit-limit enforcement, no Trial counting unit, and no screen: each is OPEN in section 8 until the owner decides, and the system refuses or marks pending rather than guessing.
