# Phase 3.10 - Tax engine (design proposal and slice plan)

Scope: SRS 6.1-6.4 and 19.8 only (flexible extensible engine; dated rates; classifications of operations, items and parties; several taxes; exemption, exception and zero rate; inclusive/exclusive; calculation base, rounding and priority rules per document type and operation; an immutable snapshot of rule, rates and results on the final document; an extension point for future national localization). **No country-specific compliance and no e-invoicing** (SRS 6.4). Acceptance (ROADMAP 3.10): deterministic exact decimal results; a snapshot never changes when rules change. No open owner decision (OD-n) applies.

Status: **slices 1 (arithmetic engine and snapshot), 2a (pure resolver) and 2b (persistence, audited configuration service, permissions) are implemented in this branch; slices 3-4 are not.** Document/framework integration belongs to 3.13; nothing here posts, stores or edits a financial document.

## Slice plan

1. **Pure engine + snapshot (this branch).** `Taxes/TaxModel.cs`, `TaxEngine.cs`, `TaxSnapshot.cs`: no database, clock, culture or floating point; arithmetic on exact rationals (`BigInteger`), ONE rounding step per amount.
2. **Persistence and rule resolution (company migration + system permissions).** Tax definitions, dated rates (no overlap per tax, never edited: a change is a new dated version), classifications (item, party, operation), rules per document type/operation (which taxes, priority, base flags, rounding policy), all immutable-versioned with audit; resolver that turns (document type, operation, item class, party class, date) into the ordered components the engine takes. Migration number: coordinate with the open 3.8D/3.9A work (0022 is contended).
3. **Management API and shared UI (Web and Tauri, Tabs standard).**
4. **Localization extension point:** a registered, versioned `ITaxLocalization` that may only ADD classifications/rules and validate inputs, never change engine arithmetic (documented and tested as an interface; no country module).

## Engine contract (slice 1)

* Inputs per line: quantity (<= 10 decimals), unit price (<= 6), discount (<= money decimals), price-includes-tax flag, ordered tax components. Non-negative only: credit notes are modelled by the document framework (reversal semantics), not by negative arithmetic.
* Component: tax id and code, **treatment** (Standard, ZeroRated, Exempt, NotApplicable), rate in percent (<= 6 decimals; zero for the three non-standard treatments), unique strictly increasing priority, and the set of EARLIER taxes whose amount is added to this tax's base (compound taxes).
* Treatments: Zero-rated, exempt and not-applicable lines contribute 0 tax but their turnover is reported separately. `TotalsByTax` is keyed by (tax, treatment, rate), so a Standard and an Exempt line of the same tax, or two rates of one tax, are never merged; a tax id keeps one code across all lines (`inconsistent_tax`). A Standard tax with a 0 % rate is non-taxable but keeps the Standard label.
* Rounding policy: money decimals (0-6); mode half-away-from-zero or half-even; level **per line** (every amount rounded once; later compound bases use the ROUNDED earlier amounts, as printed) or **per document** (exact amounts summed per tax, rounded once, then allocated to the lines by largest remainder, ties to the lower line number, so lines add up exactly; line bases are informational). Inclusive prices support per-line rounding only (`inclusive_requires_line_rounding`).
* Exclusive: net = round(quantity x price - discount); tax_i = base_i x rate_i / 100.
* Inclusive: gross G = round(quantity x price - discount) is AUTHORITATIVE. With multipliers m_i = 1 + sum(r_j m_j for the earlier taxes included in tax i's base), net0 = G / (1 + sum r_i m_i); net = round(net0); every taxable tax except the LAST taxable one is rounded; the last taxable tax is G - net - the others, so net + taxes = G exactly (no cent is invented or lost); a NEGATIVE residual is taken from the last taxable tax first, then from the earlier taxable taxes (last to first), then from the net, so no amount is ever negative. No taxable tax: net = G.
* Refusals with stable codes (no partial result): invalid precision, negative values, discount above gross, inputs or results beyond the supported range (`amount_too_large`, never an overflow), rate out of range, treatment/rate mismatch, duplicate tax or priority, a base reference that is duplicated, self-referencing, later or unknown, more than 8 taxes per line or 5000 lines (all fractions are reduced after every operation: 5000 lines x 8 compound taxes per document run in well under a second).
* **Snapshot:** `tax-snapshot-v1` stores VALUES, not references: the policy, the resolved components (with opaque rule/rate version references as strings supplied by the resolver), the inputs and the results, plus a SHA-256 over the canonical, scale-normalized JSON. `Verify` recomputes the engine from the snapshot's own inputs and compares results and hash, so a later rule/rate change cannot alter or invalidate an existing snapshot, and tampering is detected. The hash is tamper-evidence, NOT authentication: authenticity belongs to the document store and its audit chain. `Create` keeps defensive read-only copies and normalizes a missing base list to empty.

## Held for slice 2 (found by the independent review; not representable in the arithmetic slice)

* SRS 6.1 names "exceptions" (استثناء) next to exemption and zero rate. `TaxTreatment` has Standard, ZeroRated, Exempt and NotApplicable and is not persisted yet. Proposal: an "exception" is a RULE-level override (a party or item classification that resolves to Exempt/NotApplicable or to another rate), not a fifth treatment; confirm this mapping before the enum is persisted.
* The calculation base is always the net after discount. A per-document-type choice of base (before discount, plus other charges) is a rule attribute of slice 2 (`TaxBaseRule`), not an engine argument yet.
* Dated rates, classifications, per-document-type rules and priority resolution, and the localization extension point are slices 2 and 4.

## Mandatory tests (this slice)

Arithmetic matrix (single/multiple/compound taxes, zero/exempt reporting, discount, fractional quantity, both rounding modes, per-line and per-document allocation with exact sums, inclusive pricing with the residual rule, every refusal), property-style invariants (sum of lines = totals; inclusive net + taxes = gross; deterministic across repeated calls; scale-independent hash), snapshot round trip and tamper detection. PostgreSQL tests arrive with slice 2.

## Slice 2a - pure rule resolver (implemented)

`Taxes/TaxResolver.cs` turns a `TaxContext` (document type, operation, item class, party class, tax date) plus the company's tax definitions, dated rate versions and rules into the ordered `TaxComponent`s the engine takes; no database or clock. Candidate rules are active, dated around the tax date and match document type and operation; a null classification matches anything and a set one only an equal classification. For each tax the most specific candidate (two constrained dimensions beat one, one beats none) wins; equally specific candidates of one tax are `ambiguous_tax_rule` (item-only against party-only included): the company fixes its rules, nothing is guessed. The treatment and rate come from the latest dated version at or before the tax date (`no_tax_rate` if none, `invalid_tax_data` for two versions from the same date); a rule's `TreatmentOverride` (zero rated, exempt, not applicable) replaces them and is how a classification yields an exemption (the SRS "exception"). A base reference may name only an earlier-priority tax that applies to the line; a referenced tax that does not apply is simply not in that line's base. Components carry a `RuleRef` naming the rule and the exact rate version used, which the snapshot seals.

Remaining in slice 2: the company migration (definitions, append-only dated rates, classes and their item/party assignments, rules and base references, versioned rounding policy; company 0022 and system 0024 are reserved), the audited management service and the permissions. Slice 3 is the API and the shared Web/Tauri UI.

## Slice 2b - persistence and the audited configuration service (implemented)

**Migration numbers (coordinated across open branches):** company **0022** and system **0024** are this slice; PR #48 (3.8D) keeps its reserved company 0023 and system 0025, so whichever branch merges second renumbers nothing but the pinned counts in the migration-count tests (listed in the PR description). System 0024 only adds permission codes to the preset Company Administrator (the preset-role trigger is paused for exactly that statement, as in 0022/0023).

**Names are derived, not typed.** `tools/schema/company-0022-tax.cjs` holds the single SQL template with logical tokens and derives every opaque physical name as prefix + the first 8 hex digits of SHA-256(`hasm.company.0022.tax.v1:` + token). `--write` produces `0022_company_tax_engine.sql` and `CompanySchema.Tax.cs`; `--check` fails when the committed files differ; a collision with any existing name aborts the run. `TaxSchemaDerivationTests` re-derives every committed name in CI, proves uniqueness against all company and system names and checks the migration is additive (no DROP, no GRANT, nothing seeded, REVOKE on every table, trigger guards on the append-only tables).

**Tables (all configuration, no amount):** `TaxDefinition` (code and identity immutable, revision-fenced, never removed), `TaxRateVersion` (append-only; trigger refuses update, delete, truncate and any version not strictly later than the tax's latest; only Standard carries a rate, 0-1000 with 6 decimals), `TaxClass` (kind item/party immutable, unique per kind), `TaxItemClass` / `TaxPartyClass` (one class per item / party; a composite foreign key makes it impossible to put a party class on an item), `TaxRule` (document type, operation, optional item and party class, priority 1-1000, validity dates, optional treatment override; stored generated kind columns make the class foreign keys kind-safe; never removed), `TaxRuleBase` (earlier taxes whose amount joins the base), `TaxPolicyVersion` (append-only rounding policy: decimals 0-6, mode, level). Nothing is seeded; a company without a policy gets `no_tax_policy` from the resolution, not a guessed default.

**Service.** `TaxConfigService` (audited, one company transaction per write, events 1400-1409) and `TaxManagementService` (`company.tax.view` reads and resolves, `company.tax.configure` writes; a user without the permission reads and writes nothing and nothing is audited). A rate version must be strictly later than the tax's latest (history is never rewritten); two active rules of one tax, document type, operation and classification may not overlap in time (`rule_overlap`, they would always be ambiguous); an item-only and a party-only rule for one tax are still ambiguous and are refused by the resolver at resolution time. `ResolveAsync` reads classes, rates, rules and policy in one read-only repeatable-read transaction, runs the pure resolver and returns components plus the policy and its version, so the future document framework can calculate and seal a `TaxSnapshot`.

**Runtime privileges.** Taxes, classes and rules: SELECT/INSERT/UPDATE; rate and policy versions: SELECT/INSERT; item and party class assignments and rule bases: SELECT/INSERT/(UPDATE)/DELETE. These three tables are therefore added to the existing exact allow-list of DELETE-capable tables in `CompanyRuntimeUnitTests` and `GlCompletionUnitTests` (now nine); they hold replaceable configuration and every replacement is audited by the service. This is the only existing guard list extended; no protected check, policy or constraint is relaxed.

**Tests.** 10 PostgreSQL tests (`TaxConfigTests`, registry 962 -> 972) cover dated rates, kind safety by service and database, rule validation and overlap, revision fences, append-only guards, the resolution matrix (dated rates, classifications, override, compound base, engine hand-off), ambiguity and inactive-tax refusal, authorization with no audit, and concurrent rate and policy versions; 3 unit tests re-derive the physical names. Pinned migration counts in existing tests were raised (22 company, 24 system).

**Follow-ups closed after the review (slice 2c).** (1) *Rule-base revision fence in the database:* a trigger on the rule-base table refuses INSERT/DELETE unless the same transaction wrote the parent rule row (its xmin is the current transaction), so a base can no longer be edited behind the revision fence; the service already writes the rule and its base in one transaction. (2) *Removal audit:* replacing or removing an item/party class assignment records the previous class (`previous=`), a rule update records the old and new base. (3) *DELETE scope:* only three tables allow DELETE for the runtime role (item and party class assignments, rule bases), each audited and, for rule bases, now DB-fenced; nothing else can be deleted. (4) *Rate lead limit:* the SRS sets no limit on how far ahead a rate may be dated, so the 366-day cap is NOT a requirement: it is a deployment policy (`TaxConfigOptions.MaxRateLeadDays`, default 366, 0 = unlimited) whose only purpose is to stop an irreversible typo (versions are append-only and strictly ordered). The migration was regenerated (0022 is not merged yet, so still one forward migration); the existing opaque names are unchanged, two new ones were added (`f_831e3a7a`, `r_93dc07ce`). 11th PostgreSQL test (registry 972 -> 973).

## Slice 3 - management API and the shared Web/Tauri screen (implemented)

**API** (`TaxEndpoints.cs`, `/api/v1/company/taxes`): GET/POST taxes, PUT `/{id}` (If-Match), POST `/{id}/rates`, GET/POST/PUT `classes`, PUT `item-classes/{itemId}` and `party-classes/{partyId}` (body `{classId}`, null removes), GET/POST/PUT `rules`, GET/POST `policy`, GET `resolve`. The company comes only from the server-side session; every call is authorized inside `TaxManagementService` (`company.tax.view` / `company.tax.configure`); list responses carry `can.configure`. **There is no DELETE route**; revision-fenced entities answer 428 without If-Match and 412 with the current revision on a stale one. `Tax:MaxRateLeadDays` (configuration, default 366, 0 = unlimited) is bound to `TaxConfigOptions`.

**Screen** (`pages/Taxes.tsx`, route `/company/taxes`, menu entry under Company, permission `company.tax.view`): one shared screen for Web and Tauri using the single `Tabs` component, grouped by business meaning: taxes and dated rates, classes, application rules, rounding policy. Switching tabs keeps typed input; each tab reports unsaved edits (tab marker and the shared unsaved guard); controls follow `can.configure` and nothing offers deletion (deactivate only). Server refusals (overlap, ambiguity, duplicate priority, base order, stale revision) show translated reasons. Arabic RTL and English LTR messages in `messages.tax.ts`. Assigning a class to an item or party uses the API above and is still to be surfaced on the item and party screens when they are next revised.

**Tests.** 3 PostgreSQL HTTP tests (`TaxApiTests`, registry 973 -> 976): authentication and company selection on every route, no delete route, the end-to-end flow with ETags, 428/412/400 handling, resolution, and permission denial (no permission: nothing read or written; viewer cannot configure). 9 shared component tests (`taxes.test.tsx`). Frontend: 401 web tests, typecheck and production build pass locally.

Remaining: slice 4 (localization extension point) and the class pickers on the item and party screens.
