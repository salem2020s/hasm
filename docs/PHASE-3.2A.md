# Phase 3.2A — Chart of Accounts

**Status:** implemented locally on `feature/phase-3-2a-chart-of-accounts` (from main at `83e8113`, after PR #15). Nothing is applied to any permanent database.
Part of **Phase 3.2 — General Ledger foundation** (owner-approved); 3.2B (journal entries and the posting engine) follows.

## Approved scope (3.2A)
Independent chart per company (its own database, so no cross-company reference exists); a flexible hierarchical tree with no fixed depth, expressed by real parent relationships (never by code prefixes); stable internal ids independent of display codes; unique codes per company, automatic and manual assignment; the five types (Assets, Liabilities, Equity, Revenue, Expenses), debit/credit nature, Balance Sheet / Profit and Loss classification; group (parent) accounts and postable leaf accounts; posting only to ACTIVE, eligible leaf accounts; activation/deactivation without deleting history; controlled tree changes; currency attributes compatible with future posting; optimistic concurrency; transactional audit and append-only history; fine-grained RBAC; Arabic/English names with fallback; an empty chart or a generic starter template; one shared Web/Desktop screen.

## Still OUTSTANDING Release 1 Chart of Accounts requirements (explicit; NOT delivered here)
1. **Business-type templates** (the SRS requires templates for various kinds of company): only the generic template exists. Each industry template needs its own reviewed content. Scheduled as a later slice (proposal: **3.2A-2**); no dependency beyond this phase.
2. **Excel import with validation, dry-run and reconciliation** (SRS section 14: staging, Dry Run, duplicate/consistency checks, mandatory authorized approval before the final import): not delivered. It depends on this phase and on the generic import framework (staging, dry-run, approval) that serves all later imports. Scheduled as a later slice (proposal: **3.2A-3**).

The Chart of Accounts requirement as a whole is therefore NOT complete; the screen states this.

## Design decisions
1. **Tree integrity is enforced by PostgreSQL** (deferred constraint trigger, checked at commit): a parent is always a GROUP account; a non-group has no children; a child has its parent's type (hence the same statement); an account is never its own ancestor (recursive check); an active account has an active parent, and a group with an active child cannot be deactivated. Type to statement is a CHECK (Assets, Liabilities, Equity = Balance Sheet; Revenue, Expenses = Profit and Loss). The nature is stored separately, so contra accounts (accumulated depreciation, sales returns) are possible.
2. **Postable** = active and not a group (a non-group is a leaf by construction). The future posting engine must use exactly this rule.
3. **Codes are NOT immutable** (unlike branch and warehouse codes): re-coding is its own operation behind its own permission (`company.accounts.recode`), audited with the old and new code in the history; the stable id never changes. Normalisation: trim, Arabic-Indic and Extended Arabic-Indic digits to Latin, upper case; shape `[A-Z0-9][A-Z0-9._-]{0,29}`; unique case-insensitively.
4. **Automatic codes** (company setting, default on, segment width default 2, range 1 to 4, changed with `company.accounts.configure`): a child's code is its parent's code plus a zero-padded sequence number (`1` then `101`, `102`, ...); a top-level account takes the default digit of its type (1 to 5) and afterwards the next free number after 5. Collisions are skipped, never duplicated; when no code can be generated the user types one. A manual code is always accepted.
5. **The type never changes** after creation (a subtree would be invalidated); moving to another parent requires the same type. Restructuring (`company.accounts.restructure`) is audited.
6. **History protection:** nature, group flag and currency policy are protected attributes: they change only while the account has no postings. The General Ledger does not exist, so `IAccountUsageProbe` is a placeholder (it never claims history and is reported as unimplemented). As with the period close checks, once a financial module reports history while the usage probe is a placeholder, protected changes are REFUSED (`account_usage_checks_not_implemented`): no silent bypass. Names, re-coding, moving within the type and (de)activation are never frozen.
7. **Master data is not financial history:** creating, renaming and organizing accounts never activates the base-currency or time-zone lock (tested). Only real posting history, reported by the registered financial-history probes, does.
8. **Currency attributes:** policy `base` (default), `any` (any enabled currency) or `specific` (one enabled currency). The posting engine (3.2B) enforces them together with exchange rates.
9. **Template application** creates all accounts in one audited transaction, only on an EMPTY chart (accounts are never deleted, so at most once); the accounts carry the template key and are ordinary afterwards.
10. **Permissions** (company-wide only): `company.accounts.view/create/update/activate/recode/restructure/configure`, all in the preset Company Administrator (system migration 0010); branch and warehouse grants never reach the chart.

## Dependencies for Phase 3.2B (identified now; to be scheduled BEFORE enabling the affected posting operations)
3.2B must deliver everything approved for Release 1: simple and compound manual and automatic entries; Draft, Posted and Reversed states; atomic balanced posting; immutable posted entries; reversal and adjusting entries; company and fiscal-year document numbering without reuse of voided numbers; multi-currency with exchange-rate conversion and FX handling; branch and cost-center allocation; separate create, post and reverse permissions; configurable approval policies (automatic posting never bypasses applicable approvals); full `FiscalPeriodGate` integration (Final Closed never, Soft Closed only when authorized); duplicate-source protection; trial balance and basic ledger reporting. Prerequisites that do not exist yet, each to be built as its own audited slice before the operations that need it are enabled (a posting operation that would bypass a required policy must not ship):
- **Document numbering** (D-015): company/branch/type/fiscal-year sequences, protected, no reuse.
- **Exchange rates** (D-011): effective-dated rates, authorized override with reason, FX difference recognition.
- **Cost centers**: master data linked to branches, and their allocation model.
- **Approval policies engine** (D-008, D-024): configurable thresholds and separation of duties; manual and automatic posting both consult it. Until it exists, the post operation stays disabled for any document type whose policy cannot be evaluated.
- The account-usage probe, the `general_ledger` financial-history probe and the period close probes are implemented by 3.2B itself.
