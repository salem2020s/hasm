# PROPOSAL — Phase 3.2D generic import framework

**Status: APPROVED by the owner (slices S1-S5, including the Chart of Accounts adapter; all six decisions resolved below). Implementation in progress on `feature/phase-3-2d-import-framework`; the opening-balance adapter is NOT part of 3.2D.**

## Design

**Isolation rule.** Imports only ever write to import tables (staging). Business tables are touched only by an adapter's *apply* step, after validation, a successful dry run, an independent approval and a re-validation against the current data, inside one audited company transaction (or recoverable chunks, see decision 3).

**Framework (generic, no business rules)**
* *Tables (company migration 0010, opaque names like all migrations, append-only where history matters):* `ImportBatch` (adapter code, status, file name/size/SHA-256, mapping, options, plan evidence hash, creator/submitter, revision), `ImportRow` (row number, raw cells, normalized values, status, errors, row hash, resolution), `ImportEvent` (every state change). No foreign key from staging to business tables.
* *State machine (enforced by a PostgreSQL trigger and the service):* `uploaded → mapped → validated (dry run) → submitted → approved → applying → applied`; side exits `failed` (recoverable, resumable), `rejected`, `cancelled`, `expired`. Any change to file, mapping, options or resolutions returns the batch to `mapped` and voids earlier approvals (revision bound, like journal approvals).
* *Parsing (backend only):* CSV (UTF-8/BOM, delimiter detection, quoting) and `.xlsx` (read-only; values only, formulas never evaluated, no macros/external links, `.xlsm`/`.xls` rejected), content sniffing not just extension, size/row/column/zip-expansion limits, formula-injection neutralisation on any export of errors.
* *Mapping and normalization:* adapter declares target fields (name, type, required, normalizers: trim, Unicode NFC, Arabic-Indic digits, decimals, dates with explicit format, enum aliases); the user maps source columns; saved mapping templates per adapter and company.
* *Dry run:* per-row validation, intra-file and against-database duplicate detection, conflict classification, a **plan** (exact operations the apply would perform), reconciliation totals (counts, sums, debit = credit where relevant) and a reproducible evidence hash. Nothing business-side is written.
* *Approval:* reuses the existing approval machinery (document type `import_batch`, ordered stages allowed). **Floor of one independent approval that no setting can lower** (same pattern as year-end): the uploader/submitter can never approve, PostgreSQL refuses it, approvers must be currently authorized at apply time, approval binds to the batch revision and evidence hash.
* *Apply:* idempotent (batch status transition under a lock, source keys, plan-hash check: refuses if data changed since the dry run), atomic per adapter declaration, progress counters, safe retry/resume, cancel before apply, audit event per transition and summary of results.
* *RBAC:* `company.imports.view|upload|configure|submit|approve|apply|cancel` plus the adapter's own business permission (importing accounts needs the right to create accounts); company isolation by the existing per-company database/runtime role; every call re-reads permissions.
* *Adapter contract (separate code per domain):* `Code`, required permission, field schema, `Validate(row, context)`, `DetectConflicts`, `Plan`, `Apply(work, plan)` (uses the module's own services so every business rule, approval policy and DB trigger still applies), `Atomicity` (single transaction vs idempotent chunks). Chart of Accounts, opening balances, parties, items/inventory and bank statements are later adapters; none of their rules enter the framework.
* *UI:* one shared React wizard (Web and Tauri): upload, mapping, dry-run results with filters, conflicts and resolutions, reconciliation, submit, approval inbox, progress and history. Arabic RTL / English LTR.

## Owner decisions (recorded)
1. **S5 is part of 3.2D.** Slices S1 secure infrastructure and parsers, S2 mapping/normalization/validation/dry run, S3 independent approval and controlled execution, S4 shared Web/Desktop wizard, S5 the real Chart of Accounts Excel/CSV adapter, a complete end-to-end capability (not a demo). Roadmap 3.2A-3 is marked fulfilled by 3.2D only when the Chart adapter satisfies every approved 3.2A-3 requirement and test; a working framework or a test adapter alone is never reported as Chart import.
2. **Vetted read-only Excel library** (ExcelDataReader is a candidate): review license/redistribution, maintenance and advisories, pin the version, review transitive dependencies, use reading only; no custom XLSX parser unless a concrete incompatibility is proven. Formats: `.xlsx` and `.csv` only (no legacy XLS, no XLSM). Validate extension and real structure; never execute formulas, macros or external links; reject formula-bearing cells instead of trusting cached results; limits against ZIP/XML bombs, malformed files, oversized cells and resource exhaustion; stream where possible; every value untrusted; formula-injection protection for logs, previews and exports; leading zeros preserved (account codes); deterministic Unicode/Arabic/locale number handling; malicious and malformed file regression tests.
3. **Limits and transactions.** Server-enforced configurable defaults: 10 MB per file, 50,000 data rows; further configurable limits for worksheets, columns, cell length, expanded ZIP size, memory and processing time, each with a clear error. Adapters declare their execution model. All-or-nothing adapters (Chart of Accounts included) apply the whole approved batch atomically, commit nothing on any failure, keep the previous business state, keep diagnostics safely and allow idempotent retry after correction and revalidation. Chunked/resumable apply only for adapters that explicitly support it with durable checkpoints, idempotency, valid partial states and recovery; never partial financial/accounting imports to avoid a transaction limit.
4. **Encrypted original file, key management and retention (option a approved).** A reusable application-level file-encryption service is built in S1 (it is also the base for future sensitive attachments, D-031/D-032). *Envelope encryption:* AES-256-GCM per file with a random 256-bit data key (DEK) and a unique random 96-bit nonce per encryption; the DEK is wrapped under a versioned master key (KEK) with AES-256-GCM key wrapping (authenticated, unique nonce, key id and context as associated data). Only the wrapped DEK, key id/version, nonces, tags and format version are stored with the ciphertext; the header and a context string (company, batch) are authenticated, so a file cannot be swapped between batches or tampered with. *Keys:* external key files in a protected key directory (same owner-only permission model as the audit keys: Linux modes, Windows ACLs), several versions side by side, an active key id for new files, never in the repository, database, encrypted-file storage, logs, exceptions or API responses; fail closed when a required key is missing or invalid; no silent generation of a replacement; an auditable rewrap procedure re-wraps only the per-file DEKs under the new key (files stay decryptable during rotation); backup/recovery must include a separately protected copy of the key directory; keys are not tied to a machine, so a central-server migration only moves the key directory. Only .NET primitives are used. *Files:* encrypted before persistent storage, no persistent plaintext temporary files, stored outside any public path, read only through backend authorization, authentication tag verified before any plaintext is accepted. This is **not** an enterprise KMS (no HSM, no automatic rotation, no key escrow service). Tests use disposable random keys; production fails closed without valid key configuration. *Retention (company-configurable, default 30 days):* encrypted original and staging rows are removed 30 days after the batch reached a terminal state (applied, rejected, cancelled, expired); pending batches carry an explicit expiry and need renewal (which forces revalidation); an applying or failed (recoverable) batch is never removed automatically; cleanup is audited; audit events, approval decisions, hashes and reconciliation manifests follow the audit-retention policy and survive; the SHA-256 of the original and the canonical plan hash stay on the batch record so they remain verifiable after the file is gone.
5. **Conflict resolution (complete).** Default: existing business records are preserved; no automatic overwrite, merge, recoding or restructuring. The framework detects duplicate rows inside the file, matches against existing business records and conflicting identifiers, codes, parent relationships and types; it separates exact matches, resolvable conflicts and blocking validation errors; supports explicit per-row resolution choices recorded in the import history; recalculates the dry run and the plan hash after any change and voids earlier approvals when the file, mapping or a resolution changes; refuses to apply while blocking conflicts remain; and revalidates current business data inside the authorized application transaction. Each adapter declares its supported resolutions. *Chart of Accounts adapter:* never overwrites an account, never changes the immutable type, never creates duplicate codes, never violates hierarchy rules or creates cycles, never bypasses Chart RBAC, keeps stable ids, preserves Arabic and English names, respects nature/classification/currency policy/group-postable rules, matches existing accounts only by documented deterministic rules (normalized code), treats ambiguous matches as conflicts, preserves leading zeros, accepts parents after children. Initial supported resolutions: **CREATE** (new accounts) and explicit **SKIP** (existing accounts); any later modification support must go through the audited domain operations. The dry run explains what will be created, skipped, rejected or changed, and the approved plan equals the operations applied.
6. **Opening-balance imports (future adapter, NOT in 3.2D).** The adapter will create controlled DRAFT journal entries that follow the normal journal approval and posting workflow: upload, stage, validate and reconcile, mandatory independent import approval, apply creates drafts, drafts are submitted to the existing accounting approval, posting only after journal approvals and every normal posting validation. Import approval never substitutes for journal approval; both are separately enforced and audited. The uploader/submitter cannot approve their own import and the journal creator/submitter cannot approve their own journal; the same person is not automatically barred from approving in both workflows unless another approved segregation policy says so. It must respect fiscal years and periods, existing year-end closing and opening balances, balancing, branch and cost-center dimensions, currency policies and rates, duplicate prevention, idempotency, immutable posted journals and audit integrity. It stays a Release 1 deliverable on the roadmap.
