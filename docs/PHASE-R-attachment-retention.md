# HASM - Phase R: retention and purge of removed attachments (plan)

Status: **PLAN** (R1 is being built; nothing is deleted by R1). Identifiers are allocated by the lead (section "Allocations"). Technical defaults are proposed under D-048 and are fail-closed. Risk: **Critical** (a purge destroys evidence that may be legally required; it touches key custody and backups).

## 1. Source of truth

* **D-082 (owner, 2026-11-21, approved):** removed attachment data is retained according to a configurable, **company-approved legal retention policy**; without a valid policy the default is **preservation**; purge is permitted **only after retention eligibility, legal-hold verification, authorization and audited execution**; encryption keys are **never retired while retained data still needs them** (register item K).
* Related owner decisions that this plan must not contradict: D-080 item 6 (independent approval for key retirement and restore), D-081 (restore cutover creates a new audit checkpoint epoch; earlier chain preserved), D-085..D-088 (encrypted backups, backup retention minimums, legal hold on backups, key-directory backup).
* Existing behaviour (docs/PHASE-3.12.md and the code): a removed attachment is a row with state 2, who, when and why; its bytes and key id are **kept**; it is unreachable (no download, absent from lists); the row guard says never deleted, never truncated, and a removed row never changes again. Backups copy removed bytes. `maintenance/verify` and the backup trial restore treat every row, active **and removed**, as needing its file. `retainedUnderOtherKeys` / `oldKeysMayBeRetired` count removed sensitive rows.
* `docs/PHASE-4.3.md` records two dependencies on this decision: the backup ordering argument ("dump before folder copy is safe") relies on no purge, and a purge "must coordinate with a running backup".

## 2. Principles (fail closed)

1. **Preserve by default.** Every uncertainty (no policy, an unapproved policy, an unreadable policy, a clock or time-zone doubt, a failed hold lookup, a running backup) means NOT eligible and nothing is deleted.
2. **Two people, always.** The person who drafts a policy never approves it; the person who requests a purge never approves it. Enforced by the service **and** by PostgreSQL CHECK constraints (the pattern of `company.fiscalreopen`).
3. **Re-verify at every step.** Eligibility and holds are evaluated when a plan is created, when it is approved, and again per item immediately before the bytes are deleted.
4. **Bytes only.** A purge deletes the stored file. The attachment **row stays forever** (it is guarded today and also the proof): file name, content type, size, SHA-256 of the plaintext, key id, who/when/why removed. Whether metadata should also be minimised is an owner question (section 13), the default is to keep it.
5. **Never silent.** Every policy change, hold, plan, approval, rejection, execution and refusal is an audit event in the company chain.
6. **Keys follow data.** A key is retirable only when neither live data nor a retained backup still needs it (section 9).

## 3. Data model (company migration **0031** for R1, **0032** for R2 if its tables are separate; generated by `tools/schema/company-0031-attachment-retention.cjs`, names derived from a versioned token; no change to the guarded `Attachment` table, so no DROP is needed)

All four tables are append-only in the sense below and are never deleted or truncated; revision advances by one; identity and creation data are immutable.

* **`AttachmentRetentionPolicyVersion`**: `Id`, `Version` (1, 2, ... contiguous, unique), `Status` (1 draft, 2 approved, 3 revoked, 4 superseded), `Rules` (one row per rule in a child table `AttachmentRetentionRule`, see below), `EffectiveFrom` (a date, not before the approval time), `ShortensAnyPeriod` (computed at approval), `ShorteningAcknowledgement` (text, required when it shortens), `DraftedBy/At`, `ApprovedBy/At`, `RevokedBy/At/Reason`, `Note`. CHECKs: `ApprovedBy <> DraftedBy`; an approved row only changes status to revoked or superseded; a draft may be edited by its author only until submitted (the first slice may simply make drafts immutable and create a new draft instead).
* **`AttachmentRetentionRule`** (child of a version): `SubjectKind` (a registered attachment record kind, or `*` for all), `Sensitivity` (1 normal, 2 sensitive, 0 any), `RetentionMonths` (integer, 1..1200) or `Indefinite` (flag; mutually exclusive). The most specific matching rule wins (kind and sensitivity, then kind, then sensitivity, then `*`); if no rule matches, the effective rule is **Indefinite**.
* **`AttachmentLegalHold`**: `Id`, `Scope` (1 company-wide, 2 one record: `SubjectKind` + `SubjectId`, 3 one attachment: `AttachmentId`), `Reason` (required, at most 500), `Reference` (optional external case reference), `PlacedBy/At`, `ReleasedBy/At/Reason` (all null while active). A hold is released only under the rules of section 6; a released row never changes again; holds are never deleted.
* **`AttachmentPurgePlan`**: `Id`, `Status` (1 requested, 2 approved, 3 executing, 4 completed, 5 rejected, 6 expired, 7 cancelled, 8 failed), `PolicyVersion` used for the eligibility snapshot, `ItemCount`, `RequestedBy/At`, `Reason`, `ApprovedBy/At`, `HoldAttestation` (the approver's explicit statement that no legal matter outside the system requires these records; required, stored verbatim), `RejectedBy/At/Reason`, `ExpiresAtUtc`, `ExecutionStartedAt`, `CompletedAt`. CHECK `ApprovedBy <> RequestedBy`.
* **`AttachmentPurgeItem`**: `PlanId`, `AttachmentId` (unique per plan; and **unique overall**: an attachment is purged once), `EligibleSince` (date computed), `ChecksSnapshot` (policy version, rule, hold check result), `State` (1 pending, 2 bytes deleted, 3 skipped with a reason code, 4 failed), `DeletedAt`, `ReasonCode`. Only the transitions pending -> deleted/skipped/failed are allowed (trigger), nothing else changes.

A removed attachment is **purged** exactly when a purge item in state 2 exists for it. The state is derived, not stored on the guarded row.

## 4. Policy configuration and approval

* A policy is a set of rules (section 3). Technical defaults, chosen fail-closed: **no rule = Indefinite**; no approved policy = Indefinite for everything; a version is "valid" only when approved, effective, not revoked or superseded, and its approver differs from its author.
* Lifecycle: draft (`company.attachmentretention.configure`) -> approve by a different user (`...approve`) -> becomes the one effective version at `EffectiveFrom` (the previous one is superseded) -> may be revoked (approve permission, reason) which returns the company to preservation until a new version is approved.
* **No silent retroactive shortening.** For an attachment removed under an earlier version, the retention is `max(period of the version in force at its removal date, period of the version in force now)`. A new version that shortens any period is flagged at approval, the approver must write an acknowledgement, and it is audited; it still cannot make old removals eligible earlier than their original period.
* The period is counted from the removal date (`RemovedAtUtc`), in whole calendar months, UTC. **This basis is OWNER-PENDING (D-109, question 1) and is NOT fail-closed by itself** (a different basis, for example the end of the fiscal year of the related record, can make an item eligible LATER than this one). Therefore, **while D-109 is owner-pending no item is ever eligible**: the eligibility check answers `retention_basis_pending` and **R2 purge execution stays DISABLED** (a fail-closed switch in code, `retention_basis_pending`, that only a recorded owner answer to D-109 turns on). R1 and R2 may still be built; R1 deletes nothing.
* **Attachments removed before any policy existed are Indefinite** (no version was in force at their removal, so no period was ever committed to; the default is preservation). Adopting a policy later never makes them eligible; only a new owner decision could.
* Policy edits and views are audited; the approved policy text is shown with its author, approver and dates.

## 5. Eligibility check (pure function, unit tested; used three times)

Inputs: the attachment row, the policy history, the hold set, the purge items, the clock, and facts about the environment (company lock, backup running). Output: one reason code, never a boolean alone.

`Eligible` only if ALL hold: the row is removed (state 2); it is not already purged; a **valid** policy history exists (otherwise `no_valid_policy`); the applicable rule is not Indefinite (`indefinite`); `now >= removedAt + retention` (`not_yet_eligible`, with the date); **no active hold** covers it (company-wide, its record, or itself; otherwise `legal_hold` with the hold id); the key situation is known (a sensitive row's key id is readable; otherwise `key_state_unknown`); the company is not busy with a backup, migration or provisioning (`company_busy`); and the retention basis has been confirmed by the owner (`retention_basis_pending` while D-109 is owner-pending: **always, until the owner answers**). Any exception while evaluating yields `check_failed`: not eligible. For an attachment removed before any policy version existed the answer is `indefinite`.

## 6. Legal hold

* **Placing** a hold is protective and cheap: `company.attachmentretention.hold`, company-wide scope included. It takes effect at once for every later check (including plans already requested: the execution re-check refuses the item as `legal_hold`).
* **Releasing** a hold enables purge, so it needs `company.attachmentretention.approve` and a reason; the service and PostgreSQL refuse a release by the person who placed the hold. **The releaser of a hold may never approve a purge plan that contains an item the released hold covered** (checked at approval from the stored `ReleasedBy`; no time window: fail-closed). This chooses the "bar the releaser" option over a second approver for the release.
* **Verification** is both mechanical (the hold table) and attested (the approver's `HoldAttestation` on the plan). The system cannot know about a hold that was never entered, so the attestation is a mandatory human step recorded in the audit.
* **A hold on an already-purged attachment** (lead decision under D-048, consistent with D-086 "never automatically delete a backup under legal hold"): placing it marks **every retained backup set that contains that attachment** as under legal hold, so backup retention (D-086) never deletes those sets. Placing the hold warns and lists those sets. The marking uses the backup inventory (R4); until R4, every retained backup set is treated as under legal hold for D-086 purposes (no backup deletion), and the warning says the inventory is unavailable. Recorded in D-114.
* Holds are visible on the record's attachment list ("on legal hold") and on the retention screen. A hold on a record covers the record's attachments including those removed later.

## 7. Purge: request, approval, execution

1. **Preview (read only).** A paged list of removed attachments with their eligibility reason (never file names of sensitive attachments to users without the sensitive permission; ids and kinds only). Nothing changes.
2. **Request** (`...execute`): select up to a bound (default 200 per plan; configurable below a hard cap of 1000) eligible attachments, or all eligible matching a filter up to the bound, plus a reason. The service re-checks each item, stores the snapshot, sets `ExpiresAtUtc` (default 7 days), audits the request. Items found not eligible are refused by reason.
3. **Approval** (`...approve`, a different user): the approver sees counts per kind, the date range, the policy version and the holds summary, must type the attestation, may reject (reason). Approval re-checks every item; items that fail are dropped from the plan with a reason, the approver sees that before confirming.
4. **Execution** (`...execute`, may be the requester, never before approval, never after expiry; disabled while D-109 is owner-pending): first takes a **row lock on the plan and a status compare-and-set** (`approved -> executing`), so the same plan can never run twice concurrently; then takes the company lock with the shared bounded acquisition the backup uses (`company_busy` if a backup, restore, migration or provisioning holds it; the plan stays approved, nothing is lost). Per item, in this order, resumable and idempotent: re-run the eligibility check; write the purge item row (state pending) together with its audit event in ONE transaction and commit; delete the file; then mark the item "bytes deleted". A crash after the commit leaves a pending item whose file may still exist: the next run (or the orphan sweep) completes it. A crash can never leave a file deleted without a purge record. A file that is **missing before the purge** (no pending purge item was committed for it) is NEVER recorded as deleted: the item is `skipped` with the reason `file_missing_before_purge` and audit 2008 carries an integrity warning (the bytes were expected to exist; this is an integrity finding, not a successful purge). A resumed pending item whose file is already gone was deleted by this plan and is completed as deleted.
5. A plan finishes `completed` (all items deleted or skipped with reasons), or `failed` with the remaining pending items listed; it can be resumed by an authorized user (one more approval is NOT needed for the same approved items, but expiry applies to approval, not to a started execution).

Purged content cannot be restored by the application. The only copy is an older backup (section 8).

## 8. Interaction with backups (D-085..D-088, Phase 4.3)

* **Ordering and consistency.** Backups hold the company lock for their whole run and execution takes the same lock, so a purge never runs during a backup, and a backup never sees a half-executed batch. This closes the dependency recorded in PHASE-4.3 ("the dump-before-folder argument relies on R staying open"). The backup argument itself stays valid: every file referenced by a row in the dump either still exists or has a purge item **committed before the delete**; the set verification (below) understands both.
* **Purged bytes still exist in older backup sets.** A purge is a purge of the **live** installation, not erasure from history. Backup retention (D-086: daily/weekly minimums, month-end and year-end per a company legal policy, default never delete, never delete a backup under legal hold) decides how long old sets keep the bytes. This is stated in the UI at plan approval, in the audit event, and in the administrator documentation. Aligning the attachment retention with backup retention is a legal-policy matter: the company's legal policy should keep month-end/year-end backups at least as long as the longest attachment retention it purges, or accept that the bytes remain in them.
* **Set verification and trial restore** (`BackupSet`, `CompanyBackupService`, `maintenance/verify`): a row with a **completed purge item** must have **no** file (`attachment_purged`, information, not `attachment_file_missing`); a row without a purge item still requires its file. A set made before a purge verifies cleanly as before; a set made after verifies with the purged rows expected absent. The manifest's needed key ids exclude purged rows (but see section 9 for older sets).
* **Restore.** Restoring an older set brings back rows without the later purge items and the files with them: the purged content reappears as ordinary retained removed data. Nothing is deleted automatically after a restore. The preserved previous audit chain (D-081) still records the earlier purge; after cutover a read-only **purge replay report** lists attachments whose purge is in the previous epoch but not in the restored database, so an authorized user can re-request them through a new plan (new approval, fresh checks). Never automatic.
* Backup retention and attachment purge never delete the same thing: this plan deletes attachment bytes in live storage only; deleting backup sets belongs to D-086 and its own audited execution.

## 9. Interaction with key retirement (register item K, D-082, D-080 item 6)

* Today `oldKeysMayBeRetired` is true when no active-or-removed sensitive row needs the key. After this phase a **purged** row no longer needs the key, but **retained backup sets still do**. Until R4 delivers condition (b), **a purged row still counts as needing its key, or the report returns false with `backup_inventory_unavailable`; the R2 tests assert this** (so purging can never make a key look retirable). The report therefore gains a second condition (delivered by R4): a key is retirable only when (a) no live row (active, or removed and not purged) names it, **and** (b) no retained backup set lists it among its needed key ids, **and** the backup inventory is known (`backup_inventory_unavailable` makes it false: fail closed). The list of key ids per set is already in the set manifest.
* Purge never touches keys and never rewraps; rotation of removed rows is unchanged (they keep their key id). Key retirement itself still needs independent approval (D-080 item 6); its design belongs to the key-management phase and consumes this report.
* Import-file originals use the same keys but are NOT attachments; D-082 covers attachments only. Their retention is outside this plan and **they keep the existing key-retirement rule unchanged** (a key an import file needs is never reported retirable). Recorded in the register as a follow-up.

## 14. Risks

* **Irreversibility.** A purge cannot be undone in live storage; mitigated by two-person control, three re-checks, the expiry, the bound per plan, preview first, and preserved backups (which are also the residual risk: bytes survive in old sets by design).
* **Unknown legal holds.** The system only knows holds that were entered; the attestation is the control for the rest.
* **Policy errors.** A too-short period approved in good faith: mitigated by independence, shortening acknowledgement, no retroactive shortening, effective-date delay, revoke returning to preservation.
* **Physical erasure.** Unlinking a file does not guarantee physical erasure on every storage (SSD, snapshots, network shares); encryption of sensitive files helps only while their key is unavailable, and master keys are shared. Documented limitation; stronger erasure is a storage/deployment control.
* **Metadata remains.** Display file name, size, digest, key id and removal reason stay in the guarded row (and in backups); the digest of a sensitive file is never returned or audited. If the owner requires minimisation, a separate, audited redaction design is needed (it would change the guarded table: an owner decision, not part of this plan).
* **Coordination bugs with backup.** The shared lock is the control; the tests simulate a backup in progress.
* **Clock and time zone.** Eligibility is date-based UTC; a company time-zone or fiscal-calendar rule (D-086) could alter the boundary; defaults err toward later eligibility; an explicit rule would be a later, owner-approved extension.
* **Scope creep.** Import-file originals, retrieval of retained content for legal requests, per-record authorization (3.13) and backup-set deletion are separate.

## 15. Open questions for the owner (fail-closed defaults apply until answered)

1. Proposed basis: removal date, in whole months, never shortened retroactively. Does legal practice require another basis (for example from the end of the fiscal year of the related record)? Until answered: no item is eligible (`retention_basis_pending`) and purge execution is disabled.
2. Purge deletes content only and keeps the metadata row (name, size, digest, reason). Is that acceptable, or must metadata also be minimised? Default: keep (needed by the database guard and the audit proof).
3. How may an authorized person retrieve a **retained** removed attachment for a legal request? Today it is unreachable except by restore. Default: no retrieval feature in this phase.
